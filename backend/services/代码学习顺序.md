## 零、先搞清楚 services 层是什么

项目后端分三层：

```
routers/    ← HTTP 层：接参数、校验、调 services、返回响应（看不到 SQL）
   ↓
services/   ← 编排层：把多个 db 操作 + AI 调用串成一件完整的"事"（本文档）
   ↓
db/ + models/  ← 数据层：SQL 语句、等级公式、维度常量
```

**services 层的核心特征**：
1. **不写 SQL**（除了极少数联表查询）——所有数据库操作调 `db/` 的函数
2. **是"事务边界"**——`exp_service.py` 里一个函数就是一个原子事务
3. **是"AI 边界"**——所有 LLM 调用都收敛在这里，路由层不直接碰模型

判断某个逻辑该不该放 services，就看一句话：**它是"一件事"还是"一次数据库操作"？** 前者进 services，后者留在 db。

> **关于 routers 层的现状补充**（2026-09-08 改的）：项目里 **80 个纯 CRUD 端点已从 `async def` 改成 `def`**（它们本来就没有 `await`，是"假异步"）。FastAPI 对同步端点会自动丢线程池，所以同步查数据库（现在走 MySQL 连接池）不再阻塞事件循环。只有真正需要 `await` 的（调 AI、WebSocket）才保留 `async`。读 `routers/` 时看到大量 `def` 端点不要觉得奇怪。

## 三、阶段详解

### 阶段 1 · `exp_service.py`（272 行）— 先读这个，它是全项目的"事务范本"

**解决什么**：把"加经验 → 更新维度 → 重算等级 → 更新今日统计"这套原本在路由层重复 5 次的逻辑收敛成一个函数。

**核心函数**：

| 函数 | 行 | 作用 |
|---|---|---|
| `award_exp_and_recalc()` | 17 | 奖励经验的原子流程。支持传入外部 `conn`（由调用方控制事务）——这个设计是全局关键 |
| `create_action_and_award_exp()` | 125 | 创建行动记录 + 奖励经验，单连接原子提交 |

**必须看懂的三个设计**：

1. **总经验从 8 维 SUM 反算**（第 64~67 行）
   ```python
   new_total = get_total_exp_from_dimensions(user_id)   # 不是累加，是 SUM
   new_level = level_from_total_exp(new_total)
   ```
   为什么不是累加？维度表才是唯一真相源，累加会出现"总经验"和"各维度之和"两份数据打架。

2. **幂等的占位写入**（第 216 行 + 第 252~256 行）——**这是全项目最值钱的一段代码**
   ```python
   create_action_log(..., exp_earned=0)        # 1. 先占位 0
   # ... 检查 existing["exp_earned"] > 0 就说明发过了，直接返回
   award_exp_and_recalc(...)                   # 3. 发经验
   conn.execute("UPDATE action_logs SET exp_earned = ?", (dimension_exp, action_id))  # 4. 回写真值
   ```
   为什么先写 0？因为只有"占位 0 → 回写真值"才能让"这条记录发没发过经验"变成**可判断**的。写进去就写真值，回查时 `exp_earned > 0` 永远为真，无法区分新建和已发放。

3. **连接所有权模式**（第 42~44 行、第 84~92 行）
   ```python
   own_conn = conn is None
   if own_conn: conn = get_conn()
   try: ...
   except: if own_conn: conn.rollback()
   finally: if own_conn: conn.close()
   ```
   传了 `conn` 就由调用方管事务，没传就自己管——这样单条调用和"跨多表的复合操作"都能复用同一个函数。

**读完自测**：
- [ ] 为什么 `is_global_exp=True` 时不再乘 `global_rate`？
- [ ] 如果第 3 步成功、第 4 步回写失败，会怎样？当前代码有没有兜住？（提示：看 `except` 里的 rollback）
- [ ] 两个请求并发、request_id 相同时，这段幂等还能挡住吗？（答：挡不住，这是已知的改进点，见 `docs/项目坑与面试讲解.md` 坑 7）

### 阶段 2 · LLM 统一入口（2026-09-09 重构后的新核心）

#### `llm.py`（66 行）— 全项目 AI 的唯一入口

**解决什么**：原先有两套重复的 LLM 缓存（`coordinator/llm.py` 和 `ai_client._get_llm()`），现在合并成这一个工厂。

```python
def get_llm(temperature=0.3, max_tokens=9192, timeout=120.0, user_id=None) -> ChatOpenAI:
    cfg = get_active_config(user_id or 1, "llm")     # 用户配置优先，env 兜底
    ...
    cache_key = (temperature, max_tokens, timeout, model, base_url, api_key)
    if cache_key not in _llm_cache:
        _llm_cache[cache_key] = ChatOpenAI(...)
    return _llm_cache[cache_key]
```

**三个要点**：
1. **模型来源三级优先**：`model_configs` 表（用户配置）→ `.env` → 空。切换数据库里的启用模型后 key 变化 → 自动重建实例，**无需重启**
2. **缓存 key 是六元组**，含 `timeout`——因为协调器要 120s、纯文本要 300s，这是两个不同实例，不能共享
3. **默认 `max_tokens=9192`**：给协调器等长输出场景留足空间（历史值，保守保留）

> 这是面试很好讲的一块：能说清"为什么要合并"和"为什么 timeout 要进缓存 key"，说明你真读过。

#### `ai_client.py`（127 行）

**解决什么**：所有"纯文本生成"类 AI 调用的统一封装（习惯图标等）。

**三个要点**：
1. **不再自己缓存实例**——内部调 `services/llm.py` 的 `get_llm()`，自己只管"纯文本"这件事
2. **两个"不要照抄默认值"的参数**：
   - `REQUEST_TIMEOUT = 300`：httpx 默认 5 秒，推理模型慢时静默重试会放大延迟
   - `DEFAULT_MAX_TOKENS = 4096`：推理模型的 max_tokens **包含思考部分**，给小了正文会被截断
3. **两个接口**：`call_ai_text()`（一次性返回）、`call_ai_text_stream()`（异步生成器 + `astream`，供 SSE 打字机效果）

#### `ai_habit_service.py`（103 行）

**解决什么**：AI 生成习惯 SVG 图标。文件小但**安全意识值得单独学**。

- `SVG_ALLOWED_TAGS` 白名单：只允许 `svg/g/path/rect/circle...`，杜绝 `script`、`foreignObject`、`image`
- `extract_svg()` + `validate_svg()`（用 `xml.etree.ElementTree` 解析校验，不是正则糊弄）
- `call_ai_for_icon()`：调 `ai_client` 生成 → 提取 → 校验 → 失败回落默认图标

> 这是"AI 输出不可信"的典型处理：**生成 → 提取 → 白名单校验 → 降级**，四步缺一不可。

**读完自测**：为什么图标必须用白名单而不是黑名单？（答：黑名单永远列不全攻击面）

### 阶段 3 · 复杂 AI 业务（工具调用 + 容错降级）

这一阶段的文件**现在都走 `services/llm.py`**（2026-09-09 改造后不再 httpx 直调）。读它们学的是**业务逻辑和容错设计**，不是网络调用。

#### `expression_service.py`（514 行，本文件夹最大）

**解决什么**：表达训练的全部 AI 逻辑。

**读法**：不要顺序读，按"三条主线"跳读：

| 主线 | 入口 | 关键函数 |
|---|---|---|
| 出题 | `generate_question()` | `_call_llm_with_tools()` → `_parse_question_result()` → `_fallback_question()` |
| 评分 | `evaluate_answer()` | `_parse_evaluation_result()` → `_validate_evaluation()` → `_fallback_evaluation()` |
| 提示 | `generate_hints()` | `_parse_hints_result()` → `_fallback_hints()` |

**三个值得学的点**：
1. **每个 AI 功能都配一个 `_fallback_*`**——AI 挂了系统不崩，用预设题目/默认评分顶上
2. **解析与校验分离**：`_parse_*`（容错地抠出 JSON，处理模型输出带 ```json 包裹的情况）→ `_validate_*`（字段缺失补默认值、范围钳制）
3. **手写 ReAct 循环**：`_call_llm_with_tools()` 里有 `for _ in range(max_rounds)` 的工具调用循环——读完它再去看 `coordinator/agents/base.py`，会发现后者用 LangGraph 把同样的循环做得更干净

**注意工具格式**：这里用 `llm.bind(tools=EXPRESSION_QUESTION_TOOLS, tool_choice="auto")`，因为工具是 OpenAI function 格式的 dict。返回值解析用 `resp.tool_calls`（结构 `[{"name", "args", "id"}]`，`args` 已是 dict），和 httpx 直连的格式不同。

#### `asr_service.py`（142 行）

**解决什么**：DashScope paraformer 实时语音转写（WebSocket，不是 HTTP）。

- `ASRCallback(RecognitionCallback)`：回调类，接收识别结果片段
- `ASRConnection`：连接管理（也读 `model_configs` 的启用 ASR 配置）
- 配合 `routers/expression.py` 的 WebSocket 使用

> ASR 是唯一不走 `services/llm.py` 的 AI（它用阿里云 SDK 的 WebSocket）。

#### `ai_action_service.py`（75 行）— 最小样本，建议精读

**解决什么**：对话式行动记录解析。结构最简，适合**作为"一次 LLM 调用"的最小样本**：

```python
llm = get_llm(temperature=0.7, user_id=user_id)
llm_with_tools = llm.bind(tools=ACTION_PARSE_TOOLS, tool_choice="auto")
resp = await llm_with_tools.ainvoke(msgs)

if resp.tool_calls:
    return {"tool_calls": [{"id": tc["id"], "name": tc["name"], "arguments": tc["args"]} ...]}
return {"content": resp.content or ""}
```

**读完自测**：把 `ai_action_service.py` 和 `coordinator/agents/base.py` 并排看——同样是"LLM + 工具"，为什么前者只调一次就返回，后者要跑 ReAct 循环？（答：前者把 tool_calls 交给前端执行，后者在服务端闭环执行完再返回）

### 阶段 4 · `coordinator/` — LangGraph 多智能体（最难，慢慢来）

> 注意：`coordinator/llm.py` **已删除**，LLM 获取统一走 `services/llm.py`（阶段 2 已读）。

#### 顺序 1：`checkpointer.py`（15 行）→ `state.py`（57 行）

- `checkpointer.py`：全局单例 `MemorySaver`。**记住它的后果：内存存储，进程重启会话全丢**（改进方向：换 `AsyncSqliteSaver`/`PostgresSaver`）
- `state.py`：`SubgraphTask`（路由决策：domain/reason/instruction）、`RecordSummary`（跨记录记忆）、`CoordinatorState`（主编排状态，普通 TypedDict，不是 LangGraph State）

#### 顺序 2：`agents/ask_user_tool.py`（44 行）→ `agents/base.py`（199 行）

**`ask_user_tool.py`**：公共反问工具。LLM 调用它就等于"我要问用户"，返回 `{needs_user: True, question, options, domain}`。

**`base.py` 是全项目的核心**，四个机制必须吃透：

1. **ReAct 循环**（第 80~165 行）：`for _ in range(MAX_ITERS)` → LLM 决策 → 调工具 → 结果拼回 `full` → 继续
2. **三道防循环闸**（第 34~41 行）：
   ```python
   MAX_ITERS = 8          # 工具调用轮数上限
   MAX_ASK_ROUNDS = 3     # 反问超 3 轮 → 把 ask_user 从 bind_tools 移除，逼 LLM 用已有信息执行
   MAX_HISTORY = 10       # 消息窗口 = 1(instruction) + 3轮 × 3条
   ```
   注意第 93 行的**保险分支**：轮数满了 LLM 还调 ask_user，就返回失败而不是真反问
3. **反问为什么不用 `interrupt()`**：问题作为普通 `ToolMessage` 存进 checkpoint，resume 时追加 `HumanMessage` 重新 `ainvoke`。好处是没有挂起状态、"跳过"零成本、LLM 能看到自己问过什么
4. **工具调用丢线程池**（2026-09-08 改的）：
   ```python
   # 工具函数本身是同步的（内部同步查 MySQL 连接池），丢线程池避免阻塞事件循环
   tool_result = await asyncio.to_thread(tool_fn.invoke, args)
   ```
   这一步让 `asyncio.gather` 的多域派发**真正并行**（改之前是假并行）。注意区分：**工具函数本身仍是同步的**（24 个工具全是 `def`，PyMySQL 没有异步 API），改的是**调用方式**。

**`base.py` 里两个函数**：
- `make_agent_node()`（44）：工厂，返回 agent 节点函数
- `build_subgraph()`（177）：单节点 StateGraph + checkpointer 编译

#### 顺序 3：`agents/action_agent.py`（86 行）精读，其余 5 个泛读

精读 `action_agent.py` 看懂一个域长什么样：
- `@tool record_action()`（30）：业务工具定义，参数用 `Literal` 约束枚举
- `create_action_agent()`（78）：调 `build_subgraph()` 组装

其余 5 个（`query/goal/task/habit/reward_agent.py`）结构完全一样，只看**工具定义和 system prompt 的差异**即可。

#### 顺序 4：`router_node.py`（113 行）→ `synthesize_node.py`（99 行）→ `graph.py`（202 行）

- **`router_node.py`**：LLM 意图识别，输出 JSON 路由决策（哪些域 + 每个域的定制指令）。`_parse_routing_json()` 做容错解析。温度 0.1（路由要稳定）
- **`synthesize_node.py`**：把各子图结果整合成最终回复
- **`graph.py`**：**主流程不用 StateGraph**，是纯函数三段式编排
  ```
  router_node → dispatch_subgraphs(并行) → synthesize_node
  ```
  为什么不用 StateGraph？主流程没有分支和循环，`operator.add` 的状态合并会跨轮累积导致消息膨胀。**这是面试必讲的 trade-off**。

**`graph.py` 另外几个关键函数**：
- `_run_one_subgraph()`（83）：首次执行，`sub_thread_id = f"{main_thread_id}:{domain}"`（域隔离的关键）
- `resume_subgraph()`（112）：用户回答后**接回原子图 checkpoint**，不重新路由
- `dispatch_subgraphs()`（142）：`asyncio.gather(*coros, return_exceptions=True)` 并行，单域失败不影响其他
- `finalize_record()`（30）：三阶段走完才压入历史（FIFO 5 条）

**读完自测**（能答出来才算真的懂了）：
- [ ] thread_id 为什么设计成 `{main}:{domain}` 两层？
- [ ] 用户回答反问后，为什么要"接回原子图"而不是重新走一遍路由？
- [ ] 某个子图抛异常，整体会崩吗？错误结果怎么呈现给用户？
- [ ] 主流程用纯函数、子流程用 StateGraph，这个分工的依据是什么？

### 两个值得注意的设计（2026-09-23 调整）

**① `replace_tree`（整树替换）工具已删除。** 它是这套工具里破坏性最强的 ——
一次调用就清空整棵树，而 AI 是自主决定调哪个工具的。
能力已被 `create_nodes_batch` 覆盖：树为空时两者效果一样；树非空要重建时，
提示词要求「先删根节点（级联清空）再批量建」，且删根节点本身有确认守卫。

**② 会话与树是绑定的。** `_ensure_thread_belongs_to_tree()` 会校验
「这个 thread 的 state 里的 `tree_id` == 当前请求的 `tree_id`」，
不匹配就拒绝并提示重置会话。原因：checkpointer 只按 `thread_id` 恢复状态，
不校验就会出现「打开 A 树、却操作了 B 树」。
前端 `switchToTree` / 新建 / 删除 / 清空对话 都会 `resetSession()`，
但那只是 UX —— **后端不能依赖前端**（切树入口多、且能直接打 API）。

**和 coordinator 的对比**（对比着学印象最深）：

| 维度 | coordinator | skill_tree_ai |
|---|---|---|
| 主流程 | 纯函数三段式 | LangGraph StateGraph（单节点） |
| 编排复杂度 | 多域并行 | 单域单轮 |
| 会话 | 两层 thread_id（主/子域） | 单层 thread_id |
| 人工介入 | ask_user 反问 | confirm 确认守卫 |
| 状态持久化 | checkpointer（子图） | checkpointer（整图） |

## 六、常见困惑 Q&A

**Q：获取 LLM 实例的地方在哪？**

**A**：统一在 `services/llm.py` 的 `get_llm()`。2026-09-09 之前有两套（`coordinator/llm.py` 和 `ai_client._get_llm()`），已经合并了。所有 AI 调用（协调器、技能树、行动解析、表达训练、纯文本）都走这一个入口。

**Q：`coordinator/graph.py` 不用 StateGraph，那还是 LangGraph 项目吗？**

是。子 Agent 的 ReAct 循环、消息历史持久化、checkpoint 恢复都用 LangGraph。主流程不用是因为线性无分支——**知道什么时候不用某个框架，比会用它更高级**。

**Q：`operator.add` 到底坑在哪？**

它让每次节点返回值**追加**而不是覆盖。多轮对话下 `messages` 会无限膨胀；`diffs` 这类本该"每次替换"的字段如果用了 add，旧数据会跨轮残留并重复返回（`skill_tree_ai/state.py` 就踩过这个坑，已修复）。

**Q：为什么工具调用要 `asyncio.to_thread`？**

工具函数内部是同步的 PyMySQL 调用（没有异步 API），直接在 `async` 函数里调用会**卡住整个事件循环**，导致 `asyncio.gather` 的多域并行变成串行。丢线程池后事件循环不再被卡住。注意：**工具函数本身仍是同步的**，改的只是调用方式。

**Q：AI 调用失败了会怎样？**

三个层次：工具层 try/except 转成 `{success: false}` 回灌给 LLM 让它重试或换参数；服务层配 `_fallback_*` 降级；并行层用 `gather(return_exceptions=True)` 保证单域失败不影响整体。

**Q：项目的已知缺陷在哪看？**

见 `docs/项目坑与面试讲解.md`——那里按"现象 → 根因 → 处理 → 面试话术"整理了 13 个坑（已修复的、已知限制、未完成项都有）。
