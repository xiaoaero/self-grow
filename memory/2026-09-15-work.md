## 二、砍掉 `apt-get install tzdata`：构建从 4 分钟卡顿到 100 秒

本地构建时卡在第 5 步**四分钟没动静**，日志停在海外的 deb.debian.org ——
这是 Dockerfile 里**唯一连海外源**的步骤。

10 秒实测：

```bash
docker run --rm python:3.12-slim sh -c 'ls -l /usr/share/zoneinfo/Asia/Shanghai; TZ=Asia/Shanghai date'
# -rw-r--r-- ... /usr/share/zoneinfo/Asia/Shanghai   ← 本来就有
# Tue Sep 15 00:11:37 CST 2026                       ← 直接就是 CST
```

**结论**：Debian 里 `tzdata` 是 **required 优先级包**，slim 只裁文档与编译器，裁不掉它。
`ENV TZ=Asia/Shanghai` 一条就够 → 删掉整段 `apt-get`。

> **顺带纠正一个说法**：`python:3.12-slim` 现在基于 **Debian trixie / glibc 2.41**
> （不再是 bookworm），所以 manylinux_2_28 轮子完全够用。

## 五、🐛 生产首次启动：前端报「无法连接后端服务」

### 排查的破案关键

用户贴的服务端日志特征很说明问题：

- 容器正常、`/api/health` 200、浏览器（用户公网 IP）`GET /` 200、CSS/JS/config.js 全部 200
- **之后再没有任何请求进来**，而页面提示"无法连接到后端服务"

**根因**：`/api/config.js` 返回的是 `window.__SELF_GROW_API_BASE__ = 'http://127.0.0.1:3001';`
—— 这段 JS 在**用户浏览器**里执行，`127.0.0.1` 指向**用户自己那台电脑**。
浏览器去连自己本机的 3001，连接被拒 → 请求根本没发出去 → 服务端日志当然干净。
**本地开发时浏览器与服务器同机，恰好是对的，所以一直没暴露。**

### 修复

```python
scheme = (request.headers.get("x-forwarded-proto") or request.url.scheme).split(",")[0].strip()
host   = request.headers.get("host") or f"127.0.0.1:{PORT}"
api_base = f"{scheme}://{host}"
```

即**按本次请求的 Host 反推后端地址**。响应加 `Cache-Control: no-store`
（否则浏览器一直用缓存里的旧地址）。

三种场景本地实测全对：默认 Host / `Host: <公网IP>:3001` / `Host: grow.example.com` + `X-Forwarded-Proto: https`。

> **值得复用的排查法**：前端说"连不上后端"时，**先看服务端日志有没有请求** ——
> 有请求 → CORS / 权限 / 401；**一个请求都没有 → 地址算错了**（或网络/防火墙）。

## 六、🐛 新库 7 个维度显示「Lv1 / 5625 XP / 需要 150 / 100%」

**现象**（用户截图）：8 维表格里 7 维是 `Lv1 | 本级已获 5625 | 升级所需 150 | 100%`，
只有健康正常（`Lv12 | 341 | 973 | 35%`），"记录一次就正常"。

**关键突破口**：`5625 × 8 = 45000` **正好整除** → 指向 `users.total_exp = 45000`。

**根因链**（`db/init.py`）：

1. 空库时 seed 两个演示账号，其中 admin 的 `total_exp = 45000`
2. 紧接着 `migrate_total_exp_to_dimensions()` 把 total_exp **平均分**给 8 维
   （45000 // 8 = 5625），但 INSERT 里 **`level` 写死 1、`xp_to_next` 写死 150**
3. 正常路径 `upsert_dimension()` 维护的不变式是
   **`0 ≤ xp < xp_to_next`** 且 **`xp_to_next == exp_for_level(level)`**（Lv1 应为 **300**）→
   迁移写出的行**违反不变式**
4. 前端 `attributes.js` 只是照实显示 `pct = xp / xpToNext`，5625/150 = 3750% 被封顶成 100%
5. **为什么一记录就正常**：`upsert_dimension` 里有进位循环，5625 被一路进位成真实的
   Lv12 / 剩余 183 / 需要 973 —— **只有被记录过的那一维会走这个循环**，其余 7 维不动

**修法（用户拍板：把本地 data.db 里 test/admin 的真实情况原样搬进 seed）**：

1. 新增 `DEFAULT_DEMO_USERS` / `DEFAULT_DEMO_DIMENSIONS` 常量（本机真实数据：
   test Lv188/145356、admin Lv99/46923，8 维各带真实 level/xp/xp_to_next）
2. 新增 `split_total_exp(total_exp) -> (level, 本级进度, 升级所需)`：
   **唯一**保证不变式的地方，`level` 用 `MAX_DIM_LEVEL=140` 封顶
3. `migrate_total_exp_to_dimensions()` 改走 `split_total_exp()`；
   `ON CONFLICT` 从累加改成覆盖
4. 新增 **`normalize_dimension_rows()` 自愈迁移**，在 `init_db()` 里自动修违反不变式的行
   （幂等：修到就 `log.warning` 报条数，再跑一次修正 0 条）

> ⚠️ 不能删 seed 账号：`tools/init_password.py` 靠 `get_user_by_name` 找 test/admin，它**不会建号**。
> ⚠️ 另确认：项目**没有注册接口**，所以"测试用户"只能是 seed 出来的这两个。

## 七、✅ 全项目时间口径统一（一族时区 bug 的根除）

用户报「行动记录与行动历史有大 bug」。写探针脚本全量打接口后确认：
**后端接口层全部正常**（分页/分类/6 种排序/搜索/日期区间/CSV 导出，无一 500），
问题**纯粹出在时间口径** —— 全链路「UTC 与本地时间混用」。

### 三个现象

| # | 现象 | 根因 |
|---|---|---|
| A | 刚记录完，「最近行动」显示"8小时前" | `created_at` 由 SQLite `datetime('now')` 产生 = **UTC**，代码里 `datetime.now()` = **本地** → 差恒为 8 小时 |
| B | **手动记录的行动时间整体早 8 小时（数据被写坏）** | `frontend/js/pages/action.js` 用 `startTime.toISOString().replace('Z','')` —— 给的是 **UTC 壁钟**，去掉 `Z` 后被当本地时间入库。00:00~08:00 记录的**日期会退到前一天**，波及今日统计/日期筛选/每日归档/连续天数 |
| C | 前端的"今天"用 UTC 日期 | `new Date().toISOString().slice(0,10)`，UTC+8 在 00:00~08:00 取到"昨天" |

也解释了本地 `data.db` 里同一时刻的记录为何一半是 `01:00`、一半是 `17:16`：
**AI 描述记录走另一条路**（时间由 LLM 以本地格式给出）所以是对的，
手动快速记录走 `toISOString()` 所以错。

### 方案（先出文档、用户拍板后实施）

`docs/时间口径统一方案.md`（结构：摘要 → 定位与证据 → 现状盘点 → 方案选型 →
逐文件改动清单 → 验收清单 → 历史数据选项 → 实施顺序 → 风险 → 待确认）。

**用户拍板：方案 A（全链路统一「本地时间 naive」）+ 历史数据不动 + 加启动时区自检。**

> **关键技术约束**：SQLite **不支持** `ALTER TABLE ... ALTER COLUMN`，
> **已建表的默认值改不了** → 必须同时在 Python 插入时**显式写**本地时间，
> 建表默认值只对新库兜底。

### 实施（13 个文件）

- `frontend/js/utils.js` 新增 `toLocalIso()` / `todayLocal()`（含「不许用 toISOString」的注释）
- 前端替换 9 处 `toISOString()`（`action.js` / `tasks.js` / `data.js`）
  —— ⚠️ `data.js` 在 `utils.js` **之前**加载，不能调工具函数，改成就地计算
- `db/connection.py` 新增 `now_str()`；`create_action_log` / `create_task` 显式写本地时间
- `db/init.py` 12 处建表默认值 → `datetime('now','localtime')`；另 5 处运行时 SQL 同步改
- `db/stats.py` 相对时间同口径 + 兼容带偏移的旧串
- `main.py` 启动打印时区，偏移 0 时警告漏设 TZ
- 新增 `tests/test_time_consistency.py`（12 个用例）

**顺带修掉**：`db/batch.py` 的任务归档/过期判断用 `date(created_at)`，
UTC 与本地口径不一致 → 00:00~08:00 创建的任务会被归到前一天。

**验证**：全新库 start_time 原样落库、「最近行动」显示`刚刚`（修复前恒 `8小时前`）、
**真实老库拷贝也通过**（证明"显式写入"让老库也生效）、**113 passed**。
