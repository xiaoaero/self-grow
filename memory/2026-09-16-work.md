## 一、🐛 前端 `AppData.profile` 缓存永不失效

**现象**：在「开始行动」记一条行动后 —— 点「行动中心」或「属性」**维度经验不变**，
刷新页面才变；点「成长记录」**立刻变**。

**根因**：`AppData.profile` 只在页面加载时拉过一次，**之后没有任何失效机制**。

- 写入点只有两处：`app.js` 启动时拉一次、`attributes.js` 仅在缓存为空时补拉
- 读取点四处：属性页维度表、**行动中心的「升级进度」模块**、奖励解锁/领取条件判断
- 而 `history.js`（成长记录）**每次进入都重新拉并覆盖缓存** → 所以它显示最新值

→ 三条现象全部对上。记行动成功后只更新了 `AppData.todayStats` / `AppData.user`
（所以左下角经验条会动），**没碰 `AppData.profile`**。

**修法**：

1. `utils.js` 新增 **`refreshProfileCache()`**
2. 在 **5 个「写操作成功后」的钩子**调用 —— 都紧挨已有的 `reevaluateRewardsOnBackend()`，
   语义同位置好记（AI 记行动 / 手动记行动 / 打卡 / 领任务奖励 / 领目标奖励）
3. 兜底：属性页与行动中心「升级进度」改为**每次进页面都 `await refreshProfileCache()`**，
   先用缓存顶上避免白屏

> **通用教训**：前端缓存必须配失效机制（写后失效 / 读时校验）。
> 只有"启动时填充一次"的缓存遇到任何写操作都会 stale，而且**不同页面表现不一致**
> （谁恰好在进入时重新拉过，谁就是对的）—— 极易被误判成"后端没算"。
>
> ⚠️ 例外：`tasks.js` 的 `localClaimTaskExp` 是**离线降级**路径（后端都挂了），
> 那里**故意不加** `refreshProfileCache()`。

## 二、「测试连通性」支持留空 API Key

**现象**：模型配置弹窗里点「测试连通性」，不输 Key 就不给测；即使之前保存过，输入框也是空的。

**根因是三个环节一起把路堵死**：① 后端 `_to_public()` 把 `api_key` **脱敏**成 `sk-****abcd`
（**这个设计是对的**，密钥不该吐给前端）② 但 `/test` 端点里第一行就是
`if not req.api_key: return "API Key 为空"` ③ 前端也有硬拦截。

**改法**（留空 → 回落到已保存的 Key，密钥始终不出服务端）：

- `ModelConfigTest` 加 `config_id`；回落顺序：传了 `config_id` → 用该配置存的 Key
  （**校验归属，不是自己的当作不存在**）→ 否则用当前启用配置 → 都没有才报错
- 不显眼但重要：用已保存的 Key 时 `model` / `base_url` 也一并回落，成功消息标注「（使用已保存的 Key）」
- 前端：按钮带 `config_id`；编辑时 placeholder 显示脱敏值「已保存 sk-****abcd，留空即用它测试」

**实测 5 条全绿**：回落到已保存 Key / 无 Key 可回落时正确拦截 / 优先用输入的 /
**拿别人 config_id 不越权** / 回落到当前启用配置。

> **踩坑**：第一版探针没清空配置，导致两条断言全错 —— 因为 seed 的默认配置本来就是"当前启用"的，
> 回落逻辑真的去连了真实 LLM 端点（日志里看到 200）。**写这类探针前要先清场**，
> 否则既会误判，还会意外调用外部付费 API。

## 四、AI 流式输出需求盘点（改造前的分析）

全量盘了一遍 13 处 LLM 调用点，结论：

- **13 处全部是 `ainvoke`（阻塞式）**；`astream` 只有 1 处定义且**全项目零调用**
- 两个 SSE 端点都是**假的**：一个只 yield 一个 `done`，另一个把最终结果一次性塞进去；
  其中 `GET /api/coordinator/stream/{thread_id}` 更是**没挂鉴权**
- 前端完全没有 `EventSource` / `getReader`，也没有任何打字机效果

**分级结论**：

| 级别 | 场景 | 理由 |
|---|---|---|
| **① 真流式收益最大** | 协调 Agent 总结回复、技能树 AI 回复 | 等待最长（路由 + 多子 Agent ReAct 串行），输出**就是给人读的文本**，首字延迟可从数秒降到 <1s |
| **② 要"阶段进度"而非"逐字"** | 表达力三件套、习惯 SVG 图标 | 输出是 **JSON**，逐字符传等于逼前端做增量 JSON 解析（负优化）；习惯图标还必须等**完整**才能校验 → 需求是**保活防超时** |
| **③ 不需要** | 行动解析、美化题目 | 极短（要么工具调用 JSON、要么一句反问） |

### 三个技术拦路石（真做时必踩）

1. **`EventSource` 带不了 `Authorization` 头** —— 而前端是靠**包装 `window.fetch`** 注入 Bearer 的
   → 走 `EventSource` 必然 401。**正解是 `fetch` + `resp.body.getReader()`**，
   同时端点必须改成 **POST + StreamingResponse**（EventSource 只支持 GET）
2. **Nginx 主站 `location /` 没关缓冲**（只在 `/mcp` 那段关了）
3. **两个现成 SSE 端点都是假的**，别误以为"后端已就绪"

## 五、✅ 所有 AI 端点落地 SSE 流式

### 新增 `backend/services/sse.py`（统一层）

事件协议 `stage` / `token` / `error` / `done` —— **类型放 `data` 的 JSON 里，
不用 SSE 原生 `event:` 字段**，这样前端只留一个解析分支。

三个部件：

1. `sse()` / `sse_response()` —— 编码 + 响应头（**`X-Accel-Buffering: no`**）
2. `stream_events(runner, heartbeat=15)` —— 用队列解耦：`emit` 往队列塞、生成器边取边发，
   静默期发 `: ping` 心跳
3. **ContextVar 发射器**（`use_emitter` / `emit_stage` / `emit_token`）—— 本次最关键的决策

### ContextVar 那一步（最费脑的地方）

**问题**：阶段事件产生在很深的调用链里（router → graph → agent → tool），
而技能树 AI 的 LangGraph 图是**模块级单例**（编译结果被缓存），没法在编译时把每请求的回调烘进去；
一路加回调参数会污染所有签名。

**解法**：用一个 `ContextVar[Optional[Callable]]` 存当前请求的发射器。
asyncio 任务会**复制上下文**，所以 `asyncio.gather` 并发派发的多个子 Agent 各看各的，事件不串。
**没设置发射器时 `emit_stage` 是完全空操作** —— 同步路径一行都不变（有回归测试守这条不变式）。

**实测确认穿透成功**：事件流是完整的
`stage[routing] → stage[routing_done] → stage[domain_start] → stage[domain_done] → stage[synthesize] → token…`，
其中 `domain_start` 是**子图内部**推的，能收到就证明穿过了 `asyncio.gather` + LangGraph 的任务边界。

### 端点清单

| 端点 | 流式内容 |
|---|---|
| `POST /api/coordinator/chat`、`/resume` | 阶段事件 + **逐 token** |
| `POST /api/skill-trees/{id}/chat`、`/chat/resume` | 阶段事件（第 N 轮推理 / 工具 / 待确认） |
| `POST /api/expression/generate`、`/generate-hints`、`/evaluate/{id}` | 阶段事件 |
| `POST /api/habits/ai-icon` | 阶段事件 + 心跳保活 |

**为什么只有协调 Agent 逐 token**（这是会被追问的点）：技能树 AI 的回复由 LLM 通过
**`send_reply` 工具参数**生成，不是纯文本流；表达力产物是 **JSON**；
习惯图标必须等完整 SVG 才能校验。

## 六、✅ 端到端验证 SSE 穿 Nginx（含一个反直觉发现）

1. 重建镜像 → 确认新文件进镜像（⚠️ **镜像 WORKDIR 是 `/app/backend`**，不是 `/app`）
2. **`nginx -t` standalone 跑会失败**：`host not found in upstream "app:3001"`
   —— 容器外没有 compose 网络，`app` 解析不了（不是语法错）。
   **正解：`docker exec <nginx容器> nginx -t`**
3. 用 override 文件绕开被 dify 占用的 80/3001，起 app + mcp + nginx 三容器
4. 探针**看事件的到达时刻分布**，不看内容 —— 缓冲的话所有事件会在最后一刻同时到达

### 结果（真 LLM）

```
t+  0.01s  stage[routing]         正在理解你的意图…
t+  3.24s  stage[routing_done]    已规划 1 项
t+  4.70s  stage[tool]            正在执行 query_user_stats
t+  6.53s  stage[synthesize]
t+ 20.51s  16 个 token（真逐字）
t+ 20.94s  done
```

**习惯图标那次**：`t+0.02s` 收到 `stage[icon]`，之后 `16s / 32s / 48s / 64s / 81s` 各一次心跳，
`t+88.9s` 收到 `done(svg)` —— **同时证明了心跳确实顶掉了 Nginx 默认 60s 的 `proxy_read_timeout`**
（否则这条 89 秒的请求早被掐断）。

### 🔍 本次最大的发现（反直觉，容易误判）

**`X-Accel-Buffering` 会被 Nginx 消费掉，不透传给客户端。**

```
直连 app : x-accel-buffering = 'no'
经 Nginx : x-accel-buffering = None     ← 正确行为，不是配置没生效
```

它是给 Nginx 的**指令**，Nginx 读完就从响应里摘掉。第一版探针断言「响应头里应该有这个头」→ 直接误报失败。
**判断缓冲关没关只能看行为**：事件到达的时间分布，或响应头是 `Transfer-Encoding: chunked`
（出现 `Content-Length` = 被整体缓冲）。

## 七、✅ 反问并发：从「用户报一个问题」到复现出**四个**缺陷

用户报「两个反问一同到达时提交逻辑出问题」。写探针（假 LLM 按角色分派 + `TestClient` 真并发）
**复现出四个独立缺陷**：

| # | 缺陷 | 证据 |
|---|---|---|
| ① | **连点/并发重复执行子图**（会重复写库） | 单域场景并发提交两次 → `results` 变 2 条、子图跑 2 次 |
| ② | 前端**静默吞掉**第二次提交 | `resumeInterrupt` 开头 `if (this.isLoading) return` → B 卡片提交毫无反应 |
| ③ | 提交 A 会**清空 B 卡片里已输入的内容** | 重渲染直接 `innerHTML=''` 重建全部卡片 |
| ④ | **跳过 → 总结永远为空** | 跳过某域后该域永远进不了 `completed_domains` |

> 复现的坑：假 LLM 瞬间返回看不出竞态 → 子 Agent 里加 `await asyncio.sleep(0.4)` 强制在 await 点交错。

### 修复

**后端**：

- `_inflight: set[str]` **会话级处理中锁**（`/chat` 与 `/resume` 都加），冲突返回 **409**。
  占用在**返回流之前**（才拿得到干净的 409），释放在 runner 的 `finally`
  （`StreamingResponse` 是「返回即开始」，在端点里释放等于没锁）
- `ResumeRequest.skip`：跳过不重跑子图、直接标记该域完成

**前端**（`chat.js` 提交逻辑重写）：

- `_answerJobs` 队列 + `_drainAnswers()` 单飞循环 → 天然不并发
- `_interruptStatus[id]` **状态即防抖**（第一次点击同步置 `queued`，比定时器可靠）
- 重渲染前 `_captureInterruptDrafts()` **保草稿**
- 失败：卡片留原地、清除状态、输入还回去；409 额外提示"可能另一个标签页提交过"
- 进场动画 + `_interruptAnimated` 记标记防重播 + 尊重 `prefers-reduced-motion`

### 🎯 顺手造了个前端测试，当场抓到一个真 bug

浏览器不好自动化，但在 Node 里用**极简假 DOM**（~80 行）+ `vm` 装载真实 `chat.js`
就能精确制造竞态。固化为 **`frontend/tests/interrupt-submit.test.mjs`**（7 组场景）。

它立刻抓到：**失败恢复时把状态赋成字符串 `'idle'`，而卡片判断用的是 `busy = !!status`**
—— 任何真值都被当成"忙"，卡片永久卡在"排队中"、按钮再也点不动。
改成 `delete this._interruptStatus[id]` 才对。

假 DOM 的两个必踩坑：

1. **`className` 与 `classList` 必须双向同步** —— 否则 `querySelectorAll('.x')` 永远返回空数组
2. **`vm.runInContext` 里顶层 `const/let/class` 不挂 globalThis**（只有 var/函数会）
   → 源码末尾补 `;globalThis.AIChat = AIChat;`

### 设计取舍（要讲清楚的）

服务端锁会让「两个不同域同时提交」的第二个拿到 409 —— 所以前端**必须**排队串行，这是配套的。
好处是把「静默丢答案」变成「明确的顺序处理」，代价是第二个回答要等第一个跑完（通常几秒）。
比"并发导致重复写库"好得多。
