## 二、✅ 全代码审查：删净死代码（45 个文件改动，+175 / -1120 行）

> 方法论已沉淀为技能 **`dead-code-audit`**。核心原则：
> **假阳性比漏报危险得多** —— 每个候选都必须有「谁引用它」的**反证**。

### 最容易翻车的一步：调用方语料的范围

- 仓库根目录有 `login.html` / `index.html`（**不在 `frontend/` 下**）——
  只扫 `frontend/` 会把它们用到的 CSS 类全判成死的（第一版就这样，
  差点把 20 个 `login-*` 类删掉）
- `docs/` **不算调用方**，只能作「文档提及」单列（否则只被文档写到的死端点会被误判成活）
- 脚本路径必须从 `__file__` 推仓库根 —— 第一版从 `backend/` 跑，
  `walk("frontend")` 解析成 `backend/frontend`，语料全空，
  **输出「100 个死代码」**，看起来像发现了金矿，其实是 bug

### 匹配调用方要把路径编译成正则 —— 占位符有四种拼法

`/api/x/1`、`` `/api/x/${id}` ``、`'/api/x/' + id`、`'/api/x/' + id + '/y'`。
**最后一种要把变量名和收尾引号一起吃掉**，否则 `treeId` 会挡住后面的 `/publish`，
把真端点判成死的。

### 删了什么（净 -945 行）

6 个死端点（用户选「全删」）+ `viewer.html`(649 行) + 2 个手动脚本(209 行) +
`call_ai_text_stream` + `ROUTING_DECISION_SCHEMA` + 1 个常量 + 4 个 schema + `exp_rate` +
`CoordinatorState.messages` + `recalc_dimensions_from_actions` + 17 处未使用 import +
7 个无引用前端函数（连带 3 个孤儿 helper）+
**68 条废弃 CSS 规则 / 1 个孤儿 keyframes / 6 个无用 CSS 变量 / 2 个无用 SVG 渐变**。

> **删 CSS 的坑**：**必须先剥掉注释与字符串再数括号** ——
> 项目里有 `url("data:image/svg+xml,...<svg>")` 内联图标，里面的 `{}` 会让朴素括号计数全乱
> （实测 7500 行的 `pages.css` 只解析出 35 条规则）。
> 另外类名有**三种动态拼法**，第三种（`'expr__diag-status-' + type`，连字符处截断）最容易漏，
> 不处理就会把活样式删掉。

## 七、多智能体 token 开销实测与归因修正

**不能用猜的**，写了两个脚本用**真实提示词与真实工具 schema** 精确测算（`tiktoken` cl100k_base）：

- `.workbuddy/measure_token.py` —— 逐个工具/提示词精确计数
- `.workbuddy/model_token.py` —— 三场景对比建模

**实测常数（静态可复算，最硬的一块）**：

| 项 | tok |
|---|---|
| 24 个业务工具 schema | 3,278 |
| ask_user 工具 schema | 327 |
| 6 个域提示词合计 | 3,054 |
| 路由提示词 / 汇总提示词 | 999 / 235 |
| **单体每轮固定开销**（24 工具 + ask_user + 全能提示词） | **6,659** |
| **单个子 Agent 每轮固定开销**（平均） | **1,382（20.8%）** |

场景对比（已计入多出的路由+汇总 1,234 tok）：单域 2 轮省 64%、双域 4 轮省 69%、
双域 + 各反问 1 轮省 70%。

### ⚠️ 三个机制要分清哪个是真省、哪个只是防爆

1. **按域拆分 = 真省** —— 降 79% 是**纯静态测量**（提示词 + 工具 schema），
   不含任何行为假设，最经得起追问。根因：单体**每一轮**都要重发全部 24 工具 schema，
   而拆分后每个子 Agent 只带自己那份
2. **`MAX_ASK_ROUNDS=3` / `MAX_HISTORY=10` = 防爆，不是常规省** ——
   注意 `MAX_HISTORY = 1 + 3×3 = 10` **正好等于反问上限下的最大消息数**，
   所以反问 ≤3 轮时这个窗口**根本不触发**。说它"省 token"不准确，准确说法是**防止上下文失控增长**
3. **断点续跑 = 省一次路由（999）+ 不重复已完成的工具轮次**，
   但**真正价值是正确性**：避免重复执行写库型工具（这是副作用，不只是钱）

### 修正归因（用户质疑「省 70% 太大众化」，直觉是对的）

1. 业界共识是「**多 Agent 比单 Agent 更贵**」（每个 Agent 有自己的 prompt + 协调开销）。
   写"省 70%"会让懂行的面试官第一反应是**怀疑**
2. **更致命：归因错了** —— 真正省 token 的不是"多 Agent"，而是
   **"按域装载工具与提示词"**。单体 Agent 若也做意图预筛，一样能省。
   把功劳记在"多 Agent"上，等于把**可迁移的设计**说成了**架构必然**
3. 70% 依赖对比基准，换个假设数字就变

**结论：把主语从「多 Agent 架构」改成「按域装载工具与提示词」**，
token 数字**降级为佐证**、不做主线；主动讲代价（路由+汇总 1.2K 开销）比只讲收益可信得多。

**可辩护的表述（用绝对值，别用百分比）**：
> 「按域拆分后单个子 Agent 的 prompt 固定开销从 6.6K 降至平均 1.4K token」

### 挖出这个项目真正独特（别人不会这么做）的 4 个设计

| # | 设计 | 为什么独特 |
|---|---|---|
| ① | **反问做成"工具"而非"中断"** | 官方 `interrupt()` 在多域并行下**无法表达"各域独立中断"**。改用普通工具：调用即结束本轮、反问内容作为 ToolMessage 进消息历史、用户回答=追加 HumanMessage 重跑。收益：**"跳过"零成本** + 反问不丢失 + 单一状态源 |
| ② | **通过"动态改工具集"约束 LLM 行为** | 反问满 3 轮 → 从 `bind_tools` **摘掉 ask_user**，逼模型用已有信息收尾。不是"加 if 报错"，而是**改变模型能看到什么**来改变行为 |
| ③ | **防 LLM 幻觉的兜底** | 即使工具已移除，仍防模型幻觉调用它 —— 防御做到了"LLM 会幻觉"这一层 |
| ④ | **多 Agent 引入的两个新问题，都自己解了** | (a) 竞态：连点/多标签页 → 子图重复执行 → 会话级互斥锁；(b) 并发事件串扰：SSE 推事件时 gather 的子 Agent 会串流 → ContextVar 承载发射器。**这两个是"做了多 Agent 才出现"的问题** |
