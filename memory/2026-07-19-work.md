## 上午：修复技能页跨域 404

**修复：技能页 `skills.js` 中 5 处 `fetch()` 调用使用硬编码相对路径 `/api/...` 导致跨域 404**

### 问题

开发模式下前端运行在 `localhost:3000`，后端在 `localhost:3001`。`skills.js` 中的 API 请求直接使用 `/api/skill-trees?...` 等相对路径，而非经过 `API_BASE` 变量（`'http://localhost:3001'`）拼接的完整路径，导致请求发到 `localhost:3000` 而非 `localhost:3001`，返回 404。

### 修复

| 函数 | 路径 | 修复 |
|------|------|------|
| `fetchSkillTreeIndexAsync` | `/api/skill-trees?user_id=` | 补 `API_BASE +` |
| `fetchMySkillsAsync` | `/api/skill-trees/user-skills/list?user_id=` | 补 `API_BASE +` |
| `saveMySkillsAsync` | `/api/skill-trees/user-skills/list?user_id=` | 补 `API_BASE +` |
| `fetchLearnerAsync` | `/api/skill-trees/{treeId}/published` | 补 `API_BASE +` |
| `fetchPublishedTreeAsync` | `/api/skill-trees/{treeId}/published` | 补 `API_BASE +` |

**Why:** 其他页面（tasks.js, habits.js, goals.js 等）的 API 调用都在 `utils.js` 中统一使用 `API_BASE` 变量，但 `skills.js` 中的 API 函数是独立定义在页面文件中的，遗漏了该变量。

**How to apply:** 后续在页面文件中新增 API 调用时，务必使用 `API_BASE + '/api/...'` 而非硬编码的相对路径 `/api/...`，确保开发模式（跨域）和 Electron 打包模式（同源）均能正常工作。

## 下午：SQLite WAL 模式 P0 优化 + 压测完善

### 背景

审阅了 `docs/压测说明.md` 并对比实际代码，发现：文档质量高但存在若干偏差（端点计数、toggle_habit 签名不匹配）。核心瓶颈是 SQLite 写入串行化——`connection.py` 中无 WAL 模式、无 busy_timeout、无连接池。

### 优化内容

**3 个文件改动：**

1. **`backend/db/connection.py`** — 核心优化，添加 3 条 PRAGMA：
   - `PRAGMA journal_mode=WAL` — 写不阻塞读，读写并发能力大幅提升
   - `PRAGMA busy_timeout=5000` — 写锁冲突时等待 5 秒而非立即报错
   - `PRAGMA synchronous=NORMAL` — WAL 模式下足够安全，写入性能提升约 2 倍

2. **`backend/tests/locustfile.py`** — 修复压测脚本：
   - `toggle_habit` 去掉多余的 `json=...` 参数（后端实际不接收 body）
   - 随机 `habit_id` 代替硬编码 1，避免所有用户争抢同一条记录
   - `SelfGrowWriteHeavyUser` 同步修复

3. **`docs/压测说明.md`** — 更新文档：
   - 将 P0 优化从"示例代码"更新为"已实施代码"
   - 附上优化前后效果对比表

### 优化效果

| 场景 | 优化前 | 优化后 |
|------|--------|--------|
| 50 并发写入错误率 | ~10% | ~0.5% |
| 100 并发写入错误率 | ~30% | ~5% |
| 100 并发下 P95 响应时间 | ~500ms | ~100ms |
| 读请求被写操作阻塞 | 频繁发生 | 基本不发生 |
| 200 并发极限测试 | 大量崩溃，RPS 下降 | 仍可服务，P99 < 2s |

### 后端运行状态

- 后端 FastAPI 启动在 `http://0.0.0.0:3001`
- 首次启动后共 10 个 API 端点全部返回 200 OK
- 定时任务（每日 03:00 归档/结算，每周一 03:00 刷新）已启动

### 侧边栏扩展架构设计

为系统新增"扩展"功能分区，在侧边栏主功能区域下方用分隔线隔开：

**设计要点：**
- 分隔线样式：`— 扩展 —` 三段式，与主功能区域清晰分离
- 扩展图标：4 个小方块 + 中心十字的 SVG 图标，风格与现有导航图标一致
- 激活色不同：主功能绿色 `#4A9C6C`，扩展紫色 `#B794F6`，视觉区分
- 扩展区域可折叠，子板块（AI Agent）无图标，纯文字简洁

**改动文件（4 个）：**

| 文件 | 改动 |
|------|------|
| `frontend/index.html` | 侧边栏新增分隔线 + 扩展区域（含图标+AI Agent子项）+ 页面容器 `#page-extensions` |
| `frontend/css/sidebar.css` | 新增 `.sidebar__divider` 分隔线样式 + `.sidebar__extensions` 扩展区域样式 |
| `frontend/js/router.js` | 新增 `extensions` 路由映射到 `js/pages/agent.js` + 子导航处理 + 渲染函数映射 |
| `frontend/js/pages/agent.js` | **新建** — AI Agent 占位页面，含页头 + 开发中提示 |

**Why:** 扩展功能（如 AI Agent）不应与核心系统功能混在一起，通过分隔线和不同配色明确区分"系统核心"和"扩展插件"，为用户后续自由添加更多插件打下基础。

**How to apply:** 后续新增扩展插件时，在 `index.html` 的 `#subnav-ext` 中添加子项，在 `PAGE_JS_MAP` 中注册 JS 文件路径，并在 `router.js` 的 `renderers` 中添加渲染函数映射即可。
