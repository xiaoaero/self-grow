## 2. P0修复：启动时清空 tasks 表

### 问题
`backend/db/init.py` 中每次启动都执行 `DELETE FROM tasks`，导致用户关闭电脑后重启后端，今日任务全部丢失。

### 场景
```
用户创建3个今日任务 → 晚上关机 → 第二天开机 → 任务全部消失
```

### 修复
```diff
# backend/db/init.py
- # 清空旧任务数据，让 source_type 分离逻辑干净生效
- cursor.execute("DELETE FROM tasks")
```

直接删除这行代码，保留任务数据。

## 3. 启动时补归档机制

### 需求
用户每天晚上关闭电脑，凌晨3点的定时归档任务不会执行。需要在第二天启动后端时自动补归档。

### 新增函数
`backend/db/batch.py` 新增 `catch_up_missed_archives(user_id)`：

```python
def catch_up_missed_archives(user_id: int):
    """
    启动时检查：如果凌晨3点的归档任务未执行（如电脑关机），则补执行。
    - 昨天的 today/daily 任务 → 归档
    - 上周的 weekly 任务 → 归档
    """
```

### 流程
1. 检查 tasks 表是否有昨天的 today/daily 任务 → 有则标记未完成的为 expired → 归档
2. 检查 tasks 表是否有上周的 weekly 任务 → 有则标记未完成的为 expired → 归档

### 启动时调用
`backend/main.py` 在 lifespan 中调用：

```python
# 启动时补归档：检查凌晨3点的任务是否因关机未执行
log.info("🔍 检查是否有未归档的任务...")
for user in get_all_users():
    try:
        catch_up_missed_archives(user["id"])
    except Exception as e:
        log.error(f"  用户 {user['id']} 补归档失败: {e}")
```

### 效果
```
用户晚上关机 → 第二天开机 → 启动后端 → 自动补归档 → 历史任务正常显示
```

## 4. P1修复：user_id 参数被忽略

### 问题
前端传入 `user_id` 查询参数，但后端使用 `Depends(get_current_user)` 从 token 获取用户，`user_id` 被完全忽略。

### 修复
`backend/routers/tasks.py`：

```python
@router.get("/api/tasks/history")
async def list_task_history(
    user=Depends(get_current_user),
    user_id: int = None,  # 新增参数
    ...
):
    # 校验 user_id 与 token 中的用户一致
    if user_id is not None and user_id != user["id"]:
        raise HTTPException(status_code=403, detail="无权访问其他用户数据")
    return get_task_history(user["id"], ...)
```

### 效果
- 如果前端传入的 `user_id` 与 token 中的用户不一致，返回 403 错误
- 代码逻辑更清晰，消除潜在的安全隐患

## 5. P2修复：分页边界时序问题

### 问题
用户在第5页浏览，然后筛选条件变化（筛选后只有1页数据），前端会先请求 page=5，返回空数据，然后才修正为 page=1。

### 修复
`backend/db/task_history.py` 在后端处理：

```python
def get_task_history(...):
    ...
    total = count_row["cnt"]
    
    # 计算总页数，修正超出范围的页码
    total_pages = (total + page_size - 1) // page_size if total > 0 else 1
    if page > total_pages:
        page = total_pages  # 自动调整到最后一页
    
    ...
    return {
        "total": total,
        "page": page,  # 返回修正后的页码
        ...
    }
```

### 效果
- 后端自动修正超出范围的页码
- 前端无需额外请求，一次到位
- 页面切换更流畅

## 6. P3问题分析

### P3-1: 缺少重复归档检查
**当前状态**：风险较低，无需立即修复

`archive_tasks_to_history` 的流程：
1. SELECT FROM tasks → 查询要归档的任务
2. INSERT INTO task_history → 插入历史表
3. DELETE FROM tasks → 从任务表删除

任务被删除后，第二次执行时查不到这些任务，所以不会重复插入。唯一风险是步骤2和3之间进程崩溃（极罕见）。

### P3-2: 排序字段验证不完整
**当前状态**：已有兜底保护，风险较低

```python
order_map = {...}
order_sql = order_map.get(sort, "archived_at DESC, id DESC")  # 默认值兜底
```

使用 `dict.get(key, default)` 方法，无效值返回默认排序，不会造成 SQL 注入。
