## 一、清理「预留工具」的残留

顺手清掉两处**过时注释**（工具删了、注释还在提，会让人以为还有这东西）：

- `prompts/expression.py` 的小节标题「# 出题工具定义（预留联网搜索）」
- `services/expression_service.py` docstring「当前热搜搜索工具预留，暂不实现。」

### ⚠️ 关键教训：给 LLM 声明工具 ≠ 前端留 TODO

前端留 TODO 没人执行；**给模型声明工具等于告诉它「你可以用这个」** ——
它会真的去调，拿到「暂不可用」后再重新生成一遍，**白烧一整轮 LLM 往返（10~30s）**。

**前端留 TODO 无害；给模型留 TODO 是给它挖坑。**

**要加联网搜索：实现了再挂进 tools 列表。**

**核查范围**：6 个协调子 Agent（24 工具）+ 技能树 AI（9 工具）的提示词与实现逐一比对，
**没有第二处"声明了却不存在的工具"**。

## 二、项目里**两套工具挂载方式并存，都是合法的**

用户问 `EXPRESSION_QUESTION_TOOLS` / `ACTION_PARSE_TOOLS` 是干什么的，
并疑惑「挂工具不是应该用 LangChain 的方式吗」。因为**工具性质根本不同**：

| | 协调 Agent / 技能树 AI | 表达训练 / 行动解析 |
|---|---|---|
| 声明 | `@tool` 装饰的函数 | **手写 OpenAI JSON schema dict** |
| 挂载 | `llm.bind_tools([...])` | `llm.bind(tools=[...], tool_choice="auto")` |
| 执行 | `tools_by_name[name].invoke(args)` | **手动 `if name ==` 分发** |
| 见于 | `agents/base.py:78` | `expression_service.py:176`、`ai_action_service.py:48` |

**为什么不能统一**：`ACTION_PARSE_TOOLS` 里的 `send_message` / `submit_actions`
**根本没有对应的本地函数** —— 它们不是"调用一个工具"，而是
**用函数调用语法约束模型的输出格式**（structured output 的另一种用法）。
用 `@tool` 就得为"不存在的动作"造空壳函数，反而别扭。

**判断标准**：工具背后有没有**真实的本地函数**。

- 有（`record_action` 真的要写库）→ `@tool` + `bind_tools` + `.invoke()`，
  能统一注入 `user_id`、统一异常处理、丢线程池
- 没有 → 手写 schema

> `bind(tools=手写dict)` 和 `bind_tools([@tool])` **都是 LangChain 的合法用法** ——
> 前者是低层透传、后者是高层自动生成 schema。

## 三、⚠️ 顺带发现一个真实的不一致（影响对外表述准确性）

项目对外表述里有「工具枚举参数**以类型约束生成 JSON Schema**，防止无效参数」这类说法 ——
这句**只在 MCP / 子 Agent 那条链上成立**：

| | 枚举约束 |
|---|---|
| MCP / 子 Agent | `CategoryId = Literal["health", ..., "soul"]`（`mcp_server.py:112`）→ 自动生成 `enum` → 模型传不错 |
| `ACTION_PARSE_TOOLS` | `"description": "维度ID: health/study/..."` → **纯字符串说明，无 `enum`** |

**后果**：① 模型可能传错维度值（API 层不拦）② **加第 9 个维度要手改这里**
（第二处手工维护的副本，与 09-17 修掉的 `CATEGORY_MAP` 同类）。

## 四、✅ 修复：`ACTION_PARSE_TOOLS.category_id` 加上 enum 约束

```python
from models.constants import CATEGORIES
_DIMENSION_IDS  = [c["id"] for c in CATEGORIES]
_DIMENSION_HINT = "、".join(f"{c['id']}={c['name']}" for c in CATEGORIES)
...
"category_id": {
    "type": "string",
    "enum": _DIMENSION_IDS,                        # ← 新增：API 层强约束
    "description": f"维度ID（{_DIMENSION_HINT}）",  # ← 从纯 ID 列表改成带中文名
},
```

**收益**：① 模型不可能再传错维度值 ② 加维度只改 `models/constants.py` **一处**
③ description 带了中文名，对模型更友好（原来只有 ID）。

**验证**：无循环导入（`prompts` → `models.constants` → `models.level` 单向）；
`enum` 与 `CATEGORIES` 断言一致；工具列表未变；**全量 150 passed**。

## 五、发现的另外两处（未修，留给用户决定）

1. **`sub_type`（12 个子类型）仍手写在 description 里** ——
   真实定义散在 `models/constants.py` 的 `_calc_*` 函数中，**根本没有单一来源**。
   修它得先把子类型收拢成常量表，会牵动计分逻辑，**不建议贸然动**
2. **`mcp_server.py:112` 的 `CategoryId = Literal["health", ...]` 也是手写的** ——
   `Literal` 的类型参数只能是字面量，**没法从运行时列表派生**（类型系统限制）。
   但可以加**运行时断言**把它和 `DIMENSION_KEYS` 锁在一起，
   否则加维度时漏改 = 静默不一致
