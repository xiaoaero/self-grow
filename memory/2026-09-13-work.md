## 一、JWT 登录鉴权 — S1 地基（依赖 + 表结构 + 服务层）

### 背景
原实现 `get_current_user` 只校验 URL 的 `user_id` 是否存在，等同无鉴权；全后端 73 个端点依赖它。
方案文档见 `docs/登录鉴权方案选型.md`（9/10 已完成选型论证）。

### 依赖
- `pixi.toml` 加 `PyJWT>=2.8` + `bcrypt>=4.0`
- **踩坑**：原计划用 `passlib[bcrypt]`，装上后 passlib 1.7.4 与 bcrypt 5.0 不兼容（bcrypt 移除 `__about__`），连 10 位普通密码都 hash 失败。改为直接调 `bcrypt` 官方 API，依赖更少更可控。
- **踩坑**：`pixi update` 会超时无输出，`pixi install` 才正常完成。

### 数据层
- `db/init.py`：`init_auth_tables()` 新建 `refresh_tokens` / `api_keys`（带索引）；`migrate_users_auth_columns()` 给 users 补 `password_hash` / `token_version` / `last_login`（沿用项目幂等 ALTER 写法）
- 新建 `db/auth.py`：只做 SQL（符合 routers → services → db 分层）

### 服务层 `services/auth_service.py`
| 能力 | 实现 |
|---|---|
| 密钥 | 未配置 → **抛错拒绝启动**；TRUSTED_MODE → 临时密钥 + 告警（绝不用默认密钥） |
| 密码 | 超 72 字节先 SHA-256（bcrypt 硬限制）；`gensalt(rounds=12)` |
| Access | 载荷 `{sub, role, ver, exp}` HS256；验签支持 `SELF_GROW_JWT_OLD_SECRET` 轮换 |
| 失效 | 验签后仍核对 `token_version` → 改密码/踢下线即时生效 |
| Refresh | 只存 sha256；**用掉即撤销**（Rotation，重放可检测） |
| API Key | `sgk_` 前缀，供 MCP HTTP 模式 |
| 防枚举 | 用户不存在与密码错误统一返回 None；5 次失败锁 10 分钟 |

## 三、S4 — 前端改造（本轮核心）

### `frontend/js/auth.js`（新建，共享模块）
被主应用（`js/auth.js`）和技能树编辑器（`../js/auth.js`）共同加载，必须在其他脚本之前。

- **包装 `window.fetch`**：自动给本站 API 请求加 `Authorization`；**52 处 `fetch(...?user_id=)` 一行未改**
- **401 自动续期**：refresh 换一对新 token → 重放原请求；失败才清态跳登录
- **并发去重**：多个请求同时 401 只发一次 refresh（Promise 共享）
- **不拦截** `/api/auth/login`、`/api/auth/refresh`（避免递归）
- 对外：`getAuthHeaders / isAuthenticated / isTrustedMode / login / logout / redirectToLogin`

### refresh 双通道（应对 SameSite 限制）
`SameSite=Lax` 的 httpOnly Cookie 在跨域开发态（前端 5173 / 后端 3001）不随 XHR 发送。
因此：登录响应**同时**在 body 返回 `refresh_token`；`/api/auth/refresh` 取值顺序「Cookie → body」。
同源生产（Docker，后端 serve 前端）Cookie 生效防 XSS；跨域开发 body 兜底。

### CORS 收紧
原来 `allow_origins=["*"]` 会让浏览器拒绝一切携带凭证的响应。
改为显式来源 + `allow_credentials=True`，可用 `SELF_GROW_CORS_ORIGINS` 覆盖（填 `*` 则自动关闭 credentials）。
`/api/config.js` 额外注入 `window.__SELF_GROW_TRUSTED_MODE__`。

## 五、S5 — MCP API Key 接入

### 发现的安全洞
`mcp_server.py` 的 HTTP 传输模式（`MCP_TRANSPORT=streamable-http`）**此前完全裸奔**——监听 `0.0.0.0:8000`，任何人可调 24 个业务工具读写数据库。

### 两种传输分而治之
| 传输 | 鉴权 | 身份 |
|---|---|---|
| stdio | ❌ **刻意不鉴权**（本地 spawn 子进程，进程边界即信任边界；加 Key 只会让客户端配置变麻烦，也是 MCP 生态通行做法） | `SELF_GROW_USER_ID` |
| HTTP | ✅ 强制 `X-API-Key` | Key 解析出的用户 |

### 实现（mcp_server.py 底部）
- `ApiKeyMiddleware(BaseHTTPMiddleware)`：校验 `X-API-Key` 或 `Authorization: Bearer sgk_...`，复用 `auth_service.resolve_api_key()`（同一张 `api_keys` 表，用户中心可撤销）；`SELF_GROW_TRUSTED_MODE=1` 可关闭
- `build_http_app(transport)`：`mcp.http_app(transport=..., middleware=[Middleware(ApiKeyMiddleware)])` + `uvicorn.run`
- **身份注入**：新增 `_mcp_user_id` ContextVar + `current_user_id()`；16 处 `DEFAULT_USER_ID` 全部替换为 `current_user_id()` → HTTP 模式下**多用户已支持**，不再是所有人都是 user 1

### 新增 `tests/test_mcp_auth.py`（6 个用例）
无 Key 401 / 错 Key 401 / 合法 Key 放行 / Bearer 形式放行 / **撤销后立即失效** / 身份由 Key 决定。
**踩坑**：测试必须用 `with TestClient(app)` 触发 lifespan，否则 MCP session manager 未初始化会报 `Task group is not initialized`。
