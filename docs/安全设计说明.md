# Self Grow 安全设计说明

> 版本：v1.0（2026-09-13）
> 配套文档：[登录鉴权方案选型](./登录鉴权方案选型.md)（为什么这么选）、[技能树编辑器技术详解](./技能树编辑器技术详解.md)（编辑器实现）
> 本文回答的是另一个问题：**这套系统现在到底防住了什么，没防住什么。**

---

## 一、先说结论

| 维度 | 改造前 | 现在 |
|---|---|---|
| 身份认证 | ❌ 只校验 `?user_id=` 是否存在，改个数字就能看别人数据 | ✅ JWT Access + Refresh 双令牌 |
| 角色授权 | ❌ 无。角色来自 URL 参数且默认 admin | ✅ `require_admin` 依赖 + JWT 载荷携带 role |
| 密码 | ❌ users 表没有密码字段 | ✅ bcrypt(cost=12) + 超长密码前置 SHA-256 |
| 会话失效 | ❌ 不存在"会话"概念 | ✅ Refresh 落表可撤销 + token_version 全局失效 |
| 机器客户端 | ❌ 无方案 | ✅ API Key（`sgk_` 前缀，可撤销） |
| CORS | ⚠️ `allow_origins=["*"]` | ✅ 显式来源 + credentials |
| MCP HTTP | ❌ 裸奔，任何人可读写数据库 | ✅ 强制 `X-API-Key` |

**但也要清楚它的定位**：这是一个 1~5 人的个人/家庭自用系统，目标是"防住误操作和脚本小子"，**不是金融级**。下面每一节都会同时写"做了什么"和"没做什么"。

## 二、威胁模型

先看清楚要防谁，否则安全措施会做成宗教仪式。

| 攻击者 | 能力 | 本系统的防线 |
|---|---|---|
| **手贱的路人**（家人/室友/同网段的设备） | 能改 URL 参数、能敲地址 | ✅ 已防住（身份 + 角色） |
| **会抓包的脚本小子** | 能看请求、改参数、重放 | ✅ 已防住（签名验签、Refresh 轮换） |
| **拿到你电脑但没登录的人** | 能开浏览器 | ✅ 已防住（无凭证 = 401） |
| **能注入 JS 的攻击者（XSS）** | 能读 localStorage | ⚠️ 部分防住（见 7.3，这是 Access 存 localStorage 的固有代价） |
| **专业定向攻击者** | 社工、物理接触、0day | ❌ 不在防御范围内 |
| **云端多租户隔离** | — | ❌ 未做（所有 admin 可改所有技能树） |

**诚实的一句话**：最大风险其实是"自己把 `.env` 里的 `SELF_GROW_JWT_SECRET` 提交到 GitHub"——所以**代码里从不为密钥设默认值，缺失即拒绝启动**。

## 三、认证：三种客户端，三条凭证通道

### 3.1 凭证解析优先级（`routers/deps.py`）

```
① SELF_GROW_TRUSTED_MODE=1        → 固定用户（本地开发/演示，启动打告警）
② Authorization: Bearer <jwt>     → 验签 + token_version 校验
③ X-API-Key: sgk_xxx              → 查 api_keys 表（MCP / 脚本）
④ 都没有                           → 401 + WWW-Authenticate: Bearer
```

**旧的 `?user_id=` 参数不再作为身份依据**（保留参数本身无害，但后端一律以上述凭证为准）。
这是全项目最重要的一处语义变更——它把"用户自己声称我是谁"改成了"系统验证你是谁"。

> 当初把 `get_current_user` 抽到 `deps.py` 时没人想到会有回报，但这次 **73 个业务端点一行未改**就完成了全局鉴权升级。

### 3.2 三种客户端

| 客户端 | 凭证 | 为什么是这个 |
|---|---|---|
| 浏览器 | 用户名+密码 → JWT | 有交互、有 UI，体验优先 |
| MCP stdio | **无**（`SELF_GROW_USER_ID` 环境变量） | 本地 spawn 的子进程，进程边界即信任边界；加 Key 只会让配置变麻烦 |
| MCP HTTP / 脚本 | `X-API-Key` | 非交互、长期有效、可撤销可轮换 |

## 四、令牌设计

### 4.1 三种令牌对照

| | Access Token | Refresh Token | API Key |
|---|---|---|---|
| 载体 | JWT（自包含） | 随机串 | 随机串（前缀 `sgk_`） |
| 存储 | 前端 localStorage | 前端 localStorage + httpOnly Cookie | 客户端配置文件 |
| 服务端存储 | **无**（无状态） | `refresh_tokens` 表（**只存 SHA-256**） | `api_keys` 表（只存 SHA-256） |
| 有效期 | 2 小时（可配） | 30 天（可配） | 不过期，靠手动撤销 |
| 撤销方式 | 靠 `token_version` 间接失效 | 直接删/标记 revoked | 直接标记 revoked |
| 用途 | 每次 API 请求 | 换新的 Access | 机器客户端长期接入 |

### 4.2 载荷

```json
{ "sub": "2", "role": "admin", "ver": 3, "exp": 1757800000, "iat": 1757792800, "type": "access" }
```

- `role` 随凭证走 → **后端校验角色时 0 次数据库查询**（验签后直接读）
- `ver` = `users.token_version` → 改密码 / 强制下线时 +1，所有旧 Access 立即失效
- 显式 `algorithms=["HS256"]` 验签（防 `alg: none` 降级攻击）

### 4.3 Refresh 轮换（Rotation）

```
Refresh 用一次 → 旧的立即标记 revoked → 同时签发新的一对
```

**好处是重放可检测**：如果有人偷走了一个 Refresh 并用它，合法用户下次再用同一个就会失败——系统能察觉异常（当前实现是拒绝，尚未做告警，见第 10 节）。

### 4.4 三招补上"JWT 无法主动失效"

| 手段 | 生效速度 | 场景 |
|---|---|---|
| Access 只给 2 小时 | 最慢 2 小时 | 常规泄露 |
| Refresh 落表可撤销 | **立即** | 登出、登出所有设备 |
| `token_version += 1` | **立即** | 改密码、管理员踢人 |

### 4.5 refresh 双通道（一个真实的工程妥协）

`SameSite=Lax` 的 httpOnly Cookie **在跨域开发态（前端 5173 / 后端 3001）不会随 XHR 发送**。

解法：登录响应**同时**在 body 返回 `refresh_token`，`/api/auth/refresh` 取值顺序「Cookie → body」。

| 部署形态 | 生效通道 | 安全收益 |
|---|---|---|
| 同源生产（Docker，后端 serve 前端） | Cookie | JS 读不到 refresh，XSS 偷不走 |
| 跨域开发 | body | 功能可用，但 refresh 落在 localStorage |

这不是"两边都完美"，而是**明确知道代价后的选择**，并在代码注释里写清楚了。

## 五、密码存储

```python
bcrypt.hashpw(_prehash_if_long(password).encode(), bcrypt.gensalt(rounds=12))
```

| 项 | 值 | 理由 |
|---|---|---|
| 算法 | bcrypt | 自带随机盐，抗 GPU/ASIC 暴力破解 |
| cost | 12 | 单次校验约 250ms 量级，兼顾安全与体验 |
| 超长密码 | 先 SHA-256 | **bcrypt 只取前 72 字节**，不处理会静默截断 |
| 校验失败 | 统一文案 | "用户名或密码错误"，不泄露账号是否存在 |
| 暴力破解 | 5 次失败锁 10 分钟 | 内存计数器（单进程够用，见第 10 节） |

> ⚠️ **踩过的坑**：原计划用 `passlib[bcrypt]`，但 passlib 1.7.4 与 bcrypt ≥ 4.1 不兼容
> （bcrypt 移除了 `__about__`），连 10 位普通密码都 hash 失败。最终改为直接调 bcrypt 官方 API。

## 六、授权：角色与技能树三道防线

### 6.1 RBAC（当前只有两级）

```python
async def require_admin(user=Depends(get_current_user)):
    if (user.get("role") or "user") != "admin":
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return user
```

挂载位置：`skill_tree.py` 的 create / update / publish / delete + `skill_tree_ai.py` 的 chat / resume。

> **注意 AI 端点也算写操作**：`/api/skill-trees/{id}/chat` 能改树，必须和写接口一样管。这是最容易漏的一处。

**401 与 403 严格区分**：未认证 = 401（去登录），已登录但没权限 = 403（提示无权限）。混用会让前端无法区分两种处理。

### 6.2 技能树编辑器：三道防线

需求是"**普通用户根本进不去编辑器**"。但 `index.html` 是静态文件，只要被 serve 出来，藏按钮拦不住人敲地址。

| 防线 | 位置 | 能否被绕过 |
|---|---|---|
| ① 入口不渲染 | `skills.js` 非 admin 不生成"编辑技能"按钮 | ✅ 能（手敲 URL） |
| ② 页面启动自检 | 编辑器先查 `/api/auth/me`，非 admin 显示无权限 | ⚠️ 能（禁用 JS / 直调 API） |
| ③ **后端 `require_admin`** | 所有写接口非 admin → 403 | ❌ **不能，这才是真的锁** |

**第 ② 道的一个关键细节**：被拦截时**不 `new App()`**。
因为 `App` 一构造就会去拉草稿数据——普通用户虽然看不见按钮，但**未发布的树结构已经加载进页面了**。要拦就拦在初始化之前。

### 6.3 已发布内容对所有人开放

`GET /api/skill-trees/{id}/published` **不挂鉴权**。这是刻意设计：技能库的意义就是给别人学。
只有"写"和"进入编辑器"是 admin 专属。

## 七、传输与浏览器安全

### 7.1 CORS（从 `*` 收紧）

原来的 `allow_origins=["*"]` 有个致命后果：**浏览器会拒绝一切携带凭证的响应**。
一旦前端要带 `Authorization`，就必须改成显式来源 + `allow_credentials=True`。

```python
SELF_GROW_CORS_ORIGINS=""      # 未配置 → 同源 + 常见开发端口（3000/3001/5173/5500/8000/8080）
SELF_GROW_CORS_ORIGINS="*"     # 完全放开 → 自动关闭 credentials（仅无鉴权调试）
SELF_GROW_CORS_ORIGINS="https://a.com,https://b.com"   # 生产显式列白名单
```

另外默认还会按正则放行**本机任意端口**：

```python
allow_origin_regex = r"^https?://(localhost|127\.0\.0\.1)(:\d+)?$"
```

> 为什么要加正则：开发态前端端口根本没有约定（`npx http-server -p 3000`、Vite 5173、Live Server 5500……），
> 逐个列永远列不全——第一版只列了 5 个端口，用户用 3000 就直接被拦，登录页报"无法连接到后端"。
> **只匹配 localhost / 127.0.0.1，不含局域网 IP**，所以公网环境仍需用 `SELF_GROW_CORS_ORIGINS` 显式指定。

**注意 `file://` 场景**：双击 HTML 直接打开时 Origin 是 `null`，不在放行范围内（任何本地文件都能调你的 API，风险不划算）。
登录页会检测到 `location.protocol === 'file:'` 并给出明确提示，改用 `npx http-server -p 3000` 即可。

### 7.2 CSRF

| 场景 | 风险 | 现状 |
|---|---|---|
| 业务 API | 用 `Authorization` 头，不是 Cookie | ✅ 天然免疫 CSRF |
| `/api/auth/refresh` | 依赖 Cookie（同源时） | ⚠️ `SameSite=Lax` 挡住跨站表单 POST；**未做 CSRF token** |

评估：刷新端点被 CSRF 攻击的最坏结果是"攻击者刷新了你的 token"，无法拿到响应内容（同源策略），**实际风险极低**。真要补，加一个自定义头校验即可（带自定义头的请求会触发预检）。

### 7.3 XSS（最需要诚实的一节）

Access Token 存在 `localStorage`，因此**页面存在 XSS 时 token 会被窃取**。

可选的更严方案是把 Access 也放进 httpOnly Cookie——但那样就绕回了"为什么不用 Session"的问题（机器客户端无法工作）。

**当前的缓解措施**：

| 措施 | 说明 |
|---|---|
| Access 只活 2 小时 | 泄露窗口有限 |
| Refresh 同源时走 httpOnly | XSS 拿不到最有价值的那一个 |
| 前端渲染大量使用 `escapeHtml()` | 减少注入面 |
| `token_version` 可一键失效 | 发现异常立即全局踢下线 |

**建议**：如果将来引入富文本/Markdown 渲染（用户可控 HTML），必须先上 DOMPurify。
当前技能树的 AI 返回内容是当作纯文本 `textContent` 处理的，风险可控。

### 7.4 HTTPS

项目默认跑在局域网 HTTP。**局域网内风险可接受，公网暴露必须上 HTTPS**（否则 JWT 和 API Key 都是明文）。
Docker 部署方案里建议前置 Nginx + Let's Encrypt。

## 八、MCP 安全

| 传输 | 鉴权 | 身份来源 |
|---|---|---|
| stdio | ❌ 无（**刻意**） | `SELF_GROW_USER_ID` |
| HTTP | ✅ 强制 `X-API-Key` | Key 解析出的用户 |

**为什么 stdio 不鉴权**：它是用户自己 spawn 的子进程，**进程边界就是信任边界**。加 Key 只会让 Claude Desktop 的配置文件变麻烦——这也是 MCP 生态的通行做法。

**为什么 HTTP 必须鉴权**：一旦监听 `0.0.0.0:8000`，任何能访问该端口的人都能调 24 个业务工具读写数据库。改造前这一条是**完全裸奔**的。

实现（`mcp_server.py` 底部）：

```python
class ApiKeyMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        if SELF_GROW_TRUSTED_MODE: return await call_next(request)   # 本地开发开关
        ...
        user = auth_service.resolve_api_key(raw)                     # 复用 REST 的 api_keys 表
        if not user: return JSONResponse({...}, 401)
        token = _mcp_user_id.set(user["id"])                          # 身份注入 ContextVar
        try:    return await call_next(request)
        finally: _mcp_user_id.reset(token)
```

鉴权通过后用户 ID 写入请求级 ContextVar，24 个工具内部的 `current_user_id()` 会读到它
→ **HTTP 模式下多用户已支持**，不再是"所有人都是 user 1"。

## 九、AI 链路的安全

| 风险 | 处理 |
|---|---|
| AI 会话跨用户串号 | `thread_id` 编成 `stc_{user_id}_{uuid}`，不是纯 uuid |
| AI 改树绕过权限 | `/chat`、`/chat/resume` 挂 `require_admin` |
| AI 危险操作（替换整棵树 / 级联删除） | 两段式确认：工具返回 `needs_confirmation` → 前端确认卡片 → resume |
| 确认后参数被模型改写 | resume 时把 `pending["args"]` **序列化回灌**，要求"原样使用并附加 confirm=True" |
| AI 基于旧快照覆盖用户手动改动 | resume 请求可带当前树，覆盖 checkpoint 里的旧快照 |
| 提示词注入（用户在节点描述里塞指令） | ⚠️ **未专门处理**——节点描述会进入提示词。缓解：AI 只能调白名单内的 9 个工具，最坏结果是"把树改乱"，且可 Ctrl+Z 撤销 |

## 十、已知风险与改进清单（诚实版）

这份清单的价值大于前面的所有内容——**能说出自己系统的边界，比堆砌安全名词更可信**。

| # | 问题 | 影响 | 改进方案 | 优先级 |
|---|---|---|---|---|
| 1 | Access Token 存 localStorage | XSS 可窃取 | 富文本场景先上 DOMPurify；或改内存存储（代价：刷新需重登） | 中 |
| 2 | 无 HTTPS | 局域网可用，公网明文 | 前置 Nginx + Let's Encrypt | 高（若要公网） |
| 3 | 登录失败锁定在**内存** | 多实例部署失效 | 迁到 SQLite / Redis | 中 |
| 4 | Refresh 重放只拒绝不告警 | 无法察觉正在发生的攻击 | 重放时撤销整条链 + 记录告警日志 | 中 |
| 5 | 所有 admin 能改所有技能树 | 无资源级隔离 | 增加 `owner_id` + 资源级鉴权 | 中 |
| 6 | 未做 MFA | 密码泄露即失守 | TOTP（pyotp） | 低（1~5 人场景） |
| 7 | 无审计日志 | 出问题无法追溯 | 记录登录/改密/写操作到 `audit_logs` 表 | 中 |
| 8 | JWT 密钥是单值 | 轮换时旧 token 全失效 | 已有 `SELF_GROW_JWT_OLD_SECRET` 支持双密钥过渡 | 低（已缓解） |
| 9 | 未做请求限流 | 可被刷接口 | `slowapi` 或简单内存令牌桶 | 中 |
| 10 | 提示词注入未专门防护 | AI 可能被诱导改乱树 | 工具白名单 + 可撤销（已缓解）；可加敏感操作二次确认 | 低 |

## 十二、应急响应

| 事件 | 处置 |
|---|---|
| **密钥泄露** | 改 `SELF_GROW_JWT_SECRET` → 重启 → 所有人重新登录。想要平滑过渡：旧密钥填进 `SELF_GROW_JWT_OLD_SECRET` |
| **某个账号被盗** | 改该用户密码（自动 `token_version+1` + 撤销全部 Refresh） |
| **API Key 泄露** | 用户中心 → API Key → 撤销（立即生效） |
| **全员强制下线** | 批量 `bump_token_version` + `revoke_all_refresh` |
| **数据库泄露** | 密码是 bcrypt 哈希（难破解）；Refresh/API Key 只存 SHA-256（无法还原）；但仍应全员改密 + 撤销所有 Key |

## 十三、面试怎么讲这段（90 秒版）

> "原实现只校验 URL 里的 user_id 是否存在，等于没有鉴权。我用 JWT 重做了一遍：
> Access 2 小时 + Refresh 30 天，Refresh 落表可撤销、用掉即轮换，改密码时靠 `token_version` 让旧 token 全部失效——这三招补上了 JWT 天生无法主动失效的短板。
>
> 客户端分三类：浏览器走密码登录，MCP stdio 因为是本地 spawn 的子进程不做鉴权，MCP HTTP 和脚本走可撤销的 API Key。**stdio 不加 Key 是刻意的**——进程边界就是信任边界，加了只会让配置变麻烦。
>
> 授权这块我修了一个垂直越权：编辑器角色原来从 URL 读、默认还是 admin，普通用户改个参数就能获得管理员能力。现在角色由后端签发、JWT 载荷携带，写接口统一挂 `require_admin`，**入口隐藏只是 UX，后端校验才是真的锁**。
>
> 顺便提两个真实的工程妥协：一个是 `SameSite=Lax` 的 Cookie 在跨域开发态不发送，所以 refresh 做了 Cookie + body 双通道；另一个是 CORS 必须从 `*` 改成显式来源，否则浏览器会拒绝一切带凭证的响应——这两个都是不实际跑一遍发现不了的。"

**主动承认的不足**（挑两个说，显得清醒）：

1. "Access 存 localStorage，所以 XSS 场景下会被窃取——我接受这个代价是因为机器客户端必须用 Bearer，缓解手段是短有效期 + refresh 走 httpOnly。"
2. "目前所有 admin 能改所有技能树，没有做资源级隔离；登录失败锁定也是在内存里，多实例会失效。这两个是我的下一步。"
