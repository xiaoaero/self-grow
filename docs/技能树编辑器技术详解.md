## 1. 功能全景与三种角色模式

### 1.1 一个入口，三种形态

`frontend/skill-tree/index.html` 是唯一入口，通过 URL 参数切换形态：

| 参数 | 取值 | 作用 |
|---|---|---|
| `role` | `admin`（编辑）/ `user`、`viewer`（查看） | **只决定"查看模式还是编辑模式"，不再决定权限**（2026-09-11 安全改造后，权限由后端 `/api/auth/me` 判定） |
| `preview` | `true` | 预览模式：所有节点强制标记已完成，用于展示全貌 |
| `treeId` | 树 ID | 要加载哪棵树 |
| `userId` | 用户 ID | 学习进度归属（不传则从 localStorage 取） |

三种形态的能力差异：

```
admin  → 完整编辑器：工具栏 + 侧边栏(多树管理) + AI 面板 + 右键菜单 + 详情面板可操作
user   → 查看器：隐藏工具栏/侧边栏/AI面板/右键菜单，只能看与学习
preview→ 预览：再隐藏详情面板，节点全部显示为已学习，hover 显示 tooltip
```

> 历史上 `role` 直接决定权限且默认 `admin`，属于**垂直越权**（普通用户改 URL 就能编辑）。
> 现在改成"URL 只区分模式，权限问后端"，详见第 20 节。

### 1.2 功能清单

| 分类 | 功能 |
|---|---|
| 节点 | 创建根节点 / 创建子节点（自动连线）/ 编辑属性（名称、描述、标签、颜色、图标、优先级、进度）/ 删除（连带连线） |
| 连线 | 手动连线（选中节点按 `L` 或右键"从此节点连线"）/ 自动连线 / 删除连线（随节点删除） |
| 画布 | 拖拽平移（空格 + 左键 / 中键 / 空白处）、滚轮缩放（以鼠标为锚点）、按钮缩放、适应窗口（Fit） |
| 选中 | 单选、Shift 多选、Ctrl+A 全选、框选、空白处取消、Esc 取消 |
| 移动 | Ctrl + 左键拖拽（支持多选整体移动）、实时对齐参考线 |
| 历史 | 撤销 / 重做（Ctrl+Z / Ctrl+Y），栈深 50 |
| 树管理 | 新建 / 切换 / 删除技能树，修改技能介绍 |
| 发布 | 保存草稿、上线（发布到技能库）、更新已上线版本 |
| 学习 | 三态学习（未学习 → 学习中 → 已完成），前置条件校验 |
| AI | 自然语言生成/修改整棵树，危险操作二次确认 |
| 其他 | 同名节点红色光圈告警、跳转到前置节点、撤销栈保护 |

## 2. 整体架构与文件职责

```
index.html  （壳：DOM 结构 + 角色判定 + 启动脚本）
   │
   ├─ js/app.js .............. App  —— 主控制器（唯一状态源）
   │      ├─ renderer   = new TreeRenderer()      渲染
   │      ├─ interaction= new InteractionManager() 交互
   │      ├─ history    = new HistoryManager()    撤销
   │      ├─ ai         = new AIBridge()          AI
   │      ├─ sidebar    = new SkillTreeManager()  多树管理
   │      └─ detailPanel= new DetailPanel()       右侧面板
   │
   ├─ js/tree-renderer.js ... 渲染引擎（DOM 节点 + SVG 连线 + 网格 + 参考线）
   ├─ js/interaction.js ..... 交互（鼠标/键盘事件状态机）
   ├─ js/history.js ......... 撤销栈
   ├─ js/sidebar.js ......... 左侧多树管理 + 草稿持久化
   ├─ js/detail-panel.js .... 右侧节点详情
   ├─ js/ai-bridge.js ....... AI 编辑（LangGraph 端点）
   ├─ js/utils.js ........... uid / deepClone / 贝塞尔 / 边缘点 / 存储 / API
   └─ css/ .................. style.css（画布与节点）+ sidebar.css + detail-panel.css
```

**分层原则**：

- **只有 `App` 持有数据**（`this.nodes` / `this.connections`），其他模块全部通过 `app.xxx` 读写
- **渲染器不知道业务**：`TreeRenderer` 只接收节点/连线数组，不关心节点从哪来
- **交互器只改数据**：`InteractionManager` 修改 `node.x/y`，然后调用渲染器增量更新，不直接操作 DOM 结构
- **工具函数无状态**：`utils.js` 全是纯函数（除了 localStorage 读写）

### 全局引用

```js
window.__app = this;   // App 构造函数里设置
```

这个全局引用是必要的：**AI 模块、详情面板的内联 onclick、预览模式 tooltip** 都要拿到 App 实例。
代价是它也是调试入口——控制台 `__app.nodes` 就能看到全部数据。

## 3. 数据模型

### 3.1 节点（Node）

```js
{
  id: "node_lx2k3j_ab12cd",     // uid() 生成：node_ + Date.now().toString(36) + 随机
  name: "JS 基础",
  x: 80, y: 80,                 // 画布坐标（左上角，不是中心）
  size: 70,                     // 直径（正方形边长）
  shape: "round",               // round / square（渲染为 CSS class）
  icon: "📚",
  color: "#2a2a4a",             // 背景
  borderColor: "#444466",
  description: "描述文本",
  tags: ["前端", "基础"],
  priority: "none",             // none / high / medium / low（渲染为角标）
  progress: 0,                  // 0 未学习 / 50 学习中 / 100 已完成
  // ↓ 以下为运行时状态，不持久化（保存时剔除）
  _selected: false,
  _linking: false,
  _learningState: "locked",     // locked / available / learning / completed
  _nameDuplicate: false,
  _highlight: false
}
```

> **为什么要剔除 `_` 前缀字段**：这些字段是"视图状态"，如果存进数据库，
> 下次加载会出现"明明没选中却是选中态"的脏数据。清理方式：
> ```js
> const { _selected, _linking, _learningState, ...rest } = n;
> ```

### 3.2 连线（Connection）

```js
{ id: "node_xxx", from: "父节点id", to: "子节点id",
  color: "#666680", dashed: false, showArrow: true }
```

**方向语义**：`from → to` = 父 → 子。箭头始终指向 `to`（语义方向），
**不会因为子节点画在父节点左边就翻转**——这点很重要，否则"反向连线"会让箭头指向错误。

### 3.3 树（Tree）

```js
{ name: "前端学习路线", description: "…", nodes: [...], connections: [...] }
```

### 3.4 存储键设计

| Key | 内容 | 说明 |
|---|---|---|
| `skill_tree_index` | 树索引数组（不含节点） | 侧边栏列表来源 |
| `tree_{treeId}` | 草稿（完整树） | 编辑器读写 |
| `{treeId}_published` | 已发布版（含 `learner` 快照 + `publishedAt`） | 查看器读取 |
| `{treeId}_learner_{userId}` | 某用户的学习进度 `{nodeId: progress}` | 按用户隔离 |

> **注意一个历史坑**：主应用登录后写 `localStorage['sg_user']`，
> 而编辑器曾经读 `currentUser`（永远读不到 → 兜底成用户 1）。现已统一为 `sg_user` 优先。

## 4. 启动流程：从打开页面到画布出现

```
① 头部脚本：解析 URL 参数 → 判定查看/编辑模式
   ├─ 查看模式 → SKILL_TREE_ROLE_READY = true（直接放行）
   └─ 编辑模式 → 加 body.role-checking（先隐藏编辑 UI）→ 调 /api/auth/me
        ├─ is_admin → 移除 role-checking，set ROLE='admin'，允许启动
        └─ 否则    → SKILL_TREE_DENIED，渲染拦截页（不初始化 App）

② DOMContentLoaded：若允许 → new App(SKILL_TREE_ROLE)

③ App 构造函数
   ├─ 创建 6 个模块实例
   ├─ window.__app = this
   └─ 按角色分发：
        ├─ isPreview → initPreviewMode()
        ├─ isAdmin   → initToolbar() + initModals() + initDefaultTree()
        └─ else      → initUserMode()

④ initDefaultTree()：异步加载
   fetchSkillTreeIndex()                     ← 后端
     ├─ 有数据 → 取第 1 棵 → fetchSkillTreeDraft(id) → loadData(data)
     └─ 无数据/失败 → _initDefaultTreeFromLocal()    ← localStorage 兜底
```

**关键点：后端优先、localStorage 兜底。** 后端挂了编辑器依然能用（只是不同步）。

> 曾经这里有个竞态：`sidebar._initIndex()` 和 `App.initDefaultTree()` **并发**请求同一个索引，
> 且 `_initIndex` 里先赋 `currentId` 再调 `switchToTree(currentId)`，被开头的
> `if (treeId === this.currentId) return` 提前返回——等于白调一次。
> 现已改成：索引加载归 `sidebar`，**数据加载只归 `App`**，职责不重叠。

## 5. 渲染引擎：DOM + SVG 双层结构

### 5.1 为什么是"DOM 节点 + SVG 连线"

```html
<div id="canvas-container">           <!-- 视口，overflow:hidden -->
  <div id="tree-canvas">              <!-- 被 transform 的图层 -->
    <svg id="grid-layer"></svg>       <!-- 网格（背景） -->
    <svg id="selection-box-layer">    <!-- 框选矩形 -->
      <rect id="selection-box" />
    </svg>
    <svg id="connection-layer"></svg> <!-- 连线 -->
    <div id="node-layer"></div>       <!-- 节点 -->
  </div>
</div>
```

| 元素 | 技术 | 原因 |
|---|---|---|
| 节点 | **DOM div** | 要显示 emoji 文字、CSS 动画、hover 亮度、tooltip；文字排版交给浏览器最省事 |
| 连线 | **SVG path** | 需要曲线（贝塞尔）、描边渐变、发光滤镜；DOM 画曲线很痛苦 |
| 网格 | **SVG line** | 大量平行直线，SVG 一条 line 一个元素，比 div 省内存 |

**层叠顺序**：grid → selection-box → connection → node。节点在最上层，保证点击优先命中节点。

### 5.2 pointer-events 的三层设计

```css
#grid-layer, #connection-layer { pointer-events: none; }  /* 背景层不拦鼠标 */
#node-layer { pointer-events: auto; }                     /* 节点可点 */
.tree-connection { pointer-events: stroke; }              /* 连线"只在线上"可点 */
```

- `none`：鼠标事件穿透，直接落到下层 → 点空白处能触发画布平移/框选
- `stroke`：SVG 专有值，**只有描边本身可点**（而不是整个包围盒），这样连线附近仍能框选

### 5.3 为什么用 transform 而不是 left/top

```js
el.style.transform = `translate(${node.x}px, ${node.y}px)`;
```

| | `left/top` | `transform` |
|---|---|---|
| 触发的渲染阶段 | **Layout → Paint → Composite** | **只 Composite** |
| 是否引起重排 | 是（兄弟节点也要重算） | 否（走合成层） |
| 拖拽 60fps | 大树会掉帧 | 稳 |

配套：`.skill-node { will-change: transform; }` 提前提示浏览器提升为合成层。

## 6. 画布变换：平移 / 缩放 / 坐标换算

### 6.1 变换状态

```js
scale = 1        // 缩放（0.2 ~ 3）
panX = 0, panY = 0   // 平移（屏幕像素）
```

应用方式（**整个 tree-canvas 一起变换**，内部所有元素坐标保持"画布坐标"不变）：

```js
treeCanvas.style.transform = `translate(${panX}px, ${panY}px) scale(${scale})`;
```

CSS 里必须配 `transform-origin: 0 0;` —— 默认原点是中心，会导致平移/缩放的视觉位置对不上。

### 6.2 屏幕坐标 → 画布坐标（最核心的公式）

```js
screenToCanvas(screenX, screenY) {
  const rect = this.container.getBoundingClientRect();
  return {
    x: (screenX - rect.left - this.panX) / this.scale,
    y: (screenY - rect.top  - this.panY) / this.scale
  };
}
```

推导：`屏幕位置 = 容器左上角 + 平移量 + 画布坐标 × 缩放`
→ 反解：`画布坐标 = (屏幕位置 - 容器左上角 - 平移量) / 缩放`

**所有鼠标交互都必须先做这个换算**，否则缩放后点击会错位（这是新手最常踩的坑）。

### 6.3 以鼠标为锚点的缩放（滚轮）

需求：滚轮缩放时，**鼠标指向的那个点保持不动**。

```js
const mx = e.clientX - rect.left;   // 鼠标在容器内的坐标
const my = e.clientY - rect.top;
const oldScale = this.scale;
this.scale = clamp(this.scale + (e.deltaY > 0 ? -step : step), min, max);
const ratio = this.scale / oldScale;
this.panX = mx - (mx - this.panX) * ratio;
this.panY = my - (my - this.panY) * ratio;
```

推导：设鼠标处对应的画布坐标为 `C`（缩放前后不变）

```
缩放前: mx = panX_old + C * oldScale
缩放后: mx = panX_new + C * newScale
=> panX_new = mx - C * newScale = mx - (mx - panX_old) * (newScale/oldScale)
```

### 6.4 适应窗口（Fit）

```js
minX/minY/maxX/maxY  ← 所有节点的包围盒
const tw = maxX - minX + 100, th = maxY - minY + 100;   // +100 留白
scale = clamp(Math.min(cw/tw, ch/th) * 0.9, 0.2, 3);    // 取较小的缩放比，再留 10% 边距
panX = (cw - tw*scale)/2 - minX*scale;                  // 水平居中
panY = (ch - th*scale)/2 - minY*scale;
```

### 6.5 网格渲染

```js
const size = gridSize * scale;                  // gridSize = 30
const effectiveSize = size < 15 ? size * 2 : size;  // 缩得太小时隔行画，避免糊成一片
const offsetX = ((panX % effectiveSize) + effectiveSize) % effectiveSize;  // 保证正数
for (let x = offsetX; x < w; x += effectiveSize) { ...画竖线... }
```

网格是"视口内按需生成"——只画可见范围的线，不是无限大的 SVG。

## 7. 节点渲染

```js
renderNode(node) {
  let el = this.nodeEls.get(node.id);
  if (!el) { 创建 div.skill-node，appendChild，缓存到 nodeEls }
  el.className = 'skill-node ' + (node.shape || 'round');
  el.style.setProperty('--node-size',  node.size + 'px');   // CSS 变量驱动尺寸
  el.style.setProperty('--node-color', node.color);
  el.style.setProperty('--node-border',node.borderColor);
  el.style.transform = `translate(${node.x}px, ${node.y}px)`;
  this._applyVisualState(el, node);        // 选中/高亮/重名/学习状态 → class
  el.innerHTML = `…角标 + emoji + 标题…`;
  if (预览模式) this._attachTooltip(el, node);
}
```

**三个设计点**：

1. **DOM 复用**：`nodeEls` 是 `Map<nodeId, element>`，只创建一次，后续只更新内容。
   全量重建（innerHTML 清空重来）只在切换树时发生。
2. **CSS 变量传参**：尺寸/颜色走 `--node-size` 等变量，CSS 里 `width: var(--node-size)`，
   避免 JS 写一堆 style 属性。
3. **视觉状态与内容分离**（2026-09-11 性能优化）：
   ```js
   updateNodeVisual(node)   // 只 toggle class，不碰 innerHTML
   _applyVisualState(el, node)  // renderNode 和它共用
   ```
   选中、学习状态这些高频变化走前者；改名、换图标走后者。

### 7.1 学习状态的四种视觉

```css
.node-locked      /* ⛔ 未解锁：前置未完成 —— 灰暗 */
.node-available   /* 🔵 可学习 */
.node-learning    /* 🔄 学习中（progress=50） */
.node-completed   /* ✅ 已完成（progress=100）—— 金色发光 */
```

## 8. 连线渲染：贝塞尔曲线与箭头朝向

### 8.1 三次贝塞尔曲线

```js
function bezierPath(x1, y1, x2, y2, curvature = 0.4) {
  const dx = Math.abs(x2 - x1) * curvature;
  return `M ${x1} ${y1} C ${x1+dx} ${y1}, ${x2-dx} ${y2}, ${x2} ${y2}`;
}
```

控制点选 `(x1+dx, y1)` 和 `(x2-dx, y2)`：出线/入线都是**水平方向**，
这样父子节点左右排列时连线是优雅的 S 形，而不是斜线。

### 8.2 边缘点计算（连线不插入节点内部）

节点是圆（外接圆半径 = size/2），连线应该画到圆周上：

```js
function getEdgePoint(cx, cy, size, targetCx, targetCy) {
  const half = size / 2;
  const dx = targetCx - cx, dy = targetCy - cy;
  const dist = Math.sqrt(dx*dx + dy*dy);
  const ratio = half / dist;                  // 单位向量 × 半径
  return { x: cx + dx*ratio, y: cy + dy*ratio };
}
```

即：**圆心 + 单位方向向量 × 半径**。

### 8.3 三角形箭头的朝向

SVG 的 `marker-orient="auto"` 在贝塞尔末端方向突变时经常算错，
这里的做法是**手算中点切线角**：

```js
// 三次贝塞尔在 t=0.5 处的坐标（控制点 P0..P3）
B(0.5) = 0.125·P0 + 0.375·P1 + 0.375·P2 + 0.125·P3
// 导数（切线方向）
B'(0.5) = 1.5 · (P3 + P2 - P1 - P0) / ... （此处化简为代码中的 tx/ty）
const angle = Math.atan2(ty, tx) * 180 / Math.PI;
```

然后画一个"指向右"的三角形，用 `transform="translate(mx,my) rotate(angle)"` 摆到中点。

> 代码里还额外在曲线末尾追加了一小段 1px 直线指向目标圆心，这是为了让
> `orient="auto"` 体系下也能正确感知方向（防御性写法）。

### 8.4 全量重建 vs 增量更新

| 方法 | 场景 | 成本 |
|---|---|---|
| `renderConnections()` | 连线增删、状态变化 | 重建整个 `connectionLayer.innerHTML`，重新缓存 path 引用 |
| `updateConnectionPaths()` | **拖拽中**（每帧） | 遍历 `connPaths` Map，只改 `d` 属性和箭头 transform |

拖拽时用增量更新是必须的——每帧重建整个 SVG 会掉帧。

> **踩过的坑**：`renderConnections()` 用 `innerHTML` 重建，会把之前 append 的
> **对齐参考线**一起冲掉（变成游离 DOM，再也看不见）。修复：重建后重新 `appendChild` 参考线。

## 9. 交互系统：事件状态机

### 9.1 事件绑定范围

```js
container.addEventListener('mousedown', ...)   // 只在画布内
window.addEventListener('mousemove', ...)      // 全局：拖出画布也要跟手
```

### 9.3 防重复点击


## 10. 拖拽：阈值、增量累积与 RAF

### 10.1 拖拽阈值（区分"点击"和"拖拽"）

```js
dragThreshold = 4;   // 像素
if (!this.dragMoved && (Math.abs(dx) > 4 || Math.abs(dy) > 4)) {
  this.dragMoved = true;   // 超过阈值才认定为拖拽
}
```

没有阈值的话，手抖 1px 也会被当成拖动，导致"想点却变成拖"。

### 10.2 增量累积 + requestAnimationFrame

```js
// mousemove（可能一帧触发多次）
this._pendingDx += dx;
this._pendingDy += dy;
if (!this._dragRaf) {
  this._dragRaf = requestAnimationFrame(() => this._flushDrag());
}

// _flushDrag：每帧只执行一次
const dx = this._pendingDx; this._pendingDx = 0;   // 取完清零
selectedNodes.forEach(n => { n.x += dx; n.y += dy; });
el.style.transform = `translate(...)`;             // 只改 transform
this.renderer.updateConnectionPaths(...);          // 增量更新连线
```

**三层优化**：
1. 多次 mousemove 的位移**累积**起来，一帧只应用一次
2. 只改 `transform`（合成层，不触发 layout）
3. 连线走 `updateConnectionPaths` 增量更新，不重建 SVG

### 10.3 松手时才写入历史

```js
onMouseUp: if (this.dragMoved) { this._flushDrag(); this.app.saveHistory(); }
```

拖拽过程中每帧都存快照会有几十条历史 —— 只在**松手后存一次**。

## 11. 框选、连线模式与右键菜单

### 11.1 框选

```js
// mousedown 空白处：记录起点，显示 #selection-box（一个 SVG rect）
// mousemove：更新 rect 的 left/top/width/height（用 Math.min/max 处理反向拖拽）
// mouseup：hitTestRect() 找出相交的节点
hitTestRect(x1, y1, x2, y2, nodes) {
  return nodes.filter(n =>
    n.x + s > left && n.x < right && n.y + s > top && n.y < bottom);
}
```

矩形相交判定（AABB）：`节点左 < 框右 && 节点右 > 框左 && 节点上 < 框下 && 节点下 > 框上`。
（注意是"相交"而不是"包含"，与常见框选习惯一致。）

### 11.2 连线模式

```
触发：选中单个节点后按 L，或右键 → "从此节点连线"
状态：isConnecting = true, connectFrom = nodeId（该节点显示 _linking 态）
渲染：mousemove 时画一条橙色虚线 tempLine（从源节点中心到鼠标）
完成：点另一个节点 → addConnection → 重渲染连线 → 取消连线模式
取消：Esc 或点空白处（2026-09-11 修复：原来点空白会开始框选）
```

> 连线前会检查是否已存在（`from/to` 相同则跳过），避免重复连线。

### 11.3 右键菜单

```js
onContextMenu(e) {
  e.preventDefault();                    // 阻止浏览器默认菜单
  const node = hitTestNode(...);
  if (node) { 记录 contextNode，定位菜单到鼠标位置，绑定各菜单项 onclick }
}
```

菜单项：编辑 / 添加子节点 / 从此节点连线 / AI 扩展子节点 / 删除。
每项执行后 `hideContextMenu()`。

## 12. 对齐吸附参考线

拖动节点时，如果它和别的节点**中心/顶边/底边**在同一水平线（或**竖直线**）上，就画一条参考线。

```js
showAlignLines(draggedNodes, allNodes, threshold = 6) {
  const d = draggedNodes[0];       // 以第一个被拖节点为参照
  // 水平对齐：比较 Y（中心 / 顶边 / 底边 三种）
  const dy = Math.abs(dCy - cy);
  if (dy < bestHdist) { bestHdist = dy; bestH = { y: cy }; }
  const topDy = Math.abs(d.y - n.y);                    // 顶边
  const bottomDy = Math.abs((d.y + size) - (n.y + size)); // 底边
  // 垂直对齐：同理比较 X（中心 / 左边 / 右边）
}
```

- `threshold = 6`（画布像素，已考虑缩放前的坐标）
- 参考线是两条**横跨 ±5000px 的 SVG line**，显示时改 `x1/x2/y1/y2` 并 `display:''`
- 松手时 `hideAlignLines()`

> 注意：这里只"显示参考线"，**没有真正吸附**（不会自动修正坐标）——
> 是视觉辅助而非强制对齐。

## 14. 学习状态引擎

### 14.1 三态与前置条件

```js
updateLearningStates() {
  // 递归找所有祖先
  getAncestors(nodeId) => [...所有父节点、祖父节点…]   // BFS + visited 防环
  arePrereqsMet(id) => 祖先为空 || 祖先全部 progress === 100

  progress === 100        → completed
  0 < progress < 100     → learning
  前置满足                → available
  否则                    → locked
}
```

**为什么用递归找全部祖先而不是只看直接父节点**：
技能树是多层结构，"孙节点"的解锁应该要求"祖先链全部完成"，
只看直接父节点会出现"父节点已完成但祖父没完成"的逻辑漏洞。
递归里传 `visited` Set 防止连线成环导致死循环。

### 14.2 操作约束

```js
markNodeAsLearning(id)  // 未学习 → 50（学习中）
markNodeCompleted(id)   // → 100（已完成）
```

两者都先校验 `_arePrerequisitesMet()`，不满足就提示"请先完成所有前置条件"。

### 14.3 学习进度的存储与合并

```
用户操作 → learner[nodeId] = progress
        → 写 {treeId}_learner_{userId}
        → 同时写回 {treeId}_published 的 learner 字段
        → 异步 PUT /api/skill-trees/{id}/learner（后端持久化）
```

下次加载已发布树时：**本地 learner → 用 published.learner 补缺**（本地没有的用发布版快照）。
这样换设备也能保留进度。

## 15. 撤销 / 重做

### 15.1 数据结构

```js
class HistoryManager {
  stack = [];    // 快照数组
  index = -1;    // 当前指向
  maxSize = 50;

  push(state) {
    this.stack = this.stack.slice(0, this.index + 1);  // ① 截断 redo 分支
    this.stack.push(deepClone(state));
    if (this.stack.length > 50) this.stack.shift();     // ② 限长
    this.index = Math.min(this.stack.length - 1, this.index + 1);
  }
  undo() { if (canUndo) return deepClone(this.stack[--this.index]); }
  redo() { if (canRedo) return deepClone(this.stack[++this.index]); }
}
```

**语义：栈里存的是"改后快照"**（每次操作完成后的完整状态）。
`undo()` = 把 index 往前挪一格，取出那一格的状态恢复。

### 15.2 快照内容

```js
{
  nodes: deepClone(nodes 剔除 _ 前缀字段),
  connections: deepClone(connections),
  treeName, treeDescription
}
```

`deepClone` 用 `JSON.parse(JSON.stringify(x))` —— 简单可靠，
代价是不能存函数/undefined（这里都是纯数据，无所谓）。

### 15.3 三条铁律（都是踩坑换来的）

1. **先改数据，再 push**：`saveHistory()` 必须在修改**之后**调用。
   曾经 `saveNodeEdit`/`deleteSelectedNodes`/`markNode*` 都在修改前 push，
   结果 redo 恢复到的是同一个状态 —— **表现为"重做没反应"**。
2. **加载新树必须 `history.clear()`**：
   曾经 `loadData()` 也 push 快照，导致切到树 B 后按撤销 → 画布变回树 A 的内容，
   此时再保存就会**把树 A 的内容写进树 B**（数据污染）。
   现在：清空历史 + 压入"加载后基线"，保证加载后的第一次编辑仍可撤销。
3. **`newTree()` 清空后要压基线**，否则新建树后的第一个操作无法撤销。

### 15.4 什么时候不进历史

- 用户模式下（`isUser`）的学习打卡（直接落库，不需要撤销）
- 拖拽过程中（只在松手时存一次）

## 17. 保存 / 上线 / 更新

| 动作 | 做了什么 |
|---|---|
| **保存**（💾） | `_saveCurrentTree()`：写 localStorage 草稿 + 后端草稿；更新索引里的名称/节点数/时间 |
| **上线**（🚀） | 先保存 → 读取草稿 → 合并已有 `learner` 进度 → 生成 `{...树, learner, publishedAt}` → 写 `{id}_published` + 后端 publish |
| **更新**（🔄） | 与上线同一套逻辑，但**保留老版本的学习进度**（`learner` 只补缺不覆盖） |

**为什么要"只补缺"**：管理员更新树结构后，老用户已学节点的进度不能被清空。

上线前的两道校验：

```js
if (nodes.length === 0)      → "技能树为空，无法上线"
if (hasDuplicateNames())     → "存在同名节点，请先修改后再上线"
```

> 同名节点会红线告警（`_nameDuplicate`），因为发布后用户侧按名称识别节点会歧义。

## 19. AI 编辑链路

### 19.1 整体架构（LangGraph）

```
前端 ai-bridge.js
   │ POST /api/skill-trees/{id}/chat   {tree, message, selected_node_ids, thread_id}
   ↓
后端 routers/skill_tree_ai.py  （require_admin 校验）
   ↓
services/skill_tree_ai/graph.py  → StateGraph（单 agent 节点 + checkpointer）
   ↓
node.py：LLM 决策 → 调工具 → 结果回灌 → 循环（最多 10 轮）
   ↓
tools.py：8 个工具直接改 state["tree"]（按节点 ID 操作）
   ↓
返回 {reply, diffs, executed_tools, pending_confirmation, tree, thread_id}
```

### 19.2 8 个工具

`create_node` / `create_nodes_batch` / `update_node` / `delete_node` /
`add_connection` / `delete_connection` / `move_node` / `replace_tree` / `send_reply`

关键设计：

- **按节点 ID 操作**（旧版按名称，重名就出错）
- **危险操作确认守卫**：`replace_tree`、`delete_node(有子节点)` 首次调用返回
  `needs_confirmation`，前端弹确认卡片，用户确认后再带 `confirm=True` 调用
- **坐标兜底**：LLM 经常省略 x/y → `_auto_layout()` 按层级自动排布（2026-09-12 修复）

### 19.3 前端应用 AI 结果的四步

```js
_handleResponse(data) {
  1. 显示 reply
  2. 显示 executed_tools 摘要（🔧 已执行操作）
  3. if (data.diffs.length > 0) this._applyTree(data.tree)
  4. if (data.pending_confirmation) 渲染确认卡片
}

_applyTree(tree) {
  app.saveHistory();        // 改前快照 → AI 的修改可以 Ctrl+Z 撤销
  app.nodes = tree.nodes...; app.connections = tree.connections;
  app.renderAll(); app.checkDuplicateNames(); app.sidebar.refreshStats();
  app.sidebar._saveCurrentTree();   // 立即落盘
  app.saveHistory();        // 改后快照
}
```

> **为什么不用 `loadData()`**：`loadData` 会清空撤销栈（它是"切换树"的语义）。
> 这里手动压"改前 + 改后"两个快照，既保住了撤销能力，又不会串到别的树。

### 19.4 会话管理

- `thread_id` 由服务端生成（`stc_{user_id}_{uuid}`），前端只保存不生成
- 切换树 / 新建树 / 删除树 → `resetSession()`（丢弃 thread_id + 清空消息区）
- 后端重启（MemorySaver 丢失）→ resume 报 404 → 前端自动重置并提示

## 22. 知识点速查与易错清单

### 22.1 公式速查

## 23. Agent 全景：这里的"AI"到底是什么

### 23.1 两种 AI 交互范式

| 范式 | 流程 | 本项目用在哪 |
|---|---|---|
| **聊天式**（Chat） | 输入文本 → 模型 → 输出文本 | 习惯图标生成、表达训练评分 |
| **工具调用式**（Tool Use / Function Calling） | 输入文本 **+ 工具清单** → 模型输出"我要调 X 工具，参数是 Y" → **本地执行** → 结果回灌 → 模型再决策 | **技能树 AI、统一协调 Agent** |

第二种的关键差别：**模型不直接改数据，它只"提议"调用什么工具**，真正执行的是你的代码。
这带来三个好处：

1. 参数可以做**校验**（类型、枚举、范围），模型传错也不会写脏数据
2. 可以在执行前后插入**权限、确认、日志**
3. 模型能看到执行结果，**失败可以自己重试或换参数**

### 23.2 ReAct 循环

技能树 AI 用的是典型的 ReAct（Reason + Act）范式：

```
   ┌──────────────────────────────────────────────┐
   │                                              │
   ▼                                              │
组装消息（系统提示词 + 树状态 + 历史）                  │
   │                                              │
   ▼                                              │
LLM 推理 → 输出                                     │
   │                                              │
   ├─ 有 tool_calls ──→ 逐个执行工具                 │
   │                     │                        │
   │                     ├─ 需要确认 ──→ 中断返回（等用户）
   │                     └─ 结果作为 ToolMessage 追加
   │                                              │
   │                                              └── 回到顶部继续
   └─ 纯文本 / 有 send_reply ──→ 结束，返回 reply
```

循环上限 `MAX_ITERS = 10`，防止模型陷入"调用失败 → 重试 → 再失败"的死循环。

### 23.3 为什么不让 AI "直接吐一棵树的 JSON"

早期方案（旧 `/api/chat`）就是让模型一次性输出整棵树的 JSON。问题：

- 树一大，JSON 极容易截断或格式错误
- 无法做增量修改（"给这个节点加个子节点"也要重传整棵树）
- 无法复用业务校验（重名、坐标、前置关系）
- 危险操作没有确认环节

改成 Agent 之后：**每次只描述"做什么"**，由工具保证正确性。

## 25. 状态模型：`SkillTreeChatState`

```python
class SkillTreeChatState(TypedDict):
    user_id: int
    tree_id: str
    tree: dict                                  # 内存中的树（工具直接改它）
    selected_node_ids: list[str]
    messages: Annotated[list, operator.add]     # ← 累积
    diffs: list[NodeDiff]                       # ← 每次替换
    executed_tools: list[dict]                  # ← 每次替换
    reply: str | None
    pending_confirmation: PendingConfirmation | None
    ask_rounds: int
```

### 25.1 `Annotated[..., operator.add]` 到底意味着什么

这是 LangGraph 最容易被误解的一点：

| 写法 | 语义 | 适用 |
|---|---|---|
| `messages: Annotated[list, operator.add]` | 节点返回的值**追加**到已有列表 | 对话历史（必须累积） |
| `diffs: list[NodeDiff]`（普通字段） | 节点返回的值**覆盖**旧值 | 每次调用的结果集 |

**踩过的坑**：`diffs` / `executed_tools` 原本也写成 `operator.add`。
后果是——第一轮 AI 改了 3 个节点，第二轮用户只是问了个问题，
返回的 `diffs` 里**还带着第一轮的 3 条旧记录**，前端以为又有变更，重复应用。

> 判断标准很朴素：**这个字段是"历史"还是"本次结果"？**
> 历史用 `operator.add`，本次结果用普通字段。

### 25.2 `tree` 字段的特殊性

`tree` 是普通字段，但工具是**原地修改**它的：

```python
tree = _get_tree(state)              # 拿到的是同一个 dict 对象
nodes = tree.setdefault("nodes", [])
nodes.append(node)                   # 直接改
```

因为引用没变，节点返回 `{"tree": state["tree"]}` 时 LangGraph 存的是同一个对象——能正常工作，
但要注意：**工具之间共享同一份树**，工具执行顺序会影响结果（目前按模型返回顺序串行执行）。

## 26. 图：为什么只有"一个节点"

```python
graph = StateGraph(SkillTreeChatState)
graph.add_node("agent", agent_node)
graph.set_entry_point("agent")
graph.add_edge("agent", END)
return graph.compile(checkpointer=get_checkpointer())
```

整个图**只有一个节点**——循环发生在 `agent_node` 内部（for 循环），不是通过图的条件边跳转。
原因：

- 技能树 AI 的"循环"是**工具调用循环**，用 for 循环最直接
- 需要 `checkpointer` 只是为了**跨 HTTP 请求保存会话**（用户确认时恢复上下文）
- 没有路由分支、没有多子图，用图的条件边反而绕

`checkpointer` 是全局 `MemorySaver` 单例（`services/coordinator/checkpointer.py`），
通过 `thread_id` 隔离不同会话。

### 26.1 两条运行路径

| 路径 | 入口 | 输入 |
|---|---|---|
| 新会话 / 继续对话 | `run_skill_tree_chat()` | 完整 state（含 tree、user_id、首条 HumanMessage） |
| 恢复（确认 / 补充） | `resume_skill_tree_chat()` | 只传 `messages` 增量（+ 可选 `tree`），其余从 checkpoint 取 |

```python
# resume 时把 tree 放进 input —— 普通字段，整体覆盖
invoke_input = {"messages": [HumanMessage(content=content)]}
if tree is not None:
    invoke_input["tree"] = tree
result = await graph.ainvoke(invoke_input, config=config)
```

> 为什么 resume 要能传 tree：checkpoint 里存的是**上次请求时的树快照**。
> 如果用户在等待期间手动改了节点，AI 基于旧快照继续编辑，
> 返回的树会**把用户的手动改动覆盖掉**。

## 27. Agent 节点：ReAct 循环逐行

```python
async def agent_node(state):
    llm = llm_factory()                      # get_llm(temperature=0.3)
    llm_with_tools = llm.bind_tools(tools)   # 把 8 个工具定义交给模型

    messages = _truncate_messages(state.get("messages", []))
    tree_prompt = build_tree_state_prompt(state["tree"], state["selected_node_ids"])
    full = [SystemMessage(提示词), SystemMessage(树状态)] + messages

    for _ in range(MAX_ITERS):               # 10
        response = await llm_with_tools.ainvoke(full)

        if response.tool_calls:              # ① 模型要调工具
            new_messages = [response]
            for tc in response.tool_calls:
                result = tool_fn.invoke({**args, "state": state})   # 手动注入 state

                if result.get("needs_confirmation"):                # ② 需确认 → 中断
                    return {..., "pending_confirmation": {...}, "reply": 确认文案}

                if name == "send_reply" and result.get("reply"):    # ③ 最终回复
                    reply_text = result["reply"]

                if result.get("diff"): diffs.append(result["diff"]) # ④ 收集变更
                executed.append({...})
                new_messages.append(ToolMessage(
                    content=json.dumps(result, ensure_ascii=False, default=str),
                    tool_call_id=tc["id"]))

            if reply_text or diffs:          # ⑤ 有产出 → 结束本轮
                return {...}

            full = full + new_messages       # ⑥ 否则带着工具结果继续循环
            continue

        # 纯文本输出 → 当作最终回复
        return {"messages": [response], "reply": response.content, ...}

    return {"reply": "处理轮次超限，请稍后重试", ...}   # 循环用尽
```

### 27.1 设计点

| 点 | 说明 |
|---|---|
| `bind_tools` | LangChain 把 Python 函数（类型注解 + docstring）转成模型的 JSON Schema |
| `state` 注入 | 工具签名里有 `state: Annotated[dict, InjectedState()]`，`InjectedState` 会把它**从给模型的 schema 里剔除**，执行时再由代码手动塞进去 |
| 异常兜底 | 工具抛异常 → 转成 `{"success": False, message}` 回灌给模型，让它自己重试或放弃，而不是整条链路 500 |
| 结束条件 | 有 `send_reply` 或有 `diff` 就结束；否则继续循环 |
| 循环用尽 | 返回"处理轮次超限"，不会卡死 |

### 27.2 一个诚实的小瑕疵

`node.py` 定义了 `MAX_ASK_ROUNDS = 3` 并读取了 `state["ask_rounds"]`，
但**技能树 AI 没有反问工具**（只有"确认"），所以这个值目前读而未用——
它是从协调 Agent 的基座复制过来的，保留是为了将来扩展反问能力。

## 28. 消息模型与截断

### 28.1 四种消息

| 类型 | 谁产生 | 作用 |
|---|---|---|
| `SystemMessage` | 代码（每次请求拼） | 系统提示词 + 当前树状态（**不进 checkpoint 历史**） |
| `HumanMessage` | 用户输入 | 用户指令 |
| `AIMessage` | 模型输出 | 可能带 `tool_calls` |
| `ToolMessage` | 代码（执行工具后） | 工具结果，靠 `tool_call_id` **必须**对应某条 AIMessage 的 tool_call |

**铁律**：`ToolMessage` 前面必须紧跟产生它的那条 `AIMessage(tool_calls)`。
一旦这条 AIMessage 被截掉，就会留下"孤儿 ToolMessage"，大多数模型 API 直接返回 400。

### 28.2 截断策略

```python
def _truncate_messages(messages, max_recent=10):
    if len(messages) <= max_recent + 1:
        return list(messages)
    start = len(messages) - max_recent
    while start < len(messages) and isinstance(messages[start], ToolMessage):
        start += 1          # 起点不能落在 ToolMessage 上
    return [messages[0]] + messages[start:]
```

保留**首条（含初始指令）+ 最近 10 条**，起点自动跳过 ToolMessage。

> 前端旧实现（`/api/chat` 时代）用 `messages.slice(-20)` 生硬截断，
> 截断点可能正好落在 AIMessage 与它的 ToolMessage 之间 → 孤儿消息 → 400。这是重写的原因之一。

### 29.2 工具的统一协议

```python
{
  "success": True/False,        # 必填：决定循环是否结束
  "message": "给用户/模型看的说明",
  "diff": {...},                # 可选：产生了变更才带
  "needs_confirmation": True,   # 可选：危险操作首次调用时返回
  "reply": "..."                # 仅 send_reply：最终回复
}
```

### 29.3 五条设计约定

1. **一律按节点 ID 操作**（旧版按名称，重名就误伤）
2. **参数校验**：`_validate_name` / `_validate_priority`（枚举）/ `_validate_progress`（0~100）
3. **名称唯一化**：`_ensure_unique_name()` 自动加 " 2"、" 3" 后缀
4. **坐标兜底**：`_has_valid_coords()` + `_auto_layout()`（见 29.4）
5. **异常不外抛**：统一转成 `success=False`，回灌给模型

### 29.4 坐标自动布局（2026-09-12 新增）

问题：提示词写的是"**尽量**给出合理的 x/y 坐标"，模型经常省略 →
所有节点坐标都是 0 → **整棵树叠在一个点上**。

```python
_has_valid_coords(node)   # x、y 全为 0 视为"未指定"
_auto_layout(nodes, connections, start_x=80, start_y=80, gap_x=200, gap_y=110)
# BFS：根节点一列，每层向右 200px，同层垂直 110px
```

触发条件：**所有新节点都没有有效坐标时才自动布局**。
模型给了坐标就原样保留——不能抢用户排版。

### 29.5 级联删除实现

```python
child_count = 统计直接子节点
if not confirm and child_count > 0:
    return {"needs_confirmation": True, "message": "…有 N 个子节点，确认吗？"}

# 确认后：BFS 收集所有后代
deleted_ids = {node_id}; queue = [node_id]
while queue:
    cur = queue.pop(0)
    for child in [c["to"] for c in connections if c["from"] == cur]:
        if child not in deleted_ids:
            deleted_ids.add(child); queue.append(child)
```

注意：遍历用**过滤前的原始 connections**，否则边被删了就找不全后代。

## 30. 确认机制（危险操作两段式）

### 30.1 时序

```
① 用户："重新生成整棵树"
② LLM 调用 replace_tree（未给 confirm）
③ 工具返回 needs_confirmation + 提示文案
④ node.py 中断循环，返回 pending_confirmation
⑤ 后端 _format_result 带上 pending_confirmation
⑥ 前端渲染确认卡片（确认执行 / 取消）
⑦ 用户点"确认执行"
⑧ 前端 POST /chat/resume {thread_id, confirm: true, tree: 当前树}
⑨ 后端把 pending 的**原始参数**回灌：
   "[系统] 用户已确认执行「replace_tree」，原始参数：{...}。
    请原样使用这些参数并附加 confirm=True 重新调用该工具。"
⑩ 模型带 confirm=True 重调 → 真正执行 → 返回 diffs
⑪ 前端应用树
```

### 30.2 为什么要回灌原始参数（2026-09-12 修复）

原先只说"用户已确认执行 replace_tree"，模型重新调用时会**自己再生成一遍参数**——
用户确认的是"生成 A 主题 12 个节点"，执行的可能是"B 主题 8 个节点"。
现在把 `pending["args"]` 序列化后一起发回，明确要求"原样使用"。

### 30.3 为什么不用 LangGraph 的 `interrupt()`

| `interrupt()` | 本项目的做法 |
|---|---|
| 挂起图，需要专门恢复入口 | 子图正常结束，确认状态存在 `pending_confirmation` 字段 |
| 恢复要处理各种分支 | resume 就是"追加一条消息再跑一次" |
| 强阻塞，适合人工审批流 | 轻量，"取消"零成本 |

（协调 Agent 同理，用 `ask_user` 工具代替 `interrupt()`。）

## 31. 提示词工程

### 31.1 三段式拼装

```python
full_messages = [
    SystemMessage(SKILL_TREE_AI_SYSTEM_PROMPT),   # ① 角色 + 工具清单 + 规则
    SystemMessage(build_tree_state_prompt(...)),  # ② 当前树状态（每次动态生成）
] + messages                                      # ③ 对话历史
```

**树状态每次请求都重新生成**：因为树可能已被用户手动改过。
放在 SystemMessage 而不是历史消息里，保证模型每次看到的都是最新状态，也避免污染历史。

### 31.2 树状态提示词包含什么

```
当前知识树状态：
树名：前端学习路线
节点数：12，连线数：11
当前选中节点：JS 基础
节点列表（id, name, progress）：
- node_abc | 前端路线 | progress=0
- node_def | JS 基础 | progress=50
连线列表（from → to）：
- 前端路线 → JS 基础
```

**只给 id / name / progress，不给描述和标签** —— 控制 token，需要细节时模型再调工具。

### 31.3 系统提示词 10 条规则（要点）

1. 空树 + 要求生成 → 直接用 `replace_tree`
2. 扩展子节点 → `create_nodes_batch`
3. 修改已有树 → 细粒度工具
4. 危险操作 → 先确认再执行
5~6. 图标用 emoji、颜色用 hex、优先级四选一
7. **必须用 node_id，不要用名称**
8~9. 给出合理坐标（父左子右、间距 120~160）
10. 操作完用 `send_reply` 汇报

### 31.4 温度选择

```python
get_llm(temperature=0.3)
```

工具调用场景要**稳定**：温度太高会出现奇怪的工具参数。
对比：协调 Agent 路由节点 0.1（更稳），文本生成 0.7。

## 32. 会话与持久化

### 32.1 thread_id

```python
thread_id = thread_id or f"stc_{user_id}_{uuid.uuid4().hex[:12]}"
```

- 首次请求不传 → 服务端生成，返回给前端保存
- 后续带上 → 续接同一会话（checkpoint 里有完整历史）
- **编入 user_id** → 即使 thread_id 泄露也过不了归属校验（防御纵深）

### 32.2 MemorySaver 的后果

| 优点 | 缺点 |
|---|---|
| 零配置、零依赖、够快 | **后端重启 → 所有会话丢失** |

前端已兜底：resume 报 404 / 会话相关错误 → `resetSession()` + 提示"后端可能重启"。
根本方案是换**持久化 checkpointer**（Postgres / Redis 实现，改动只在 `checkpointer.py` 一个文件）；
在那之前，前端把对话记录**按树存进 localStorage**，重进页面至少能看到历史（AI 上下文仍会丢）。

### 32.3 会话重置时机（前端）

| 时机 | 原因 |
|---|---|
| 切换技能树 | 会话绑定的是旧树 |
| 新建 / 删除技能树 | 同上 |
| 点"🗑 清空对话" | 用户主动 |
| resume 失败（404） | 服务端会话已失效 |

## 33. 前端 `AIBridge` 全解析

### 33.1 方法清单

| 方法 | 作用 |
|---|---|
| `sendMessage()` | 发送用户指令（首次 / 续接） |
| `resume(confirm, message)` | 回答确认卡片 |
| `_request(path, body)` | 统一 fetch（带 `?user_id=`、错误解析） |
| `_handleResponse(data)` | 渲染回复 / 工具日志 / 应用树 / 确认卡片 |
| `_applyTree(app, tree)` | 把返回的树写回画布 + 存历史 + 落盘 |
| `buildTreePayload(app)` | 组装当前树（剔除 `_` 字段） |
| `_renderConfirmCard()` | 渲染确认 / 取消按钮 |
| `resetSession()` | 丢弃 thread_id + 清空消息区 |
| `expandNode(name)` | 右键"AI 扩展" → 开面板 + 发送 |

### 33.2 请求与响应字段

```js
// 请求
{ tree: {name, description, nodes[], connections[]},
  message: "…",
  selected_node_ids: [...],
  thread_id: "stc_1_abc..." }

// 响应
{ thread_id, reply, diffs[], executed_tools[],
  pending_confirmation: {tool, args, message} | null,
  tree: {...} }
```

### 33.3 应用树的四个关键决策

```js
_applyTree(app, tree) {
  app.saveHistory();                    // ① 改前快照（保证可撤销）
  app.nodes = tree.nodes.map(...);
  app.connections = tree.connections;
  app.renderAll();
  app.checkDuplicateNames();
  app.sidebar.refreshStats();
  app.sidebar._saveCurrentTree();       // ② 立即落盘，不等用户点保存
  app.saveHistory();                    // ③ 改后快照
  showToast('🎨 AI 已更新技能树');
}
```

1. **不用 `loadData()`**：它会清空撤销栈（那是"切换树"语义）；
   这里手动压前后两个快照，AI 的改动就能 Ctrl+Z 撤销
2. **立即落盘**：否则 AI 修改只在内存里，刷新就没了
3. **判定用 `diffs.length > 0`**：曾以 `executed_tools.some(t => t.success)` 判断，
   而 `send_reply` 也是 success → 纯聊天也会重绘画布并弹提示
4. **payload 带连线样式**（color / dashed / showArrow）：否则服务端重建连线后样式丢失

## 34. diff 机制

```python
NodeDiff = {
  "op": "create" | "update" | "delete" | "connect" | "disconnect" | "move" | "replace",
  "node_id": ..., "parent_id": ..., "data": {...},
  "changes": {...}, "from_id": ..., "to_id": ..., "x": ..., "y": ...,
  "message": "..."
}
```

**当前前端用法**：只用 `diffs.length > 0` 作为"是否变了"的信号，然后整体应用 `tree`，
没有逐条回放 diff。

**为什么不逐条回放**：整体替换更简单不会漏；技能树数据量小（几十节点），全量重绘可接受；
逐条回放要处理顺序与冲突。

**什么时候该改**：节点上千、或需要"只高亮变更部分"的动画时。

## 35. 多模型热切换

```python
# services/coordinator/llm.py
def get_llm(temperature=0.3, user_id=None):
    cfg = get_active_config(user_id or 1, "llm")
    model   = (cfg or {}).get("model")   or AI_MODEL
    api_key = (cfg or {}).get("api_key") or AI_API_KEY
    base_url= (cfg or {}).get("base_url")or AI_BASE_URL

    cache_key = (temperature, model, base_url, api_key)
    if cache_key not in _llm_cache:
        _llm_cache[cache_key] = ChatOpenAI(...)
    return _llm_cache[cache_key]
```

**"热"在哪**：每次调用都读库里的启用配置，配置一变 → 缓存 key 变 → 未命中 → 重建实例。
用户在用户中心切换模型，**下一次 AI 请求就生效，不用重启**。

| 参数 | 值 | 原因 |
|---|---|---|
| `timeout` | 120s | 生成整棵树可能很慢 |
| `max_retries` | 0 | 生成类任务重试只会放大延迟 |
| `max_tokens` | 9192 | 推理模型的 max_tokens **包含思考部分**，给小了正文会被截断 |

> 已知隐患：缓存字典没有上限，频繁切模型会留下多个实例。
> 改进是加 LRU 或 TTL —— **面试时主动说出来是加分项**。

## 36. 与"统一协调 Agent"的对比

同一个项目里有两套 Agent，对比着看最容易理解设计取舍：

| 维度 | 技能树 AI | 统一协调 Agent |
|---|---|---|
| 目的 | 编辑一棵树 | 用自然语言操作全部业务数据 |
| 主流程 | **LangGraph StateGraph**（单节点） | **纯函数三段式**（路由 → 并行派发 → 汇总） |
| 子结构 | 无 | 6 个域子图（action/query/goal/task/habit/reward） |
| 状态持久化 | checkpointer（整图） | checkpointer（主 + 子图两层 thread_id） |
| 人工介入 | `pending_confirmation` 确认卡片 | `ask_user` 反问工具（FIFO 队列） |
| 工具数量 | 9 | 24 |
| 循环上限 | `MAX_ITERS=10` | `MAX_ITERS=8` + `MAX_ASK_ROUNDS=3` + `MAX_HISTORY=10` |
| 为什么这么选 | 单域单轮，图足够；需要跨请求保存上下文 | 多域并行有反问，但主流程无分支 → 不需要 StateGraph |

**一句话记忆**：
> 主流程线性就用纯函数编排，需要**跨请求恢复**才上 checkpointer；
> 单一任务循环用 StateGraph 单节点；多域协作才需要子图。

## 37. Agent 基础概念补遗

### 37.1 Function Calling 的底层

模型其实没有"执行"任何东西，它输出的只是一个结构化"意图"：

```json
{"tool_calls": [{"id": "call_1", "name": "create_node", "args": {"name": "闭包"}}]}
```

你的代码拿到后查表、执行、把结果作为 `ToolMessage` 塞回消息列表，再问模型一次。
**整个"智能"来自模型能根据工具结果继续推理。**

### 37.2 工具定义从哪来

```python
@tool
def create_node(name: str, icon: str = "📚", ...):
    """创建一个新节点。如果提供了 parent_id，会自动建立连线。

    Args:
        name: 节点名称（必填）
    """
```

LangChain 从**类型注解 + docstring** 自动生成 JSON Schema。所以：

- 参数名和注释要写清楚（模型靠它理解语义）
- 用 `Literal` 约束枚举 → 生成 `enum`，在协议层拦住非法值
- docstring 里的 `Args:` 会被解析成参数描述

### 37.3 checkpointer 存了什么

每个 `thread_id` 一个存档：完整 state（messages、tree、diffs、pending_confirmation…）。
`resume` 时先读档，再把新消息追加进去跑一次。
**内存版的代价**：进程重启存档全丢；多实例部署不共享。

### 37.4 温度怎么选

| 场景 | 温度 | 例子 |
|---|---|---|
| 结构化决策（路由、工具调用） | 0.1 ~ 0.3 | 路由节点 0.1、技能树 AI 0.3 |
| 内容生成（文案、题目） | 0.7 | 表达训练出题 |
| 需要创意 | 0.9+ | 本项目暂无 |

## 40. 面试怎么讲技能树 Agent（一分钟版）

> "技能树 AI 我用 LangGraph 做了一个单节点的 ReAct Agent：模型不直接改数据，
> 而是调用我定义的 8 个工具，工具按节点 ID 操作内存里的树，
> 执行结果作为 ToolMessage 回灌给模型继续推理，最多循环 10 轮。
>
> 危险操作做了两段式确认——工具首次返回 `needs_confirmation`，前端弹确认卡片，
> 用户确认后走 resume 端点，后端把**原始参数回灌**要求原样执行，
> 避免'确认的是 A、执行的是 B'。会话用 checkpointer 持久化，thread_id 编入 user_id 隔离。
>
> 两个决策值得说：一是**主流程没用图的条件边**，因为循环发生在节点内部，
> 图只负责跨请求保存上下文；二是前端以 **diffs 非空**判定是否应用结果，
> 而不是看工具是否执行成功——否则纯聊天也会触发一次全树重绘。"

**两个主动承认的不足**（显得清醒）：

1. checkpointer 用内存 `MemorySaver`，重启丢会话，换持久化 checkpointer 即可
2. 树状态提示词没做节点数截断，节点上百时 token 消耗会明显上升

### 41.1 手势映射

| 操作 | 行为 |
|---|---|
| 左键点/拖节点 | **只选中，不拖** |
| **Ctrl/Cmd + 左键拖节点** | 拖动（单个、或框选的一整组，都要按 Ctrl） |
| Shift + 左键 | 加减选（不进拖动） |

| 空格 / 中键拖 | 平移画布 |
| 多选右键菜单「移动」 | 另一套：跟随鼠标、再点一下放下、**0.1s 防抖** |

> 回归：`frontend/tests/tree-editor-features.test.mjs`（含静态断言，改坏了会红）。

### 41.2 网格：按「单位区域」扩展

- `unit = 300` 画布 px（= 10 个 30px 细格）
- 区域 = **内容包围盒按 unit 取整外扩**，所以节点拖到哪边、哪边就多一格
- 空树给**视口中心那一格**（"一开始只有一个单位区域，就是中间"）
- ⚠️ **接缝只画内部的，而且很淡**（`.grid-unit-seam`，opacity 0.18）——
  画成和外框一样明显，多格区域看起来像"几块板子拼起来"。区域感由外框 `.grid-region` 表达
- 纯函数 `utils.js::gridRegionFor()`（好测，不用开浏览器）

### 41.3 框选矩形：**SVG `<rect>` 必须用属性定位**

`#selection-box` 是 SVG 元素，所以：

```js
// ✗ 对 SVG 无效 —— 这个框曾经因此**从来没显示过**
box.style.left = x + 'px';
// ✓ 唯一正确写法
box.setAttribute('x', x); box.setAttribute('width', w);
```

配套两条：框选层要 `overflow: visible`（SVG 默认 hidden，平移后框会被裁）；
rect 加 `vector-effect="non-scaling-stroke"`（虚线粗细不随缩放变）。
回归：`frontend/tests/selection-box.test.mjs`。

### 41.4 多选右键菜单

选中 ≥2 个节点时右键出这套（单选时是另一套）：

| 菜单项 | 行为 |
|---|---|
| **移动** | 选中节点整体跟随鼠标（1:1 位移），**再点一下放下**；`moveModeMinMs = 100` 防抖 |
| **删除边** | `utils.js::edgesAmong()` —— **只删两端都在选中集合里的**边（连向外部节点的边要留着） |
| **删除结点** | 删除选中节点及其连线 |

### 41.5 AI 对话：按树持久化 + 上下文 5 轮

**持久化**（后端 checkpointer 是内存的，重启即失 ⇒ 只能前端存）：

- 每棵树两个 localStorage key：`skilltree_ai_msgs_<treeId>` / `skilltree_ai_thread_<treeId>`
- 切树**不再清空**（旧实现切走再切回对话就没了）；删除树时 `forgetTree()` 连记录一起删
- 会话失效（后端重启）**只丢 thread、不清历史** —— 面板上还看得到之前说了什么
- 切树的动作统一挂在 `app.loadData()` 末尾的 `ai.syncTree(currentId)`（一处覆盖所有入口）

**上下文**：只带最近 **5 个来回**（`node.py::MAX_CONTEXT_ROUNDS`）

⚠️ 按**轮**裁剪、不按条数：一轮 ReAct = `AIMessage(tool_calls)` + N 条 `ToolMessage` + `AIMessage`，
按条数切极易切在 tool_calls 与它的 ToolMessage 之间 → **孤儿 ToolMessage** → LLM API 400。
切点必须落在 `HumanMessage` 上（上一轮的工具消息已配完对）。

### 41.6 两条"看起来像没存上"的坑

1. **列表的 `id` 必须是 `tree_id` 字符串**，不能是数据库自增主键 ——
   前端到处用 `t.id` 拼 API 路径，给自增主键会变成 `POST /api/skill-trees/3/chat` → **404
   「技能树不存在」**，症状和"树根本没存上"一模一样
2. **列表字段后端 snake_case、前端 camelCase**，映射在 `utils.js::normalizeTreeEntry()`。
   不映射的表现是「进去全是 0 节点 + 日期空白，点开那棵树才对」

### 41.7 AI 编辑生成的硬要求（提示词层）

- 第一个节点直接是知识点，**不要**写成「XX 学习路线」这种标题
- 结构不要一条直线 / 只有一个分叉：至少 **3~5 条分支、3~4 层**
- 提示词保持精简（≤20 行）：**只写"什么时候该调工具"**，工具清单和参数细节放工具自己的 docstring
- ⚠️ 用户说「推荐 / 建议 / 该怎么学」时**不许动树** —— 只给文字方案 + 结尾问一句
  「要我建出来吗？」，等确认再调工具（"拿不准一律按咨询处理"，代价不对称）
