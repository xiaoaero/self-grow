## 一、简历项目条目（最终版，可直接复制）

**项目名称**：Self-Grow 个人成长数据系统 —— AI 增强的自我量化 Web 应用
**担任角色**：独立开发（产品与架构设计，AI 辅助编码）
**技术栈**：Python · FastAPI · SQLite · 原生 JavaScript · LangChain / LangGraph · FastMCP · Docker

**条目（5 条，按重要性排序）：**

1. 设计八维能力量化模型（健康/学习/关系/工作/创作/财务/爱好/魅力），各维度设置独立经验系数与全局折算率（如关系 0.5、爱好 0.75），健康维度下再细分睡眠与运动等子类并对睡眠引入作息连续性奖惩；将日常行为映射为可累积的等级成长体系，共 10 个段位

2. 基于 LangGraph 构建多智能体协调层：LLM 路由节点将自然语言指令分发至 6 个领域子 Agent 并行执行，通过 checkpointer 持久化会话并结合中断机制实现缺失信息反问，支持一句话完成跨模块数据操作

3. 基于 FastMCP 将 24 个业务工具封装为标准 MCP 服务（stdio / streamable-http 双传输），可接入任意 MCP 客户端；工具枚举参数以类型约束生成 JSON Schema，从协议层限制大模型非法入参

4. 设计 20 张表的领域模型与 90+ REST 端点，采用 routers / services / db 三层分层；经验结算采用"占位写入 → 回写真值"的两级幂等机制，避免定时任务与手动操作重复发放

5. 前端以零框架原生 JS 实现 SPA（手写路由 + 页面脚本按需加载），首屏仅加载核心脚本；启动时 8 个接口并行请求且各自独立容错，后端不可用时自动降级为本地数据继续渲染

## 三、深挖问答（15 题，每题都要能脱口而出）

### AI 应用方向

**Q1 为什么主流程不用 LangGraph StateGraph？**
主流程是线性三段（路由 → 并行派发 → 汇总），没有分支和循环。StateGraph 的 `operator.add` 状态合并语义会把每次节点返回值追加累积，多轮对话下 messages 无限膨胀。所以主流程用普通 async 函数编排，只有子 Agent 内部的 ReAct 循环用 StateGraph + checkpointer。
*追问*「什么时候该用 StateGraph？」→ 有分支、循环、条件边，或需要持久化中断恢复时。

**Q2 反问为什么不用 LangGraph 的 interrupt()？**
三个理由：(1) interrupt 依赖挂起状态，需要额外恢复入口和线程管理；我把反问当普通 ToolMessage 持久化进 checkpoint，resume 时追加 HumanMessage 重新 ainvoke，单一状态源。(2) 用户"跳过/放弃"零成本，不用处理各种 resume 分支。(3) 反问问题本身留在消息历史里，LLM 恢复后能看到自己问过什么，不会重复问。
*追问*「那 interrupt 适合什么？」→ 人工审批那种强阻塞的 human-in-the-loop 流程。

**Q3 怎么防止大模型死循环或无限反问？**
三道闸：① `MAX_ITERS=8`，ReAct 循环上限；② `MAX_ASK_ROUNDS=3`，反问超 3 轮就把 ask_user 从 bind_tools 里移除，逼 LLM 用已有信息执行或直接放弃——且留了保险分支，万一还是调用了，返回失败而不是真反问；③ `MAX_HISTORY=10`，消息窗口截断，保留首条 instruction + 最近 9 条，防上下文膨胀。

**Q4 多模型热切换怎么实现的？**
两层。存储层：model_configs 表存多套配置（model / base_url / api_key）带启用标记，增删改只做标记不物理删除。运行时：`get_llm()` 每次调用都读库里当前启用配置，用 (temperature, model, base_url, api_key) 四元组做缓存 key，配置一变 key 就变 → 缓存未命中 → 重建实例，切换后无需重启。配置无效时回退 .env。
*追问*「缓存会无限增长吗？」→ 会，配置频繁切换时旧实例会残留，改进是加 LRU 或 TTL。**主动说出来，这是加分项。**

**Q5 怎么保证大模型不乱传参数？**
三层约束：① 枚举参数全部用 `typing.Literal`，自动生成 JSON Schema 的 enum，在协议层就限制住；② user_id 由工具层统一注入，不让模型自己填，避免越权；③ 工具执行包 try/except，异常转成 `{"success": false, message}` 回灌给模型，让它自己重试或换参数，而不是整条链路崩掉。

**Q6 一次大模型调用超时或失败了怎么办？**
协调器层：各子图用 `asyncio.gather(return_exceptions=True)` 并行，单域失败不影响其他域；失败结果以 `{error: true}` 参与最终汇总，主 Agent 在总结阶段能看到哪个域失败并如实告知用户。LLM 层：`max_retries=0`，不在 SDK 层重试——重试会放大延迟；超时设 120 秒。

**Q7 会话隔离怎么做的？多用户会串吗？**
thread_id 设计为 `{main_thread_id}:{domain}`，主会话和每个子域各有独立 checkpoint，多域并行时消息互不污染。**但用户身份这块有硬伤**：`get_current_user` 只是校验 URL 上的 `user_id` 参数是否存在，不是真正的鉴权——没有 token/password，任何人改 `?user_id=` 就能访问别人的数据。这是我最清楚的一个缺陷，改进方向是 JWT + 中间件。**这题必须主动认，别等对方挖出来。**

### 全栈方向

**Q8 20 张表是怎么划分的？**
四组：① 用户与统计（users、user_stats_daily、user_monthly_stats、user_dimensions）；② 行为与习惯（action_logs、habits、habit_checkins、routine_streak）；③ 目标与任务（goals、goal_milestones、tasks、task_history、scheduled_tasks）；④ 激励与扩展（rewards、reward_drafts、model_configs、skill_trees、user_skills、expression_questions、expression_answers）。

**Q9 为什么不用 ORM？**
单用户、单实例、SQLite，ORM 的收益（跨库迁移、复杂关系映射）用不上，反而多一层心智负担和调试成本。我直接用 sqlite3 + Row Factory（结果能按字段名取值），SQL 全在 db/ 层，路由层看不到 SQL。代价是没有迁移工具，schema 变更靠幂等的 CREATE TABLE IF NOT EXISTS 加手工 ALTER——**这是我下次会换成 Alembic 的地方。**

**Q10 经验结算的幂等怎么保证？（杀手锏题）**
两级。第一级 request_id 去重：create_action_log 内部用 request_id + user_id + start_time 查重，命中就返回已有 id 不新建。第二级是关键——写入时 exp_earned 先占位 0，奖励算完再 UPDATE 回写真值。占位 0 的意义是让"这条记录是否已发过经验"变得可判断：回查 exp_earned > 0 即已发放，直接返回 0 不重复发。整个流程在单个 connection 上，一次 commit。
*追问*「并发下会重复吗？」→ 会。两个请求同时创建、同时查到 0，就会各发一次。SQLite 单写入者加单用户场景所以没暴露。改进方案是给 request_id 加 UNIQUE 约束 + INSERT OR IGNORE，或引入分布式锁。**主动说出来，这是加分项。**

**Q11 等级为什么是从 8 维 SUM 重算，而不是累加？**
因为等级是全局的、经验是分维度的。每次只更新对应维度，总经验从 user_dimensions 实时 SUM，再用 `level_from_total_exp` 反解等级。这样维度表始终是唯一真相源，不会出现"总经验"和"各维度之和"两份数据打架。代价是每次多一次 SUM，这个量级可忽略。

**Q12 前端为什么不用框架？**
想验证零依赖能撑到什么体量，顺便练浏览器原生能力。实现是手写哈希路由 + 页面 JS 按需加载，首屏只加载核心脚本；启动用 Promise.all 并行拉 8 个接口，每个挂 `.catch(() => null)` 单独容错，后端挂了页面仍能用本地默认数据渲染。
代价很明确：pages.css 堆到 7500 行、组件复用靠手写模板函数、状态管理靠全局对象、没有响应式。**这是我下次会改的地方——继续做的话会换 Vue，或至少把 CSS 按页拆分。**

**Q13 部署怎么做的？**
Docker 单容器，FastAPI 同进程提供 API 和静态资源（StaticFiles 挂载），不用配 nginx 反向代理，本机和手机局域网访问都打同一个端口。依赖用 pixi 锁定，导出 requirements.txt 给 Docker 用，避免开发机与容器版本漂移。

**Q14 定时任务多实例部署会重复执行吗？**
会。APScheduler 是进程内的，跑两个容器同一个 job 就触发两次。目前单实例部署所以没问题。改进方案是把调度独立成单独进程，或用分布式锁 / 数据库 job 执行记录做幂等。

**Q15 这个项目有什么不足？**
挑 3 个说，语气要平静：
1. 没有真正的身份认证——`get_current_user` 只校验 user_id 存在，没有 token/password，任何人改 query 参数就能访问他人数据（改进：JWT）
2. 前端零框架导致样式层膨胀到 7500 行，组件复用靠手写，没有响应式
3. 测试覆盖不够，只有 2 个测试文件，mostly 靠手动验证
4. （可选）经验结算的幂等在并发下有竞态窗口
