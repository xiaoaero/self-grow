# Self Grow — 时间口径统一方案

> 2026-09-15 排查「行动记录 / 行动历史 / 最近行动板块」时发现的问题与修复方案。
> 状态：**✅ 已实施**（2026-09-15）。采用方案 A（统一本地时间），
> 历史数据按**选项 1 不处理**。实施记录见文末第 10 节。

---

## 0. 摘要

后端接口层是健康的（分页、筛选、排序、搜索、导出全部实测正常，无 500）。
问题出在**时间口径**：全项目「UTC 时间」与「本地时间（CST）」在两个方向上混用，
导致三个可见现象：

| # | 现象 | 严重度 |
|---|---|---|
| A | 刚记录完，「最近行动」显示 **"8小时前"**（永远差 8 小时） | 中（观感差、显假） |
| B | 手动记录的行动，**时间整体早 8 小时**；00:00~08:00 记录的行动会**落到前一天** | **高（数据被写错）** |
| C | 前端的"今天"用 UTC 日期，UTC+8 在 **00:00~08:00 取到昨天** | 中 |

**推荐路线**：全链路统一到 **本地时间（naive local）**，与项目主体保持一致，改动面最小。
**历史数据是否需要纠正**，单列一节（第 6 节）供决策。

---

## 1. 三个现象的定位与证据

### A. 相对时间恒定差 8 小时

`backend/db/stats.py:34-47`：

```python
created_str = d.get("created_at") or d.get("start_time", "")
created_dt = datetime.datetime.fromisoformat(created_str)
delta = now - created_dt          # now = datetime.datetime.now() → 本地时间
```

`action_logs.created_at` 由建表默认值 `DEFAULT (datetime('now'))` 生成 ——
SQLite 的 `datetime('now')` **永远是 UTC**；而 `now` 是本地时间（容器 `TZ=Asia/Shanghai`）。
两者相减**恒多 8 小时**。

实测：POST 一条行动后 `created_at = '2026-09-14 23:24:22'`（UTC），本地此刻 09-15 07:24
→ delta 正好 8h00m → 输出 `"8小时前"`。且**不管实际差几小时，结果都是 8小时前**。

### B. 手动记录的时间整体早 8 小时（写坏数据）

`frontend/js/pages/action.js:1272`（睡眠路径 1264 同款）：

```js
const startIso = startTime.toISOString().replace('Z', '');
```

`toISOString()` 返回 **UTC 壁钟**，去掉 `Z` 后后端用 `datetime.fromisoformat` 按
**本地时间**解析入库。

实测（node）：

```
本机 09:00 记录  →  前端发送 "2026-09-15T01:00:00.000"  →  落库 01:00
```

确认弹窗显示的是 `09:00 → 10:00`，用户看到 09:00，库里却是 01:00。
**00:00~08:00 记录的行动，日期会退到前一天**，连带影响今日统计、日期区间筛选、
每日归档（`db/batch.py`）、连续天数。

### C. 前端"今天"用 UTC 日期

`action.js:767 / 777 / 845`、`tasks.js:47`、`data.js:25`：

```js
new Date().toISOString().slice(0, 10)    // UTC 日期
```

UTC+8 在 00:00~08:00 会取到"昨天" → 「今日已记录睡眠」标记与查询和后端对不上。

### 旁证：库里数据是混的

`backend/data.db` 的 `action_logs` 共 246 条，用 `start_time - created_at`（created_at 是 UTC）
做判别，口径分布：

| 差值区间 | 条数 | 判读 |
|---|---|---|
| `> +6h` | 201 | 本地口径（正确） |
| `-1h ~ +1h` | 20 | **UTC 口径（错）** |
| `< -1h` | 17 | **UTC 口径（错，且是"补记过去时段"的记录）** |
| `+1h ~ +6h` | 7 | 灰区 |
| 带时区偏移 | 1 | AI 路径（格式也不同） |

> 说明：两条入口的时间来源不同 —— **AI 描述记录**（`action.js:1072`）
> 的时间由模型按本地格式给出，所以是对的；**手动快速记录**走 `toISOString()`，所以错。
> 201 条 `>+6h` 多为早期批量导入的模拟数据（created_at 集中、start_time 是整点）。

## 2. 现状盘点：谁在用哪个口径

| 位置 | 口径 | 备注 |
|---|---|---|
| 多数建表默认值 `DEFAULT (datetime('now'))` | **UTC** | init.py:150/181/228/256/292/314/336/353 |
| 少数后加表 `DEFAULT (datetime('now','localtime'))` | 本地 | init.py:499/518/694/715 |
| `db/batch.py` 的 `datetime.date.today()` | 本地 | 归档按"今天" |
| `main.py` APScheduler `CronTrigger(hour=3)` | 本地 | 容器 TZ 已设 |
| `user_stats_daily.date`（由 Python 写入） | 本地 | `strftime('%Y-%m-%d')` |
| 前端 `new Date().toISOString()` | **UTC** | 9 处（见第 4 节） |
| 前端展示（`new Date(字符串)`） | 隐式本地 | 无时区的串被当本地解析 |

**结论：口径已经三方混用**（SQLite 默认值 UTC / Python 本地 / 前端 toISOString UTC），
不是单点 bug，而是缺少一条统一约定。

## 3. 方案选型

### 方案 A：全链路统一「本地时间，naive」（推荐）

- 存储与传输都用 `YYYY-MM-DDTHH:mm:ss`（不带时区），语义是"用户所在时区的墙上时间"
- **优点**：与项目主体一致（`date.today()`、cron、部分建表默认值已如此）；改动面最小；
  不需要引入任何时区库；单人单机单时区场景下语义自然
- **缺点**：将来若支持跨时区用户 / 多机部署在不同时区，需要重构

### 方案 B：全链路统一「UTC，存储带偏移」

- 存储用 `...Z` 或 `+00:00`，前端展示时转本地
- **优点**：理论上更规范，天然支持跨时区
- **缺点**：要改 APScheduler 的小时数、`date.today()`、`batch.py`、`user_stats_daily`、
  所有 SQL 的 `date()` 函数语义，以及前端全部时间展示；改动面是方案 A 的 5~8 倍；
  而本项目的产品形态（个人成长打卡，单时区）用不上

### 结论

**选方案 A**。理由：收益/代价比明显；且方案 A 做完后，未来若要迁 UTC，
届时是一次独立的、有明确边界的重构（把 naive local 一次性转成带偏移）。

## 4. 改动清单（方案 A）

### 4.1 前端：新增两个工具函数（`frontend/js/utils.js`）

```js
/** 本地墙上时间的 ISO 形式：2026-09-15T09:00:00（不带 Z，不带偏移） */
function toLocalIso(date) {
    const d = date || new Date();
    const p = n => String(n).padStart(2, '0');
    return `${d.getFullYear()}-${p(d.getMonth() + 1)}-${p(d.getDate())}` +
           `T${p(d.getHours())}:${p(d.getMinutes())}:${p(d.getSeconds())}`;
}

/** 本地日期：2026-09-15（替代 toISOString().slice(0,10)） */
function todayLocal(date) {
    return toLocalIso(date).slice(0, 10);
}
```

### 4.2 前端：替换 9 处

| 文件:行 | 现状 | 改为 |
|---|---|---|
| `pages/action.js:1272` | `startTime.toISOString().replace('Z','')` | `toLocalIso(startTime)` |
| `pages/action.js:1264` | `sleepStartDate.toISOString().replace('Z','')` | `toLocalIso(sleepStartDate)` |
| `pages/action.js:1072` | `a.start_time \|\| new Date().toISOString()` | `a.start_time \|\| toLocalIso()` |
| `pages/action.js:767` | `new Date().toISOString().slice(0,10)` | `todayLocal()` |
| `pages/action.js:777` | 同上（睡眠标记） | `todayLocal()` |
| `pages/action.js:845` | 同上（查今日睡眠） | `todayLocal()` |
| `pages/tasks.js:47` | `now.toISOString().slice(0,10)` | `todayLocal(now)` |
| `data.js:25` | `new Date().toISOString().slice(0,10)` | `todayLocal()`（**注意**：本文件在 utils.js 之前加载，实际实现是就地计算） |
| `pages/skills.js:702` | `new Date().toISOString()` | **本次不改**（见下方说明） |

> `pages/skills.js:702` 与 `skill-tree/js/sidebar.js:74` 写的是技能树元数据 `updatedAt`：
> 没有后端解析、只用于展示，且两处都是 ISO-with-Z（口径自洽、浏览器能正确转本地）。
> 而 `frontend/skill-tree/` 是独立小应用，不加载 `utils.js`，改一处反而造成两个写入方格式不一致。
> 因此**有意保留**，属于已知的、无影响的不一致。

### 4.3 后端：相对时间按同一口径比较（`db/stats.py`）

```python
# 修正前：created_at（UTC）与 now（本地）直接相减
# 修正后：两边都当本地时间（新数据写入即本地；历史数据见第 6 节）
now = datetime.datetime.now()
created_dt = datetime.datetime.fromisoformat(created_str)
if created_dt.tzinfo is not None:        # 兼容历史里带偏移的数据
    created_dt = created_dt.astimezone().replace(tzinfo=None)
delta = now - created_dt
```

### 4.4 后端：写入时显式写本地时间，不再依赖 SQLite 默认值

**关键约束：SQLite 不支持 `ALTER TABLE ... ALTER COLUMN`，已建表的默认值改不了。**
所以不能只改建表语句，必须同时在**插入时显式赋值**：

```python
# db/actions.py::create_action_log
now_str = datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S")
conn.execute(
    "INSERT INTO action_logs (..., created_at) VALUES (..., ?)",
    (..., now_str),
)
```

并同步把建表语句的默认值改成 `datetime('now','localtime')`（对新库生效，作兜底）。
涉及表：`action_logs` 以及其它 `DEFAULT (datetime('now'))` 的写入路径
（habits / tasks / goals / rewards 等，逐个人工确认后统一）。

> **这一步还顺手修掉一个隐藏问题**：`db/batch.py` 的任务归档/过期判断用的是
> `date(created_at) = 昨天`（batch.py:29/75），而 `created_at` 是 UTC、
> 比较基准 `date.today()` 是本地 —— 所以 **00:00~08:00 创建的任务会被归到前一天**，
> 归档和"过期"判断都会错位。把 `created_at` 改成写入本地时间后这个问题一并消失。
> （注意：已经归档进 `task_history` 的历史结果不会回滚。）

### 4.5 睡眠 / 复盘等"每日一次"判断

后端 `has_sleep_record_today` / `has_finance_review_this_half` 用
`datetime.now().strftime('%Y-%m-%d')` 与 `substr(start_time,1,10)` 比较 ——
4.2 修好后两边口径一致，无需额外改动。**改造后需回归验证。**

## 6. 历史数据要不要纠正（需决策）

**注意：只改代码不会让旧数据变对 —— 界面只是忠实渲染库里的值。**
不处理的话，历史记录仍会显示成早 8 小时的样子。

### 选项 1：不动历史数据（推荐）

- 理由：库里两种口径混着（AI 路径是对的、手动路径错的），**无差别 `+8h` 会把对的那批改坏**
- 代价：旧记录时间仍偏 8 小时，但新记录从此正确

### 选项 2：用启发式脚本纠正（可先 dry-run）

判别规则（`created_at` 是 UTC，可作为"落库时刻"参照）：

| `start_time - created_at` | 判读 | 动作 |
|---|---|---|
| `≤ +6h` | UTC 口径（写错了） | `start_time`/`end_time` **+8h** |
| `> +6h` | 本地口径（对的） | 不动 |
| 带 `+00:00` / `Z` | AI 路径（对的） | 不动 |

脚本要求：
1. 先 `--dry-run` 打印"将要修改的行 + 修改前后值"，人工过一遍
2. 修改前自动备份 `data.db`
3. 只动 `action_logs`，不动 `created_at`

### 选项 3：只修"跨天"的那批

- 只纠正 `start_time` 的**日期**与 `created_at` 日期不一致的行（影响统计口径的那批），
  时间部分不动 —— 折中方案，但会造成同一批数据内部不一致，不推荐

## 8. 风险与已知限制

1. **测试环境的时区依赖**：`pytest` 在本机 UTC+8 跑；若将来在 UTC 的 CI 中跑，
   断言本地时间的用例会失败。建议测试里**固定 TZ**（`os.environ["TZ"]="Asia/Shanghai"`）
   或对时间断言做相对化处理
2. **容器时区仍是前提**：本地口径依赖 `TZ=Asia/Shanghai`（Dockerfile 已设、compose 可覆盖）。
   一旦容器忘记设 TZ，又会整体偏 8 小时 —— 建议在 `lifespan` 启动日志里打印一次当前时区
3. **`created_at` 主要用途是审计/相对时间**，改成本地后，"同一时刻多机写入"的排序语义不变，
   但如果有跨时区客户端接入，仍会错 —— 已记入第 3 节方案 A 的已知限制
4. **不改前端展示逻辑**：前端渲染 `new Date("2026-09-15T09:00:00")`（无时区串）时按本地解析，
   与方案 A 一致，无需额外改动；这也是选方案 A 的一个隐性收益

### 10.4 已知的、有意保留的不一致

`frontend/js/pages/skills.js:702` 与 `frontend/skill-tree/js/sidebar.js:74` 的
技能树 `updatedAt` 仍用 `toISOString()`（ISO-with-Z）。理由见第 4.2 节注释：
无后端解析、仅供展示、两处格式自洽，且 `skill-tree/` 是独立小应用用不到工具函数。
