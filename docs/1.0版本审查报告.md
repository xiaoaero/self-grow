1. 打开 `backend/models/level.py`
2. 在 `exp_for_level` 函数体最前面加一行：
   ```python
   def exp_for_level(L: int) -> int:
       """计算从 L 级升到 L+1 级所需的经验值"""
       if L >= 200:          # ← 新增：满级后无下一级

       if L <= 0:

   function expForLevel(L) {

   }
   ```

### 7. 定时任务函数是同步阻塞的，会阻塞事件循环

**文件**: `backend/main.py:70`

**问题**: `run_daily_refresh()` 和 `run_weekly_refresh()` 是同步函数，内部遍历所有用户执行 SQL 操作。在 `AsyncIOScheduler` 中执行同步函数会阻塞整个 asyncio 事件循环，期间所有 API 请求都无法响应。

**例子**: 凌晨 3:00 定时任务触发，系统中有 2 个用户。`run_daily_refresh` 对每个用户执行归档、刷新、结算、快照 4 步操作，每步涉及多次数据库读写。整个过程可能耗时 2-5 秒，这期间如果用户在前端操作，所有请求都会挂起直到定时任务完成。

**修复**:

1. 打开 `backend/main.py`
2. 在文件顶部添加 import：
   ```python
   import asyncio
   ```
3. 找到 `lifespan` 函数中定时任务的注册位置（约第 69-71 行）：
   ```python
   scheduler.add_job(run_daily_refresh, CronTrigger(hour=3, minute=0))
   scheduler.add_job(run_weekly_refresh, CronTrigger(day_of_week='mon', hour=3, minute=5))
   ```
4. 改为用 `asyncio.to_thread` 包装同步函数：
   ```python
   async def async_daily_refresh():
       await asyncio.to_thread(run_daily_refresh)

   async def async_weekly_refresh():
       await asyncio.to_thread(run_weekly_refresh)

   scheduler.add_job(lambda: asyncio.ensure_future(async_daily_refresh()), CronTrigger(hour=3, minute=0))
   scheduler.add_job(lambda: asyncio.ensure_future(async_weekly_refresh()), CronTrigger(day_of_week='mon', hour=3, minute=5))
   ```
5. 或者更简洁的方式（APScheduler 支持 async 函数）：
   ```python
   scheduler.add_job(run_daily_refresh, CronTrigger(hour=3, minute=0), max_instances=1, misfire_grace_time=300)
   ```
   并在 `run_daily_refresh` 前加上线程执行器配置：
   ```python
   from apscheduler.executors.pool import ThreadPoolExecutor
   scheduler = AsyncIOScheduler(executors={'default': ThreadPoolExecutor(1)})
   ```

**测试**:

1. 启动后端服务
2. 在终端模拟定时任务触发（Python 交互式）：
   ```python
   import time
   # 在另一个终端启动计时
   start = time.time()
   # 手动触发同步版本的 run_daily_refresh()
   from db.batch import archive_incomplete_tasks, refresh_daily_tasks
   archive_incomplete_tasks(1)
   refresh_daily_tasks(1)
   elapsed = time.time() - start
   print(f"定时任务耗时: {elapsed:.2f}s")
   ```
3. 在定时任务执行期间，并发发一个 API 请求：
   ```bash
   # 终端1：执行定时任务
   curl http://localhost:3001/api/health
   # 终端2：同时发 API 请求，记录响应时间
   time curl http://localhost:3001/api/health
   ```
4. 修复前：API 请求会等到定时任务完成后才响应（总时间 ≈ 定时任务耗时 + 正常响应时间）
5. 修复后：API 请求应立即响应（不受定时任务阻塞）
6. 验证定时任务本身仍正常执行：检查数据库中新创建的每日任务、习惯结算 EXP 等

**问题**: `renderHistory`、`renderSkills` 等都是 async 函数，但 `renderFn()` 调用没有 await。如果用户快速切换页面，前一个页面的异步渲染可能在后一个页面渲染时继续修改 DOM。

**例子**: 用户快速点击"成长记录"→"奖励商城"。`renderHistory()` 开始异步加载热力图数据，用户此时已切到奖励页。热力图数据返回后，Chart.js 尝试在已被隐藏的 `<canvas id="profile-radar">` 上绘制，可能报错或绘制到错误位置。

### 13. `int(dimension_exp)` 截断而非四舍五入

**文件**: `backend/services/exp_service.py:54`

**问题**: `upsert_dimension(user_id, category, int(dimension_exp))` 使用 `int()` 截断小数，而不是 `round()` 四舍五入。

**例子**: 用户运动 30 分钟，`_calc_health_sport` 返回 `dimension_exp = 3.75 * 2 = 7.5`。`int(7.5)` = 7，丢失 0.5 EXP。如果用户每天运动 30 分钟，一个月下来少记录约 15 EXP。

**修复**: `int(dimension_exp)` → `round(dimension_exp)`

### 15. 目标 deadline 的 UTC 解析导致时区偏移

**文件**: `frontend/js/pages/goals.js:119`

**问题**: `new Date("2026-12-31")` 被解析为 UTC 午夜时间，而 `new Date()` 是本地时间。在 UTC+8 时区，deadline 变成了 12月30日 16:00，导致剩余天数少1天。

**例子**: 用户设置目标截止日期为 2026-12-31，12月30日晚上 20:00 查看目标。本地时间距离截止还有 28 小时，但 `new Date("2026-12-31")` 被解析为 UTC 00:00 = 北京时间 08:00，已经是"过去"了，显示"已过期 -1 天"。

**修复**: 解析时加上时间部分 `new Date(goal.deadline + "T23:59:59")`。

### 16. 满级后 `current_exp` 可能变为负数

**文件**: `backend/models/level.py:30`

**问题**: `level_from_total_exp` 封顶在 200，但 `new_current = new_total - total_exp_for_level(200)` 在总经验超过满级累计经验时会产生负数。

**例子**: 用户总经验 1,000,000，`total_exp_for_level(200)` = 约 980,000。`new_current = 1,000,000 - 980,000 = 20,000`，目前还好。但如果未来经验公式调整或数据异常导致 `total_exp < total_exp_for_level(200)`，`new_current` 就变成负数，前端显示 "还需 -5000 EXP"。

**修复**: 在 `level_from_total_exp` 中加 `return min(level, 200)` 并在调用方对 `new_current` 加 `max(0, ...)`。
