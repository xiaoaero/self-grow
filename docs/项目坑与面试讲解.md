# 第一部分：已修复的坑（讲"我发现并修了"）

## 坑 1：80 个"假异步"端点（async def 但没有 await）

**现象**

项目里有 **80 个路由端点** 长这样：

```python
@router.get("/api/users/profile")
async def user_profile(user=Depends(get_current_user)):
    total_exp = get_total_exp_from_dimensions(user_id)   # 同步 sqlite3
    today_row = get_user_stats(user_id, today)           # 同步 sqlite3
    return {...}
```

写了 `async def`，但函数体里**一个 `await` 都没有**——套了个异步的壳，里面全是同步查库。

**根因**

可能是"看到 FastAPI 例子都写 async，就跟着写了"，或者"以为 async 就一定更快"。实际上：
- `async def` 端点在事件循环里跑，同步的 `sqlite3` 调用会**卡住整个事件循环**
- 而 `def`（同步）端点 FastAPI 会自动丢线程池，反而**不会**阻塞事件循环

也就是说，这些端点写成 `async` 比写成同步**更糟**。

**处理**（2026-09-08）

用 `ast` 模块精确扫描（判断函数体有无 `Await` 节点 + 有无 `@router` 装饰器），批量把 80 个端点的 `async def` 改成 `def`。

```python
# 保留 15 个真正有 await 的（调 AI / WebSocket），其余 80 个删掉 async
```

**面试话术**

> "我用 ast 扫了一遍，发现有 80 个端点写着 `async def` 但函数体里根本没有 `await`，是'假异步'——它们套了个异步的壳，里面却是同步 sqlite3，反而会阻塞事件循环。我把纯 CRUD 的端点改成了同步 `def`，FastAPI 会自动把它们丢到线程池，事件循环就空出来了。"

**加分点**：能说出判断标准——"函数体里有没有 await，有就保持 async，没有就改 def"。

## 坑 2：同步 sqlite3 阻塞事件循环（子 Agent 工具调用）

**现象**

协调 Agent 的 6 个子 Agent 用 `asyncio.gather` **并行**派发，但实际是**串行**执行的。

**根因**

`agents/base.py` 里执行工具是同步调用：

```python
tool_result = tool_fn.invoke(args)   # 同步！工具内部是同步 sqlite3
```

`gather` 确实并发启动了 6 个协程，但每个子 Agent 执行工具时会**卡住整个事件循环**——就像服务员在等菜时把身体横在厨房门口，其他客人全进不来。

**关键点**：要区分两层——
- **工具函数本身**是同步的（24 个工具全是 `def`，内部同步 sqlite3）—— 这个改不了
- **调用工具的方式**是同步的 —— 这个必须改

**处理**（2026-09-08）

```python
import asyncio

# 工具是同步的（内部是同步 sqlite3），丢线程池避免阻塞事件循环
tool_result = await asyncio.to_thread(tool_fn.invoke, args)
```

**为什么不用"工具改 async"**：那要换异步数据库驱动（`aiosqlite`）并改 24 个工具函数，单用户 SQLite 场景下收益不匹配成本。丢线程池一行解决。

**面试话术**

> "子 Agent 派发看起来是 `asyncio.gather` 并行的，但因为工具调用是同步的，实际是串行——事件循环被卡住了。我改成 `await asyncio.to_thread(...)` 丢线程池，6 个域才真正并行起来。这里有个容易混的点：工具函数本身还是同步的（Python 的 sqlite3 只有同步 API，改不了），我改的是**调用方式**——把同步操作挪出事件循环。"

**加分点**：能讲清"操作本身同步"和"调用方式同步"的区别——这是很多人答不上来的。

## 坑 3：两套重复的 LLM 实例缓存

**现象**

项目里有两个地方在缓存 `ChatOpenAI` 实例：

| | 缓存 1 | 缓存 2 |
|---|---|---|
| 位置 | `coordinator/llm.py` | `ai_client.py` |
| 缓存结构 | dict（多实例） | 单例（只存一个） |
| 缓存 key | 四元组 | 五元组（多了 max_tokens） |
| max_tokens | 固定 9192 | 默认 4096 |
| timeout | 120s | 300s |

**根因**

两个模块各自演化，都实现了"从 `model_configs` 表读配置 → env 兜底 → 缓存实例"这套逻辑，但参数细节岔开了。典型的代码重复。

**处理**（2026-09-09）

抽成统一工厂 `services/llm.py`：

```python
def get_llm(temperature=0.3, max_tokens=9192, timeout=120.0, user_id=None) -> ChatOpenAI:
    cfg = get_active_config(user_id or 1, "llm")   # 用户配置优先，env 兜底
    ...
    cache_key = (temperature, max_tokens, timeout, model, base_url, api_key)
    if cache_key not in _llm_cache:
        _llm_cache[cache_key] = ChatOpenAI(...)
    return _llm_cache[cache_key]
```

删除 `coordinator/llm.py`，6 个调用方改成 `from services.llm import get_llm`。

**关键设计**：`timeout` 必须进缓存 key——协调器要 120s、纯文本要 300s，这是两个不同的实例，不能共享。

**面试话术**

> "我发现项目里有两套 LLM 缓存逻辑，一套在协调器、一套在纯文本客户端，各自维护、参数还不一样。我抽了一个统一的 LLM 工厂，缓存 key 用六元组（含 timeout，因为不同场景超时需求不同），合并后所有 AI 调用走同一个入口，加参数只改一处。"

## 坑 4：AI 模型配置分裂（行动 AI 用 env，协调器用数据库）

**现象**

- 行动板块的"记录行动 AI"用的是 `.env` 里的模型（`qwen3.7-flash`）
- 协调 Agent 用的是数据库 `model_configs` 表里的模型（`qwen3.7-plus`）

同一个系统里两个 AI 用不同模型，而且改数据库配置对行动 AI 无效。

**根因**

行动 AI 是旧链路遗留，直接用 `httpx` 裸写 HTTP 请求：

```python
from config import AI_BASE_URL, AI_API_KEY, AI_MODEL   # 直接读 env
resp = await client.post(f"{AI_BASE_URL}/chat/completions", ...)
```

绕过了 `model_configs` 表，也就绕过了"用户可配置 + 热切换"的能力。

**处理**（2026-09-09）

去掉裸 httpx，改用 LangChain 统一入口：

```python
from services.llm import get_llm

llm = get_llm(temperature=0.7, user_id=user_id)
llm_with_tools = llm.bind(tools=ACTION_PARSE_TOOLS, tool_choice="auto")
resp = await llm_with_tools.ainvoke(msgs)
```

连带把表达训练 AI 的 3 处 httpx 也一起改了。

**两个技术细节**（面试能讲就很加分）：
1. 用 `llm.bind(tools=...)` 而非 `bind_tools`——因为项目里的 tools 是 OpenAI function 格式的 dict，`bind` 底层原样传参最保险
2. LangChain 返回的 `resp.tool_calls` 结构是 `[{"name", "args", "id"}]`（`args` 已是 dict），和 httpx 直连的 `[{"id", "function": {"name", "arguments"}}]` 不同，返回值解析要对应调整

**面试话术**

> "行动板块的 AI 走的是旧链路，用 httpx 裸写 HTTP 直连 env 配置，和协调 Agent 用的数据库配置是两套，导致同一个系统里模型不一致、也没法热切换。我把它改成走统一的 LLM 工厂，用 LangChain 的 `bind` 传工具，现在所有 AI（除语音）统一是'用户配置优先、env 兜底'。"

# 第二部分：已知限制（讲"我知道，也有方案"）

## 坑 6：没有真正的身份认证（最严重）

**现象**

`routers/deps.py` 的 `get_current_user` 长这样：

```python
async def get_current_user(user_id: int = Query(...)):
    user = get_user(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
```

**只校验 `user_id` 存不存在，没有 token、没有密码。** URL 上的 `?user_id=` 客户端可以随便改——改一下就能访问别人的数据。

94 个端点里，76 个带这个（形同虚设的）校验，**16 个连它都没有**。

**根因**

个人项目，一开始就"给自己用"，没做鉴权。后来功能越加越多，鉴权始终没补。

**为什么还没修**

改鉴权是**牵一发动全身**的改动：前端所有请求都要带 token，后端要加登录态校验。不是加个装饰器就能解决的。

**改进方案**（面试说这个）

1. 登录端点验证密码，签发 JWT
2. 全局中间件校验 token，把 `user_id` 从 token 里取（不再信 URL 参数）
3. 前端统一在请求头带 `Authorization: Bearer <token>`

**面试话术**

> "这个项目目前没有真正的身份认证——`get_current_user` 只校验 URL 上的 user_id 存不存在，可被伪造。这是我最清楚的一个缺陷。改进方案是引入 JWT：登录签发 token，中间件校验并从 token 取 user_id，而不是信 URL 参数。没做是因为它会牵动前端所有请求，不是加个装饰器就完事的——如果要做成多用户 SaaS，这是第一个必须补的。"

**为什么主动说这个反而加分**：承认最严重的问题 + 给出清晰方案 = 说明你真的懂。藏着掖着被问出来才是灾难。

## 坑 7：经验结算的幂等在并发下有竞态窗口

**现象**

经验结算用"占位 0 → 回写真值"两级幂等：

```python
# 1. 创建记录时 exp_earned 先占位 0
action_id = create_action_log(..., exp_earned=0, request_id=request_id, conn=conn)

# 2. 检查是否发过经验
existing = conn.execute("SELECT exp_earned FROM action_logs WHERE id = ?", (action_id,)).fetchone()
if existing and existing["exp_earned"] > 0:
    return {"exp_earned": 0, "message": "该行动已记录过，不重复奖励经验值"}

# 3. 发经验
service_result = award_exp_and_recalc(..., conn=conn)

# 4. 回写真值
conn.execute("UPDATE action_logs SET exp_earned = ? WHERE id = ?", (dimension_exp, action_id))
conn.commit()
```

**为什么先写 0**：如果写入时就带真实经验值，就无法区分"这条是新创建的"还是"已经发过经验的"了。占位 0 后，回查 `exp_earned > 0` 才知道发过。

**竞态在哪**

两个并发请求同时 `create` 出同一条记录、同时查到 `exp_earned = 0`，就会**各发一次经验**。

**为什么当前没暴露**：SQLite 单写入者 + 项目是单用户场景。

**改进方案**：给 `request_id` 加 `UNIQUE` 约束 + `INSERT OR IGNORE`，或引入分布式锁。

**面试话术**

> "经验结算我做了两级幂等：request_id 去重 + 占位 0 回写真值。但它有个竞态窗口——并发两个请求可能同时查到 0 而重复发。目前 SQLite 单写入者加单用户场景不会触发，要做多用户就得给 request_id 加唯一约束或者上锁。"

## 坑 8：编排状态和会话历史都在内存

**现象**

两个东西都在进程内存里：

| 东西 | 位置 | 问题 |
|------|------|------|
| 编排状态 `_thread_store` | `routers/coordinator.py` | TTL 30 分钟，重启丢失，多实例不共享 |
| 会话历史 checkpointer | `MemorySaver` | 重启后所有子图会话历史全丢 |

**后果**

- 重启容器 → 所有进行中的多轮对话丢失
- 多实例部署 → 请求打到不同实例，会话对不上

**改进方案**

- 编排状态迁 Redis
- checkpointer 换 `AsyncSqliteSaver` / `PostgresSaver`

**面试话术**

> "协调 Agent 的编排状态和 LangGraph 的会话历史都在内存里，重启就丢、多实例也不共享。单实例部署没问题，要横向扩展就得把编排状态迁 Redis、checkpointer 换成数据库版。"

## 坑 9：APScheduler 多实例会重复执行

**现象**

每日 03:00 的定时任务（归档 + 结算）用 `APScheduler`，它是**进程内**调度。

如果 `docker compose up --scale=2` 起两个实例，同一个 job 会**执行两次**——用户经验重复结算。

**改进方案**：把调度独立成单独进程，或加分布式锁（Redis / 数据库 job 执行记录做幂等）。

**面试话术**

> "定时任务用的是 APScheduler，进程内调度。单实例没问题，多实例部署会导致同一个任务执行两次——那时候得把调度拆成独立进程或者加分布式锁。"

## 坑 10：SQLite 的并发写入上限（但有 WAL 缓解）

**现象**

SQLite 同一时刻只允许一个写入者。高并发写入会出现 `database is locked`。

**已做的缓解**（`db/connection.py`）：

```python
conn.execute("PRAGMA journal_mode=WAL")       # 写不阻塞读
conn.execute("PRAGMA busy_timeout=5000")      # 锁冲突等 5 秒而非立即报错
conn.execute("PRAGMA synchronous=NORMAL")     # WAL 下够安全，写入性能约 2 倍
```

**什么时候才需要换**：多用户高并发写、多实例部署。当前单用户场景完全够用。

**面试话术**

> "数据库用的 SQLite，我已经开了 WAL（写不阻塞读）、busy_timeout（锁等待而非报错）、synchronous=NORMAL。个人应用场景完全够，什么时候会换 PostgreSQL？多用户高并发写、或者要多实例部署共享一个库的时候。现在换属于过度设计。"

**加分点**：能说出"什么时候不该优化"——这比知道怎么优化更难得。

## ✅ 已完成 & 坑 11：SSE 流式输出（2026-09-16 全量落地）

**（改造前的状态）** `/api/coordinator/stream/{thread_id}` 只是占位，只吐一条 `done`；
技能树那个 `GET /{tree_id}/chat/stream` 也是假的（把最终结果一次性塞进去）。
`services/ai_client.call_ai_text_stream()` 写好了但**全项目零调用**。

**（现在）** 所有 AI 端点都改成流式，事件协议统一在 `services/sse.py`：

| 端点 | 流式内容 |
|---|---|
| `POST /api/coordinator/chat`、`/resume` | 阶段事件（路由 / 每个子 Agent 起止 / 工具执行）+ **逐 token** |
| `POST /api/skill-trees/{id}/chat`、`/chat/resume` | 阶段事件（第 N 轮推理 / 正在执行哪个工具 / 需要确认） |
| `POST /api/expression/generate`、`/generate-hints`、`/evaluate/{id}` | 阶段事件（产物是 JSON，不做逐字符） |
| `POST /api/habits/ai-icon` | 阶段事件 + 心跳保活（`max_tokens=10000`，要等几十秒） |

**实现上最难的一环**：阶段事件是在**很深的调用链里**产生的
（router → graph → agent → tool），而技能树 AI 的 LangGraph 图还是**模块级单例**，
没法在编译时把每个请求的回调烘进去。最后用 `ContextVar` 做发射器 ——
`asyncio` 任务会复制上下文，所以 `asyncio.gather` 并发派发的多个子 Agent
各自看到自己的发射器，事件不会串。**没启用流式时它是完全空操作**，
同步路径一行都不会变（有回归测试守着这条不变式）。

**顺手修掉的两个隐患**：
1. `GET /api/coordinator/stream/{thread_id}` **没挂鉴权**，知道 thread_id 就能查 —— 已删除
2. 浏览器原生 `EventSource` **不能自定义请求头**，而本项目的身份是
   `auth.js` 包装 `fetch` 注入的 `Authorization: Bearer` —— 用 EventSource 必然 401。
   所以前端走 `fetch` + `resp.body.getReader()` 自己解析（`frontend/js/sse.js`），
   协议也相应做成 POST。

**踩坑提醒**：Nginx 不关 `proxy_buffering` 会把 SSE 事件攒着一次性发，
表现成"流式看起来没生效"。除了在 nginx 里显式关，后端每个流式响应还会带
`X-Accel-Buffering: no` —— 这个头跟着代码走，换部署方式也不会丢。

## 坑 12：写操作确认流未实现

AI 识别到"跑步 30 分钟"后**直接写库**，没有二次确认。

**改进**：机制其实已经有了——`ask_user` 工具能发起反问。只要在提示词里加"写库前先确认"，就能用现有机制实现确认卡片，不用改代码结构。

## 坑 13：工具参数校验缺失

MCP Server 的工具用 `Literal` 约束了枚举参数（协议层拦截很好），但协调 Agent 子图工具的**数值范围、非空校验**还没做（`tools.py` 里 `raise ValueError` 为 0）。

**改进**：在 `@tool` 函数内补坐标范围、名称非空、优先级枚举等校验，非法值返回错误给 LLM 让它自愈，而不是抛异常。

# 第四部分：面试话术总纲

## 一、被问"项目有什么不足"时

**不要说**："没什么大问题" / "都挺好的"（不诚实，且显得没思考）
**也不要**：一次性倾倒 10 个问题（显得项目很烂）

**正确做法**：说 2-3 个，按"严重程度"排序，每个配方案。

推荐组合：

> 1. **"没有真正的身份认证"**（最严重，显得你懂安全）+ JWT 方案 —— ✅ 已落地
> 2. **"状态都在内存"**（架构债）+ Redis / 数据库方案
> 3. **"没有资源级隔离"**（所有 admin 可改所有技能树）+ 加 owner 校验
>
> ⚠️ **不要再说"流式没做"了 —— 2026-09-16 已经全量落地**。
> 反过来可以主动讲："我把所有 AI 端点都改成了 SSE 流式，其中协调 Agent 是真逐 token，
> 表达力那几个因为是 JSON 产物所以只推阶段进度 —— 逐字符传 JSON 反而逼前端做增量解析，
> 那是负优化。"

说完补一句：

> "这些都是我知道并且有明确改进方案的——前两个是架构层面的，要在做多用户 SaaS 前补上；最后一个是体验优化，优先级低一些。"

## 二、被问"你做过什么优化"时

用已修复的坑，按"发现问题 → 定位 → 解决 → 效果"讲：

> "我做了一轮异步化改造：先用 ast 扫描发现 80 个端点是'假异步'（async def 但无 await），改成同步 def 让 FastAPI 丢线程池；然后把子 Agent 的同步工具调用改成 `asyncio.to_thread` 丢线程池，这样 `gather` 派发的 6 个域才真正并行；顺带把两套重复的 LLM 缓存合并成了一个统一工厂。"

## 三、核心原则

1. **主动承认 > 被拆穿**：主动说"我知道这里有问题"，比被问出来强一百倍
2. **承认 + 方案 = 能力**：只说问题显得菜，说问题 + 说方案显得懂
3. **区分"改不了"和"没改"**：
   - "SQLite 只有同步 API" → 改不了（讲清楚为什么）
   - "多模型配置没有加密存储" → 没改，优先级低（单机自用场景）
   - "流式" → **已做了**，别再当"没做"讲（讲了会被追问，然后发现你说的是旧状态）
4. **讲"什么时候不该优化"**：能说出"单用户场景换 MySQL 是过度设计"，比知道 10 种优化手段更难得

## 四、三个杀手锏细节（讲了就能证明代码是你读过的）

1. **"主流程没用 StateGraph"**：主流程是线性三段，StateGraph 的 `operator.add` 会跨轮累积消息；只有子 Agent 内部循环才用状态图
2. **"反问没用 interrupt()"**：`interrupt` 适合强阻塞的人工审批，补参数场景用它会很别扭；改成"反问即正常结束 + 消息追加恢复"，换来单一状态源、零成本放弃
3. **"经验幂等的占位 0"**：写入时先填 0 再回写真值，是为了让"这条是否发过经验"变得可判断
