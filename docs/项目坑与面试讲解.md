# 第一部分：已修复的坑（讲"我发现并修了"）

## 坑 1：80 个"假异步"端点（async def 但没有 await）

**现象**

项目里有 **80 个路由端点** 长这样：

```python
@router.get("/api/users/profile")
async def user_profile(user=Depends(get_current_user)):
    total_exp = get_total_exp_from_dimensions(user_id)   # 同步 DB 调用（PyMySQL）
    today_row = get_user_stats(user_id, today)           # 同步 DB 调用（PyMySQL）
    return {...}
```

写了 `async def`，但函数体里**一个 `await` 都没有**——套了个异步的壳，里面全是同步查库。

**根因**

可能是"看到 FastAPI 例子都写 async，就跟着写了"，或者"以为 async 就一定更快"。实际上：
- `async def` 端点在事件循环里跑，同步的数据库调用（PyMySQL）会**卡住整个事件循环**
- 而 `def`（同步）端点 FastAPI 会自动丢线程池，反而**不会**阻塞事件循环

也就是说，这些端点写成 `async` 比写成同步**更糟**。

**处理**（2026-09-08）

用 `ast` 模块精确扫描（判断函数体有无 `Await` 节点 + 有无 `@router` 装饰器），批量把 80 个端点的 `async def` 改成 `def`。

```python
# 保留 15 个真正有 await 的（调 AI / WebSocket），其余 80 个删掉 async
```

**面试话术**

> "我用 ast 扫了一遍，发现有 80 个端点写着 `async def` 但函数体里根本没有 `await`，是'假异步'——它们套了个异步的壳，里面却是同步 DB 调用，反而会阻塞事件循环。我把纯 CRUD 的端点改成了同步 `def`，FastAPI 会自动把它们丢到线程池，事件循环就空出来了。"

**加分点**：能说出判断标准——"函数体里有没有 await，有就保持 async，没有就改 def"。

## 坑 2：同步 DB 调用阻塞事件循环（子 Agent 工具调用）

**现象**

协调 Agent 的 6 个子 Agent 用 `asyncio.gather` **并行**派发，但实际是**串行**执行的。

**根因**

`agents/base.py` 里执行工具是同步调用：

```python
tool_result = tool_fn.invoke(args)   # 同步！工具内部是同步 DB 调用
```

`gather` 确实并发启动了 6 个协程，但每个子 Agent 执行工具时会**卡住整个事件循环**——就像服务员在等菜时把身体横在厨房门口，其他客人全进不来。

**关键点**：要区分两层——
- **工具函数本身**是同步的（24 个工具全是 `def`，内部同步 DB 调用）—— 这个改不了
- **调用工具的方式**是同步的 —— 这个必须改

**处理**（2026-09-08）

```python
import asyncio

# 工具是同步的（内部是同步 DB 调用），丢线程池避免阻塞事件循环
tool_result = await asyncio.to_thread(tool_fn.invoke, args)
```

**为什么不用"工具改 async"**：那要换异步数据库驱动（`aiomysql`）并改 24 个工具函数，收益不匹配成本。丢线程池一行解决。

**面试话术**

> "子 Agent 派发看起来是 `asyncio.gather` 并行的，但因为工具调用是同步的，实际是串行——事件循环被卡住了。我改成 `await asyncio.to_thread(...)` 丢线程池，6 个域才真正并行起来。这里有个容易混的点：工具函数本身还是同步的（PyMySQL 只有同步 API，改不了），我改的是**调用方式**——把同步操作挪出事件循环。"

**加分点**：能讲清"操作本身同步"和"调用方式同步"的区别——这是很多人答不上来的。

## 坑 3：两套重复的 LLM 实例缓存

**现象**

项目里有两个地方在缓存 `ChatOpenAI` 实例：

| | 缓存 1 | 缓存 2 |
|---|---|---|
| 位置 | `coordinator/llm.py` | `ai_client.py` |
| 缓存结构 | dict（多实例） | 单例（只存一个） |
| 缓存 key | 四元组 | 五元组（多了 max_tokens） |
| max_tokens | 固定 9192 | 默认 4096 |
| timeout | 120s | 300s |

**根因**

两个模块各自演化，都实现了"从 `model_configs` 表读配置 → env 兜底 → 缓存实例"这套逻辑，但参数细节岔开了。典型的代码重复。

**处理**（2026-09-09）

抽成统一工厂 `services/llm.py`：

```python
def get_llm(temperature=0.3, max_tokens=9192, timeout=120.0, user_id=None) -> ChatOpenAI:
    cfg = get_active_config(user_id or 1, "llm")   # 用户配置优先，env 兜底
    ...
    cache_key = (temperature, max_tokens, timeout, model, base_url, api_key)
    if cache_key not in _llm_cache:
        _llm_cache[cache_key] = ChatOpenAI(...)
    return _llm_cache[cache_key]
```

删除 `coordinator/llm.py`，6 个调用方改成 `from services.llm import get_llm`。

**关键设计**：`timeout` 必须进缓存 key——协调器要 120s、纯文本要 300s，这是两个不同的实例，不能共享。

**面试话术**

> "我发现项目里有两套 LLM 缓存逻辑，一套在协调器、一套在纯文本客户端，各自维护、参数还不一样。我抽了一个统一的 LLM 工厂，缓存 key 用六元组（含 timeout，因为不同场景超时需求不同），合并后所有 AI 调用走同一个入口，加参数只改一处。"

## 坑 4：AI 模型配置分裂（行动 AI 用 env，协调器用数据库）

**现象**

- 行动板块的"记录行动 AI"用的是 `.env` 里的模型（`qwen3.7-flash`）
- 协调 Agent 用的是数据库 `model_configs` 表里的模型（`qwen3.7-plus`）

同一个系统里两个 AI 用不同模型，而且改数据库配置对行动 AI 无效。

**根因**

行动 AI 是旧链路遗留，直接用 `httpx` 裸写 HTTP 请求：

```python
from config import AI_BASE_URL, AI_API_KEY, AI_MODEL   # 直接读 env
resp = await client.post(f"{AI_BASE_URL}/chat/completions", ...)
```

绕过了 `model_configs` 表，也就绕过了"用户可配置 + 热切换"的能力。

**处理**（2026-09-09）

去掉裸 httpx，改用 LangChain 统一入口：

```python
from services.llm import get_llm

llm = get_llm(temperature=0.7, user_id=user_id)
llm_with_tools = llm.bind(tools=ACTION_PARSE_TOOLS, tool_choice="auto")
resp = await llm_with_tools.ainvoke(msgs)
```

连带把表达训练 AI 的 3 处 httpx 也一起改了。

**两个技术细节**（面试能讲就很加分）：
1. 用 `llm.bind(tools=...)` 而非 `bind_tools`——因为项目里的 tools 是 OpenAI function 格式的 dict，`bind` 底层原样传参最保险
2. LangChain 返回的 `resp.tool_calls` 结构是 `[{"name", "args", "id"}]`（`args` 已是 dict），和 httpx 直连的 `[{"id", "function": {"name", "arguments"}}]` 不同，返回值解析要对应调整

**面试话术**

> "行动板块的 AI 走的是旧链路，用 httpx 裸写 HTTP 直连 env 配置，和协调 Agent 用的数据库配置是两套，导致同一个系统里模型不一致、也没法热切换。我把它改成走统一的 LLM 工厂，用 LangChain 的 `bind` 传工具，现在所有 AI（除语音）统一是'用户配置优先、env 兜底'。"

# 第二部分：已修复的坑（讲"怎么修的"）

## 坑 6：`?user_id=` 当身份（✅ 2026-09-13 已修复）

**当时的现象**

`routers/deps.py` 的 `get_current_user` 长这样：

```python
async def get_current_user(user_id: int = Query(...)):
    user = get_user(user_id)            # 只查"存不存在"
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
```

**这不是鉴权，只是存在性校验** —— `user_id` 来自 URL query，客户端随便改一下就能读别人的数据。
当时 94 个端点里 76 个挂着这个（形同虚设的）依赖，**16 个连它都没有**。

**难在哪**：不是加个装饰器就完事 —— 前端所有请求都要开始带凭证、后端要有签发与续期、
MCP 和脚本这两类非浏览器客户端也要有通道。

**怎么修的**

1. **凭证解析链收敛在一处**（`routers/deps.py`）：
   ① `SELF_GROW_TRUSTED_MODE`（本地演示）② `Authorization: Bearer <jwt>`
   ③ `X-API-Key`（MCP / 脚本）④ 都没有 → 401 + `WWW-Authenticate`
2. **JWT 双令牌**：Access 2h + Refresh 30d；Refresh **用掉即轮换**（重放可检测）、
   只存 SHA-256、可单条撤销；改密码时 `token_version + 1` 让旧 token 全部失效
3. **API Key**：同样只存 SHA-256，用户中心一键撤销 —— 覆盖不是浏览器的客户端
4. **前端零改动接入**：`frontend/js/auth.js` 包装 `window.fetch` 自动带 `Authorization`
   并处理 401 自动续期，于是 **52 处 `fetch(...?user_id=)` 一行没改**
5. **RBAC**：`require_admin` 挂到技能树写操作与 AI 端点（AI 能改树，按写操作管）

**面试话术**

> "早期 `get_current_user` 只校验 URL 上的 user_id 存不存在，可以被任意伪造 —— 这是我最清楚的一个缺陷。
> 后来补上了：核心是把**凭证解析收敛到一个依赖**里，这样 73 个业务端点一行没改就完成了鉴权升级。
> 令牌设计上做了 Refresh 轮换（用掉即失效、重放能被检测）和 `token_version` 撤销；
> 因为还有 MCP 和脚本两类客户端，额外做了可撤销的 API Key 通道。
> 这个改动最难的不是密码学，是**不破坏已有的 52 处前端请求**。"

**为什么这题讲起来加分**：不是"我做了 JWT"，而是能说清「**先收敛入口，再升级全局**」这个顺序 ——
如果一上来就逐个改端点，改动面会大到不敢做。

## 坑 7：经验结算的幂等在并发下有竞态窗口

**现象**

经验结算用"占位 0 → 回写真值"两级幂等：

```python
# 1. 创建记录时 exp_earned 先占位 0
action_id = create_action_log(..., exp_earned=0, request_id=request_id, conn=conn)

# 2. 检查是否发过经验
existing = conn.execute("SELECT exp_earned FROM action_logs WHERE id = ?", (action_id,)).fetchone()
if existing and existing["exp_earned"] > 0:
    return {"exp_earned": 0, "message": "该行动已记录过，不重复奖励经验值"}

# 3. 发经验
service_result = award_exp_and_recalc(..., conn=conn)

# 4. 回写真值
conn.execute("UPDATE action_logs SET exp_earned = ? WHERE id = ?", (dimension_exp, action_id))
conn.commit()
```

**为什么先写 0**：如果写入时就带真实经验值，就无法区分"这条是新创建的"还是"已经发过经验的"了。占位 0 后，回查 `exp_earned > 0` 才知道发过。

**竞态在哪**

两个并发请求同时 `create` 出同一条记录、同时查到 `exp_earned = 0`，就会**各发一次经验**。

**为什么当前没暴露**：经验结算由单用户串行触发，写路径很短，撞上窗口的概率极低。

**改进方案**：给 `request_id` 加 `UNIQUE` 约束 + `INSERT OR IGNORE`，或引入分布式锁。

**面试话术**

> "经验结算我做了两级幂等：request_id 去重 + 占位 0 回写真值。但它有个竞态窗口——并发两个请求可能同时查到 0 而重复发。目前单用户场景不会触发，要做多用户就得给 request_id 加唯一约束或者上锁。"

## 坑 8：编排状态和会话历史都在内存

**现象**

两个东西都在进程内存里：

| 东西 | 位置 | 问题 |
|------|------|------|
| 编排状态 `_thread_store` | `routers/coordinator.py` | TTL 30 分钟，重启丢失，多实例不共享 |
| 会话历史 checkpointer | `MemorySaver` | 重启后所有子图会话历史全丢 |

**后果**

- 重启容器 → 所有进行中的多轮对话丢失
- 多实例部署 → 请求打到不同实例，会话对不上

**改进方案**

- 编排状态迁 Redis
- checkpointer 换持久化实现（Postgres / Redis），把会话从进程内存里挪出去

**面试话术**

> "协调 Agent 的编排状态和 LangGraph 的会话历史都在内存里，重启就丢、多实例也不共享。单实例部署没问题，要横向扩展就得把编排状态迁 Redis、checkpointer 换成数据库版。"

## 坑 9：APScheduler 多实例会重复执行

**现象**

每日 03:00 的定时任务（归档 + 结算）用 `APScheduler`，它是**进程内**调度。

如果 `docker compose up --scale=2` 起两个实例，同一个 job 会**执行两次**——用户经验重复结算。

**改进方案**：把调度独立成单独进程，或加分布式锁（Redis / 数据库 job 执行记录做幂等）。

**面试话术**

> "定时任务用的是 APScheduler，进程内调度。单实例没问题，多实例部署会导致同一个任务执行两次——那时候得把调度拆成独立进程或者加分布式锁。"

## 坑 10：MySQL 的锁等待默认是**一年**，能把整站挂死

**现象（真发生过）**

一次写入失败（`skill_trees.data` 是 `varchar(255)`，真实树 JSON 写进去报 **1406 Data too long**），
异常路径跳过了 `commit()` / `close()` → 连接没归还 → **事务挂着不结束、行锁不释放**。
之后对该行任何 `DELETE` 都是 `Lock wait timeout`，而 **`SELECT` 完全正常**
（InnoDB 是 MVCC 快照读，不加锁）——所以特别难查。

**关键数字**：MySQL 的 `lock_wait_timeout` 默认 **31536000 秒 = 一年**。
配合 DBUtils `PooledDB(blocking=True)`（池满时**无限等待，也没有超时**），
一旦有锁竞争就是「接口不报错、也不返回、整站挂死」——而且**没有任何日志**。

**已做的处理**

| 位置 | 做法 |
|---|---|
| `db/backend.py::_INIT_COMMAND` | 连接层 `SET lock_wait_timeout=30` / `innodb_lock_wait_timeout=30` |
| 所有写函数 | 统一 `try / except rollback / finally close()`，失败路径也要归还连接 |
| 连接代理 | `MysqlConn.__del__` 兜底归还（防"忘了 close"静默耗尽连接池） |
| 连接池大小 | 20 且不往下调（子 Agent 用 `asyncio.gather` + `to_thread`，池满就整站卡死） |

**判据（怎么确认是这个问题）**

```sql
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx;
```

出现 `trx_query` 是 `(idle)` 但 `trx_started` 很久之前的事务 = **有人借了连接没还**。
`KILL <trx_mysql_thread_id>` 可以救急（需要 root）。

**同一次事故的另一半**：那条 1406 之所以能藏很久，是因为 `varchar(255)` 在 SQLite 下**完全无害**
（SQLite 无类型，几 KB JSON 照存）。迁到 MySQL 后列宽才变成硬限制 ——
而"建一条空记录"的冒烟**永远测不出来**（空对象存得进去）。
现在 `db/init.py::migrate_json_column_widths()` 会读 `information_schema` 自动加宽，
失败 `log.error` 不吞。

**面试话术**

> "我遇到过最阴的一个 bug：一次写入失败（列宽不够报 1406），异常路径跳过了 commit/close，
> 事务和行锁就留在池里。之后那行数据怎么删都是 Lock wait timeout，但 SELECT 完全正常 ——
> 因为 InnoDB 是快照读。根因是 MySQL 的 lock_wait_timeout 默认是**一年**，
> 这段代码里没有任何超时。我改成连接层设 30 秒 + 写操作统一 try/rollback/finally，
> 并留了一条排查判据：查 `information_schema.innodb_trx` 里 `trx_query` 为 `(idle)` 的长期事务。"

**加分点**：能说出"什么时候不该优化"同样难得 —— 单用户、单实例的场景，
分库分表 / 消息队列都是过度设计；但**连接池大小和锁超时不属于"优化"，是正确性**。

# 第三部分：还在的欠账（讲"下一步会做"）

> 这一节原来是"SSE 未实装 / 写操作没确认 / 工具参数没校验"三条 ——
> **它们都已经做完了**，记录在下面「已还清」里。下面是**当前**还在的欠账。

## 欠账 1：会话与编排状态都在内存里

- LangGraph 的 checkpointer 是 `MemorySaver`（进程内存）→ 后端一重启，所有 AI 会话丢失
- 协调 Agent 的编排状态存在内存 dict（`_thread_store`，TTL 30min）→ 重启即失、多实例不通用
- 副作用：技能树 AI 的对话记录只能由**前端**按树持久化（localStorage）—— 换浏览器就没了

**改进**：换持久化 checkpointer（Postgres / Redis 实现），把 `_thread_store` 落库。
改动集中在 `checkpointer.py` 与 coordinator 的会话层。

## 欠账 2：定时任务在多实例下会重复执行

`AsyncIOScheduler` 是**进程内**调度器 —— 起两个 app 实例，每天的归档/结算/AI 资讯抓取就会各跑一份。

**改进**：加分布式锁（MySQL `GET_LOCK` 就够），或把调度拆成独立进程。
当前单实例部署不会触发，但**上多副本之前必须补**。

## 欠账 3：技能树 AI 没有资源级隔离

`require_admin` 只保证了"只有管理员能编辑"，但没有"这个管理员只能编辑**自己的**树"这一层。
`tree_id` 在库里是全局 UNIQUE，写路径会校验 `user_id` 归属，所以不会串数据；
但一个 admin 可以给另一个 admin 的树发 AI 指令（只要知道 tree_id）。

**改进**：把归属校验前移到 AI 端点的入口（现在是在 DB 层），或引入协作/共享模型。

## 已还清（曾经列在这里，别再说"没做"）

- ~~**SSE 流式输出未实装**~~ → **已全部实装**：8 个 AI 端点都是 `POST + SSE`，
  事件协议统一在 `services/sse.py`（`stage` / `token` / `error` / `done`）。
  协调 Agent 是真逐 token；技能树 AI 与表达训练只推**阶段进度**
  （它们的产物分别是工具参数和 JSON，逐字符传等于逼前端做增量 JSON 解析，是负优化）。
- ~~**写操作确认流未实现**~~ → **已实现**：`ask_user` 工具 + `needs_user` 标志 +
  resume 追加 HumanMessage；技能树的危险操作（级联删除）走 `pending_confirmation` 确认卡片。
  ⚠️ 反问**没有**用官方 `interrupt()` —— 多域并行下它无法表达"各域独立中断"。
- ~~**工具参数校验缺失**~~ → **已补**：`services/tool_args.py::coerce_json_args()`
  在工具执行前容错（模型常把数组/对象序列化成 JSON 字符串），
  `tools.py::_as_list()` 兜住嵌在数组里的字符串；非法值返回结构化错误交给 LLM 自愈。
  静态护栏：`tests/test_skill_tree_ai_tools.py::TestJsonStringArgs`。
- ~~**没有真正的身份认证**~~ → **已落地**：JWT 双令牌（Access 2h + Refresh 30d 轮换）+
  RBAC（`require_admin`）+ 可撤销 API Key（SHA-256 落库）+ 登录失败锁定。
  详见 [登录鉴权方案选型](./登录鉴权方案选型.md)。

# 第四部分：面试话术总纲

## 一、被问"项目有什么不足"时

**不要说**："没什么大问题" / "都挺好的"（不诚实，且显得没思考）
**也不要**：一次性倾倒 10 个问题（显得项目很烂）

**正确做法**：说 2-3 个，按"严重程度"排序，每个配方案。

推荐组合（**别再讲"没有身份认证/SSE 没做"了，那些都做完了，讲了会被追问穿**）：

> 1. **"会话状态都在内存里"**（架构债，最严重）+ 换持久化 checkpointer
> 2. **"定时任务在多实例下会重复执行"**（部署层面的真问题）+ 分布式锁 / 独立调度进程
> 3. **"技能树 AI 只有角色隔离、没有资源级隔离"**（权限粒度）+ 归属校验前移

说完补一句：

> "这些都是我知道并且有明确改进方案的 —— 第一条是架构层面，要在做多用户 SaaS 前补上；
> 第二条上多副本就必须补；第三条是权限粒度，优先级最低。"

## 二、被问"你做过什么优化"时

用已修复的坑，按"发现问题 → 定位 → 解决 → 效果"讲：

> "我做了一轮异步化改造：先用 ast 扫描发现 80 个端点是'假异步'（async def 但无 await），改成同步 def 让 FastAPI 丢线程池；然后把子 Agent 的同步工具调用改成 `asyncio.to_thread` 丢线程池，这样 `gather` 派发的 6 个域才真正并行；顺带把两套重复的 LLM 缓存合并成了一个统一工厂。"

## 三、核心原则

1. **主动承认 > 被拆穿**：主动说"我知道这里有问题"，比被问出来强一百倍
2. **承认 + 方案 = 能力**：只说问题显得菜，说问题 + 说方案显得懂
3. **区分"改不了"和"没改"**：
   - "PyMySQL 只有同步 API" → 改不了（讲清楚为什么）
   - "流式没做" → 优先级低，不是不会
4. **讲"什么时候不该优化"**：能说出"单用户单实例上分库分表/消息队列是过度设计"，比知道 10 种优化手段更难得

## 四、三个杀手锏细节（讲了就能证明代码是你读过的）

1. **"主流程没用 StateGraph"**：主流程是线性三段，StateGraph 的 `operator.add` 会跨轮累积消息；只有子 Agent 内部循环才用状态图
2. **"反问没用 interrupt()"**：`interrupt` 适合强阻塞的人工审批，补参数场景用它会很别扭；改成"反问即正常结束 + 消息追加恢复"，换来单一状态源、零成本放弃
3. **"经验幂等的占位 0"**：写入时先填 0 再回写真值，是为了让"这条是否发过经验"变得可判断
