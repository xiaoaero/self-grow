# 第一部分：设计模式是什么

## 1.1 从"重复代码"说起

先不讲任何理论，我们看一个真实的故事。

Self Grow 项目早期，后端有一个 `server.py` 文件（现在已经重构了），里面"记录行动 → 加经验 → 更新维度 → 重算等级 → 更新今日统计"这段流程，**重复出现了 5 次**。每次都是几乎一样的代码：

```python
# 早期 server.py 里的重复代码（伪代码，示意）
# 场景1：手动记录行动
new_id = create_action_log(...)
# 加经验、更新维度、重算等级、更新统计……（几十行）

# 场景2：AI 批量提交行动
new_id = create_action_log(...)
# 又是同样一套加经验、更新维度、重算等级、更新统计……（又是几十行）

# 场景3、4、5：任务完成、习惯结算、目标领取……
# 还是这一套……
```

这段代码有 5 份拷贝，意味着：

1. **改一处要改五处**——如果某天计分规则变了，得小心翼翼地在 5 个地方同步改，漏一处就出 bug。
2. **新手看不懂**——每份代码都纠缠在一起，读起来像一团乱麻。
3. **无法测试**——因为逻辑分散，没法单独验证"加经验"这一步对不对。

后来，项目把这段流程抽成了一个**门面函数**（见 §3.2 门面模式），放进了 `services/exp_service.py`，所有地方统一调用它。重复代码消失了。

**这就是设计模式要解决的核心问题**：不是"代码跑得对不对"，而是"代码改起来、读起来、扩展起来痛不痛苦"。

## 1.2 设计模式的定义（一句话）

> **设计模式（Design Pattern）**：是对软件开发中反复出现的、特定场景下的问题的**通用解决方案**，是前人踩坑总结出来的"套路"。

注意三个关键词：

- **反复出现**：不是一次性的奇技淫巧，而是成千上万个项目都遇到过的问题。
- **特定场景**：每个模式都有它的适用场景，用错了场景反而有害。
- **通用解决方案**：它是"思路"和"骨架"，不是可以直接复制粘贴的代码。同样一个"单例模式"，在 Python、Java、JavaScript 里的写法完全不同，但思路一样。

**大白话**：设计模式就像"菜谱"。你不需要每次做红烧肉都从"猪是什么"开始研究，直接照着前人验证过的菜谱做就行。但菜谱也不是死板的——你可以根据口味调整调料。

## 1.3 设计模式的三大分类

经典的设计模式（GoF，"四人帮"的缩写，指 1994 年《设计模式》一书的四位作者）共 23 种，分为三大类：

| 分类 | 解决什么问题 | 一句话记忆 | 本项目例子 |
|------|------------|-----------|-----------|
| **创建型** | **对象怎么"造"出来** | 怎么 new 对象更灵活 | 单例、工厂（`make_agent_node`） |
| **结构型** | **对象怎么"拼"在一起** | 类和类怎么组合 | 门面（`exp_service`）、适配器（`ai_client`） |
| **行为型** | **对象怎么"协作"和"分工"** | 对象之间怎么交互 | 策略（`calculate_exp`）、模板方法（`base.py`） |

**大白话**：

- 创建型 = 盖房子的"砖头怎么生产"。
- 结构型 = "砖头怎么砌成墙、墙怎么拼成房"。
- 行为型 = "房子里的人怎么分工配合"。

我们这篇文档不会把所有 23 种都讲一遍（很多在 Python/Web 项目里很少用到），而是挑**本项目真实用到、且面试常考**的模式，逐个讲透。

## 1.4 两个前置武器：抽象 与 多态

在讲具体模式之前，有两个概念必须先懂，否则后面全是天书。

### 武器一：抽象（Abstraction）

**抽象**就是"抓重点、忽略细节"。

```python
# 抽象前：每个维度单独写一套计分
def 算学习经验(时长):
    return 时长 // 20 * 10

def 算运动经验(时长):
    return 时长 // 15 * 3.75

def 算爱好经验(时长):
    return 时长 * 2 / 3
```

这三段代码"计分"这个动作是一样的，只是规则不同。抽象就是抽出"计分"这个共同点：

```python
# 抽象后：统一入口，内部再分派
def calculate_exp(category_id, duration, ...):
    # 根据维度调用对应的计分函数
    if category_id == "study":
        return _calc_study(duration, ...)
    elif category_id == "health":
        return _calc_health(duration, ...)
    # ...
```

这样调用方只需要记住"`calculate_exp` 能计分"这一件事，不用管内部有 8 个维度、几十种规则。

### 武器二：多态（Polymorphism）

**多态**就是"同一个调用，对不同对象产生不同行为"。

```python
# 多态：同样调用 .invoke()，但不同的工具函数做不同的事
tool_fn.invoke(args)   # 如果是 record_action，就记录行动
tool_fn.invoke(args)   # 如果是 create_goal，就创建目标
```

在本项目里，`base.py` 的 `make_agent_node` 工厂返回的 agent 节点，对 6 个域（action/query/goal/task/habit/reward）都用**同一套循环**去跑，但每个域传入的工具不同、prompt 不同，最终行为就完全不同。这就是多态 + 抽象的力量。

# 第二部分：创建型模式

创建型模式回答一个问题：**对象怎么"造"出来**。造对象本身不是难事，`ChatOpenAI(...)` 谁都会写；难的是——**什么时候造、造几个、造哪种、谁来造**。

## 2.1 单例模式（Singleton）

### 是什么

**单例模式**：保证一个类**在整个程序运行期间只有一个实例**，并提供全局访问入口。

### 为什么需要它

有些对象天生"只能有一个"，或者"多建一个就是浪费"：

- **数据库连接**：连接池只需要一份，谁要用谁拿。
- **配置对象**：配置文件读一次就够，没必要反复读。
- **日志器**：所有模块往同一个日志器写。

**大白话**：单例就像"公司的公章"。全公司只有一个公章，谁要盖章都来找这个公章，而不是每人自己刻一个——自己刻的话，盖出来的章还不一致，出了问题也没法追溯。

### 项目里的真实代码

项目里有两处教科书级的单例。

**例子 1：全局 Checkpointer（`services/coordinator/checkpointer.py`）**

```python
from langgraph.checkpoint.memory import MemorySaver

_checkpointer = MemorySaver()

def get_checkpointer() -> MemorySaver:
    """获取全局 checkpointer 单例"""
    return _checkpointer
```

这里 `_checkpointer` 在模块加载时创建一次，之后所有主图、子图都通过 `get_checkpointer()` 拿到**同一个**实例。为什么要单例？因为 checkpointer 负责持久化对话历史，如果每个子图各自 new 一个，历史就"各记各的"，用户回答反问后就找不到之前的上下文了。

**例子 2：AI 客户端（`services/ai_client.py`）**

```python
# 模块级单例：复用 TCP/TLS 连接，避免每次调用重建
_llm_instance: ChatOpenAI | None = None
_llm_cache_key: tuple | None = None

def _get_llm(temperature=0.7, max_tokens=DEFAULT_MAX_TOKENS, user_id=None):
    global _llm_instance, _llm_cache_key
    cfg = get_active_config(user_id or 1, "llm")
    model = (cfg or {}).get("model") or AI_MODEL
    api_key = (cfg or {}).get("api_key") or AI_API_KEY
    base_url = (cfg or {}).get("base_url") or AI_BASE_URL

    cache_key = (temperature, max_tokens, model, base_url, api_key)
    if _llm_instance is None or _llm_cache_key != cache_key:
        _llm_instance = ChatOpenAI(
            model=model, api_key=api_key, base_url=base_url,
            temperature=temperature, max_tokens=max_tokens, ...
        )
        _llm_cache_key = cache_key
    return _llm_instance
```

为什么要单例？代码注释说得很清楚：**复用 TCP/TLS 连接，避免每次调用重建**。每次创建 `ChatOpenAI` 都要重新做 DNS 解析、TLS 握手，几十毫秒就没了。缓存住实例，连接池就能复用。

### 单例的"升级版"：带缓存键的单例

注意上面 `_llm_instance` 这个单例有一个巧妙之处——它**不是死板地永远只建一次**，而是带了一个 `cache_key`：

```python
if _llm_instance is None or _llm_cache_key != cache_key:
    _llm_instance = ChatOpenAI(...)   # 重建
    _llm_cache_key = cache_key
```

当 `temperature`、`model`、`base_url`、`api_key` 这四个参数之一变了，`cache_key` 就变了，就会**重建**实例。这实现了项目的一个需求——**切换模型即时生效**（在 `model_configs` 表里改启用模型，下次调用自动用新模型）。

**大白话**：这不是"一个公章用到死"，而是"公章上刻的字变了，就换一个新公章"。这比死板的单例更灵活。

### 什么时候用 / 什么时候不用

**✅ 适合**：
- 创建成本高（连接池、模型实例），需要复用。
- 状态需要全局共享（checkpointer 的对话历史）。

**❌ 慎用**：
- 别把什么都做成单例——单例本质是**全局可变状态**，会导致代码耦合、难以测试。
- 本项目早期如果没做缓存键，而是死板单例，就没法支持"多模型热切换"了。

## 2.2 工厂模式（Factory）

### 是什么

**工厂模式**：不直接 `new` 对象，而是通过一个"工厂函数/类"来创建对象，把"创建对象的逻辑"和"使用对象的逻辑"分离。

### 为什么需要它

想象你要创建 6 个域的 AI 子 agent，每个 agent 的结构很像（都是"LLM + 工具 + 反问循环"），但工具和提示词不同。如果不用工厂，你会在主流程里写 6 段几乎一样的"创建代码"：

```python
# 不用工厂：6 段重复的创建代码
agent1 = StateGraph(ActionState)
agent1.add_node("agent", make_node([record_action], "action", ...))
agent1.set_entry_point("agent")
agent1.add_edge("agent", END)
compiled1 = agent1.compile(checkpointer=...)

agent2 = StateGraph(GoalState)
agent2.add_node("agent", make_node([create_goal, ...], "goal", ...))
# ... 又是几乎一样的一套
```

工厂模式就是把这套"创建流程"抽成一个函数，你只要告诉它"参数不同"就行。

### 项目里的真实代码

**例子 1：`make_agent_node` 工厂函数（`services/coordinator/agents/base.py`）**

```python
def make_agent_node(tools, domain: str, domain_label: str, system_prompt: str):
    """构建 agent 节点函数（工厂）

    Args:
        tools: 业务工具列表
        domain: 域标识（action/query/goal/task/habit/reward）
        domain_label: 前端显示标签（如 "🏃 行动记录"）
        system_prompt: 系统 prompt 文本

    Returns:
        agent_node(state) async 函数
    """
    all_tools = list(tools) + [ask_user]   # 统一接入反问工具
    tools_by_name = {t.name: t for t in all_tools}

    async def agent_node(state):
        # ... 统一的 ReAct 循环（见 §4.2 模板方法）
        ...

    return agent_node
```

看这个函数——它**自己不干活**，它**造一个"会干活的函数"**并返回。这就是工厂的核心特征：**返回值是一个对象（这里是函数）**。

**例子 2：`build_subgraph` 工厂 + 各域"包装函数"**

`base.py` 里还有一个更高级的工厂：

```python
def build_subgraph(state_class, tools, domain, domain_label, system_prompt):
    """构建子图（单节点 StateGraph + 全局 checkpointer）"""
    from langgraph.graph import StateGraph, END
    from services.coordinator.checkpointer import get_checkpointer

    graph = StateGraph(state_class)
    graph.add_node("agent", make_agent_node(tools, domain, domain_label, system_prompt))
    graph.set_entry_point("agent")
    graph.add_edge("agent", END)
    return graph.compile(checkpointer=get_checkpointer())
```

而每个域的文件（比如 `agents/action_agent.py`）又提供了一层"极简的命名工厂"：

```python
def create_action_agent():
    """创建行动记录子图"""
    return build_subgraph(
        state_class=ActionSubgraphState,
        tools=TOOLS,
        domain="action",
        domain_label="🏃 行动记录",
        system_prompt=ACTION_AGENT_SYSTEM_PROMPT,
    )
```

三层工厂分工清晰：

1. `make_agent_node` 造"节点函数"。
2. `build_subgraph` 造"编译好的子图"。
3. `create_action_agent` 造"特定域的子图"（把参数填好）。

**大白话**：这就像一个工厂流水线——`make_agent_node` 是"总装线"，`build_subgraph` 是"打包车间"，`create_action_agent` 是"下单入口"。你要一个 action 子图，不用自己懂流水线，喊一声 `create_action_agent()` 就行。

### 工厂的"注册表"变体

`services/coordinator/agents/__init__.py` 里还有一个非常漂亮的写法——**字典注册表**：

```python
# 域名 → 子图构建函数 映射
SUBGRAPH_BUILDERS = {
    "action": create_action_agent,
    "query": create_query_agent,
    "goal": create_goal_agent,
    "task": create_task_agent,
    "habit": create_habit_agent,
    "reward": create_reward_agent,
}
```

主编排 `graph.py` 里派发子图时，直接用域名查表：

```python
builder = SUBGRAPH_BUILDERS.get(domain)
if not builder:
    log.warning(f"未知域：{domain}")
    return [], []
agent = builder()   # 调用对应的 create_xxx_agent()
```

**这个设计的妙处**：将来要加第 7 个域（比如"笔记域"），只需要：

1. 写一个 `note_agent.py`，里面定义 `create_note_agent()`。
2. 在 `SUBGRAPH_BUILDERS` 里加一行 `"note": create_note_agent`。

主流程 `graph.py` **一行都不用改**。这就是工厂 + 注册表带来的"开闭原则"（见 §5.2）。

### 什么时候用 / 什么时候不用

**✅ 适合**：
- 创建逻辑复杂、需要复用（本项目创建子图）。
- 有多个相似对象需要创建，未来可能增加新类型（本项目 6 个域）。

**❌ 慎用**：
- 如果只有一种对象、创建逻辑就一行，直接 `ChatOpenAI(...)` 就行，别为了"看起来高级"硬套工厂。

## 2.3 建造者模式（Builder）

### 是什么

**建造者模式**：当一个对象的构建过程**很复杂、分很多步**时，把"构建步骤"逐步拆分、逐步填充，最后产出对象。

### 为什么需要它

有些对象不是一句 `new` 就能造好的，而是要"先加节点、再设入口、再连边、最后编译"这样一步步来。

### 项目里的真实代码

`build_subgraph` 其实同时体现了**建造者**的思想：

```python
graph = StateGraph(state_class)          # 第 1 步：创建空的图
graph.add_node("agent", ...)             # 第 2 步：往图里加节点
graph.set_entry_point("agent")           # 第 3 步：设置入口
graph.add_edge("agent", END)             # 第 4 步：连接边
return graph.compile(checkpointer=...)   # 第 5 步：编译产出最终对象
```

每一步都是"往一个半成品上添东西"，最后 `compile()` 一次性产出"成品"。这正是建造者的精髓：**把复杂的构造过程分解成清晰的、可读的步骤**。

另一个体现建造者思想的地方是**消息列表的逐步构建**（`base.py` 的 `make_agent_node` 内部）：

```python
full = [SystemMessage(content=system_prompt)] + messages   # 先放系统提示 + 历史

for _ in range(MAX_ITERS):
    response = await llm_with_tools.ainvoke(full)
    if response.tool_calls:
        new_messages = [response]
        for tc in response.tool_calls:
            # ... 逐步往 new_messages 里 append 工具结果
            new_messages.append(ToolMessage(...))
        full = full + new_messages    # 拼回上下文，继续下一轮
```

这里 `full` 这个列表就是"被逐步建造的对象"：先放系统提示，再一轮轮往里追加"AI 回复 + 工具结果"，直到对话结束。

### 什么时候用

**✅ 适合**：对象构造分多步、每步可独立配置、步骤顺序有意义（StateGraph、SQL 查询拼接、HTML 生成）。
**❌ 慎用**：对象构造就 1~2 个参数时，建造者反而啰嗦。

# 第三部分：结构型模式

结构型模式回答一个问题：**对象之间怎么"拼"起来**。核心是"组合"和"解耦"。

## 3.1 适配器模式（Adapter）

### 是什么

**适配器模式**：把一个接口"翻译"成另一个接口，让原本不兼容的东西能一起工作。

**大白话**：出国旅游带的"转换插头"。中国的插头是两脚扁的，国外的插座是三脚圆的——你不需要改插头，也不需要改插座，加一个"转换插头"就行。适配器就是这个"转换插头"。

### 项目里的真实代码

**例子 1：`ai_client.py` 把 LangChain 的接口适配成项目自己的简单接口**

项目里调用 AI 的地方很多（习惯分析、行动解析、技能树），但大家不想记住 `ChatOpenAI` 那套复杂的 API（要建实例、组装消息、处理流式……）。于是 `ai_client.py` 提供了一个"傻瓜接口"：

```python
async def call_ai_text(system_prompt: str, user_message: str,
                       temperature=0.7, max_tokens=DEFAULT_MAX_TOKENS,
                       user_id=None) -> str:
    """调用 AI 模型，返回纯文本回复"""
    llm = _get_llm(temperature=temperature, max_tokens=max_tokens, user_id=user_id)
    messages = [
        SystemMessage(content=system_prompt),
        HumanMessage(content=user_message),
    ]
    response = await llm.ainvoke(messages)
    return response.content.strip()
```

调用方只需要：

```python
text = await call_ai_text("你是助手", "帮我分析一下")
```

至于背后是 LangChain 还是原生 httpx、怎么组装消息、怎么处理异常，调用方**完全不关心**。这就是适配器：**把复杂的底层 API，翻译成简单易用的上层 API**。

**例子 2：`mcp_server.py` 把业务函数适配成 MCP 协议工具**

MCP（Model Context Protocol）是一种让 AI 客户端（Claude Desktop、Cursor 等）调用工具的标准协议。项目的业务函数本来只能被自己的 FastAPI 调用，现在通过 `@mcp.tool()` 装饰器"适配"成了 MCP 工具：

```python
@mcp.tool()
def record_action(category: CategoryId, detail: str, duration: int,
                  start_time: str, sub_type: Optional[SubType] = None) -> dict:
    """记录一条个人行动并自动结算经验值"""
    return create_action_and_award_exp(
        user_id=DEFAULT_USER_ID, category=category, detail=detail,
        duration=duration, start_time=start_time, sub_type=sub_type,
    )
```

注意：底层的业务逻辑 `create_action_and_award_exp` **一行没改**，只是外面"包了一层"适配成 MCP 工具。同一份业务逻辑，既能服务 FastAPI，又能服务 MCP 客户端——这就是适配器带来的"一处实现，多处复用"。

### 什么时候用

**✅ 适合**：
- 想把第三方库的复杂接口简化成自己的简单接口。
- 想复用现有业务逻辑去对接不同的协议/框架（本项目 FastAPI + MCP 双接口）。

**❌ 慎用**：不要过度包装——如果底层接口本来就好用，直接用它，别为了"统一"硬加一层。

---

## 3.2 门面模式（Facade）

### 是什么

**门面模式**：对外提供一个**统一、简单的入口**，隐藏内部一堆复杂的子系统的调用细节。

**大白话**：门面就像"酒店前台"。你想住店，不用自己去联系保洁、厨房、安保、财务——所有需求跟**前台**一个人说就行，前台在背后协调各部门。门面就是那个"前台"。

### 项目里的真实代码

项目里最典型的门面就是 `services/exp_service.py`。

**门面一：`award_exp_and_recalc`**（核心经验结算流程）

```python

    2. 从 8 维 SUM 总经验，重算等级
    3. 更新用户表
    4. 更新今日统计
    5. 返回 exp_result + today_stats
    """

    #     level_from_total_exp / update_user_exp / upsert_user_stats 等一堆函数
```

**门面二：`create_action_and_award_exp`**（更上层的一站式入口）

```python
def create_action_and_award_exp(user_id, category, duration, start_time, ...) -> dict:
    """原子事务：创建行动记录 + 计算并奖励经验值"""
    # 内部：create_action_log（先占位 exp=0）→ 幂等检查 →
    #       award_exp_and_recalc（结算经验）→ 回写真值 → commit
```

现在，路由层（`routers/actions.py`）只要：

```python

```

一行就完成了原本几十行的流程。而 MCP 层（`mcp_server.py`）也复用同一个门面：

```python

```

**门面的价值**，项目注释里一句话点透了：

> 消除 server.py 中该模式重复 5 次的问题。

### 门面 vs 适配器，别搞混

这是新手最容易混的两个模式：

| | 门面（Facade） | 适配器（Adapter） |
|---|---|---|
| 目的 | **简化**调用（多个子系统 → 一个入口） | **转换**接口（A 接口 → B 接口） |
| 重点 | 隐藏复杂度 | 让不兼容的兼容 |
| 大白话 | 酒店前台（协调各部门） | 转换插头（翻译插头形状） |

**项目对照**：`award_exp_and_recalc` 是**门面**（把 5 个 db 操作合并成一个入口）；`call_ai_text` 是**适配器**（把 LangChain 的接口翻译成简单接口）。

### 什么时候用

**✅ 适合**：一组复杂的操作经常被一起调用（本项目经验结算）。
**❌ 慎用**：门面太多层会变成"俄罗斯套娃"，调用链太深反而难懂。

## 3.3 装饰器模式（Decorator）

### 是什么

**装饰器模式**：不修改原函数/对象的代码，动态地给它"加上"新功能。

**大白话**：就像给手机"套壳"。手机本身没变，套上壳就多了防摔、支架、磁吸等功能。壳可以随时摘掉，手机还是那个手机。

### Python 里的特殊之处

Python 有**语法层面的装饰器**（`@` 符号），这是 Python 的语法糖，但它背后的思想和 GoF 装饰器模式一脉相承——**不侵入原函数，动态增强功能**。

### 项目里的真实代码

FastAPI 的路由装饰器是项目里用得最多的"装饰器"：

```python
@router.post("/api/actions")
async def create_action(req: CreateActionRequest, user=Depends(get_current_user)):
    """提交行动记录"""
    ...
```

`@router.post("/api/actions")` 装饰器做了很多"额外的事"：注册路由路径、指定 HTTP 方法、绑定请求体解析、生成 OpenAPI 文档……但你写 `create_action` 函数时，只需要专注业务逻辑，这些"额外的事"由装饰器自动完成。

同理，MCP 和 LangChain 的工具装饰器：

```python
@tool
def record_action(category, detail, duration, ...):
    """记录用户的行动并计算经验值"""
    ...
```

```python
@mcp.tool()
def create_goal(title, intro, ...):
    """创建新目标及里程碑"""
    ...
```

`@tool` 会把一个普通函数包装成"能被 LLM 识别并调用"的工具（自动生成参数 schema、让 LLM 知道何时调用它）。

### 装饰器的"叠加"

装饰器可以叠着用，像洋葱一样一层套一层：

```python
@router.get("/api/actions")        # 外层：注册路由
async def list_actions(
    user=Depends(get_current_user),  # 依赖注入（见 §6.1）
    page: int = 1, page_size: int = 20, ...
):
    ...
```

这里至少叠了两种增强：`@router.get`（路由注册）和 `Depends(get_current_user)`（用户校验）。原函数只关心"查数据并返回"。

### 什么时候用

**✅ 适合**：日志、鉴权、缓存、性能统计等"横切关注点"——这些功能跟业务无关，但很多地方都要。
**❌ 慎用**：装饰器叠太多层，出问题时不好定位（到底哪一层出了问题）。

## 3.4 代理模式与享元模式（Proxy & Flyweight）

这两个模式在本项目里其实是"结伴出现"的，一起讲。

### 是什么

- **代理模式**：给一个对象找个"替身"，访问替身时，替身可以加一些额外逻辑（比如缓存、权限检查、延迟加载），然后再转发给真身。
- **享元模式**：通过**共享**来减少大量相似对象的创建，节省内存/资源。

**大白话**：
- 代理 = "经纪人"。你想联系明星，先联系经纪人，经纪人决定要不要转达。
- 享元 = "共享单车"。全城不需要每人一辆车，共享一批车，谁要用谁骑。

### 项目里的真实代码

`services/coordinator/llm.py` 里的 LLM 缓存，同时体现了这两个思想：

```python
# 缓存实例：{cache_key: ChatOpenAI}
# cache_key 含 model/base_url/api_key，切换模型后 key 变化 → 重建实例
_llm_cache: dict[tuple, ChatOpenAI] = {}

def get_llm(temperature=0.3, user_id=None) -> ChatOpenAI:
    cfg = get_active_config(user_id or 1, "llm")
    model = (cfg or {}).get("model") or AI_MODEL
    api_key = (cfg or {}).get("api_key") or AI_API_KEY
    base_url = (cfg or {}).get("base_url") or AI_BASE_URL

    cache_key = (temperature, model, base_url, api_key)
    if cache_key not in _llm_cache:
        _llm_cache[cache_key] = ChatOpenAI(...)   # 第一次才真正创建
        log.info(f"创建 LLM 实例: model={model}, temperature={temperature}")
    return _llm_cache[cache_key]                   # 之后直接返回缓存
```

拆解一下这里的思想：

- **代理的"缓存"逻辑**：调用方调 `get_llm(...)`，它先查缓存，命中就**不创建真身**（`ChatOpenAI`），直接返回缓存里的替身。这是代理模式里"缓存代理"的典型做法。
- **享元的"共享"逻辑**：相同的 `(temperature, model, base_url, api_key)` 组合，**共享同一个实例**，而不是每次都 new 一个。如果程序里有 100 次调用用的是同一套模型参数，就只创建 1 个实例，而不是 100 个。

（严格说，`_llm_cache` 是个"多例缓存池"，不是严格意义的单例——不同参数组合会有不同实例。这其实比单例更实用，因为项目支持"多模型热切换"。）

### 什么时候用

**✅ 适合**：创建对象昂贵、且对象可复用时（模型实例、连接池、线程池）。
**❌ 慎用**：缓存要处理好"失效"问题——本项目用 `cache_key` 变化来自动失效，如果你缓存了会变化的数据而忘了失效，就会出"脏数据"的 bug。

# 第四部分：行为型模式

行为型模式回答一个问题：**对象之间怎么"协作、分工、流转"**。

## 4.1 策略模式（Strategy）

### 是什么

**策略模式**：定义一组算法/规则，把它们各自封装起来，让它们可以**互相替换**。调用方只需要知道"我有一组策略可选"，不关心具体用哪个。

**大白话**：策略模式就像"手机导航选路线"——同一个"从 A 到 B"，有"最快路线""最短路线""避免高速"等多种策略。你可以随时切换，而"导航"这个动作本身不变。

### 项目里的真实代码

项目里最典型的策略模式是**经验计分**（`models/constants.py`）。

`calculate_exp` 是"统一入口"（相当于"导航"这个动作），内部根据维度分派到不同的计分策略：

```python
def calculate_exp(category_id, duration, sub_type=None, ...):
    """根据新计分规则计算维度经验"""
    if category_id == "health":
        return _calc_health(duration, sub_type, sleep_start, sleep_end, ...)
    elif category_id == "study":
        return _calc_study(duration, global_rate)
    elif category_id == "relation":
        return _calc_relation(duration, sub_type, global_rate)
    elif category_id == "work":
        return _calc_work(sub_type, global_rate)
    elif category_id == "create":
        return _calc_create(duration, sub_type, global_rate)
    elif category_id == "finance":
        return _calc_finance(duration, sub_type, global_rate, today)
    elif category_id == "hobby":
        return _calc_hobby(duration, global_rate)
    elif category_id == "soul":
        return _calc_soul(duration, global_rate)
```

而每个 `_calc_xxx` 就是**一个独立的策略**，规则各不相同：

```python
def _calc_study(duration, global_rate):
    """学习：floor(duration/20) × 10，最小20分钟"""
    blocks = duration // 20
    exp = blocks * 10
    return {...}

def _calc_health_sport(duration, global_rate):
    """运动：floor(duration/15) × 3.75，最小15分钟"""
    blocks = duration // 15
    exp = blocks * 3.75
    return {...}

def _calc_hobby(duration, global_rate):
    """爱好：40/h"""
    exp = duration * 2 / 3
    return {...}
```

**策略模式的精髓**：调用方（比如 `routers/actions.py` 和 `services/exp_service.py`）只需要调 `calculate_exp(category, duration, ...)`，**完全不用关心**内部有多少种计分规则、每种规则怎么算。哪天想改"学习"的计分规则，只改 `_calc_study` 一个函数，其他维度、所有调用方都不受影响。

### 项目的"朴素实现" vs "经典实现"

严格说，GoF 的策略模式是用"策略接口 + 多个策略类"实现的（每个策略是一个类，继承同一接口）。而项目里用的是**更朴素的实现**——`if/elif` + 多个独立函数。

这完全没问题！**策略模式的核心是"把可变算法封装起来、可替换"，而不是"必须用类"**。Python 里，函数本身就是一等公民，用 `if/elif` 分派到不同函数，就是策略模式的一种轻量实现。

**延伸思考**：如果将来维度越来越多、规则越来越复杂（比如 8 维变成 30 维），`if/elif` 会越来越长，那时可以升级成"字典映射"的写法：

```python
# 升级版：策略注册表（思路，未在项目中）
_EXP_CALC = {
    "health": _calc_health,
    "study": _calc_study,
    "relation": _calc_relation,
    # ...
}
def calculate_exp(category_id, ...):
    fn = _EXP_CALC.get(category_id)
    return fn(...) if fn else {...}
```

这跟 §2.2 的 `SUBGRAPH_BUILDERS` 注册表是同一个思路——**用字典替代 if/elif，更易扩展**。

### 什么时候用

**✅ 适合**：一个行为有多种算法/规则，需要按条件切换，且可能增减（计分规则、排序算法、支付方式、优惠策略）。
**❌ 慎用**：如果规则只有 2~3 种且永不变化，`if/elif` 直接写反而更清晰，别硬套。

---

## 4.2 模板方法模式（Template Method）

### 是什么

**模板方法模式**：定义一个算法的**骨架**（步骤固定），把其中某些步骤**留给子类/参数去实现**。

**大白话**：就像"泡面的说明书"——步骤固定：撕开包装 → 放调料 → 倒开水 → 等 3 分钟。但"放什么调料"这一步，不同口味的泡面不一样。骨架不变，细节可变。

### 项目里的真实代码

项目里最典型的模板方法是 `make_agent_node`（`services/coordinator/agents/base.py`）。

它定义了一个**固定的 ReAct 循环骨架**（ReAct 是 AI Agent 的一种工作模式：**推理 → 行动 → 观察 → 再推理**）：

```python
def make_agent_node(tools, domain, domain_label, system_prompt):
    all_tools = list(tools) + [ask_user]
    tools_by_name = {t.name: t for t in all_tools}

    async def agent_node(state):
        llm = get_llm(temperature=0.3, user_id=state.get("user_id", 0))
        # ... 窗口截断 ...
        full = [SystemMessage(content=system_prompt)] + messages

        for _ in range(MAX_ITERS):          # ← 固定骨架：循环
            response = await llm_with_tools.ainvoke(full)   # ① 问 LLM

            if response.tool_calls:          # ② LLM 要调工具
                new_messages = [response]
                for tc in response.tool_calls:
                    name = tc["name"]
                    if name == "ask_user":   # ③ 反问分支
                        # ... 返回反问结果
                    else:                    # ④ 业务工具分支
                        tool_fn = tools_by_name.get(name)
                        # 工具是同步的，丢线程池避免阻塞事件循环（2026-09-08 起）
                        tool_result = await asyncio.to_thread(tool_fn.invoke, args)
                        # ...
                full = full + new_messages    # ⑤ 拼回上下文，继续循环
                continue

            # ⑥ LLM 输出纯文本 → 结束
            return {...}

    return agent_node
```

这个骨架对 6 个域**完全一样**：都是"问 LLM → 调工具 → 判断反问/完成 → 循环"。但不同域通过**传入不同的 `tools` 和 `system_prompt`** 来改变行为：

```python
# 行动域：传入 record_action 工具 + 行动 prompt
create_action_agent = build_subgraph(state_class=ActionSubgraphState, tools=[record_action], ...)

# 目标域：传入 create_goal 等工具 + 目标 prompt
create_goal_agent = build_subgraph(state_class=GoalSubgraphState, tools=[create_goal, ...], ...)
```

**这就是模板方法的精髓**：**骨架（循环、反问、工具执行）由模板定死，细节（有哪些工具、提示词是什么）由参数注入**。

### 模板方法 vs 策略模式，别搞混

这两个也容易混，但区别很关键：

| | 模板方法 | 策略模式 |
|---|---|---|
| 变化的是 | 算法里的**某些步骤** | **整个算法** |
| 控制权 | 骨架在"父类"，由父类控制流程 | 由调用方选择用哪个策略 |
| 大白话 | 泡面骨架不变，换调料 | 导航动作不变，换路线 |

**项目对照**：`make_agent_node` 是**模板方法**（ReAct 循环骨架固定，换工具/prompt）；`calculate_exp` 是**策略**（计分算法整体可替换）。

### 什么时候用

**✅ 适合**：多个场景流程高度相似、只有局部不同（本项目 6 个域 agent）。
**❌ 慎用**：骨架太死会限制灵活性——本项目就遇到了这个问题：`make_agent_node` 的循环逻辑足够通用，但如果某个域需要完全不同的循环，就得另写。好在目前 6 个域都能套进这个骨架。

---

## 4.3 状态模式 / 状态机（State）

### 是什么

**状态模式 / 状态机**：一个对象有多个**状态**，状态之间可以**转换**，且在不同状态下，对同一操作的反应不同。

**大白话**：就像"外卖订单"——有"待付款 → 已付款 → 配送中 → 已完成"等状态。在"待付款"状态点"取消"，和在"配送中"状态点"取消"，结果是完全不同的。

### 项目里的真实代码

**例子 1：任务状态（`mcp_server.py` 里的枚举约束）**

项目的任务有明确的状态流转：

```python
TaskStatus = Literal["todo", "doing", "done"]
# todo（待办）→ doing（进行中）→ done（已完成）
```

通过 `typing.Literal` 把状态限定为这三个值，LLM 传非法状态（比如 `"finished"`）会在调用前被 schema 拦截。这就是"状态机"的最小实现——**限定合法状态，防止非法状态**。

**例子 2：协调 Agent 的编排状态流转（`services/coordinator/graph.py` + `state.py`）**

主编排的"状态"是一个 `TypedDict`（`CoordinatorState`），它在三段式流程中不断流转：

```python
class CoordinatorState(TypedDict, total=False):
    user_id: int
    user_message: str
    pending_tasks: list[SubgraphTask]      # 待派发的子任务
    results: list[dict]                    # 子图返回结果
    interrupts: list[dict]                 # 反问事件
    completed_domains: list[str]           # 已完成的域
    final_reply: str                       # 最终回复
```

状态流转（`run_coordinator`）：

```python
async def run_coordinator(state):
    # 阶段一：路由 → 填 pending_tasks
    routing = await router_node(state)
    state["pending_tasks"] = routing.get("pending_tasks", [])

    # 阶段二：并行派发 → 填 results / interrupts / completed_domains
    disp = await dispatch_subgraphs(state)
    state["results"] = disp.get("results", [])
    state["interrupts"] = disp.get("interrupts", [])
    state["completed_domains"] = disp.get("completed_domains", [])

    # 阶段三：判断"全部完成"还是"等待反问"
    pending_domains = {t["domain"] for t in state["pending_tasks"]}
    if pending_domains and (pending_domains - set(state["completed_domains"])):
        state["final_reply"] = ""          # 有反问未答 → 不总结
    else:
        syn = await synthesize_node(state)  # 全部完成 → 总结
        state["final_reply"] = syn.get("final_reply", "")
    return state
```

**这就是一个隐式的状态机**：状态（`state` 字典）在"路由 → 派发 → 总结"三个阶段间流转，每个阶段读状态、改状态。`pending_tasks`（还有未完成）和 `completed_domains`（已完成）的集合运算，本质是"状态转换的判定条件"。

**例子 3：子图的显式状态机（LangGraph StateGraph）**

子 agent 用的是 LangGraph 的 `StateGraph`，这是一个**显式的状态机框架**：

```python
graph = StateGraph(ActionSubgraphState)   # 定义状态
graph.add_node("agent", make_agent_node(...))  # 定义节点（状态）
graph.set_entry_point("agent")             # 初始状态
graph.add_edge("agent", END)               # 状态转换（agent → 结束）
```

这里"节点"就是状态，"边"就是状态转换。虽然子图目前只有"agent → END"一条边，但 LangGraph 的 StateGraph 天然支持多节点、分支、循环——这正是状态机思想在 AI Agent 编排里的应用。

### 什么时候用

**✅ 适合**：对象有明显的"生命周期"或"阶段"（订单、任务、审批流、Agent 编排）。
**❌ 慎用**：状态太多、转换太乱时，状态机反而难维护——本项目主流程刻意**不用** StateGraph（见 §7.2），就是因为主流程是线性三段，用状态机反而复杂化。

## 4.4 观察者模式（Observer）

### 是什么

**观察者模式**：一个对象（主题）状态变化时，自动通知所有"订阅"了它的对象（观察者）。

**大白话**：就像"公众号订阅"。你关注了一个公众号，它每次发文你都能收到推送。公众号（主题）不需要知道你是谁，只需要"群发"；你（观察者）也不需要天天去刷，等着推送就行。

### 项目里的真实代码

项目里的观察者模式体现在**定时任务调度**（`main.py`）。

APScheduler 就是一个典型的"事件驱动 + 观察者"框架——你注册"回调函数"（观察者），调度器（主题）在到点时自动触发它们：

```python
@asynccontextmanager
async def lifespan(app_instance):
    scheduler = AsyncIOScheduler(executors={'default': ThreadPoolExecutor(1)})
    # 注册两个"观察者"：到点自动执行
    scheduler.add_job(run_daily_refresh, CronTrigger(hour=3, minute=0))       # 每天 3 点
    scheduler.add_job(run_weekly_refresh, CronTrigger(day_of_week='mon', hour=3, minute=5))  # 每周一 3:05
    scheduler.start()
    yield
    if scheduler:
        scheduler.shutdown(wait=False)
```

这里 `run_daily_refresh` 和 `run_weekly_refresh` 就是两个"观察者"，它们不需要自己写 `while True + sleep` 去轮询"到 3 点了吗"，而是**注册给调度器，到点被自动调用**。

### 观察者 vs 轮询

观察者模式的核心价值是**把"主动轮询"变成"被动通知"**：

- **轮询（polling）**：自己每隔一段时间去查"有变化吗"，浪费资源、有延迟。
- **观察者（observer）**：注册后躺平等通知，实时、省资源。

前端里其实也处处是观察者——DOM 的 `addEventListener` 就是最经典的观察者实现：

```javascript
// 前端的观察者模式（示意）
button.addEventListener('click', handleClick);  // "订阅"点击事件
```

按钮（主题）被点击时，自动通知 `handleClick`（观察者）。按钮不需要知道有哪些函数监听它。

### 什么时候用

**✅ 适合**：一个状态变化要通知多个对象（定时任务、事件系统、UI 数据绑定）。
**❌ 慎用**：观察者多了、通知链长了，可能"牵一发动全身"，难以调试（谁触发的？通知了谁？）。

## 4.5 责任链模式（Chain of Responsibility）

### 是什么

**责任链模式**：把多个处理者串成一条链，请求沿链传递，每个处理者决定"自己处理"还是"传给下一个"。

**大白话**：就像"公司审批流"——你的报销单先给组长，组长签不了传给经理，经理签不了传给总监……每个环节要么处理，要么往后传。

### 项目里的真实代码

FastAPI 的**中间件链**和**依赖链**，都是责任链的体现。

**中间件链（`main.py`）**：

```python
app = FastAPI(title="Self Grow Backend", version="1.0.0", lifespan=lifespan)

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_methods=["*"],
    allow_headers=["*"],
)
```

一个 HTTP 请求进来后，会**依次经过**各个中间件：先经过 CORS 中间件（处理跨域）→ 再进入路由处理函数 → 返回时再反向经过一遍中间件。每个中间件都可以在"处理"和"放行"之间做选择。这就是责任链——**请求沿着中间件链传递，每环各司其职**。

**依赖注入链（`routers/actions.py`）**：

```python
@router.post("/api/actions")
async def create_action(req: CreateActionRequest, user=Depends(get_current_user)):
    ...
```

请求进来时，FastAPI 会**先执行 `get_current_user`**（校验用户存在）→ 通过后才执行 `create_action`。`get_current_user` 就是责任链上的"前置处理者"，它校验不通过就抛 `HTTPException`（中断链条），通过就把 `user` 传下去。

### 什么时候用

**✅ 适合**：请求要经过多个"关卡"依次处理，且顺序重要（中间件、鉴权、日志、限流）。
**❌ 慎用**：链条太长、每环职责不清时，请求"走到哪了"很难追踪。

## 4.6 命令模式（Command）

### 是什么

**命令模式**：把"一个操作"封装成"一个对象/函数"，从而可以**统一地记录、排队、撤销、执行**这些操作。

**大白话**：就像"遥控器的按键"。每个按键封装了一个命令（开空调、调温度、换台）。你可以按下（执行）、也可以记录按了什么（日志）、甚至可以撤销。

### 项目里的真实代码

项目里的"工具函数"（`@tool`、`@mcp.tool()`）本质就是**命令**。

每个工具是一个独立的、可被统一调度的操作：

```python
@tool
def record_action(category, detail, duration, ...):
    """记录用户的行动并计算经验值"""
    ...
```

而在 `base.py` 的 ReAct 循环里，这些"命令"被**统一地**查找、执行：

```python
for tc in response.tool_calls:
    name = tc["name"]
    tool_fn = tools_by_name.get(name)   # 按名字找到"命令"
    if tool_fn:
        # 工具是同步的（内部同步 sqlite3），丢线程池避免阻塞事件循环
        tool_result = await asyncio.to_thread(tool_fn.invoke, args)   # 统一执行命令
```

注意这里的精妙之处：LLM 不是直接调用某个具体函数，而是"发出一个命令请求"（`tool_calls`，包含工具名和参数），由循环**统一解释执行**。这带来一个巨大好处——**命令可以被拦截、记录、控制**：

- 可以在执行前**校验参数**（`mcp_server.py` 里用 `Literal` 枚举拦截非法值）。
- 可以**统一捕获异常**（`base.py` 里 `try/except` 包住所有工具调用）。
- 可以**记录日志**（谁在什么时候执行了什么命令）。
- 可以**限制执行次数**（`MAX_ITERS = 8` 防无限循环）。

如果 LLM 直接调用函数，这些"统一控制"的能力就都没了。命令模式让"执行操作"这件事变成了可管理的第一等公民。

### 什么时候用

**✅ 适合**：操作需要被统一调度、记录、排队、撤销（Agent 工具调用、宏命令、事务日志）。
**❌ 慎用**：简单的直接调用不需要封装成命令，否则就是"杀鸡用牛刀"。

# 第五部分：设计原则 SOLID

设计模式是"招式"，SOLID 是"内功心法"。理解了 SOLID，你会发现设计模式不过是这些原则的**具体落地**。

## 5.1 单一职责原则（SRP，Single Responsibility Principle）

> **一个类/函数只做一件事，只有一个"变化的原因"。**

**项目对照**：`db/` 目录下每个文件只负责一个域——`db/actions.py` 只管行动记录，`db/goals.py` 只管目标，`db/habits.py` 只管习惯……这就是 SRP 在**文件/模块层面**的体现。

反过来看反例：早期的 `server.py` 一个文件里塞了所有路由 + 业务逻辑 + 计分规则，一件事变了（比如计分规则），整个文件都要动。这就是违反 SRP 的典型症状。

**大白话**：一个工具只干一种活。螺丝刀就是拧螺丝的，别指望它还能敲钉子、开瓶盖。

## 5.2 开闭原则（OCP，Open/Closed Principle）

> **对扩展开放，对修改关闭。** 增加新功能时，尽量"新增代码"，而不是"修改现有代码"。

**项目对照**：`SUBGRAPH_BUILDERS` 注册表就是 OCP 的完美例子。加第 7 个域，只需**新增**一个 `create_note_agent()` 并在字典里加一行，**不用修改** `graph.py` 的主流程。

```python
SUBGRAPH_BUILDERS = {
    "action": create_action_agent,
    "query": create_query_agent,
    # 将来加：
    # "note": create_note_agent,   ← 新增，不改主流程
}
```

**大白话**：改装车，应该"加装新零件"，而不是"把发动机拆了重造"。

## 5.3 里氏替换原则（LSP，Liskov Substitution Principle）

> **子类/子类型可以无差别地替换父类/基类型，程序行为不变。**

**项目对照**：6 个域的 agent 都通过 `build_subgraph` + `make_agent_node` 工厂生产，产出的都是"编译好的子图"，主流程 `dispatch_subgraphs` 用 `asyncio.gather` 统一调用，**不关心是哪个域的图**。因为它们遵守同一个"接口契约"（都接受 `state`、返回 `result`），所以可以互相替换、统一处理。

```python
coros = [_run_one_subgraph(task["domain"], ...) for task in pending_tasks]
outcomes = await asyncio.gather(*coros)   # 统一处理，不管哪个域
```

**大白话**：公司里"主管"这个岗位，谁来当都能干主管的活（开同样的会、签同样的字），不因为换了个人流程就崩。

## 5.4 接口隔离原则（ISP，Interface Segregation Principle）

> **不要强迫调用方依赖它用不到的接口。** 接口要小而专，不要大而全。

**项目对照**：`services/ai_client.py` 提供了两个**小而专**的接口——`call_ai_text`（要纯文本就用它）和 `call_ai_text_stream`（要流式输出就用它），而不是一个"上帝接口"塞满所有参数和模式。调用方只依赖自己需要的那一个。

**大白话**：餐厅菜单应该分类（汤、菜、饭），而不是一张纸全列上，让只想喝汤的人也得翻完整本。

## 5.5 依赖倒置原则（DIP，Dependency Inversion Principle）

> **高层模块不应该依赖低层模块，两者都应该依赖抽象。**

**项目对照**：路由层（高层）依赖的是 `services/exp_service.py` 的门面函数（抽象），而不是直接依赖 `db/` 里的一堆具体函数。`routers/actions.py` 调的是：

```python
service_result = award_exp_and_recalc(user_id, req.category_id, dimension_exp, ...)
```

而不是在路由里直接写 `upsert_dimension(...)`、`update_user_exp(...)` 等一串底层调用。这样，底层数据库实现怎么改（比如从 SQLite 换成 MySQL），路由层都不用动。

**大白话**：你依赖的是"插座"这个标准（抽象），而不是某一家厂商的插头（具体实现）。换厂商的电器，插座不用换。

# 第六部分：框架自带的"隐藏设计模式"

这一部分很重要：**很多设计模式你不用自己实现，框架已经帮你实现了**。学会"识别框架里的设计模式"，是面试的加分项，也是用懂框架的关键。

## 6.1 依赖注入（Dependency Injection，DI）

### 是什么

**依赖注入**：对象不自己创建它依赖的东西，而是由外部"注入"进来。

**大白话**：你不需要自己造一辆车，公司（框架）把车配给你（注入）。你要做的只是"声明你需要一辆车"。

### 项目里的真实代码

FastAPI 的 `Depends` 就是依赖注入的典型。

`routers/deps.py` 定义了一个"可注入的依赖"：

```python
async def get_current_user(user_id: int = Query(..., description="用户 ID")):
    """验证用户存在的依赖注入函数。替代 server.py 中 ~31 次重复的"用户不存在"检查。"""
    user = get_user(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
```

路由函数**声明**它需要这个依赖，FastAPI 自动注入：

```python
@router.post("/api/actions")
async def create_action(req: CreateActionRequest, user=Depends(get_current_user)):
    user_id = user["id"]   # user 是框架注入的，不是自己 new 的
    ...
```

### 依赖注入的价值

项目注释里这句话是关键：

> 替代 server.py 中 ~31 次重复的"用户不存在"检查。

原来项目里有 31 处路由都写了同样的"查用户 → 不存在就报错"的代码。用 `Depends(get_current_user)` 之后：

1. **消除重复**：31 份拷贝 → 1 个依赖函数。
2. **声明式**：路由只需说"我需要一个已校验的用户"，不用写校验逻辑。
3. **可测试**：可以注入"假用户"来测试，不用真的连数据库。

**大白话**：依赖注入让"你要什么"和"怎么造出来"分离。路由说"我要一个用户"，至于用户怎么查、怎么校验，是框架和 `get_current_user` 的事。

### 什么时候用

**✅ 适合**：鉴权、数据库连接、配置等"横切依赖"。
**❌ 慎用**：不是所有东西都要注入，过度注入会让函数签名长得吓人。

## 6.2 生命周期钩子（观察者 + 模板方法）

`main.py` 里的 `lifespan` 也体现了框架级的设计模式：

```python
@asynccontextmanager
async def lifespan(app_instance):
    # 启动时：初始化调度器、注册任务
    scheduler = AsyncIOScheduler(...)
    scheduler.add_job(run_daily_refresh, CronTrigger(hour=3, minute=0))
    scheduler.start()
    yield                      # ← 应用运行期间停在这里
    # 关闭时：清理资源
    if scheduler:
        scheduler.shutdown(wait=False)

app = FastAPI(..., lifespan=lifespan)
```

这里 `lifespan` 是 FastAPI 提供的**生命周期钩子**——框架在"应用启动"和"应用关闭"两个时机自动调用你的代码（观察者模式的框架级应用）。而你只需要"填充"启动做什么、关闭做什么（模板方法的框架级应用）。

**大白话**：框架说"我给你留了两个空位：开机时、关机时"，你往空位里填代码就行。不用自己操心"什么时候开机、什么时候关机"。

# 第七部分：如何在项目里用好设计模式

学完这么多模式，最容易犯的错误就是**过度设计**——看什么都想套模式。这一部分讲清楚"怎么判断该不该用"。

## 7.1 识别"重复代码"是起点

设计模式的**第一信号永远是重复代码**。回看本项目：

- "加经验流程"重复 5 次 → 引出**门面模式**（`exp_service.py`）。
- "用户不存在检查"重复 31 次 → 引出**依赖注入**（`get_current_user`）。
- "6 个域的 agent 创建"结构雷同 → 引出**工厂 + 模板方法**（`make_agent_node`）。

**判断公式**：当你发现自己在"复制粘贴然后改一点点"时，停下来问一句——**是不是该抽象了？**

## 7.2 从本项目学会的"反过度设计"教训

本项目最有价值的教训，恰恰是**主动拒绝某个模式**。

看 `graph.py` 开头的注释：

```python
本模块只做编排，不再使用 LangGraph StateGraph（主流程是线性三段，无分支/循环，
LangGraph 的 operator.add 状态合并反而会引入跨轮累积问题）。
```

项目**曾经**用 LangGraph 的 StateGraph 来编排主流程（状态机模式），但发现：

- 主流程就是"路由 → 派发 → 总结"三段直线，**没有分支、没有循环**。
- 强行用 StateGraph 的状态合并机制（`operator.add`），反而引入了"跨轮累积"的 bug。

于是项目**主动退回去**，改成纯函数编排（`run_coordinator`），子图的 ReAct 循环才保留 StateGraph。

**这个教训极其重要**：**设计模式是手段，不是目的。** 一个工具（StateGraph）再强大，用错了场景（线性流程不需要状态机）就是负担。

**另一个教训**：`models/constants.py` 里 `exp_rate` 字段是"遗留未使用"的——当初设计了它，但实际计分靠 `_calc_*` 硬编码。**设计要落地**，设计了却不用，就是技术债。

## 7.3 设计模式学习路线建议

对于刚开始学设计模式的你，建议按这个顺序：

1. **先掌握"抽象 + 多态"**（§1.4）——这是地基。
2. **重点吃透 5 个高频模式**：单例、工厂、策略、门面、模板方法。这 5 个占了 Web 项目里 90% 的模式使用场景，且本项目全部有真实例子。
3. **再学框架自带的**：依赖注入、装饰器、观察者（§6）——这些你不用实现，但要会"识别和利用"。
4. **了解 SOLID**（§5）——理解模式的"为什么"。
5. **最后读一遍本项目代码**，拿着"速查表"（附录）去代码里找对应，从"看懂了"到"会用"。

**检验是否学会的标准**：能不能对着一个全新的、没写过的功能，自己判断"这里该用工厂吗？该用策略吗？还是直接写就行？"——而不是"把 23 种模式背下来"。

| **单例** | 创建型 | `checkpointer.py` 的 `_checkpointer`；`ai_client.py` 的 `_llm_instance` | 全局只建一个实例，复用连接/共享状态 |
| **工厂方法** | 创建型 | `agents/base.py` 的 `make_agent_node`、`build_subgraph` | 造"会干活的函数/子图" |
| **工厂注册表** | 创建型 | `agents/__init__.py` 的 `SUBGRAPH_BUILDERS` | 字典映射"域名 → 工厂"，加域不改主流程 |
| **建造者** | 创建型 | `build_subgraph` 的分步构建；消息列表逐步拼接 | 把复杂构造拆成清晰步骤 |
| **适配器** | 结构型 | `ai_client.py` 封装 ChatOpenAI；`mcp_server.py` 适配 MCP | 把复杂/异构接口翻译成简单/统一接口 |
| **门面** | 结构型 | `exp_service.py` 的 `award_exp_and_recalc`、`create_action_and_award_exp` | 把"加经验 5 步流程"合并成一个入口 |
| **装饰器** | 结构型 | FastAPI `@router.post`；`@tool`、`@mcp.tool()` | 不改原函数，动态加功能（路由注册、工具包装） |
| **代理 + 享元** | 结构型 | `coordinator/llm.py` 的 `_llm_cache` | 缓存代理 + 共享实例，避免重复创建模型 |
| **策略** | 行为型 | `models/constants.py` 的 `calculate_exp` + `_calc_*` | 计分算法按维度可替换 |
| **模板方法** | 行为型 | `agents/base.py` 的 `make_agent_node` | ReAct 循环骨架固定，换工具/prompt |
| **状态机** | 行为型 | LangGraph `StateGraph`（子图）；`CoordinatorState` 流转；任务 `todo/doing/done` | 状态 + 状态转换 |
| **观察者** | 行为型 | `main.py` 的 APScheduler 定时任务；前端 `addEventListener` | 到点/事件自动通知 |
| **责任链** | 行为型 | FastAPI 中间件链 + `Depends` 依赖链 | 请求沿链传递，每环各司其职 |
| **命令** | 行为型 | `@tool` / `@mcp.tool()` 工具函数 | 把操作封装成可统一调度/记录的命令 |
| **依赖注入** | （框架级） | `routers/deps.py` 的 `get_current_user` + `Depends` | 声明需要什么，框架注入，消除重复校验 |

## 附录 C：一句话总结

- 想**少造重复对象** → 单例、享元。
- 想**灵活造对象** → 工厂、建造者。
- 想**简化接口** → 门面、适配器。
- 想**不侵入地加功能** → 装饰器、代理。
- 想**让算法可替换** → 策略、模板方法。
- 想**让对象状态流转清晰** → 状态机。
- 想**让变化自动通知** → 观察者。
- 想**让请求依次过闸** → 责任链。
- 想**把操作变成可管理的对象** → 命令。

**记住**：模式是"菜谱"不是"枷锁"。项目里的代码就是最好的老师——当你能说出"这里用了单例，因为它要复用连接；那里用了门面，因为它要消除重复"，设计模式就真正内化成了你的能力。
