# 第 1 章 云服务器是什么

## 1.1 从「三层服务模型」理解云

云厂商卖的东西是分层的，**理解层次才知道自己在买什么**：

| 层 | 名称 | 你管什么 | 厂商管什么 | 典型产品 |
|---|---|---|---|---|
| IaaS | 基础设施即服务 | 系统、运行时、应用、数据 | 硬件、虚拟化、网络 | **云服务器（CVM）** |
| PaaS | 平台即服务 | 只写应用代码 | 系统、运行时、扩缩容 | 云函数 SCF、容器服务 TKE |
| SaaS | 软件即服务 | 只用 | 全部 | 企业微信、腾讯文档 |

**本项目属于 IaaS 场景**：你要自己装 Docker、自己管数据、自己配 HTTPS。
好处是**可控、便宜、能学到东西**；代价是运维全归你。

> 面试小知识：面试官问"为什么不用 Serverless 部署"，可以答：
> "Serverless 冷启动对 SQLite 这种有状态服务不友好，而且我这个规模下，
> 一台 2C2G 的成本和改造成本都比 Serverless 低。"

## 1.2 云服务器的几种"形态"

以腾讯云为例，常见的几种：

| 产品 | 定位 | 特点 | 适合本项目？ |
|---|---|---|---|
| **CVM 云服务器** | 标准 IaaS | 规格自由、可挂多块云盘、可加带宽 | ✅ 首选 |
| **轻量应用服务器 (Lighthouse)** | 简化版 CVM | 套餐制（含流量包）、便宜、防火墙配置更简单 | ✅ 也够用，更省钱 |
| 容器服务 TKE | K8s 托管 | 需要集群、有最低成本 | ❌ 杀鸡用牛刀 |
| 云函数 SCF | Serverless | 无状态、冷启动 | ❌ 有 SQLite 和定时任务 |

**怎么理解"轻量"和"CVM"的区别**：

- 轻量 = 固定套餐（如 2C2G + 40GB SSD + 每月 300GB 流量），操作界面简化，**防火墙在控制台独立标签页**
- CVM = 规格自选（CPU/内存/带宽/云盘分开买），**网络安全靠安全组**，企业级功能更多

> 本项目的部署环境就是 CVM（腾讯云 Ubuntu 26.04）。

## 1.3 怎么选规格（结合本项目实际需求）

先算清楚项目要什么：

| 资源 | 本项目的需求 | 依据 |
|---|---|---|
| CPU | 1 核能用，2 核舒服 | FastAPI 单进程 + 轻量计算，AI 请求是 IO 等待 |
| 内存 | **2 GB 起** | pip 安装依赖时峰值很高（langchain/langgraph），1G 容易被 OOM Kill |
| 磁盘 | 20 GB 起 | 镜像约 1~2 GB（含依赖）+ 构建缓存 + 代码 + 数据库 |
| 带宽 | **1~3 Mbps 足够** | 只有你/家人访问，无大文件下载 |
| 公网 IP | 需要 | 手机、外部访问 |

**推荐配置（性价比）**：

```
2 核 2 GB / 40 GB SSD / 3 Mbps 带宽 / Ubuntu 22.04 或 24.04 LTS
```

**为什么内存比 CPU 重要**：Python 依赖安装是这个项目里最吃资源的环节。177 → 132 个包，
`pip install` 的峰值内存可以到 1 GB 以上，1G 内存的机器很可能在构建阶段就被杀。

> **构建被 kill 的典型信号**：日志最后是 `exit code 137`（128 + 9 = SIGKILL），
> 或者只有一句 `Killed`。这时候加 swap 就能解决（见 3.6）。

## 1.4 计费模式

| 模式 | 说明 | 适合 |
|---|---|---|
| **包年包月** | 预付，单价最低 | 长期使用的个人项目 ✅ |
| 按量计费 | 按小时，随停随用 | 临时测试 |
| 竞价实例 | 价格浮动，可能被回收 | 跑批任务，**不适合网站** |

**学生党/个人项目实践**：云厂商常年有"新用户特惠"（如 1~2 核 2G 一年几十到一百多），
包年包月比按量划算很多。注意**到期后不续费数据会被保留一段时间再释放**，别等到最后一天。

## 1.5 云硬盘

| 类型 | 特点 | 本项目 |
|---|---|---|
| 高效云盘 | 便宜、够用 | ✅ 完全够 |
| SSD 云盘 | 更高 IOPS | 数据库压力大时考虑 |
| 增强型 SSD | 最高性能 | 不需要 |

**关键认知**：云盘可以**在线扩容**（控制台把 40G 改成 60G），但**扩完还要在系统里扩分区**，
否则 `df -h` 还是旧大小。详见 3.5。

## 1.6 公网带宽（最容易超支的地方）

两种计费方式，**务必搞懂再买**：

| 方式 | 计费 | 特点 |
|---|---|---|
| **按带宽** | 固定 X Mbps，包月 | 费用可预测，超了就慢（不会扣钱） |
| **按流量** | 按实际 GB 计费 | 平时便宜，**被刷流量会天价账单** |

**本项目的流量估算**：

```
页面首次加载：HTML/CSS/JS 约 1~2 MB
之后每次操作：API JSON，几十 KB
每天自用 20 次操作 ≈ 5 MB
一个月 ≈ 150 MB
```

所以 **1 Mbps 按带宽计费**完全够，而且不用担心被刷。

> ⚠️ 安全提醒：按流量计费的机器，如果被人刷（比如挂了个被扫到的大文件），
> 一晚上可能产生几千块账单。个人项目**一律选按带宽**。

## 1.7 公网 IP 与弹性 IP（EIP）

- **普通公网 IP**：随实例生命周期，停机可能变
- **弹性公网 IP (EIP)**：独立资源，可解绑再绑到别的实例，**按小时计费**
- **内网 IP**：VPC 内的地址，同一 VPC 的机器之间用它通信（免费、快、不经公网）

**本项目的场景**：直接用实例自带的公网 IP 即可，不需要 EIP。

> 常见的坑：**服务器重启后公网 IP 变了**，然后你发现 CORS 白名单、DNS 解析全失效。
> 这就是我们为什么建议买 EIP 或绑定域名（域名解析跟着走，不跟着 IP 走）。

## 1.8 地域与可用区

```
地域（Region）：上海 / 北京 / 广州 / 香港 …
    └── 可用区（Zone）：上海一区 / 上海二区 …
```

**选择原则**：

- 就近：你在哪，就选附近的地域（延迟低）
- **是否需要备案**：**中国内地地域绑定域名必须 ICP 备案**；中国香港/海外不需要
- 同项目多机器要选同一 VPC

**备案这件事**：

| 服务器位置 | 用 IP 访问 | 用域名访问 |
|---|---|---|
| 中国内地 | 可以 | **必须备案**（腾讯云可代提交，7~20 天） |
| 中国香港 / 海外 | 可以 | 不需要备案 |

> 面试常问"为什么用香港服务器"——常见答案是"不想备案"或"面向海外用户"。
> 但**个人项目用 IP 访问 + 自签/Let's Encrypt 证书的路径更简单**，本项目就先用 IP。

## 1.9 镜像（Image）

| 类型 | 说明 |
|---|---|
| 公共镜像 | 厂商提供的干净系统（Ubuntu / CentOS / TencentOS） |
| 自定义镜像 | 你把自己机器做成模板，可用于批量开机器 |
| 共享镜像 | 别人分享给你的 |
| 应用镜像 | 预装了环境（如宝塔、Docker、LNMP）——**新手友好，但会带一堆你不知道的东西** |

**建议**：选**干净的公共镜像**（Ubuntu LTS），自己装需要的软件。
预装环境镜像虽然方便，但出问题时你会不知道从哪查起。

## 1.10 快照 vs 自定义镜像

| | 快照 Snapshot | 自定义镜像 |
|---|---|---|
| 对象 | **一块云盘** | **整台实例**（含系统盘+数据盘配置） |
| 用途 | 数据备份、回滚 | 批量创建相同环境的机器 |
| 恢复 | 用快照回滚磁盘 | 用镜像新建实例 |
| 成本 | 按容量计（比磁盘便宜） | 同快照 |

**实践建议**：**在动 SSH 配置、改安全组这类"可能把自己锁外面"的操作之前，先打个快照。**
几毛钱的成本，换来的是"随时回滚"。

> 这个建议来自本次部署：改 `sshd_config` 时如果写错，SSH 会直接起不来，
> 只能靠控制台 VNC 救场。有快照就一键回滚。

# 第 2 章 网络：安全组、端口、DNS

## 2.1 VPC 与子网

**VPC（私有网络）** = 你在云上的一块隔离的虚拟局域网。

```
VPC 10.0.0.0/16
 ├── 子网 A（上海一区）10.0.1.0/24  ← 你的服务器在这
 └── 子网 B（上海二区）10.0.2.0/24
```

**要点**：

- 同一 VPC 内的机器**内网互通**（用私有 IP），不经过公网、不计流量费
- 不同 VPC 默认隔离
- 默认会给你建一个"默认 VPC"，个人项目不用改

**为什么知道这个有用**：以后如果加一台机器跑数据库，用内网 IP 连接，
既快又安全（数据库端口不用对公网开放）。

## 2.2 公网访问的两道门

这是**最容易卡住新手**的地方。访问一台云服务器，要同时通过两道门：

```
你的浏览器
    ↓
【第一道】云厂商安全组 / 防火墙   ← 控制台配置
    ↓
【第二道】系统内防火墙（ufw / firewalld）  ← 服务器里配置
    ↓
    你的服务（3001 端口）
```

**任何一道没开，都访问不通**。而且两道的"默认策略"可能相反：

| | 典型默认 |
|---|---|
| 安全组 | 看模板：有的全放行，有的只开 22 |
| ufw | **inactive（等于全放行）** |
| firewalld | 默认拒绝 |

> 本次部署实测：腾讯云安全组有一条 `0.0.0.0/0 ALL 允许` 的默认规则（等于全开），
> 而 `ufw` 是 `inactive`。所以 3001 一开始就是通的，不需要额外配置。

## 2.3 安全组详解

### 2.3.1 三个核心特性

| 特性 | 含义 | 实际影响 |
|---|---|---|
| **白名单** | 只放行明确允许的，其余全拒 | 想开某端口必须显式加规则 |
| **有状态** | 允许入站后，该连接的**出站回包自动放行** | 不用为响应单独配出站规则 |
| **按序匹配** | 规则**从序号小到大匹配，命中即停止** | 上面一条 `ALL 允许` 会让后面所有规则失效 |

### 2.3.2 怎么读一条规则

```
来源            协议端口     策略     备注
0.0.0.0/0       ALL          允许     Default rule
│               │            │
│               │            └─ 允许 / 拒绝
│               └─ 端口范围，可以用逗号：TCP:80,443
└─ 允许访问的来源 IP 段
```

**来源写法**：

| 写法 | 含义 |
|---|---|
| `0.0.0.0/0` | 任意 IPv4（**等于全网开放**） |
| `::/0` | 任意 IPv6 |
| `120.229.11.7/32` | **仅这一个 IP**（`/32` 表示单个地址） |
| `10.0.0.0/16` | 一个网段 |

> **`/32` 一定要写**。只写 IP 不带掩码，有些控制台会报格式错误或理解成别的含义。

### 2.3.3 最小权限原则怎么落地

默认模板的 `0.0.0.0/0 ALL 允许` **把整台机器所有端口暴露在公网**。
个人项目虽然风险有限，但正确做法是改成白名单：

| 来源 | 协议端口 | 策略 | 说明 |
|---|---|---|---|
| `你的固定IP/32` | TCP:22 | 允许 | SSH，只允许自己 |
| `0.0.0.0/0` | TCP:80,443 | 允许 | Web 服务 |
| 其余 | — | 拒绝 | 默认 |

**操作顺序（错了会把自己锁外面）**：

```
1. 先加 22 规则（限定你的 IP）
2. 开新终端验证 SSH 还能连
3. 再加 80/443
4. 最后才删掉那条 ALL 允许
```

> ⚠️ 如果你的公网 IP 是动态的（家宽常见），限定 `/32` 后某天 IP 变了就连不上了。
> 这时候要么改回 `0.0.0.0/0` 开 22（弱一点但可用），要么用云厂商的 VNC 登录改回来。
> **个人项目折中方案**：22 保持 `0.0.0.0/0`，但**禁用密码登录只用密钥**（见 3.2），
> 这样爆破也进不来。

### 2.3.4 安全组改动的连带影响

腾讯云加规则时会提示：

> "该安全组已关联 1 个实例，添加规则会影响所有已关联实例"

这说明**安全组是复用的资源**，一台机器可能绑多个安全组（取并集）。
改之前先确认这个安全组还绑了哪些机器，别改坏别人的服务。

## 2.4 系统防火墙（ufw）

如果安全组已经配好，`ufw` 其实是可选的双保险。要用的话：

```bash
# ⚠️ 顺序不能反：先放行 22，再 enable
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 3001/tcp

sudo ufw --force enable
sudo ufw status verbose
```

**常见坑**：

- 忘了 `allow 22` 就 `enable` → 立刻 SSH 断连（`ufw` 默认拒绝所有入站）
- Docker 会**绕过 ufw**：`docker -p 3001:3001` 的端口映射是写进 iptables 的 NAT 规则，
  优先级在 ufw 之前 → **即使 ufw 拒绝了 3001，容器端口依然对公网开放**。

> 第二条是**很重要的认知**：容器端口不要靠 ufw 保护，要靠**安全组**或
> **只绑回环地址**（`127.0.0.1:3001:3001`，见 4.4）。

## 2.5 端口与服务对照表

| 端口 | 服务 | 何时开放 |
|---|---|---|
| 22 | SSH | 必须（建议限来源） |
| 80 | HTTP | 要用 Nginx / 申请证书 |
| 443 | HTTPS | 要上 HTTPS |
| **3001** | **本项目后端** | **临时验证用，配好 Nginx 后关闭** |
| 8000 | MCP HTTP 模式 | 仅在需要远程 MCP 时 |
| 3306 | MySQL | 本项目不用 |
| 6379 | Redis | 本项目不用 |

## 2.6 端口排查三板斧

```bash
# ① 服务在监听吗？（在服务器上跑）
ss -lntp | grep 3001
#   LISTEN 0 128 0.0.0.0:3001 0.0.0.0:* users:(("python",pid=123,fd=8))

# ② 本机能通吗？（排除服务本身的问题）
curl -v http://127.0.0.1:3001/api/health

# ③ 外部能通吗？（在你自己电脑上跑）
#   Windows PowerShell: Test-NetConnection 你的IP -Port 3001
#   Linux/Mac:          nc -zv 你的IP 3001
```

**按结果定位**：

| ① 监听 | ② 本机 curl | ③ 外部 | 结论 |
|---|---|---|---|
| ❌ | ❌ | ❌ | 服务没起来 → 看日志 |
| ✅ | ✅ | ❌ | **网络层被拦** → 安全组 / ufw |
| ✅ | ❌ | ❌ | 服务起了但端口不对 / 崩了 |
| ✅ | ✅ | ✅ | 服务正常 |

**这条分支逻辑能省你 90% 的排查时间**：先确定"是服务问题还是网络问题"。

## 2.7 DNS 域名解析

| 记录类型 | 用途 | 例子 |
|---|---|---|
| **A** | 域名 → IPv4 | `grow.example.com` → `111.229.152.184` |
| AAAA | 域名 → IPv6 | — |
| CNAME | 域名 → 另一个域名 | 常用于 CDN |
| TXT | 文本验证 | 证书验证、SPF |

**要点**：

- 解析生效时间看 **TTL**（一般 600 秒 / 10 分钟）
- `dig` / `nslookup` 可以查当前解析结果
- 改了 A 记录后，本地可能被系统 DNS 缓存——`ipconfig /flushdns`（Windows）

## 2.8 备案（中国内地特有）

**规则**：服务器在中国内地，**用域名提供 Web 服务就必须 ICP 备案**。
用 IP 访问不受此限制。

| 场景 | 是否要备案 |
|---|---|
| 内地服务器 + IP 访问 | ❌ |
| 内地服务器 + 域名访问 | ✅ **必须** |
| 中国香港/海外 + 域名 | ❌ |

备案流程：在云厂商控制台提交 → 上传材料 → 厂商初审 → 管局审核（约 7~20 天）。
备案期间域名不能用来访问 Web（否则会被拦）。

> **个人项目的现实选择**：先用 IP 跑起来（验证功能），
> 需要正式对外时再备案。面试演示用 IP 完全没问题。

## 2.9 HTTPS 与证书

### 2.9.1 为什么本项目必须上 HTTPS

不是"最佳实践"这种空话：

```
JWT 的 Access Token 在 Authorization 请求头里明文传输
API Key 也是明文
HTTP 下，同一局域网/链路上的任何人抓到包就能盗用你的身份
```

### 2.9.2 三种证书获取方式

| 方式 | 成本 | 适用 |
|---|---|---|
| **Let's Encrypt** | 免费，90 天自动续期 | ✅ 个人项目首选 |

# 第 3 章 Linux 运维基础

## 3.1 用户与权限

### 3.1.1 为什么不用 root

| 风险 | 说明 |
|---|---|
| 一条 `rm -rf` 可能删掉整个系统 | root 没有任何保护 |
| 被爆破的代价最大 | 攻击者直接拿到整机 |
| 没有审计 | 分不清是谁干的 |

**正确姿势**：普通用户 + `sudo` 提权。

```bash
whoami          # 看当前用户
id              # 看 uid、gid、所属组
sudo -l         # 看当前用户能执行哪些 sudo 命令
```

### 3.1.2 云服务器默认用户

| 厂商/镜像 | 默认用户 |
|---|---|
| 腾讯云 Ubuntu | `ubuntu` |
| 腾讯云 CentOS | `root` 或 `centos` |
| 轻量应用服务器 | `lighthouse` 或 `root` |
| AWS Ubuntu | `ubuntu` |
| AWS Amazon Linux | `ec2-user` |

> **第一件事永远是 `whoami`**，别凭印象。

### 3.1.3 `docker` 组 ≈ root（重要认知）

```bash
sudo usermod -aG docker $USER
newgrp docker
```

**为什么要加这个组**：不加的话每条 docker 命令都要 `sudo`。

**但要知道代价**：`docker` 组的成员可以执行

```bash
docker run -v /:/host -it alpine chroot /host
```

这条命令直接把宿主机根目录挂载进容器，**等于拿到 root**。
所以：

- 单人服务器：加就加了，方便优先
- 多人共用：应该用 **rootless mode** 或给 sudo 做审计

> 面试加分点：能说出"docker 组等价 root"这个事实，说明你理解容器隔离的边界。

## 3.2 SSH 加固

### 3.2.1 加固清单

| 措施 | 配置 | 说明 |
|---|---|---|
| 禁用 root 登录 | `PermitRootLogin no` | 防止爆破 root |
| 禁用密码登录 | `PasswordAuthentication no` | 只能用密钥 |
| 用密钥认证 | `~/.ssh/authorized_keys` | 比密码强得多 |
| 改端口 | `Port 2222` | **收益低，不建议**（容易忘） |
| fail2ban | 默认配置 | 防爆破，可选 |

### 3.2.2 ⚠️ 坑 1：`authorized_keys` 存在但可能是空的

本次部署真实踩到：

```bash
$ ls -la ~/.ssh/authorized_keys
-rw------- 1 ubuntu ubuntu 0 Sep 11 23:22 /home/ubuntu/.ssh/authorized_keys
                            ↑ 大小是 0！
```

文件**存在但不代表有密钥**。云镜像/cloud-init 可能只创建了空文件。

**在禁用密码登录前必须验证**：

```bash
wc -l ~/.ssh/authorized_keys      # 期望 >= 1
# 更可靠：新开终端实测能免密登录
```

> **血泪教训**：如果 `authorized_keys` 是空的，你又禁用了密码登录，
> 就彻底进不去了（只能靠云控制台 VNC 救场）。

### 3.2.3 ⚠️ 坑 2：OpenSSH 是「第一个匹配值生效」

这是本手册里**最值得记住的一条**。

**配置结构**（Ubuntu 22.10+）：

```
/etc/ssh/sshd_config            ← 主配置，顶部有：
    Include /etc/ssh/sshd_config.d/*.conf     ← 先加载这个目录
    ...
    #PasswordAuthentication yes              ← 主配置里的（靠后）
```

**规则**：`man sshd_config` 明确写着——

> "Unless noted otherwise, for each keyword, the **first obtained value** will be used."

也就是 **第一个匹配到的值生效**，不是最后一个。

**实际踩坑过程**：

```bash
# 腾讯云 cloud-init 生成了：
/etc/ssh/sshd_config.d/50-cloud-init.conf:1:PasswordAuthentication yes

# 我一开始这样改（以为数字大优先级高）：
printf 'PasswordAuthentication no\n' | sudo tee /etc/ssh/sshd_config.d/99-hardening.conf

# 验证结果 —— 没生效！
$ sudo sshd -T | grep passwordauthentication
passwordauthentication yes          ❌
```

**原因**：glob 按**字典序**展开，`50-cloud-init.conf` 排在 `99-hardening.conf` 前面，
而 Include 又在主配置最前面 → 50 的 `yes` 是"第一个匹配值"，赢。

**正确解法**：文件名要**小于**云厂商的编号：

```bash
rm -f /etc/ssh/sshd_config.d/99-hardening.conf
printf 'PasswordAuthentication no\nPermitRootLogin no\n' | sudo tee /etc/ssh/sshd_config.d/00-hardening.conf

sudo sshd -T | grep -E "^(permitrootlogin|passwordauthentication)"
# permitrootlogin no
# passwordauthentication no         ✅ 这才对
```

### 3.2.4 安全改配置的标准流程

```bash
# ① 备份
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

# ② 改（并处理 drop-in，用 00- 前缀）
...

# ③ 语法校验（能救命！）
sudo sshd -t && echo "配置正确" || echo "有错，别重启"

# ④ 用 sshd -T 看「最终生效值」（不是看文件内容！）
sudo sshd -T | grep -E "^(permitrootlogin|passwordauthentication)"

# ⑤ 重启
sudo systemctl restart ssh

# ⑥ 保持当前终端不关，新开一个终端验证能登录 → 才关旧终端
```

> **第 ④ 步是关键习惯**：配置文件里写了什么 ≠ sshd 实际用了什么。
> 只有 `sshd -T` 输出的是真相。

### 3.2.5 救命入口

**动手前先确认云控制台的 VNC / WebShell 能打开**（腾讯云：实例 → 右上角「登录」）。
这是 SSH 配错后唯一的后悔药。

## 3.8 定时任务 crontab

```bash
crontab -e            # 编辑当前用户的
crontab -l            # 查看
sudo crontab -e       # root 的
```

**格式**：

```
分 时 日 月 周   命令
0  3  *  *  *   /path/to/backup.sh >> /var/log/backup.log 2>&1
│  │  │  │  └─ 周（0-6，0=周日）
│  │  │  └─ 月
│  │  └─ 日
│  └─ 时
└─ 分
```

**三个坑**：

1. **cron 的环境变量和你 shell 里的不一样**（PATH 很短）→ 命令写绝对路径
2. **输出默认发邮件** → 一定要重定向 `>> log 2>&1`，否则日志乱丢
3. **别和容器内的定时任务重复**：本项目 APScheduler 在容器内跑定时任务，

## 3.9 时间与时区 ⚠️

### 3.9.1 查看和设置

```bash
timedatectl                          # 看当前时区
timedatectl list-timezones | grep Shanghai
sudo timedatectl set-timezone Asia/Shanghai
date                                 # 验证
```

### 3.9.2 ⚠️ 坑：Docker 容器默认是 UTC

**这是本项目部署中最隐蔽的一个坑**，值得单独讲。

容器内默认时区是 **UTC**，而宿主机的时区**不会自动传进容器**。

**本项目的代码大量依赖本地时间**：

| 位置 | 用法 | UTC 下的后果 |
|---|---|---|
| `db/init.py` 建表默认值 | `datetime('now','localtime')` | 存的时间比实际早 8 小时 |
| `db/batch.py` | `datetime.date.today()` | 北京时间 00:00~08:00 期间「今天」还是前一天 |
| `main.py` APScheduler | `CronTrigger(hour=3)` | **UTC 03:00 = 北京 11:00 才跑定时任务** |

**症状**：

- 你在"今天"打了卡，第二天看发现日期不对
- 说好的凌晨 3 点归档，结果是上午 11 点才执行
- 数据库里的创建时间总是差 8 小时

**解决**（本项目已采用）：

```dockerfile
# Dockerfile
ENV TZ=Asia/Shanghai
RUN apt-get update \
    && apt-get install -y --no-install-recommends tzdata \
    && rm -rf /var/lib/apt/lists/*
```

```yaml
# docker-compose.yml
environment:
  TZ: ${TZ:-Asia/Shanghai}
```

**为什么还要装 `tzdata`**：Debian slim 镜像里 `/usr/share/zoneinfo` 可能不存在，
只设 `TZ` 环境变量但找不到时区数据文件，仍然会回落到 UTC。

**验证**：

```bash
docker compose exec app date
# 期望：CST 时区的时间，与你的手表一致
docker compose exec app python -c "import datetime; print(datetime.datetime.now())"
```

> **通用经验**：任何"和日期/时间打交道"的服务放进容器，
> 第一件事就是确认时区。这一类 bug 不会报错，只会让数据慢慢错掉。

# 第 4 章 Docker 在服务器上的特殊性

> Docker 本身的原理见 [Docker技术详解与部署实战](./Docker技术详解与部署实战.md)，本章只讲**服务器环境下特有的问题**。

## 4.1 安装方式

```bash
# 官方脚本（推荐，自动配置 apt 源）
curl -fsSL https://get.docker.com | sudo sh

# 验证
docker version
docker compose version      # 注意：docker compose（子命令），不是 docker-compose（旧版独立程序）
```

**几种安装方式的区别**：

| 方式 | 版本 | 说明 |
|---|---|---|
| `get.docker.com` 脚本 | 最新 | ✅ 推荐 |
| `apt install docker.io` | 较旧 | Ubuntu 源的版本 |
| 云厂商应用镜像预装 | 不确定 | 可能缺 compose 插件 |

**验证 compose**：

```bash
docker compose version     # v2+ 才是插件版
docker-compose version     # v1（Python 版，已停止维护）
```

## 4.2 存储目录与磁盘

Docker 的所有数据都在 `/var/lib/docker`：

```
/var/lib/docker/
├── image/overlay2/     镜像层（最大）
├── containers/         容器（含日志）
├── volumes/            命名卷 ← 你的 data.db 在这
├── buildkit/           构建缓存
└── ...
```

**常见问题**：磁盘满了。清理顺序：

```bash
docker system df                    # 先看什么占地方
docker image prune -a               # 删无用镜像
docker builder prune                # 删构建缓存
docker container prune              # 删已停止容器
# ⚠️ 千万别随便 docker volume prune —— 那会删掉你的数据库！
```

**把 Docker 数据目录挪到大盘**（如果系统盘小）：

```bash
sudo systemctl stop docker
sudo mv /var/lib/docker /data/docker
# 编辑 /etc/docker/daemon.json 加 "data-root": "/data/docker"
sudo systemctl start docker
```

## 4.3 容器网络的特殊性

### 4.3.1 端口映射绕过 ufw

```
用户 → 公网 → iptables NAT（Docker 写的）→ 容器:3001
                    ↑
              ufw 的规则在这一层之前还是之后？→ 之后！
```

**Docker 的端口映射规则优先级高于 ufw**。所以：

> **不要指望 ufw 保护容器端口，要用安全组，或只绑回环。**

### 4.3.2 只绑回环（生产推荐）

```yaml
ports:
  - "127.0.0.1:3001:3001"     # 只有本机能访问，外部走 Nginx
```

这样即使安全组开了 3001，外部也连不上（因为服务只监听回环）。

## 4.4 卷与数据

| 类型 | 写法 | 数据在哪 |
|---|---|---|
| **命名卷** | `data:/data` | `/var/lib/docker/volumes/<项目名>_data/` |
| 绑定挂载 | `/host/path:/data` | 宿主机指定路径 |
| 匿名卷 | `/data`（不指定源） | 随机 ID，难管理 |

**本项目的关键约定**：

```yaml
volumes:
  - data:/data                     # 挂载点
environment:
  SELF_GROW_DATA_DIR: /data        # 应用写这里 → 必须一致！
```

**这两个值必须一致**。如果不设 `SELF_GROW_DATA_DIR`，应用会把 `data.db` 写到
代码目录（容器可写层）→ **删容器数据就没了**。

**危险操作警告**：

```bash
docker compose down            # ✅ 保留卷
docker compose down -v         # ❌ -v 会删除卷 = 删库！
```

## 4.5 资源限制

不设限制时，一个容器能吃掉整台机器的资源。生产建议：

```yaml
mem_limit: 1g
cpus: 1.0
```

**为什么重要**：如果应用有内存泄漏或死循环，没有限制会拖垮宿主机上其他服务
（包括你的 SSH 都可能卡死，导致救都救不回来）。

## 4.6 日志轮转

Docker 默认用 `json-file` 驱动，**无限增长**。

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"     # 单文件最大 10MB
    max-file: "3"       # 最多保留 3 个（共 30MB）
```

**不配的后果**：一个高频打日志的容器，几天能写满磁盘，然后**所有服务挂掉**。

## 4.7 开机自启

```yaml
restart: unless-stopped
```

| 值 | 含义 |
|---|---|
| `no` | 不自动重启 |
| `on-failure` | 非 0 退出才重启 |
| `always` | 总是重启（手动 stop 也会）
| **`unless-stopped`** | 除非手动停，否则总是重启 ✅ |

**注意**：Docker 服务本身要开机自启：

```bash
sudo systemctl enable docker
```

两个都要，缺一不可：Docker 起了 + 容器策略是 `unless-stopped` → 服务器重启后服务自动回来。

## 4.8 时区与 locale

见 3.9。**容器内必须显式设置 `TZ`**，否则走 UTC。

## 4.9 常用运维命令（服务器版）

```bash
# 状态总览
docker compose ps
docker ps -a
docker stats

# 日志
docker compose logs -f --tail 100
docker compose logs -t app | tail -50      # 带时间戳

# 进容器
docker compose exec app bash

```

# 第 6 章 坑清单（按类别）

每条格式：**现象 → 根因 → 解决 → 预防**

## 6.1 网络类

### 坑：`0.0.0.0` 打不开

- **现象**：启动日志打印 `Uvicorn running on http://0.0.0.0:3001`，点进去浏览器说"无法访问此网站"
- **根因**：`0.0.0.0` 是「监听所有网卡」的**绑定地址**，不是可路由的**目标地址**
- **解决**：用 `http://localhost:3001` 或 `http://127.0.0.1:3001` 或 `http://公网IP:3001`
- **预防**：应用启动日志应打印可访问地址（本项目已在 `lifespan` 里做了）

### 坑：公网能 ping 通但端口连不上

- **现象**：`ping` 通，浏览器打不开
- **根因**：ping 走 ICMP，浏览器走 TCP。ICMP 通不代表 TCP 端口开放
- **解决**：按 2.6 的三板斧确认是安全组还是服务问题

### 坑：CORS 报错，表现为"后端没启动"

- **现象**：前端页面提示"无法连接到后端服务"，但后端明明在跑
- **根因**：浏览器跨域拦截。本项目后端默认只放行 `localhost` / `127.0.0.1`
- **解决**：`SELF_GROW_CORS_ORIGINS=http://你的IP:3001`
- **预防**：前端错误提示要展示**目标地址**和**当前源**，一眼看出是不是跨域（本项目已做）

### 坑：安全组改了不生效

- **根因**：规则是**按序号从上到下匹配，命中即停**。上面有条 `ALL 允许` 就没后面的事了
- **解决**：检查是不是已有"通配"规则在前面
- **预防**：加规则时从具体到宽泛；不要把通配规则放前面

### 坑：Docker 端口绕过 ufw

- **现象**：ufw 明明拒绝了 3001，外部还是能访问
- **根因**：Docker 的 NAT 规则优先级在 ufw 之前
- **解决**：用安全组控制；或 `127.0.0.1:3001:3001` 只绑回环

## 6.2 SSH 类

### 坑：禁用密码登录后进不去

- **根因**：没先确认密钥可用
- **解决**：云控制台 VNC 登录改回来
- **预防**：改之前 `wc -l ~/.ssh/authorized_keys` + 新终端实测免密登录

### 坑：改了 sshd_config 但没生效

- **根因**：`/etc/ssh/sshd_config.d/*.conf` 里的文件覆盖了，且 OpenSSH 是**第一个值胜出**
- **解决**：用 `00-hardening.conf`（字典序在云厂商的 50 之前）
- **预防**：改完**一定**用 `sshd -T` 看最终值，不要只看文件内容

### 坑：重启 sshd 后服务起不来

- **根因**：配置语法错误
- **解决**：VNC 进去，恢复 `/etc/ssh/sshd_config.bak`
- **预防**：重启前先 `sudo sshd -t` 校验语法

### 坑：SSH 突然连不上，密钥没变

- **可能原因**：动态公网 IP 变了，而安全组限定了 `/32`
- **解决**：控制台 VNC 登录，放宽来源或更新 IP
- **预防**：家宽用户别把 22 限太死，或改用密钥认证来抵御爆破

## 6.3 Docker 类

### 坑：删容器后数据没了

- **根因**：没挂卷，或 `SELF_GROW_DATA_DIR` 与实际挂载点不一致
- **解决**：确认 `volumes: - data:/data` + `SELF_GROW_DATA_DIR=/data` 两处一致
- **预防**：部署后跑一次 `down` + `up` 验证数据还在

### 坑：`docker compose down -v` 删库

- **根因**：`-v` 会删除卷
- **预防**：养成不用 `-v` 的习惯；重要数据先备份

### 坑：磁盘被日志写满

- **根因**：json-file 日志默认无限增长
- **解决**：配 `logging.options.max-size`
- **预防**：所有 compose 服务都加日志轮转

### 坑：构建时被 OOM Kill（exit 137）

- **根因**：内存不足
- **解决**：加 swap
- **预防**：2G 内存起步

### 坑：`docker` 命令要 sudo

- **根因**：当前用户不在 docker 组
- **解决**：`sudo usermod -aG docker $USER` 然后**退出重登**（`newgrp` 只影响当前 shell）
- **预防**：装完 Docker 第一件事就是加组

## 6.4 配置类

### 坑：JWT 密钥没配，服务能起但登录 500

- **现象**：容器正常启动，一登录就 500
- **根因**：密钥是**懒加载**的，只在签发 token 时才读 → 启动时不报错
- **解决**：本项目已改为**启动时** `ensure_jwt_secret()` 校验，缺密钥直接拒绝启动
- **预防**：所有"必须的配置"都应在启动时校验，不要推迟到首次使用

### 坑：`.env` 重复键

- **现象**：明明填了值，`docker compose config` 显示是空的
- **根因**：`cp .env.example .env` 后用了 `echo >>` 追加，产生两行同名键
- **解决**：用 `sed -i "s|^KEY=.*|KEY=值|"` 就地替换
- **预防**：**永远不要对"已有键的文件"用 `>>` 追加**

### 坑：把文档示例行原样粘进配置

- **现象**：CORS 没生效
- **根因**：粘进去的是 `#   SELF_GROW_CORS_ORIGINS=http://你的IP:3001`，带 `#` 是注释
- **预防**：文档里的示例行要标清楚"这行是注释/这行要改"

### 坑：改了 .env 但容器没生效

- **根因**：环境变量是**容器创建时**注入的，`docker compose restart` 不会重新读取
- **解决**：`docker compose up -d`（会重建容器）
- **预防**：改 `.env` 后统一用 `up -d` 而不是 `restart`

## 6.5 依赖与构建类

### 坑：`requirements.txt` 混入 conda 包（本项目真实踩到）

- **现象**：
  ```
  ERROR: Invalid requirement: '_openmp_mutex==4.5'
         Expected package name at the start of dependency specifier
  ```
- **根因**：导出脚本用了 `pixi list --json`（**conda 视角**），混进：
  - `_openmp_mutex`、`_python_abi3_support`（下划线开头，PEP 508 非法）
  - `bzip2`、`ca-certificates`（PyPI 上没有）
  - `brotli-python`（PyPI 上叫 `brotli`）
- **解决**：改用 `importlib.metadata.distributions()`（**Python 发行版视角**）导出，
  自动得到正确的 PyPI 名称，包数 177 → 132
- **预防**：**pixi/conda 与 pip 的包名空间不同**。任何"从 conda 锁文件导出 pip 清单"的脚本，
  必须走 Python 发行版元数据

### 坑：`pywin32` 混入 requirements.txt，构建 388 秒后失败（本项目真实踩到）

- **现象**：

  ```
  Collecting pywin32-ctypes==0.2.3 ...                      (跑到第 99 行)
  ERROR: Could not find a version that satisfies the requirement pywin32==312
         (from versions: none)
  ERROR: No matching distribution found for pywin32==312
  failed to solve: process "/bin/sh -c pip install ..." did not complete successfully
  ```

  最难受的是**失败时机**：pip 会先把前面一百多个包**全部下载完**，最后才在 `pywin32` 上撞墙。
  实测整个构建跑了 **388 秒**，前面的下载全部白费。

- **根因**：`pywin32` 是 Windows 专属发行版，PyPI 上**只有 `win32` / `win_amd64` 轮子**，
  Linux 下 `from versions: none` —— 一个可用文件都没有。
  它本身只是 `keyring` 的 `sys_platform == "win32"` 条件依赖，但
  **conda 解析依赖时会忽略 PyPI 的 sys_platform 标记**，按宿主机（Windows）直接装进了开发环境，
  再被导出脚本原样写进清单。同批漏出来的还有 `pywin32-ctypes`、`win_inet_pton`。

- **绕过的弯路（值得记）**：第一反应是「读 WHEEL 文件的 `Tag:`，把带 win 的剔掉」。**行不通** ——
  实测在 Windows 环境的 `site-packages` 里，`cryptography`、`pydantic_core`、`pillow`
  这些**跨平台**包的 WHEEL 同样写着 `Tag: cp312-cp312-win_amd64`，和 `pywin32` 一模一样。
  靠 tag 无法区分「跨平台包在 Windows 上恰好装了 win 轮子」和「本身只发布 Windows 版的包」，
  唯一可靠的离线信号是**包名**。

- **解决**：在 `tools/export_reqs.py` 里维护 `PLATFORM_ONLY` 黑名单，并做 **PEP 503 名字归一化**
  （`win_inet_pton` 的元数据名是下划线形式，不归一化就会漏网）。导出时剔除并打印 `[SKIP]` 日志：

  ```
  [OK] 已写入 requirements.txt：129 个包
  [SKIP] 已剔除 3 个平台专属包（仅 Windows 存在）：
         - pywin32==312
         - pywin32-ctypes==0.2.3
         - win_inet_pton==1.1.0
  ```

- **预防**：
  1. 依赖清单**永远不要手工编辑**（尤其别手工注释掉报错那行），一律重新导出
  2. 导出脚本必须**打日志说明剔除了什么**，否则换台机器你不知道自己少了什么
  3. 用 pip 的跨平台 dry-run **在本地提前拦**，别等服务器跑 6 分钟才失败：

     ```bash
     python -m pip install --dry-run --ignore-installed --no-deps \
       --only-binary=:all: \
       --platform manylinux_2_28_x86_64 --platform manylinux_2_27_x86_64 \
       --platform manylinux_2_17_x86_64 --platform manylinux2014_x86_64 \
       --python-version 3.12 --target /tmp/pipverify \
       -r backend/requirements.txt
     ```

     末尾 `Would install ...` = 全部可解析。

     ⚠️ `--platform` 要给**多个**标签。`pillow 12.3.0` 只发了 `manylinux_2_28` 轮子，
     只给 `manylinux2014_x86_64` 会误报 `No matching distribution found for pillow==12.3.0`。

### 坑：构建慢 —— 跨境拉包 388 秒

- **现象**：`pip install` 阶段每个包都要几十秒，129 个包拉到最后还失败了
- **根因**：服务器在国内，直连 `pypi.org` 跨境单线程下载，链路抖动、速度不稳
- **解决**：Dockerfile 换国内镜像源 + 抗抖动参数

  ```dockerfile
  ARG PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple
  RUN pip install --no-cache-dir --retries 5 --timeout 60 \
          -i "${PIP_INDEX_URL}" -r backend/requirements.txt
  ```

  写成 `ARG` 而不是硬编码：海外机器上
  `docker compose build --build-arg PIP_INDEX_URL=https://pypi.org/simple` 即可切回官方源
- **预防**：任何**跨境拉包**的构建步骤都该配镜像源；`--retries` / `--timeout` 是抗抖动必备

### 坑：pip 装依赖时编译失败

- **现象**：`error: command 'gcc' failed`
- **根因**：某个包没有预编译 wheel，需要编译器
- **解决**：slim 镜像里装 `build-essential`，或用多阶段构建
- **预防**：优先选有 wheel 的包

### 坑：改了代码但容器里没变

- **根因**：没重新构建镜像
- **解决**：`docker compose up -d --build`
- **预防**：把 `--build` 加到你的升级脚本里

## 6.6 数据类

### 坑：SQLite 备份拿到损坏文件

- **根因**：直接 `cp` 正在写入的 `data.db`（WAL 模式下尤其危险）
- **解决**：用 SQLite 的在线备份 API：
  ```bash
  docker compose exec app python -c "
  import sqlite3
  s=sqlite3.connect('/data/data.db'); d=sqlite3.connect('/data/backup.db')
  with d: s.backup(d)
  print('ok')"
  ```
- **预防**：把备份写成脚本并加进 crontab

### 坑：时间戳差 8 小时 / 日期算错

- **根因**：容器时区是 UTC
- **解决**：`ENV TZ=Asia/Shanghai` + 装 `tzdata`
- **预防**：所有容器化服务都显式设时区

## 6.7 性能类

### 坑：服务器内存逐渐被吃满

- **排查**：`docker stats`、`ps aux --sort=-%mem`
- **常见原因**：Python 进程内存泄漏、日志/缓存无限增长
- **缓解**：`mem_limit` 限制容器；配日志轮转；定期重启（`restart` 策略）
- **本项目已缓解**：`mem_limit: 1g` + 日志轮转

### 坑：SSH 卡死

- **根因**：内存被吃光（OOM），系统响应不了
- **解决**：控制台 VNC 重启
- **预防**：给关键容器设 `mem_limit`，加 swap

## 6.8 流程类

### 坑：本地提交没推送，服务器上没有

- **现象**：服务器 `git pull` 之后仍然缺文件
- **根因**：本地 commit 了但没 push
- **解决**：`git push` 后再到服务器 `git pull`
- **预防**：部署前在服务器上 `git log --oneline -1` 确认 commit 是预期的那个

### 坑：`git add -A` 提交了不该提交的文件

- **现象**：删掉的文件被提交为删除；或者密钥被提交
- **根因**：没看完整的 `git status`（只看前几十行）
- **解决**：`git revert` 或重建提交
- **预防**：`git add -A` 前先 `git status --short | wc -l` 看数量对不对

### 坑：`.gitignore` 没覆盖新增的敏感文件

- **现象**：`.env` 被提交
- **根因**：`.gitignore` 里只写了 `backend/.env`，没写根目录的 `.env`
- **解决**：补 `/.env`
- **预防**：新增任何"放密钥的地方"时，同步更新 `.gitignore`

## 6.9 成本类

### 坑：按流量计费被刷

- **现象**：账单异常高
- **根因**：按流量计费的机器，被别人刷（大文件、被扫的漏洞）
- **预防**：个人项目一律选**按带宽**计费

### 坑：忘记取消按量计费实例

- **预防**：不用就销毁；设置余额告警

## 8.2 备份策略

**3-2-1 原则**（简化版）：

- 至少 **3** 份数据
- **2** 种介质（本地 + 云存储）
- **1** 份异地

对个人项目的现实版本：

| 频率 | 内容 | 方式 |
|---|---|---|
| 每天 | `data.db` | SQLite backup API → 拷到本地 |
| 每周 | 整个卷 | tar 打包 |
| 变更前 | 整机 | 云盘快照 |

**备份脚本示例**（`~/backup.sh`）：

```bash
#!/bin/bash
set -e
cd ~/self-grow
DATE=$(date +%F)

# 在线安全备份（不能直接 cp）
docker compose exec -T app python -c "
import sqlite3
s=sqlite3.connect('/data/data.db'); d=sqlite3.connect('/data/backup.db')
with d: s.backup(d)
print('backup done')"

docker cp self-grow:/data/backup.db ./backup-$DATE.db
docker compose exec -T app rm -f /data/backup.db

# 只保留最近 30 天
find . -name "backup-*.db" -mtime +30 -delete
echo "[$(date)] backup ok: backup-$DATE.db"
```

```bash
chmod +x ~/backup.sh
crontab -e
# 每天凌晨 4 点
0 4 * * * /home/ubuntu/backup.sh >> /var/log/sg-backup.log 2>&1
```

**恢复演练**（重要！没演练过的备份等于没有备份）：

```bash
docker compose stop
docker cp ./backup-2026-09-14.db self-grow:/data/data.db
docker compose start
```

# 第 9 章 面试怎么讲

## 9.1 一分钟版本

> "我把它部署在腾讯云的一台 Ubuntu 服务器上，用 Docker 单容器跑。
>
> 部署过程里有几件事值得说：
>
> **一是安全加固**。服务器默认允许 root 远程登录、允许密码认证，我都关掉了，
> 改成只用密钥。改的时候踩了一个坑——Ubuntu 新版把 SSH 配置拆到了
> `sshd_config.d/` 目录，而且 OpenSSH 的规则是**第一个匹配值生效**而不是最后一个，
> 所以我一开始用 `99-hardening.conf` 没生效，得用 `00-` 前缀排在云厂商的
> `50-cloud-init.conf` 前面才行。改完一定用 `sshd -T` 看最终生效值，不能只看文件。
>
> **二是构建时的依赖问题**。我本地用 pixi（conda）管依赖，Docker 里用 pip 装，
> 第一次构建挂在 `pip install` 上，报 `_openmp_mutex` 解析失败——
> 因为我从 conda 的锁文件导 requirements 时，把 C 库和 conda 专有包也带进去了。
> 改成从 Python 发行版元数据导出之后，包数从 177 降到 132，构建就通了。
> 这件事让我意识到**两种包管理器交接的地方最容易出问题**。
>
> **三是时区**。容器默认 UTC，而我的项目大量用本地时间——SQLite 的
> `datetime('now','localtime')`、`date.today()`、以及每天 3 点的定时任务。
> 不设时区的话，定时任务会在上午 11 点跑，凌晨 0 到 8 点期间"今天"还会算成前一天。
> 这类 bug 不报错，只会让数据慢慢错掉，所以我在 Dockerfile 和 compose 里都显式设了 `TZ`。"

## 9.2 常见追问

| 问题 | 要点 |
|---|---|
| 为什么用 Docker 而不是直接装？ | 环境一致；依赖隔离；迁移只带镜像；`requirements.txt` 从 pixi 锁定版本导出保证开发/生产一致 |
| 数据怎么保证不丢？ | 命名卷把 `/data`（`data.db` + `uploads`）持久化；`SELF_GROW_DATA_DIR` 必须与挂载点一致；备份用 SQLite 在线备份 API 而不是 `cp` |
| 密钥怎么管？ | 环境变量注入，绝不在镜像里——镜像分层，写进去再删也能被 `docker history` 看到 |
| 为什么不多开几个容器做高可用？ | SQLite 单文件 + APScheduler 定时任务，多副本会导致任务重复执行和锁竞争。这是**为规模做的正确取舍**，要上量得先换掉 SQLite |
| 怎么保护数据库端口？ | 不暴露；将来拆库也用 VPC 内网通信 |
| 为什么会踩 SSH 那个坑？ | 云厂商的 cloud-init 会写 drop-in 覆盖你的配置；而且 OpenSSH 是 first-wins 语义，和 Nginx 之类的"后者覆盖"习惯相反 |
| 时区问题怎么发现的？ | 部署后 `docker compose exec app date` 验证，发现是 UTC 而不是 CST |

## 9.3 加分点

- **"我先跑了一遍诊断命令再动手"** —— 云镜像差异大，照抄教程容易踩空
- **"我把 CORS 从 `*` 收紧成白名单"** —— 最小权限原则
- **"安全组默认模板太宽，我后来改成只开 22/80/443"** —— 主动意识到默认配置的问题
- **"我给容器设了 `mem_limit`，避免它拖垮宿主机"** —— 知道资源隔离
- **"备份我做过恢复演练"** —— 没演练过的备份等于没有备份

# 附录 B 排查决策树

## B.1 网站打不开

```
浏览器打不开
├─ 是 DNS 问题吗？（域名解析到正确 IP 了吗）
│   └─ dig 域名 → 看解析结果
├─ 是本机问题吗？（服务器上 curl）
│   ├─ curl 127.0.0.1:3001/api/health
│   │   ├─ 失败 → 服务问题
│   │   │   ├─ docker compose ps 容器在跑吗？
│   │   │   │   ├─ 没跑 → docker compose logs 看报错
│   │   │   │   └─ 在跑 → 看是不是端口配错了
│   │   │   └─ ss -lntp | grep 3001 有监听吗？
│   │   └─ 成功 → 是网络层问题，往下
│   └─ 
└─ 是网络层问题吗？
    ├─ 安全组放行了吗？（控制台看入站规则）
    ├─ ufw 开了吗？（sudo ufw status）
    └─ 端口绑定对吗？（docker compose config 看 ports）
```

## B.2 登录失败

```
能打开页面但登录失败
├─ 报 500
│   └─ 十有八九是 SELF_GROW_JWT_SECRET 没配
│       └─ docker compose config | grep JWT_SECRET
├─ 报 401（用户名或密码错误）
│   └─ 密码初始化了吗？
│       └─ docker compose exec app python tools/init_password.py
├─ 页面提示"无法连接到后端"
│   └─ CORS 没配
│       └─ SELF_GROW_CORS_ORIGINS 要是你访问的地址
└─ 请求根本没发出（网络报错）
    └─ 用 F12 Network 面板看请求状态
```

## B.3 数据不见了

```
重启后数据没了
├─ 容器被删过吗？
├─ 卷挂载了吗？
│   └─ docker compose config 看 volumes
├─ SELF_GROW_DATA_DIR 与挂载点一致吗？
│   └─ 都应该是 /data
└─ 有没有跑过 docker compose down -v 或 docker volume prune？
    └─ 那就是真删了 → 从备份恢复
```

## B.4 时间不对

```
时间/日期不对
├─ 宿主机时间对吗？（timedatectl）
├─ 容器时间对吗？（docker compose exec app date）
│   └─ 是 UTC → 设 TZ 环境变量 + 装 tzdata
└─ 是数据库里的历史数据已经错了？
    └─ 只能手动修，或接受（新数据从设置时区那刻起是对的）
```

## 结语

云服务器部署真正的难点**不在敲命令**，而在：

1. **知道有哪几层**（安全组 / 系统防火墙 / 应用 / 容器网络）
2. **知道怎么定位是哪一层出的问题**（B 章决策树）
3. **知道默认配置往往是不安全的**（root 可登录 / 密码可登录 / 安全组全开 / 时区 UTC）

这三条学会了，换任何云厂商、任何项目都能迁移。

> 最后一条建议：**每次"可能把自己锁外面"的操作前，先打个快照或备份配置。**
> 这个习惯能让你在没有把握的时候依然敢于动手——而敢于动手，是学会运维的唯一途径。
