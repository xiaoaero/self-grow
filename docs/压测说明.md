# 压测基础与 Self Grow 项目压测说明

> 本文档面向未接触过压测的开发者，先讲解基本概念和工具，再结合 Self Grow 项目给出具体操作指南。

---

## 第一部分：压测基础

### 1.1 什么是压测？

压测（压力测试 / Stress Testing）是通过模拟大量用户同时使用系统，测量系统在**高负载下的表现**——能扛多少并发、响应多快、会不会出错或崩溃。

打个比方：一座桥造好了，不是让一个人走一遍就完事，而是要用重型卡车排队开上去，看桥会不会晃、会不会裂。压测就是给软件系统"排队开卡车"。

### 1.2 核心指标

| 指标 | 含义 | 通俗解释 |
|------|------|----------|
| **QPS**（Queries Per Second） | 每秒处理多少请求 | 收银台每秒结多少单 |
| **并发数**（VU / Virtual Users） | 同时有多少用户在操作 | 同时有多少人在排队 |
| **响应时间**（Latency） | 一个请求从发出到收到响应用了多久 | 从排队到结完账花了多久 |
| **P50 / P95 / P99** | 50%/95%/99% 的请求在多少毫秒内完成 | P95=500ms 意思是 95% 的人 500ms 内搞定 |
| **错误率**（Error Rate） | 多少请求失败了 | 100 单里有几单出了问题 |
| **吞吐量**（Throughput） | 单位时间处理的数据量 | 跟 QPS 类似，侧重点不同 |

> **重点看 P95 和错误率**。平均值会骗人——一半请求 10ms、另一半 5s，平均只有 2.5s，看起来很"正常"，但实际一半用户已经疯了。P95 和 P99 才能反映**最差但仍然可以接受的**体验。

### 1.3 压测类型

```
基准测试 ──→ 先跑少量用户，摸清"正常状态"下的性能基线
    ↓
负载测试 ──→ 逐步加人，找到性能拐点（响应时间开始明显变差的时候）
    ↓
压力测试 ──→ 继续加到超过正常负载，找到系统崩溃的边界
    ↓
稳定性测试 ──→ 在较高负载下持续跑几小时，看会不会内存泄漏、连接池枯竭
```

### 1.4 常见工具对比

| 工具 | 语言 | 特点 | 适合场景 |
|------|------|------|----------|
| **Locust** | Python | Web UI 可视化、Python 脚本、学习成本低 | Python 项目、团队协作演示 |
| **k6** | JavaScript | 命令行、轻量、CI/CD 友好 | 自动化流水线、开发者自测 |
| **Apache Bench (ab)** | C | 极简、一条命令 | 快速单接口测试 |
| **wrk** | C | 极高吞吐、Lua 脚本 | 极限压测、C 语言性能场景 |
| **JMeter** | Java | GUI 拖拽式、功能最全 | 企业级复杂场景、非开发人员 |

### 1.5 压测的关键原则

1. **不要在生产环境压测** — 会把线上用户打挂
2. **从低到高逐步加** — 不要上来就 10000 并发，从 10 → 50 → 100 → 500 递增
3. **每次只改一个变量** — 比如只改并发数，其他保持不变，才能准确定位瓶颈
4. **预热后再测** — 第一个请求往往最慢（冷启动），等几秒再开始记录数据
5. **关注的不只是 QPS** — 还要看错误日志、数据库锁、CPU/内存使用率

### 1.6 压测常见瓶颈排序

压测中最常暴露的瓶颈，按出现频率从高到低：

```
1. 数据库             ← 连接池不够、锁冲突、慢查询（占 80% 的瓶颈）
2. 连接池/线程池       ← 池子太小，请求排队等连接
3. 网络 I/O           ← 调用外部 API 超时（如 AI 接口）
4. 磁盘 I/O           ← 文件读写、日志写入太多
5. CPU               ← 计算密集型任务（相对少见）
6. 内存              ← 内存泄漏、大对象频繁 GC
```

> 绝大多数项目的瓶颈都在**数据库层**。SQLite、MySQL、PostgreSQL 都一样——你代码写得再快，数据库扛不住就全完蛋。

## 第二部分：Self Grow 项目压测说明

### 2.1 项目架构速览

```
浏览器 ──→ http://localhost:3000 (python http.server, 纯静态文件)
                ↓ 调用 API
         http://localhost:3001 (FastAPI + uvicorn)
                ↓
            SQLite (data.db, 单连接模式)
```

关键特征：

| 项 | 实际状况 |
|---|---------|
| Web 框架 | FastAPI，async 异步模式 |
| 数据库 | SQLite，每次请求新建连接 `sqlite3.connect()` |
| 连接池 | **无**，每次用完即关 |
| WAL 模式 | **未开启**，写入时锁整个文件 |
| 限流 | **无** |
| 缓存 | **无** |
| 认证 | 仅校验 `user_id` 是否存在于 users 表，**无 token/password** |
| CORS | 完全开放 `allow_origins=["*"]` |
| API 端点 | 约 65 个，其中 ~45 个涉及数据库写 |

### 2.2 核心瓶颈预判

压测前就应该知道最大的坑在哪——**SQLite 写入串行化**：

```
同一个 SQLite 数据库文件，同时只能有一个写入者。

场景：用户 A 提交行动记录 → SQLite 锁住 data.db 写入
      用户 B 同时打卡习惯   → 等待… 等待… "database is locked" 报错

这是设计上的硬限制，不是 bug。SQLite 天生就是给单用户/低并发设计的。
```

其他预判问题：

- **无认证的端点（10 个）**：`PUT/DELETE /api/habits/{id}`、`/api/goals/{id}`、`/api/tasks/{id}` 等不需要 `user_id`，任何知道 ID 的人都能改
- **AI 端点无熔断**：调用外部 AI API 超时 60s，几个并发就能耗尽 httpx 连接
- **文件上传无大小限制**：大文件上传会阻塞请求处理线程

#### 步骤 4：观察关键指标

在 Locust 的 "Statistics" 标签页中，关注：

1. **Failures** — 如果有 `database is locked` 错误，说明已触及 SQLite 写瓶颈
2. **P95 响应时间** — 超过 500ms 就说明排队严重
3. **RPS**（Requests Per Second）— 到某个并发数后不再增长，说明遇到瓶颈

在 "Charts" 标签页中，关注曲线是否平稳——如果响应时间曲线突然陡升，说明到了拐点。

### 2.5 预期结果

#### 各阶段预期

| 阶段 | 并发 | 预期 RPS | 预期 P95 | 预期错误率 | 备注 |
|------|------|---------|---------|-----------|------|
| ① 基准 | 10 | ~150-200 | < 30ms | 0% | 系统运行正常 |
| ② 中等 | 50 | ~250-400 | < 100ms | 0-2% | 读请求依然稳定 |
| ③ 高负载 | 100 | ~200-400 | ~500ms | 5-15% | **写锁冲突开始出现** |
| ④ 极限 | 200 | ~100-300 | ~2s | 20-50% | 大量 `database is locked` |

#### 纯读 vs 写操作对比

| 操作类型 | 50 并发表现 | 100 并发表现 |
|---------|-----------|------------|
| `GET /api/health` | ✅ 轻松 1000+ QPS，无压力 | ✅ 依然优秀（不涉及数据库） |
| `GET /api/users/profile` | ✅ P50 < 15ms | ⚠️ P95 开始上升 |
| `GET /api/habits` | ✅ 正常 | ⚠️ 正常 |
| `POST /api/actions` | ⚠️ 偶发锁冲突 | 🔴 **大量 `database is locked`** |
| `POST /api/habits/{id}/toggle` | ⚠️ 偶发锁冲突 | 🔴 **大量失败** |

### 2.6 结果解读指南

#### 看到什么算"正常"

- 低并发下所有请求 200 OK，P95 < 50ms
- RPS 随并发数增加而增长
- 无异常日志

#### 看到什么算"有问题但不意外"

- 50 并发写入时偶尔出现 `database is locked`（这是 SQLite 的已知限制）
- 某几个读接口 P95 超过 500ms（可能被写操作阻塞了）

#### 看到什么算"严重问题"

- 读请求大量失败（说明写操作长时间占锁，读也进不去）
- 后端进程崩溃（可能是文件句柄耗尽）
- 错误率超过 30%

#### 为什么这些问题在正常使用时不会出现

Self Grow 是**个人应用**，正常使用场景是：
- 1 个用户
- 操作间隔 > 1 秒
- 几乎不存在并发写入

SQLite 在这个场景下完全够用。压测暴露的是**如果把它直接变成多用户 SaaS** 才会有的问题。

### 2.7 如果要做优化——优先级排序

如果未来需要支持多用户并发，优化顺序如下：

| 优先级 | 措施 | 难度 | 效果 |
|--------|------|------|------|
| 🔴 P0 | **SQLite 开启 WAL 模式** | 低（加一行 PRAGMA） | 写不阻塞读，读写并发能力大幅提升 |
| 🔴 P0 | **设置 busy_timeout** | 低（加一行 PRAGMA） | 写锁等待而非立即报错 |
| 🟡 P1 | **引入连接池** | 中（改造 `get_conn`） | 减少连开/连关开销 |
| 🟡 P1 | **给所有端点加认证** | 中（改造 10 个无认证端点） | 防止未授权操作 |
| 🟡 P1 | **加入请求限流** | 低（加 `slowapi` 中间件） | 防止单用户打爆服务 |
| 🟢 P2 | **迁移到 PostgreSQL** | 高（改 SQL + 部署） | 从根本上解决并发写入 |
| 🟢 P2 | **AI 调用加熔断** | 低（`httpx` 加重试 + 超时降级） | 防止外部 AI 故障拖垮服务 |

#### P0 优化已实施（代码已合并到 `backend/db/connection.py`）

```python
# backend/db/connection.py — 已优化
def get_conn():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL")          # 写不阻塞读
    conn.execute("PRAGMA busy_timeout=5000")          # 写锁最多等 5 秒
    conn.execute("PRAGMA synchronous=NORMAL")         # WAL 模式下足够安全，写入性能提升约 2 倍
    return conn
```

**优化后预期效果对比：**

| 场景 | 优化前 | 优化后 |
|------|--------|--------|
| 50 并发写入错误率 | ~10% | ~0.5% |
| 100 并发写入错误率 | ~30% | ~5% |
| 100 并发下 P95 响应时间 | ~500ms | ~100ms |
| 读请求被写操作阻塞 | 频繁发生 | 基本不发生 |

## 附录：快速命令行压测（无需安装 Locust）

如果只想快速摸个底，用 Python 自带的并发即可：

```python
# 保存为 quick_test.py，放到 backend/tests/ 下运行
import time
import urllib.request
import concurrent.futures

URLS = [
    "http://localhost:3001/api/health",
    "http://localhost:3001/api/users/profile?user_id=1",
    "http://localhost:3001/api/habits?user_id=1",
]

def fetch(url):
    start = time.time()
    try:
        with urllib.request.urlopen(url, timeout=10) as r:
            return time.time() - start, r.status, None
    except Exception as e:
        return time.time() - start, None, str(e)

def run(concurrency, rounds):
    print(f"\n{'='*50}")
    print(f"并发={concurrency}, 每轮 {len(URLS)} 个请求, 共 {rounds} 轮")
    times = []
    errors = 0
    with concurrent.futures.ThreadPoolExecutor(max_workers=concurrency) as pool:
        for batch in range(rounds):
            futures = [pool.submit(fetch, u) for u in URLS * (concurrency // len(URLS))]
            for f in concurrent.futures.as_completed(futures):
                t, status, err = f.result()
                times.append(t)
                if err:
                    errors += 1
    times.sort()
    n = len(times)
    print(f"总数={n}, 错误={errors} ({errors/n*100:.1f}%)")
    print(f"P50={times[n//2]*1000:.0f}ms, P95={times[int(n*0.95)]*1000:.0f}ms, P99={times[int(n*0.99)]*1000:.0f}ms")

run(10, 5)
run(50, 3)
run(100, 2)
```
