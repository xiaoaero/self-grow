## 第一部分：压测基础

### 1.1 什么是压测？

压测（压力测试 / Stress Testing）是通过模拟大量用户同时使用系统，测量系统在**高负载下的表现**——能扛多少并发、响应多快、会不会出错或崩溃。

打个比方：一座桥造好了，不是让一个人走一遍就完事，而是要用重型卡车排队开上去，看桥会不会晃、会不会裂。压测就是给软件系统"排队开卡车"。

### 1.2 核心指标

| 指标 | 含义 | 通俗解释 |
|------|------|----------|
| **QPS**（Queries Per Second） | 每秒处理多少请求 | 收银台每秒结多少单 |
| **并发数**（VU / Virtual Users） | 同时有多少用户在操作 | 同时有多少人在排队 |
| **响应时间**（Latency） | 一个请求从发出到收到响应用了多久 | 从排队到结完账花了多久 |
| **P50 / P95 / P99** | 50%/95%/99% 的请求在多少毫秒内完成 | P95=500ms 意思是 95% 的人 500ms 内搞定 |
| **错误率**（Error Rate） | 多少请求失败了 | 100 单里有几单出了问题 |
| **吞吐量**（Throughput） | 单位时间处理的数据量 | 跟 QPS 类似，侧重点不同 |

> **重点看 P95 和错误率**。平均值会骗人——一半请求 10ms、另一半 5s，平均只有 2.5s，看起来很"正常"，但实际一半用户已经疯了。P95 和 P99 才能反映**最差但仍然可以接受的**体验。

### 1.3 压测类型

```
基准测试 ──→ 先跑少量用户，摸清"正常状态"下的性能基线
    ↓
负载测试 ──→ 逐步加人，找到性能拐点（响应时间开始明显变差的时候）
    ↓
压力测试 ──→ 继续加到超过正常负载，找到系统崩溃的边界
    ↓
稳定性测试 ──→ 在较高负载下持续跑几小时，看会不会内存泄漏、连接池枯竭
```

### 1.4 常见工具对比

| 工具 | 语言 | 特点 | 适合场景 |
|------|------|------|----------|
| **Locust** | Python | Web UI 可视化、Python 脚本、学习成本低 | Python 项目、团队协作演示 |
| **k6** | JavaScript | 命令行、轻量、CI/CD 友好 | 自动化流水线、开发者自测 |
| **Apache Bench (ab)** | C | 极简、一条命令 | 快速单接口测试 |
| **wrk** | C | 极高吞吐、Lua 脚本 | 极限压测、C 语言性能场景 |
| **JMeter** | Java | GUI 拖拽式、功能最全 | 企业级复杂场景、非开发人员 |

### 1.5 压测的关键原则

1. **不要在生产环境压测** — 会把线上用户打挂
2. **从低到高逐步加** — 不要上来就 10000 并发，从 10 → 50 → 100 → 500 递增
3. **每次只改一个变量** — 比如只改并发数，其他保持不变，才能准确定位瓶颈
4. **预热后再测** — 第一个请求往往最慢（冷启动），等几秒再开始记录数据
5. **关注的不只是 QPS** — 还要看错误日志、数据库锁、CPU/内存使用率

### 1.6 压测常见瓶颈排序

压测中最常暴露的瓶颈，按出现频率从高到低：

```
1. 数据库             ← 连接池不够、锁冲突、慢查询（占 80% 的瓶颈）
2. 连接池/线程池       ← 池子太小，请求排队等连接
3. 网络 I/O           ← 调用外部 API 超时（如 AI 接口）
4. 磁盘 I/O           ← 文件读写、日志写入太多
5. CPU               ← 计算密集型任务（相对少见）
6. 内存              ← 内存泄漏、大对象频繁 GC
```

> 绝大多数项目的瓶颈都在**数据库层**。SQLite、MySQL、PostgreSQL 都一样——你代码写得再快，数据库扛不住就全完蛋。

## 第二部分：Self Grow 项目压测说明

### 2.1 项目架构速览

```
浏览器 ──→ http://localhost:3001 (FastAPI + uvicorn，同时提供前端静态文件)
                ↓ 同步 SQLAlchemy-free 原生 SQL（PyMySQL）
         MySQL 8.0 (DBUtils 连接池，池大小 20)
```

关键特征（**2026-09-24 核实**）：

| 项 | 实际状况 |
|---|---------|
| Web 框架 | FastAPI；**纯 CRUD 端点是同步 `def`**（FastAPI 自动丢线程池），AI 与流式端点是 `async` |
| 数据库 | **MySQL 8.0**（2026-09-23 彻底移除 SQLite），源码即 MySQL 原生 SQL |
| 连接池 | ✅ `DBUtils.PooledDB(blocking=True)`，池大小 20，`close()` = 归还连接 |
| 锁等待 | ✅ `lock_wait_timeout` / `innodb_lock_wait_timeout` 设成 **30 秒**（MySQL 默认是**一年**） |
| 时区 | ✅ 连接层 `SET time_zone='+08:00'`（建表默认值 `now()` 也走它） |
| 限流 | **无**（单用户场景够用；公网暴露前应加） |
| 缓存 | **无**（多模型实例有 LRU 缓存，但业务数据不缓存） |
| 认证 | ✅ **JWT 双令牌**（Access 2h + Refresh 30d 轮换）+ RBAC + 可撤销 API Key；凭证解析收敛在 `routers/deps.py` |
| CORS | 默认放行 localhost / 127.0.0.1 任意端口（`allow_origin_regex`）；公网需用 `SELF_GROW_CORS_ORIGINS` 显式指定 |
| API 端点 | **101 个**（`app.openapi()` 实测），全部经 `get_current_user` 或显式豁免 |

### 2.1.1 认证现状

> ⚠️ 这一节原来记的是"`?user_id=` 可被任意伪造、这是项目最严重的安全缺口" ——
> **2026-09-13 已落地 JWT 鉴权，该缺口已关闭**。压测脚本要注意：现在请求必须带凭证。

凭证解析优先级（全在 `routers/deps.py` 一处）：

```

④ 都没有                         → 401
```

> **压测前先拿一个 token**：`POST /api/auth/login`（`{"username":"test","password":"test123456"}`），
> 之后每个请求带 `Authorization: Bearer <access_token>`。
> `?user_id=` 仍可传（老代码兼容），但**不再作为身份依据**。
> 详见 [登录鉴权方案选型](./登录鉴权方案选型.md)。

### 2.2 核心瓶颈预判

压测前就应该知道最大的坑在哪 —— **两个"无限等待"叠在一起**：

```
① DBUtils PooledDB(blocking=True)：池满时**无限等待，没有超时**
② MySQL lock_wait_timeout 默认 31536000 秒（一年）

场景：协调 Agent 用 asyncio.gather 并行跑 6 个子 Agent，
      每个工具调用都 to_thread + get_conn()
      → 池被占满 → 后面的请求无限排队（不报错、不返回）
      → 整站"看起来还活着，但一个都不回"

这不是 bug，是"默认值不适合这个用法"——所以池大小设 20 且不往下调，
锁等待显式设 30 秒，让它在超时后**报错**而不是静默挂死。
```

其他预判问题：

- **写入路径有明显的串行点**：MySQL 单行 `UPDATE`（如 `users` 的等级/经验）会被行锁串行化。
  写密集压测能压出 `Lock wait timeout`，这是预期结果，不是 bug
- **AI 端点耗时远高于 CRUD**：外部模型调用几十秒是常态，`max_retries=0`，
  几个并发就能把线程池占满 —— 压测时 AI 端点要单列，别与 CRUD 混在一个百分比里
- **文件上传无大小限制**：大文件上传会阻塞请求处理（奖励图片上传）
- ~~**子图工具是同步调用**~~（**已于 2026-09-08 修复**）：原 `agents/base.py` 里 `tool_fn.invoke(args)` 为同步执行，在 async 节点中会阻塞事件循环、多域"并行"实际串行；现已改为 `await asyncio.to_thread(tool_fn.invoke, args)` 丢线程池，事件循环不再被卡住

1. **Failures** — 出现 `Lock wait timeout exceeded` 说明行锁竞争严重；

### 2.6 结果解读指南

#### 看到什么算"正常"

- 低并发下所有请求 200 OK，P95 < 50ms
- RPS 随并发数增加而增长
- 无异常日志

#### 看到什么算"有问题但不意外"

- 50 并发写入时偶尔出现 `Lock wait timeout exceeded`（同一条 `users` 行的经验更新会串行化）
- 某几个读接口 P95 超过 500ms（应用层面线程池被占，不是数据库扛不住）
- AI 端点 P95 几十秒（外部模型耗时，与并发无关）

#### 看到什么算"严重问题"

- **请求既不返回也不报错**（连接池被打满 + `blocking=True` 无超时）——
  这是本项目最需要警惕的失败模式，见 §2.2 第 ① 条
- 后端进程崩溃（可能是线程池 / 文件句柄耗尽）
- 错误率超过 30%

#### 为什么这些问题在正常使用时不会出现

Self Grow 是**个人应用**，正常使用场景是：
- 1 个用户，操作间隔 > 1 秒，几乎不存在并发写入
- 连接池 20 在单用户下绰绰有余

压测暴露的是**如果把它直接变成多用户 SaaS** 才会有的问题：
到那时要动的是「连接池调大 + 加限流 + 会话状态外置」，而不是换数据库。

### 2.7 如果要做优化——优先级排序

如果未来需要支持多用户并发，优化顺序如下：

| 优先级 | 措施 | 难度 | 效果 | 状态 |
|--------|------|------|------|------|
| ✅ 已做 | **JWT 双令牌鉴权** | 中 | 关掉"`?user_id=` 可伪造"这个最大缺口（见 §2.1.1） | 2026-09-13 落地 |
| ✅ 已做 | **引入连接池**（DBUtils，池 20） | 中 | 省掉每次请求的 TCP + 认证握手 | 已实施 |
| ✅ 已做 | **锁等待显式设 30 秒** | 低（连接层一行） | 从"静默挂死"变成"按时报错" | 已实施 |
| ✅ 已做 | **写操作统一 try/rollback/finally** | 低 | 失败也归还连接，不留"锁坟场" | 已实施 |
| ✅ 已做 | **纯 CRUD 端点改同步 `def`** | 低 | FastAPI 自动丢线程池，事件循环空出来 | 已实施 |
| 🟡 P1 | **加入请求限流** | 低（`slowapi` 中间件） | 防止单用户/异常流量打爆服务 | **未做** |
| 🟡 P1 | **AI 调用加熔断/重试** | 低（超时 + 降级） | 防止外部 AI 故障拖垮线程池 | **未做** |
| 🟢 P2 | **会话状态外置**（checkpointer 换持久化） | 中 | 多实例部署的前提 | **未做** |
| 🟢 P2 | **定时任务加分布式锁** | 低（MySQL `GET_LOCK`） | 多副本下不重复执行 | **未做** |

#### 已实施的两条关键改动（代码见 `backend/db/backend.py`）

```python
# ① 连接池：池满时 blocking=True 会无限等待，所以池不能小，且必须能观测
_POOL = PooledDB(creator=pymysql, maxconnections=20, blocking=True, ...)

# ② 连接初始化命令：MySQL 默认 lock_wait_timeout 是 31536000 秒（一年），
#    配合上面那条"无限等待"，一旦有锁竞争就是整站挂死且无日志
_INIT_COMMAND = (
    "SET time_zone = '+08:00', "          # 时间口径（建表默认值 now() 也走它）
    "lock_wait_timeout = 30, "            # 不要默认的一年
    "innodb_lock_wait_timeout = 30"
)
```

| 场景 | 改造前（估算） | 改造后（估算） |
|------|--------|--------|

## 附录：快速命令行压测（无需安装 Locust）

如果只想快速摸个底，用 Python 自带的并发即可：

```python
# 保存为 quick_test.py，放到 backend/tests/ 下运行
import time
import urllib.request
import concurrent.futures

URLS = [
    "http://localhost:3001/api/health",
    "http://localhost:3001/api/users/profile?user_id=1",
    "http://localhost:3001/api/habits?user_id=1",
]

def fetch(url):
    start = time.time()
    try:
        with urllib.request.urlopen(url, timeout=10) as r:
            return time.time() - start, r.status, None
    except Exception as e:
        return time.time() - start, None, str(e)

def run(concurrency, rounds):
    print(f"\n{'='*50}")
    print(f"并发={concurrency}, 每轮 {len(URLS)} 个请求, 共 {rounds} 轮")
    times = []
    errors = 0
    with concurrent.futures.ThreadPoolExecutor(max_workers=concurrency) as pool:
        for batch in range(rounds):
            futures = [pool.submit(fetch, u) for u in URLS * (concurrency // len(URLS))]
            for f in concurrent.futures.as_completed(futures):
                t, status, err = f.result()
                times.append(t)
                if err:
                    errors += 1
    times.sort()
    n = len(times)
    print(f"总数={n}, 错误={errors} ({errors/n*100:.1f}%)")
    print(f"P50={times[n//2]*1000:.0f}ms, P95={times[int(n*0.95)]*1000:.0f}ms, P99={times[int(n*0.99)]*1000:.0f}ms")

run(10, 5)
```
