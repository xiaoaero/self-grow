# 第一部分：异步编程基础

## 1.1 为什么要异步？

### 大白话：餐厅服务员的比喻

想象一个餐厅，服务员的工作模式分两种：

**同步（sync）模式**：
> 服务员点完一桌菜，就**站在厨房门口死等**，菜做好了才端过去，然后才去招呼下一桌。一个服务员同一时刻只能服务一桌。

**异步（async）模式**：
> 服务员点完一桌菜就立刻去招呼下一桌，厨房做好了会"叫号"，服务员再回来端菜。一个服务员能同时服务很多桌。

**本质区别**：同步在"等待"的时候，人是**闲着**的；异步在"等待"的时候，人**去干别的**。

### 为什么 Web 应用特别需要异步？

Web 服务器的大部分时间都在**等待**：

- 等数据库查询返回（几毫秒~几十毫秒）
- 等外部 API 返回（几百毫秒~几十秒，尤其 AI 接口）
- 等文件读写完成

这些等待期间，CPU 是**空闲**的。如果同步处理，一个请求在等数据库时，整个服务器就傻等着，其他请求排队。异步让服务器在"等待 A 请求的数据库"时，去处理 B 请求。

**项目结合**：Self Grow 后端有 **126 个 `async def` 函数、50 处 `await`**。比如协调 Agent 等 AI 大模型回复（可能要十几秒），这十几秒里服务器可以同时处理其他用户的请求。

### 异步 = 快吗？

**不是！** 这是个关键认知：

- 异步**不能**让单个任务变快（一次数据库查询该多快还是多快）
- 异步让**多个任务"同时"进行**，提高的是**吞吐量**（单位时间处理的任务数）

**大白话**：异步不是"把一碗饭煮得更快"，而是"同时煮很多碗饭"。

## 1.2 同步 vs 异步 vs 多线程 vs 多进程

这是新手最容易混淆的四个概念：

| 方案 | 原理 | 适合场景 | 优点 | 缺点 |
|------|------|---------|------|------|
| **同步** | 顺序执行，一个做完再下一个 | 简单脚本 | 简单直观 | 等待时资源闲置 |
| **异步** | 单线程内"协作式"切换任务 | **大量 I/O 等待**（网络/数据库/文件） | 开销小、可扛高并发 | 代码稍复杂、阻塞操作会拖垮 |
| **多线程** | 多个线程真正并行（但 Python 有 GIL 限制） | I/O + 需要"真正同时" | 概念直观 | 线程切换开销、共享数据易出 bug |
| **多进程** | 多个进程各自独立 | **CPU 密集计算**（算图、压缩） | 绕过 GIL、真并行 | 内存开销大、通信麻烦 |

**核心判断标准**：

- 任务是**等 I/O**（网络、数据库、文件）→ 用**异步**（或线程）
- 任务是**纯计算**（跑循环、算矩阵）→ 用**多进程**（或线程，但 Python 的 GIL 让多线程算不了 CPU 密集任务）

**Python 的 GIL 是什么**：全局解释器锁，它保证同一时刻只有一个线程在执行 Python 字节码。所以 Python 的"多线程"对 CPU 密集任务没有加速效果，但对 I/O 密集任务有用（等 I/O 时会释放 GIL）。

**项目结合**：Self Grow 是典型的 I/O 密集应用（查数据库、调 AI API），所以用**异步**最合适。但注意——项目的数据库操作是**同步**的（`PyMySQL`），这在异步框架里有坑，见 §4.1。

## 1.3 核心概念

| 概念 | 大白话 |
|------|--------|
| **协程（coroutine）** | 用 `async def` 定义的函数，能被"暂停"和"恢复" |
| **事件循环（event loop）** | 调度中心，负责"谁先跑、谁暂停、谁恢复" |
| **await** | "我先挂起，去干别的，等这个结果好了再回来" |
| **Task** | 把协程包装成"可被调度"的任务 |
| **Future** | 一个"未来才会有结果"的占位符 |

### 事件循环如何工作

```
事件循环（单线程）
   │
   ├── 任务 A：await 数据库查询 ──► 挂起，去干别的
   ├── 任务 B：await AI 接口 ─────► 挂起，去干别的
   ├── 任务 C：正在执行 ──────────► 跑
   │
   └── 数据库查询好了 → 通知事件循环 → 恢复任务 A 继续
```

**关键**：事件循环是**单线程**的，它靠"任务主动让出控制权"（await）来实现并发，而不是靠多个线程同时跑。

## 1.4 什么时候该用异步？

### ✅ 适合异步

- Web 服务器（FastAPI 就是异步的）
- 大量外部 API 调用（AI、爬虫）
- 数据库读写（配合异步驱动）
- 文件读写、网络下载

### ❌ 不适合异步

- 纯 CPU 计算（用多进程）
- 简单的、跑完就退出的脚本（直接同步更简单）

**项目结合**：协调 Agent 的"并行派发 6 个子 Agent 查 AI"是典型的异步场景——6 个 AI 调用如果串行要 6 倍时间，并行只要约 1 倍时间。

## 1.5 异步编程的发展史（为什么语法这么"绕"）

理解了历史，就理解了为什么 `async/await` 要这么写。

### 第一代：多线程/多进程

最早解决"同时干多件事"的办法是开多个线程。但线程有三大麻烦：

1. **共享数据要加锁**（多个线程同时改一个变量会乱）
2. **切换开销大**（操作系统层面的切换，成本高）
3. **Python 的 GIL** 让多线程对 CPU 密集任务没用

### 第二代：回调（Callback）

后来出现了"回调"：启动一个操作时，传入"完成后要执行的函数"。

```javascript
// 回调风格（JavaScript 早期）
fetchData(function(result) {
    process(result, function(data) {
        save(data, function() {   // 层层嵌套
            // 回调地狱（callback hell）
        });
    });
});
```

**问题**：层层嵌套，代码可读性极差，错误处理困难。这就是著名的"回调地狱"。

### 第三代：async/await（现代方案）

`async/await` 让异步代码**看起来像同步代码**：

```python
async def fetch_and_save():
    result = await fetch_data()      # 看起来像同步，其实是异步
    data = await process(result)
    await save(data)
```

**没有嵌套，没有回调，可读性回到同步时代，但保留了异步的性能。** 这就是现代语言（Python、JavaScript、C#、Rust 等）都采用 `async/await` 的原因。

### Python 的 asyncio

Python 从 **3.4** 开始引入 `asyncio`，3.5 加入 `async/await` 语法糖，此后不断完善（3.7 的 `asyncio.run`、3.9 的 `to_thread`、3.11 的性能大幅优化）。

**项目结合**：Self Grow 用的是 Python 3.12（`pixi.toml` 里 `python = "3.12.*"`），享受了 asyncio 的最新优化。

## 1.6 协程 vs 线程 vs 进程：深入对比

| 维度 | 协程（asyncio） | 线程（threading） | 进程（multiprocessing） |
|------|----------------|------------------|------------------------|
| 切换成本 | 极低（用户态切换，纳秒级） | 中（内核态切换，微秒级） | 高（进程切换） |
| 内存开销 | 极小（KB 级） | 小（MB 级栈） | 大（独立内存空间） |
| 并发数量 | 可上万 | 几百 | 几十 |
| 数据共享 | 共享（需注意交错） | 共享（需加锁） | 不共享（需 IPC） |
| 适合 | I/O 密集 | I/O 密集（需真并发时） | CPU 密集 |
| Python GIL 影响 | 无（单线程） | 有（CPU 密集无法加速） | 无（各进程独立） |
| 是否"真并行" | 否（单线程协作） | 是（但受 GIL 限） | 是 |

### 关键结论

1. **协程是"假的并行"**：单线程内靠"让出控制权"实现并发，同一时刻只有一个协程在跑。所以 CPU 密集任务用协程没用。
2. **线程是"真的并行"，但 Python 有 GIL**：I/O 等待时会释放 GIL，所以多线程对 I/O 密集有效，对 CPU 密集无效。
3. **进程是"彻底的并行"**：各进程独立 GIL、独立内存，CPU 密集就用它。

### 什么时候用哪个（决策口诀）

```
等 I/O（网络/数据库/文件）→ 协程（首选，开销最小）
   └─ 需要"真正同时跑"且库不支持异步 → 线程
纯计算（CPU 密集）→ 进程
```

**项目结合**：Self Grow 的数据库操作是同步的 `PyMySQL`（不支持原生异步），所以理论上"查库"这部分应该用线程而非协程。但项目实际把同步查库写进了 `async` 函数里，这就埋下了 §4.1 那个"阻塞事件循环"的坑。

# 第二部分：Python 异步核心语法

## 2.1 async def / await

```python
# 定义协程
async def fetch_data():
    result = await db_query()     # 等待数据库查询（挂起，让出控制权）
    return result
```

- `async def` 定义一个**协程函数**，调用它不会立即执行，而是返回一个协程对象
- `await` 只能在 `async def` 函数内使用，作用是"等待一个异步操作完成"

**项目结合**：`backend/routers/coordinator.py` 的 `chat` 端点就是协程：

```python
@router.post("/chat")
async def chat(request: ChatRequest, user=Depends(get_current_user)):
    state = await run_coordinator(state)   # 等待协调器跑完（内部有多个 AI 调用）
```

## 2.2 事件循环：asyncio.run

协程不能自己跑，需要事件循环驱动它：

```python
import asyncio

async def main():
    print("hello")

asyncio.run(main())   # 启动事件循环，运行 main 直到结束
```

**FastAPI 的特别之处**：FastAPI（基于 uvicorn）**自己管理事件循环**，你不需要写 `asyncio.run`。你只要定义 `async def` 端点，uvicorn 会自动把请求调度到这个事件循环里。

## 2.3 并发：gather / create_task / wait

三个工具都能实现并发，但语义不同：

### ① asyncio.gather —— 并发执行，等全部完成

```python
results = await asyncio.gather(task_a(), task_b(), task_c())
# 三个协程并发执行，全部完成后返回结果列表
```

**项目结合**：`backend/services/coordinator/graph.py` 用它并行派发多个子 Agent：

```python
coros = [_run_one_subgraph(task["domain"], ...) for task in pending_tasks]
outcomes = await asyncio.gather(*coros, return_exceptions=True)
```

- `*coros`：把列表展开成多个参数
- `return_exceptions=True`：某个协程抛异常时不中断整体，而是把异常对象放进结果列表

### ② asyncio.create_task —— 手动创建任务，不立即等待

```python
task = asyncio.create_task(some_coroutine())   # 立即开始执行，不阻塞
# ... 干别的
result = await task                            # 之后再等待结果
```

`create_task` 适合"先启动、后收集"的场景。

### ③ asyncio.wait —— 等任意一个完成

```python
done, pending = await asyncio.wait(
    [task_a, task_b],
    return_when=asyncio.FIRST_COMPLETED,   # 任意一个完成就返回
)
```

`asyncio.wait` 比 `gather` 更灵活，可以指定"等全部完成"还是"等第一个完成"。

### 三者对比

| 工具 | 何时返回 | 用途 |
|------|---------|------|
| `gather` | 全部完成 | 并行跑，收集所有结果 |
| `create_task` | 立即（任务后台跑） | 先启动后等待 |
| `wait` | 可配置（任一/全部） | 需要"抢先完成"语义 |

### 补充：awaitable 的三种类型

`await` 后面能跟的东西，统称 **awaitable**（可等待对象）。Python 里有三种：

| 类型 | 是什么 | 例子 |
|------|--------|------|
| **协程（coroutine）** | `async def` 函数调用返回的对象 | `await foo()` |
| **Task** | 被事件循环调度的协程 | `await asyncio.create_task(foo())` |
| **Future** | 低层的"未来结果"占位符 | `await loop.create_future()` |

日常写代码，绝大多数时候你 `await` 的是**协程**或 **Task**。Future 是底层概念，`asyncio` 内部用，业务代码很少直接碰。

### 补充：Semaphore（信号量）—— 限制并发数量

`asyncio.gather` 会**同时**启动所有协程。但有时候你不想"全部同时"——比如同时调 100 个外部 API，可能把对方打爆、或耗尽自己的连接。

**Semaphore（信号量）** 就是"并发闸门"：最多允许 N 个协程同时通过。

```python
import asyncio

sem = asyncio.Semaphore(5)   # 最多同时 5 个

async def fetch(url):
    async with sem:                    # 拿到"通行证"才能进
        return await call_api(url)     # 超过 5 个就在这排队

# 100 个任务，但最多同时 5 个在跑
await asyncio.gather(*[fetch(u) for u in urls])
```

**大白话**：信号量像"5 个窗口的银行"——100 个人来办业务，最多 5 个人同时在窗口，其余排队，办完一个进一个。

**项目结合**：协调 Agent 的 `asyncio.gather` 并行派发子 Agent 时**没有**用信号量限流（子 Agent 最多 6 个，量不大，暂不需要）。但如果将来子 Agent 数量增多，或者要批量调外部 API，就应该加 Semaphore 限流。

### 补充：asyncio.Queue（异步队列）—— 生产者消费者

`asyncio.Queue` 是协程间安全传递数据的队列，经典的生产者-消费者模式：

```python
import asyncio

queue = asyncio.Queue(maxsize=10)

async def producer():
    for i in range(100):
        await queue.put(i)       # 队列满了会等待
    await queue.put(None)        # 结束信号

async def consumer():
    while True:
        item = await queue.get() # 队列空了会等待
        if item is None:
            break
        await process(item)

await asyncio.gather(producer(), consumer())
```

**为什么用队列而不是普通 list**：普通 list 在多协程交错时会有竞态（见 §4.6），而 `asyncio.Queue` 内部处理好了"满了阻塞、空了等待"的逻辑。

**项目结合**：`expression.py` 的语音识别"收音频 → 发结果"其实就是一个生产者-消费者场景，不过它用的是"轮询 + 状态检查"而非队列（`asyncio.sleep(0.05)` 轮询 ASR 结果），改造成队列会更优雅。

## 2.4 取消与超时

### 取消任务

```python
task = asyncio.create_task(long_running())
# ... 决定不跑了
task.cancel()          # 请求取消
try:
    await task
except asyncio.CancelledError:
    print("任务被取消了")
```

`cancel()` 会让任务抛 `CancelledError`，你可以在 `except` 里做清理工作。

### 超时

```python
try:
    result = await asyncio.wait_for(slow_task(), timeout=10)
except asyncio.TimeoutError:
    print("超时了")
```

`wait_for` 是"设个闹钟"，超时自动取消任务。**调用外部 API（尤其 AI）一定要设超时**，否则一个慢请求会一直挂着。

## 2.5 异步上下文管理器（async with）

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app):
    # 启动时做的事
    scheduler.start()
    yield           # ← 运行期间停在这里
    # 关闭时做的事
    scheduler.shutdown()
```

和普通 `with` 一样，但 `__enter__` / `__exit__` 是异步的（可以 await）。

**项目结合**：`backend/main.py` 用它管理定时任务的启停：

```python
@asynccontextmanager
async def lifespan(app_instance):
    scheduler = AsyncIOScheduler(...)
    scheduler.add_job(run_daily_refresh, CronTrigger(hour=3, minute=0))
    scheduler.start()                  # 启动时：启动定时任务
    yield                              # 应用运行
    scheduler.shutdown(wait=False)     # 关闭时：停止定时任务
```

## 2.6 异步生成器（yield + async）

```python
async def event_generator():
    for i in range(10):
        yield f"data: {i}\n\n"    # 生成一块数据，暂停
```

异步生成器是"能 `await` 的生成器"，常配合流式响应使用（见 §3.6）。

# 第三部分：项目里的异步实战

> 这一部分逐个讲解 Self Grow 里**真实的异步代码**，理解它们就是最好的学习。

## 3.1 FastAPI 的 async 端点

**代码位置**：`backend/routers/coordinator.py`

```python
@router.post("/chat")
async def chat(request: ChatRequest, user=Depends(get_current_user)):
    state = await run_coordinator(state)
    return {"thread_id": thread_id, "reply": ..., "interrupts": ...}
```

- `async def` 端点：uvicorn 会用事件循环调度它
- `await run_coordinator(...)`：等待协调器完成（内部会调用 AI，可能耗时十几秒），这期间事件循环能处理其他请求

**为什么端点要写 `async`**：FastAPI 对 `async def` 端点在事件循环里跑，对 `def`（同步）端点丢线程池跑。如果端点里有 `await`（等 I/O），就该用 `async def`，这样才能发挥异步的并发优势。

## 3.2 并行派发：asyncio.gather

**代码位置**：`backend/services/coordinator/graph.py`

```python
coros = [
    _run_one_subgraph(task["domain"], task.get("instruction", ""), user_id, main_thread_id)
    for task in pending_tasks
]
outcomes = await asyncio.gather(*coros, return_exceptions=True)
```

**这段代码做的事**：

1. 用户说一句话，路由判断要调用 6 个子 Agent（记行动、查统计、建任务...）
2. 把 6 个子 Agent 的协程打包成列表
3. `asyncio.gather` **同时启动** 6 个，各自去调 AI
4. `return_exceptions=True`：某个子 Agent 失败了不影响其他

**对比**：如果串行 `for task in tasks: await run(task)`，6 个 AI 调用要 6 倍时间；`gather` 并行只需约 1 倍时间。

> ⚠️ 但这里有个隐藏问题：子 Agent 内部执行工具是**同步**的，导致并行不彻底，见 §4.1。

## 3.3 双向并发 + 取消：WebSocket 语音识别（最精彩的案例）

**代码位置**：`backend/routers/expression.py`（约 375-455 行）

这是项目里**最值得精读**的一段异步代码——语音识别（ASR）需要同时做两件事：**收音频** + **发识别结果**，任何一方出错都要停下来。

```python
async def receive_audio():
    while True:
        data = await websocket.receive_bytes()   # 收浏览器传来的音频分片
        if asr and asr.is_running:
            asr.send_audio(data)

async def send_results():
    while True:
        result = asr.get_result()
        if result:
            await websocket.send_json({"type": "transcript", "text": ...})
        await asyncio.sleep(0.05)   # 50ms 轮询一次识别结果

# 并发启动两个协程
receive_task = asyncio.create_task(receive_audio())
send_task = asyncio.create_task(send_results())

# 等任意一个完成（客户端断开 或 ASR 出错）
done, pending = await asyncio.wait(
    [receive_task, send_task],
    return_when=asyncio.FIRST_COMPLETED,
)

# 取消另一个还没完成的任务
for task in pending:
    task.cancel()
```

### 这段代码展示了哪些知识点？

1. **`create_task` 并发两个协程**：收和发同时进行
2. **`asyncio.wait(FIRST_COMPLETED)`**：任意一个结束（比如用户断开连接）就继续，不等另一个
3. **`task.cancel()`**：主动取消另一个任务
4. **`asyncio.sleep(0.05)`**：在 while 循环里主动让出控制权，避免死循环霸占事件循环
5. **`CancelledError` 处理**（在 `send_results` 内部）：
   ```python
   except asyncio.CancelledError:
       pass   # 被取消时优雅退出
   ```

**大白话**：这就像一个"双向对讲机"——一边听（收音频），一边说（发结果），哪边断了就挂断整体，并关闭另一边。

## 3.6 流式响应：StreamingResponse

**代码位置**：`backend/routers/coordinator.py`

```python
@router.get("/stream/{thread_id}")
async def stream_events(thread_id: str):
    async def event_generator():
        state = _get_state(thread_id)

    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

- `event_generator` 是**异步生成器**，`yield` 一块，客户端就收到一块

**用途**：AI 生成回答时，边生成边推送，用户不用等全部生成完。本项目已经全部实装：
8 个 AI 端点都是 `POST + SSE`，事件协议（`stage` / `token` / `error` / `done`）统一在
`backend/services/sse.py`；协调 Agent 是真逐 token，技能树 AI 与表达训练只推阶段进度。

```python
response = await llm_with_tools.ainvoke(full)   # 异步调用 LLM
```

LangChain 的每个同步方法几乎都有对应的异步版本：

| 同步 | 异步 | 含义 |
|------|------|------|
| `invoke` | `ainvoke` | 调用一次 |
| `stream` | `astream` | 流式调用 |
| `batch` | `abatch` | 批量调用 |

## 3.8 异步流式生成器：AI 打字机输出

**代码位置**：`backend/services/ai_client.py`

这是项目里**异步生成器最标准的用法**——AI 长文本"打字机式"输出：

```python
async def call_ai_text_stream(system_prompt, user_message, ...):
    llm = _get_llm(...)
    messages = [SystemMessage(content=system_prompt), HumanMessage(content=user_message)]

    async for chunk in llm.astream(messages):    # ① async for 迭代流
        if isinstance(chunk, ChatGenerationChunk):
            text = chunk.text
        else:
            text = getattr(chunk, "content", "") or ""
        if text:
            yield text                           # ② yield 一块，返回一块
```

### 这里涉及三个异步知识点

**① `async for`（异步迭代）**：和普通 `for` 一样循环，但每次迭代可以 `await`。`llm.astream()` 返回一个异步迭代器，AI 生成一块就吐一块。

**② `yield`（异步生成器）**：`call_ai_text_stream` 本身是异步生成器——它不一次返回全部结果，而是"生成一块、返回一块"。调用方用 `async for` 或 `await` 逐个接收。

**③ 为什么不重试**：代码注释里写得很清楚——"生成中断后重试无意义"。流式生成一旦开始，中断了从头重试只会浪费 token。

### 对比：一次性 vs 流式

| 方式 | 方法 | 用户体验 |
|------|------|---------|
| 一次性 | `await llm.ainvoke()` | 等十几秒，一次性拿到全文 |
| 流式 | `async for chunk in llm.astream()` | 边生成边显示，像打字机 |

**项目结合**：`call_ai_text_stream` 目前主要用于习惯分析等长文本场景。协调 Agent 的最终回复还没用上流式（SSE 端点还是占位），这是待优化项。

## 3.9 同步实现 vs 异步实现：同一件事的两种写法

项目里有两套 AI 调用方式，正好构成"同步 vs 异步"的完整对照：

### 旧链路（httpx 同步风格）

**代码位置**：`backend/services/ai_service.py`、`ai_action_service.py`

```python
# 用 httpx 直接发 HTTP 请求（旧链路，~90 行）
import httpx
resp = httpx.post(url, json=payload, headers=headers)   # 同步阻塞
data = resp.json()
```

**特点**：`httpx.post` 是**同步**的，发出去就等着，期间什么也干不了。

### 新链路（LangChain 异步风格）

**代码位置**：`backend/services/ai_client.py`、`coordinator/`

```python
# 用 LangChain 的异步接口
response = await llm.ainvoke(messages)              # 异步，等待期间可处理别的
async for chunk in llm.astream(messages):           # 异步流式
    ...
```

**特点**：`ainvoke` / `astream` 是**异步**的，等待 AI 回复期间，事件循环可以去处理其他请求。

### 为什么新链路更好？

1. **并发能力**：异步接口下，一个请求等 AI 时，服务器能处理其他请求；同步接口下，服务器就被"卡住"了
2. **流式输出**：`astream` 支持打字机式输出，`httpx.post` 只能等全部返回
3. **统一封装**：LangChain 屏蔽了不同模型厂商的 HTTP 细节

> 这也是项目技术演进的一个缩影：从"手写 httpx 同步调用"（旧链路）演进到"LangChain 异步调用"（新链路），旧链路的 `/api/chat` 已标记 deprecated 但未删除。

# 第四部分：常见坑与最佳实践

## 4.1 ⚠️ 最大的坑：同步阻塞事件循环

这是异步编程最常见的坑。**本项目曾经踩过，已于 2026-09-08 修复**——下面先看"坑长什么样"，再看"现在怎么解决的"，两个都值得记住。

**代码位置**：`backend/services/coordinator/agents/base.py`

### 修复前：同步调用卡住事件循环

```python
# agent_node 是 async 函数
async def agent_node(state):
    ...
    for _ in range(MAX_ITERS):
        response = await llm_with_tools.ainvoke(full)   # ✅ 异步，没问题
        ...
        tool_result = tool_fn.invoke(args)              # ❌ 同步！阻塞事件循环
```

#### 问题在哪？

`agent_node` 是异步的，`await llm.ainvoke` 是正确的（等 AI 时让出控制权）。但紧接着的 `tool_fn.invoke(args)` 是**同步**调用——工具内部是同步的 DB 操作（`PyMySQL`）。

**后果**：同步的数据库操作会**卡住整个事件循环**。就像餐厅服务员在等菜时，突然"把身体横在厨房门口"，其他所有客人都进不来。

#### 为什么会导致"并行不彻底"？

回想 §3.2 的 `asyncio.gather` 并行派发 6 个子 Agent——`gather` 确实并发启动了 6 个协程，但因为每个子 Agent 内部执行工具时用同步 `invoke` 阻塞事件循环，6 个"并行"实际会**串行**执行。

### 修复后：丢线程池（现在的写法）

```python
import asyncio

tool_fn = tools_by_name.get(name)
if tool_fn:
    try:
        # 工具是同步的（内部是同步 DB 调用），丢线程池避免阻塞事件循环
        tool_result = await asyncio.to_thread(tool_fn.invoke, args)   # ✅ 异步
    except Exception as e:
        log.error(f"工具 {name} 执行异常：{e}")
        tool_result = {"success": False, "message": f"工具执行异常：{e}"}
```

**关键点**：工具函数**本身**仍然是同步的（6 个域共 24 个工具全是 `def`，内部是同步 DB 调用，这个改不了），但**调用它的方式**变成异步了——丢到线程池后，事件循环不再被卡住，`gather` 的 6 个"并行"才真正并行起来。

> 核心认知：**"操作本身同步"和"调用方式同步"是两回事**——前者改不了，后者必须改。面试时把这个区分讲清楚，比背概念有说服力。

### 两种修法（以及本项目为什么选 to_thread）

**方案一：丢线程池（本项目采用）**

```python
import asyncio
result = await asyncio.get_event_loop().run_in_executor(None, tool_fn.invoke, args)
# 或者用 asyncio.to_thread（Python 3.9+，本项目用这个）
result = await asyncio.to_thread(tool_fn.invoke, args)
```

**方案二：把工具改成异步**

```python
async def record_action(...):        # 工具改成 async
    return await db.query_async(...) # 用异步数据库驱动

result = await record_action(**args)
```

**为什么选方案一**：本项目是单用户场景，方案二要换异步数据库驱动（`aiomysql`）、改 24 个工具函数，收益不匹配成本。方案一改一行就解决，性价比最高。

### 判断标准（背下来）

> **在 `async def` 函数里，凡是会"等"的操作，都要 `await`；不能 `await` 的同步操作，就丢线程池（`to_thread`/`run_in_executor`），或者干脆改成异步。**

## 4.2 别用 time.sleep，用 asyncio.sleep

```python
# ❌ 错：time.sleep 会阻塞整个事件循环
import time
async def bad():
    time.sleep(1)          # 整个服务卡 1 秒

# ✅ 对：asyncio.sleep 只挂起当前协程
async def good():
    await asyncio.sleep(1) # 让出控制权，事件循环去处理别的
```

**项目结合**：`expression.py` 的 `send_results` 里用的是 `await asyncio.sleep(0.05)`，正确 ✅。

## 4.3 别在 async 里做 CPU 密集计算

```python
async def bad():
    # 100 万次循环的纯计算，会阻塞事件循环
    total = sum(i * i for i in range(10_000_000))
```

CPU 密集计算没有"等待"过程，await 也没用，它会一直占用 CPU，其他任务全卡住。这类任务应该丢多进程：

```python
result = await asyncio.to_thread(cpu_heavy)   # 至少丢线程，虽然 GIL 下仍受限
# 真正的 CPU 密集用 ProcessPoolExecutor
```

## 4.4 取消要处理 CancelledError

任务被 `cancel()` 时，会抛 `CancelledError`。如果不处理，可能留下"半途而废"的脏状态：

```python
async def worker():
    try:
        while True:
            await do_something()
    except asyncio.CancelledError:
        cleanup()          # 清理资源
        raise              # 重要：重新抛出，让取消传播
```

> 注意：捕获 `CancelledError` 后要 `raise` 重新抛出，否则任务会"吞掉"取消请求，导致 `await task` 永远不返回。

**项目结合**：`expression.py` 的 `send_results` 正确处理了 `CancelledError`：

```python
except asyncio.CancelledError:
    pass   # 被取消时优雅退出
```

## 4.5 gather 的异常处理

```python
# 默认：一个协程抛异常，gather 立即抛异常，其他协程还在跑（可能泄漏）
results = await asyncio.gather(a(), b(), c())

# 推荐：return_exceptions=True，异常不中断，逐个检查
results = await asyncio.gather(a(), b(), c(), return_exceptions=True)
for r in results:
    if isinstance(r, Exception):
        log.error(f"任务失败: {r}")
```

**项目结合**：`graph.py` 的 `asyncio.gather(*coros, return_exceptions=True)` 用了正确的写法 ✅。

## 4.6 共享状态的竞态（单线程也有交错）

很多人以为"异步是单线程的，所以不会有并发问题"。**这是错的。**

虽然协程是单线程，但它们会在 `await` 处**交错执行**。如果多个协程同时读写同一个变量，在 `await` 前后可能出现"读到一半被打断"的情况。

```python
counter = 0

async def increment():
    global counter
    current = counter          # ① 读到 0
    await asyncio.sleep(0)     # ② 让出控制权！另一个协程插进来
    counter = current + 1      # ③ 写回 1（但另一个协程可能已经写过了）

# 两个协程并发跑 increment，期望 counter=2
await asyncio.gather(increment(), increment())
# 实际可能 counter=1（都读到了 0）
```

### 怎么避免？

**关键**：只有"读 → await → 写"这样的**非原子操作**才有竞态。如果读写之间没有 `await`（不交出控制权），就是原子的，不会有问题。

```python
# 安全：读写之间没有 await，不会被交错
async def increment_safe():
    global counter
    counter += 1              # 一行内完成，原子操作
```

如果确实需要在 `await` 前后保护共享状态，用 `asyncio.Lock`：

```python
lock = asyncio.Lock()

async def increment():
    async with lock:          # 拿到锁
        current = counter
        await asyncio.sleep(0)
        counter = current + 1
```

**项目结合**：协调 Agent 的编排状态 `_thread_store`（内存 dict）是共享的，但因为它只在**同一个事件循环**里通过 `await` 前后的简单读写操作，且每个 thread_id 独立，目前没有暴露竞态问题。如果将来加"全局计数器""跨请求的缓存写"就要小心了。

## 4.7 死锁：永远等不到的结果

**死锁**是两个协程互相等待对方，结果谁也动不了。

```python
async def a():
    await b()      # a 等 b
async def b():
    await a()      # b 等 a → 死锁
```

### 常见的死锁场景：在协程里同步等待协程

```python
# ❌ 错：在协程里用同步方式等一个协程
async def outer():
    result = inner()          # inner() 返回协程，但没 await，也没 run
    # inner 永远不执行，result 是协程对象，不是结果

# ❌ 更糟：在协程里 asyncio.run（嵌套事件循环）
async def outer():
    result = asyncio.run(inner())   # 报错：事件循环已在运行
```

**正确的做法**：在协程里等协程，就是 `await`；`asyncio.run` 只用在**最外层**（程序入口）。

### 另一个死锁源：`wait_for` 嵌套 + 未取消

两个协程互相 `wait_for` 等待对方完成，且都设了超时，但超时后没正确取消对方，就可能挂起。

**项目结合**：`expression.py` 的语音识别用 `asyncio.wait(FIRST_COMPLETED)` + 显式 `task.cancel()` 正确避免了"一个断了另一个还挂着"的死锁隐患。

## 4.8 常见误用清单（速查）

| 误用 | 后果 | 正确做法 |
|------|------|---------|
| 在 async 里用 `time.sleep` | 阻塞整个事件循环 | `await asyncio.sleep` |
| 在 async 里用同步 `requests.get` | 阻塞事件循环 | `httpx.AsyncClient` / `to_thread` |
| 在 async 里 `asyncio.run` | 嵌套事件循环报错 | 直接 `await` |
| 调用 `async def` 函数但不 `await` | 协程没执行 | 记得 `await` 或 `create_task` |
| 同步函数里调用 `async def` | 拿不到结果 | 用 `asyncio.run` 包一层 |
| 忘处理 `CancelledError` | 任务泄漏/脏状态 | `except CancelledError: cleanup(); raise` |
| `gather` 不用 `return_exceptions` | 一个失败全部中断 | 加 `return_exceptions=True` |
| 在 async 里做 CPU 密集计算 | 卡住事件循环 | 丢进程池 |

# 第五部分：常见问题 Q&A

**Q1：我到底该把函数写成 `async def` 还是 `def`？**

看函数里有没有"等待"：

- 有 `await`（等数据库、等 API、等 I/O）→ 必须 `async def`
- 没有等待、就是纯计算或纯同步操作 → 用 `def`，FastAPI 会自动丢线程池跑

**Q2：为什么我的异步代码没有变快？**

最常见的原因是：**你 `await` 的是同步阻塞操作**。`await` 只能让"真正的异步操作"（如 `asyncio.sleep`、`httpx` 异步客户端、异步数据库驱动）让出控制权。如果 `await` 的是 `time.sleep` 或同步的 DB 驱动，那和同步没区别，甚至更慢。

**Q3：`asyncio.gather` 和 `asyncio.wait` 到底怎么选？**

- 要"全部结果"，一个失败就整体失败 → `gather`
- 要"全部结果"，但个别失败不影响 → `gather(..., return_exceptions=True)`
- 要"任意一个完成就继续" → `wait(..., return_when=FIRST_COMPLETED)`

**Q4：FastAPI 的 async 端点里能调同步函数吗？**

能，但不推荐。如果同步函数很耗时（如大查询），会阻塞事件循环。正确做法是 `await asyncio.to_thread(同步函数)`，把同步函数丢到线程池。

**Q5：Python 异步和 JavaScript 的 async/await 一样吗？**

核心思想一样（都是"等待时让出控制权"），但底层不同：

- JavaScript：天生单线程 + 事件循环，异步是**唯一**的并发方式
- Python：可以多线程/多进程，异步（asyncio）是**可选**的并发方式之一

所以 Python 里更要搞清楚"什么时候该用异步、什么时候用线程/进程"。

**Q6：协程里能不能用 `requests` 库？**

不能直接用。`requests` 是同步库，会阻塞事件循环。要用 `httpx.AsyncClient`（异步版），或者 `await asyncio.to_thread(requests.get, url)` 丢线程池。

| **await** | "挂起当前协程，等这个结果" |
| **Task** | 被事件循环调度的协程 |
| **gather** | 并发跑多个协程，等全部完成 |
| **create_task** | 启动一个协程，不立即等它 |
| **wait** | 并发跑多个，可配置等任一/全部完成 |
| **取消（cancel）** | 请求一个任务停止 |
| **CancelledError** | 任务被取消时抛的异常 |
| **asyncio.sleep** | 异步等待，不阻塞事件循环 |
| **run_in_executor / to_thread** | 把同步阻塞操作丢到线程池 |
| **GIL** | Python 全局锁，限制多线程的 CPU 并行 |
| **asynccontextmanager** | 异步版的 with（启动/清理都要 await） |
| **StreamingResponse** | 流式响应，边生成边推送 |
| **ainvoke** | LangChain 的异步调用方法 |
