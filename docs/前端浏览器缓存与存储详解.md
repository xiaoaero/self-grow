## 1. 浏览器存储全景概览

浏览器端可用的存储机制对比：

| 机制 | 容量 | 持久性 | 作用域 | 是否异步 | 数据类型 | 本项目使用 |
|------|------|--------|--------|----------|----------|-----------|
| **localStorage** | ~5MB | 永久（除非手动清除） | 同源（协议+域名+端口） | 同步 | 仅字符串 | ✅ 大量使用 |
| **sessionStorage** | ~5MB | 窗口/标签页关闭前 | 同源+同窗口 | 同步 | 仅字符串 | ✅ 少量使用 |
| **Cookies** | ~4KB | 可设过期时间 | 同源（可跨路径） | 同步 | 仅字符串 | ❌ 未使用 |
| **IndexedDB** | 通常无上限（硬盘） | 永久 | 同源 | 异步 | 结构化数据 | ❌ 未使用 |
| **Cache API** | 取决于浏览器 | 永久（可手动清除） | 同源 | 异步 | HTTP 请求/响应 | ❌ 未使用 |
| **内存变量** | 取决于页面 | 页面刷新即失 | 全局/模块作用域 | 同步 | 任意 JS 类型 | ✅ 大量使用（AppData） |

## 2. Web Storage 规范

### 2.1 localStorage —— 持久化存储

**原理：**

localStorage 是浏览器提供的一种**键值对（Key-Value）存储**，数据以字符串形式保存在浏览器的**本地磁盘**上。

- **生命周期**：数据一旦存入，**永远不会自动过期**。即使关闭浏览器、重启电脑，数据依然存在。只有通过 JS 代码手动删除（`removeItem`）、用户清除浏览器数据，或存储满后浏览器主动清理，才会消失。
- **作用域**：受**同源策略**限制——相同协议（http/https）+ 相同域名 + 相同端口 才能访问同一个 localStorage。例如 `http://localhost:3000` 存的 key，在 `http://127.0.0.1:3000` 读不到。
- **容量**：不同浏览器略有差异，通常 **5MB 左右**。
- **同步 API**：所有操作都是**同步阻塞**的，即调用 `getItem` 时会阻塞 JS 主线程直到数据读取完成。

**核心 API：**

```js
// 存储（key 和 value 都必须是字符串）
localStorage.setItem('key', 'value');

// 读取
const val = localStorage.getItem('key');  // 返回 null 表示不存在

// 删除单个
localStorage.removeItem('key');

// 清空全部
localStorage.clear();

// 获取数量
const len = localStorage.length;

// 按索引取 key
const keyName = localStorage.key(0);
```

**存储非字符串数据类型：**

因为 localStorage 只接受字符串，存储对象/数组时必须手动序列化：

```js
// 存对象 → 先 JSON.stringify 转成字符串
const user = { id: 1, name: 'test' };
localStorage.setItem('sg_user', JSON.stringify(user));

// 读对象 → 先 JSON.parse 转回对象
const raw = localStorage.getItem('sg_user');
const userObj = raw ? JSON.parse(raw) : null;
```

### 2.2 sessionStorage —— 会话级存储

**原理：**

sessionStorage 与 localStorage 的 API 完全一致，但**生命周期**不同：

- **生命周期**：数据仅在**当前浏览器标签页（Tab）**打开期间存在。关闭标签页或浏览器窗口后数据立即清除。**刷新页面不会丢失**，但「在新标签页中打开」会产生一个新的 sessionStorage。
- **作用域**：同源 + **同窗口**。即使两个标签页打开同一个网站，它们的 sessionStorage 也是隔离的。

**核心 API：**

与 localStorage 完全一样（`setItem` / `getItem` / `removeItem` / `clear`），只是作用对象不同。

**关键区别一句话总结：**

> 刷新页面 → 两者都在；关闭标签页 → sessionStorage 丢，localStorage 在；重启电脑 → sessionStorage 丢，localStorage 在。

---

### 2.3 Web Storage 的通用特性

**1. 事件监听 —— storage 事件**

当**其他同源标签页**修改 localStorage 时，当前页面会触发 `storage` 事件（注意：修改数据**的页面本身不会触发**）：

```js
window.addEventListener('storage', (e) => {
    console.log('key:', e.key);           // 被修改的 key
    console.log('oldValue:', e.oldValue); // 旧值
    console.log('newValue:', e.newValue); // 新值
    console.log('url:', e.url);           // 触发修改的页面 URL
});
```

**效果举例**：用户在两台显示器上各打开一个标签页，在 A 页修改了用户名，B 页可以通过 storage 事件自动刷新显示。

**2. QuotaExceededError 异常**

当存储空间不足时，`setItem` 会抛出 `QuotaExceededError`。所有操作都需要 `try-catch` 包裹。

**3. 隐私模式限制**

大多数浏览器的**无痕/隐私模式**下，localStorage 依然可用，但数据在关闭最后一个隐私窗口后自动清除。部分旧版浏览器在隐私模式下完全禁用 localStorage。

## 3. localStorage 在本项目中的应用

### 3.1 用户登录态存储

**键名：** `sg_user`

**作用：** 保存当前登录用户的基本信息（id、name 等），用于全站判断"谁在使用"。

**代码示例（`frontend/js/utils.js`）：**

```js
function getCurrentUser() {
    try {
        const raw = localStorage.getItem('sg_user');
        return raw ? JSON.parse(raw) : null;
    } catch (e) {
        return null;
    }
}

function requireLogin() {
    const user = getCurrentUser();
    if (!user) {
        window.location.href = '../login.html';
        return false;
    }
    return true;
}
```

**效果举例：**

- 用户登录后，后端返回的 user 信息存入 `sg_user`
- 之后每次刷新页面，`getCurrentUser()` 直接从 localStorage 读取，不需要再次请求后端
- 如果用户清除浏览器数据中的 localStorage，则会被踢回登录页

**为什么不只用内存变量？** 因为刷新页面会丢失 JS 内存中的所有变量。localStorage 让登录态在刷新后依然保持。

**数据格式：**

```js
// 存储的数据结构大概这样
{
    "id": 1,
    "name": "test",
    "level": 188,
    // ... 其他用户字段
}
```

### 3.2 本地任务兜底持久化

**键名：** `sg_tasks_local_{userId}`（按用户 ID 隔离）

**作用：** 在任务列表（今日任务/本周任务）中，把用户创建的任务额外存一份到 localStorage。当后端异常或网络抖动时，作为本地兜底保证数据不丢。

**代码示例（`frontend/js/pages/tasks.js`）：**

```js
const LOCAL_TASKS_KEY = 'sg_tasks_local_' + (getCurrentUser()?.id || 'guest');

/** 保存本地任务到 localStorage 兜底 */
function saveLocalTaskToStorage(task) {
    try {
        const raw = localStorage.getItem(LOCAL_TASKS_KEY);
        const tasks = raw ? JSON.parse(raw) : [];
        if (!tasks.some(t => t.id === task.id)) {  // 避免重复
            tasks.push(task);
            localStorage.setItem(LOCAL_TASKS_KEY, JSON.stringify(tasks));
        }
    } catch (e) {
        console.warn('保存本地任务失败:', e);
    }
}

/** 从 localStorage 加载本地任务并合并到 todayTasks/weekTasks */
function loadLocalTasksIntoToday() {
    try {
        const raw = localStorage.getItem(LOCAL_TASKS_KEY);
        if (!raw) return;
        const tasks = JSON.parse(raw);
        // ... 按是否为今日任务/本周任务分类合并到对应的前端数组
        // 同时清理过期条目并回写 localStorage
        localStorage.setItem(LOCAL_TASKS_KEY, JSON.stringify(stillValid));
    } catch (e) {
        console.warn('加载本地任务失败:', e);
    }
}
```

**效果举例：**

- 用户在任务板块创建了 5 个「今天要做的事」
- 如果网络抖动导致后端保存失败，这些任务仍然保存在 localStorage 中
- 用户刷新页面后，`loadLocalTasksIntoToday()` 将本地任务合并回前端列表，用户看不到任何异常
- 凌晨 3 点后端归档时，这些任务会被统一写入数据库

**为什么需要"兜底"而不是唯一存储？**

> 任务数据**核心在后端数据库**，localStorage 只是**防丢的保险**。后端是权威来源，localStorage 是辅助缓存。

### 3.3 睡眠记录每日标记

**键名：** `sg_sleep_recorded_date`

**作用：** 记录用户今天是否已经记录过睡眠。因为睡眠每天只能记录一次，用 localStorage 做持久化标记，防止跨页面/跨刷新的重复提交。

**代码示例（`frontend/js/pages/action.js`）：**

```js
function markSleepRecordedToday() {
    var today = new Date().toISOString().slice(0, 10);  // "2026-07-30"
    window._sleepRecordedToday = true;                   // 内存标记（快速判断）
    try {
        localStorage.setItem('sg_sleep_recorded_date', today);  // 持久标记
    } catch(e) {}
}

function isSleepRecordedToday() {
    if (window._sleepRecordedToday) return true;   // 内存中有标记 → 直接返回
    try {
        var saved = localStorage.getItem('sg_sleep_recorded_date');
        if (saved === new Date().toISOString().slice(0, 10)) {
            window._sleepRecordedToday = true;      // 同步到内存标记
            return true;
        }
    } catch(e) {}
    return false;
}
```

**效果举例：**

- 用户早上记录了睡眠（23:00 → 07:00）
- `markSleepRecordedToday()` 将今天日期存入 localStorage
- 用户之后切换到仪表盘又切回来，`isSleepRecordedToday()` 返回 true，睡眠输入区域隐藏
- **关键**：即使刷新页面，localStorage 中的日期标记依然存在，用户无法在同一天再次记录睡眠
- 第二天 localStorage 中的日期变成了昨天，`isSleepRecordedToday()` 返回 false，允许记录新睡眠

**为什么不用纯内存标记？**

因为刷新会丢失。如果只靠 `window._sleepRecordedToday`，用户刷新后又可以再次记录睡眠，失去"每天一次"的限制效果。

**为什么同时用内存标记 + localStorage？**

这种设计叫**双层缓存**：
- 内存标记（`window._sleepRecordedToday`）— 极速判断，`O(1)` 不涉及磁盘 I/O
- localStorage 标记 — 刷新/重启后依然有效
- 两者协同：内存中有的优先用内存，没有的去 localStorage 查，查到同步到内存

### 3.4 表达训练草稿管理

**键名：** `expr_answering_draft`

**作用：** 表达训练答题过程中，用户可能意外刷新或关闭页面。草稿机制会把答题进度（问题、已写答案、计时状态等）存入 localStorage，恢复时从断点继续。

**代码示例（`frontend/js/pages/agent.js`）：**

```js
const DRAFT_KEY = 'expr_answering_draft';

function saveDraft() {
    if (!STATE.currentQuestion || !STATE.currentAnswerId) return;
    if (!STATE.isAnswering && !STATE.answerText && !STATE.asrText) return;

    const text = STATE._draftRestoredText
        ? STATE._draftRestoredText + (STATE.asrText || '')
        : STATE.asrText || STATE.answerText || '';

    localStorage.setItem(DRAFT_KEY, JSON.stringify({
        question: STATE.currentQuestion,           // 当前题目
        answerId: STATE.currentAnswerId,           // 后端回答记录 ID
        attempt: STATE.currentAttempt,             // 第几次尝试
        answerText: text,                          // 已写内容
        fillerWords: STATE.fillerWords,            // 已检测出的填充词
        startTime: STATE.startTime,                // 开始答题时间
        pausedTime: STATE.pausedTime,              // 暂停时间
        isPaused: STATE.isPaused,                  // 是否处于暂停状态
        timestamp: Date.now(),                     // 草稿保存时间
    }));
}

function clearDraft() {
    localStorage.removeItem(DRAFT_KEY);
}

function getDraft() {
    try {
        const data = localStorage.getItem(DRAFT_KEY);
        return data ? JSON.parse(data) : null;
    } catch { return null; }
}
```

**效果举例：**

- 用户正在答 AI 出的表达训练题，已经写了一半答案
- 不小心按了 F5 刷新页面
- 页面加载后检测到 `expr_answering_draft` 存在，弹出"发现未完成的答题，是否恢复？"
- 用户点击确认 → 题目、已写内容、剩余时间全部恢复，可以继续作答
- 用户正常提交回答后 → `clearDraft()` 清理草稿

**数据格式：**

```js
{
    "question": "请描述一次你解决复杂问题的经历",
    "answerId": 42,
    "attempt": 1,
    "answerText": "在一次项目中...（部分文字）",
    "fillerWords": [],
    "startTime": "2026-07-30T10:30:00.000Z",
    "pausedTime": null,
    "isPaused": false,
    "timestamp": 1722316800000
}
```

### 3.5 技能树数据存储（大量使用）

技能树是本项目中 **localStorage 使用最密集** 的模块，涉及多个 key 和复杂的降级策略。

## 4. sessionStorage 在本项目中的应用

**键名：** `lastPage` / `lastSubPage`

**作用：** 记住用户当前在哪个页面，刷新后自动回到之前的位置，但关闭标签页再重新进入则回到仪表盘首页。

**代码示例（`frontend/js/router.js`）：**

```js
// 每次切换页面时保存
function navigateTo(pageName, subPage) {
    // ... 渲染页面 ...

    // 保存当前页面到 sessionStorage
    sessionStorage.setItem('lastPage', pageName);
    if (subPage) {
        sessionStorage.setItem('lastSubPage', subPage);
    } else {
        sessionStorage.removeItem('lastSubPage');
    }
}
```

**初始化时恢复（`frontend/js/app.js`）：**

```js
document.addEventListener('DOMContentLoaded', async () => {
    // ... 加载数据 ...

    // 从 sessionStorage 恢复上次页面
    const lastPage = sessionStorage.getItem('lastPage');
    if (lastPage) {
        const lastSubPage = sessionStorage.getItem('lastSubPage');
        navigateTo(lastPage, lastSubPage || undefined);
    } else {
        navigateTo('dashboard');  // 首次进入 → 仪表盘
    }
});
```

**效果举例：**

- 用户在"任务 → 本周任务"页面操作
- 不小心按了刷新 → 页面自动恢复到"任务 → 本周任务"
- 用户做完了当前操作，关闭标签页去吃午饭
- 午饭后重新打开网站 → 回到仪表盘（因为 sessionStorage 随标签页关闭而清除）

**为什么选 sessionStorage 而不是 localStorage？**

因为这是**有意识的 UX 设计**：

| 场景 | 期望行为 | 选择的存储 |
|------|----------|-----------|
| 刷新页面 | 保持当前页面 | sessionStorage ✔ |
| 关闭标签页重进 | 回到仪表盘首页 | sessionStorage 自动清除 ✔ |
| 同站跨标签页 | 各自独立 | sessionStorage 天然隔离 ✔ |

如果用 localStorage，关闭一周后再打开网站还会回到之前的位置，这反而不是用户期望的。

## 5. 存储降级策略

本项目中存在大量「后端优先，localStorage 兜底」的模式。这是 SPA 应用在**弱网或后端异常**时的常见策略。

### 5.1 标准降级模式

```js
// 一般形式
async function fetchXXX() {
    try {
        const data = await requestBackend();
        if (data) {
            // 成功 → 缓存到 localStorage 作为下次降级的资本
            localStorage.setItem('xxx_cache', JSON.stringify(data));
            return data;
        }
    } catch(e) {
        // 网络异常 → 静默失败，走降级
    }
    // 后端不可用 → 从 localStorage 读取旧数据
    return loadFromLocal();
}
```

### 5.2 项目中的实际降级案例

**技能树索引（`frontend/js/pages/skills.js`）：**

```js
async function fetchSkillTreeIndexAsync() {
    const uid = getCurrentUser()?.id;
    if (uid) {
        try {
            const res = await fetch(API_BASE + '/api/skill-trees?user_id=' + uid);
            if (res.ok) {
                const data = await res.json();
                if (data.trees && data.trees.length > 0) {
                    localStorage.setItem('skill_tree_index', JSON.stringify(data.trees));
                    return data.trees;  // ★ 后端数据
                }
            }
        } catch(e) {}
    }
    return loadSkillTreeIndexLocal();  // ★ 降级到 localStorage
}
```

**技能树加载（`frontend/skill-tree/js/app.js`）：**

```js
_loadPublishedTree(treeId) {
    fetchPublishedSkillTree(treeId).then(function(serverTree) {
        if (serverTree && serverTree.published_data) {
            // ☆ 后端成功 → 缓存 + 渲染
            saveToStorage(treeId + '_published', pd);
            self.loadData(pd);
            return;
        }
        // ★ 后端无数据 → localStorage
        self._loadPublishedTreeFromLocal(treeId);
    }).catch(function() {
        // ★ 后端不可用 → localStorage
        self._loadPublishedTreeFromLocal(treeId);
    });
}

_loadPublishedTreeFromLocal(treeId) {
    var published = loadFromStorage(treeId + '_published');
    if (published) { this.loadData(published); return; }
    var draft = loadFromStorage('tree_' + treeId);
    if (draft) { this.loadData(draft); return; }
    showToast('未找到该技能树数据', 'error');
}
```

### 5.3 降级模式的三种数据流状态

```
正常 → 后端拉数据 → 缓存到 localStorage → 渲染
      ↓
弱网 → 后端口误 → 从 localStorage 读取旧数据 → 渲染（可能不是最新）
      ↓
无数据 → localStorage 也没有 → 显示空状态/错误提示
```

**效果举例：**

- **正常情况**：用户打开技能页面，后端返回最新数据，**同时**缓存一份到 localStorage
- **断网情况**：用户打开技能页面，后端请求失败，从 localStorage 读取上一次成功缓存的数据，页面依然能展示（虽然可能不是最新版本）
- **第一次使用**：后端有数据但 localStorage 为空 → 后端优先；后端无数据 localStorage 也无 → 显示空状态

## 6. 用户数据隔离方案

本系统支持多用户登录，但 localStorage 是**同源共享**的，即同一域名下所有用户共用同一个存储空间。必须手动实现隔离。

### 6.1 方案一：key 中拼接 userId

```js
// 任务列表 — 每个用户有自己的 key
const LOCAL_TASKS_KEY = 'sg_tasks_local_' + (getCurrentUser()?.id || 'guest');

// 技能列表 — 同样按用户隔离
const KEY = 'my_skills_' + uid;  // → 'my_skills_1', 'my_skills_2'

// 学习进度 — 按树 + 用户隔离
const KEY = treeId + '_learner_' + userId;
// → 'tree_abc_learner_1', 'tree_abc_learner_2'
```

### 6.2 方案二：key 中拼接 userId（技能树索引）

```js
// skills.js
function loadMySkillsLocal() {
    const uid = getCurrentUser()?.id || 'guest';
    const raw = localStorage.getItem('my_skills_' + uid);
    return raw ? JSON.parse(raw) : [];
}
```

### 6.3 不隔离的后果

```js
// 错误示范 — 没有用户隔离
localStorage.setItem('my_skills', JSON.stringify(skills));

// 用户 A 登录，添加了 3 个技能
// 用户 A 登出，用户 B 登录
// 用户 B 看到的「我的技能」是用户 A 的数据 ❌
```

**效果举例：**

隔壁老王在家用同一个浏览器登录系统。如果没有用户隔离：
- 老王添加了「健身」「阅读」「编程」三个技能
- 老王切换账号登录，或者你登录后
- 你会看到老王的三个技能出现在「我的技能」里
- 正确的做法：`my_skills_2`（用户 2）和 `my_skills_3`（用户 3）各自独立

### 6.4 不隔离在 key 中的数据——登录态

`sg_user` 不需要隔离，因为它**只存当前登录用户**。切换用户时会覆盖写入。

## 7. 与后端数据库的关系与分工

### 7.1 各自定位

| 层次 | 存储位置 | 代表数据 | 特点 |
|------|----------|----------|------|
| **权威数据层** | 后端 SQLite | 用户信息、习惯、任务、目标、技能树草稿/发布 | 持久可靠、支持查询/排序/分页 |
| **缓存加速层** | localStorage | 技能树索引缓存、用户列表缓存 | 避免重复请求、离线可用 |
| **防丢兜底层** | localStorage | 本地任务列表 | 后端不可用时保证数据不丢 |
| **会话恢复层** | sessionStorage | 最后访问的页面 | 刷新后保持位置 |
| **运行时数据层** | 内存变量（AppData） | 当前页面的 UI 状态 | 最快读写，刷新即失 |

### 7.2 典型数据流

```
                    ┌───────────────┐
                    │  用户操作页面  │
                    └──────┬────────┘
                           │
                    ┌──────▼────────┐
                    │  更新内存变量  │  ← 立即响应，毫秒级
                    │  (AppData)    │
                    └──────┬────────┘
                           │
                    ┌──────▼────────┐
                    │  同步到后端 API │  ← 异步请求，可能有延迟
                    │  (fetch)      │
                    └──────┬────────┘
                           │
                    ┌──────▼────────┐
                    │  后端写入数据库 │  ← 最终持久化
                    │  (SQLite)     │
                    └───────────────┘

                    同时：写入 localStorage 兜底
```

### 7.3 为什么不能只用一个？

- **只用 localStorage**：数据只在浏览器端，换设备/清缓存就丢了，无法跨设备同步
- **只用后端**：网络异常时用户无法操作，刷新页面需要等待后端返回数据
- **只用内存变量**：刷新就丢，用户 5 分钟的工作白费

**三者互补的关系：**

```
内存变量  →  最快响应，用户操作的即时反馈
  ↓
localStorage →  防刷新丢失，离线可用，启动时快速展示
  ↓
后端数据库  →  权威数据源，跨设备同步，持久保障
```

## 8. 未使用但值得了解的浏览器存储机制

### 8.1 Cookies

**原理：**

Cookies 是浏览器中**最古老**的存储机制。每次请求都会**自动附加**到 HTTP 请求头中发送给服务器。

**特点：**

| 属性 | 值 |
|------|-----|
| 容量 | 约 4KB |
| 生命周期 | 可设置 expires 或使用 Session Cookie（关闭浏览器即失） |
| 作用域 | 同源 + 可限制路径 |
| 传输方式 | 每次 HTTP 请求自动携带 |
| 安全 | 可设置 HttpOnly（JS 不可读）、Secure（仅 HTTPS）、SameSite（防 CSRF） |

**JS 操作方式：**

```js
// 读取所有 cookie（返回字符串如 "key1=val1; key2=val2"）
document.cookie;

// 设置（每次只能设置一个）
document.cookie = "theme=dark; path=/; max-age=86400";

// 删除（设置过期时间为过去）
document.cookie = "theme=; expires=Thu, 01 Jan 1970 00:00:00 GMT";
```

**为什么不用于本项目？**

本项目是 SPA（单页应用），后端不依赖 session/cookie 鉴权，而是通过**请求参数传 userId** 实现多用户支持。因此不需要 cookies。Cookies 的主要应用场景是传统 MPA（多页应用）中的 Session 管理。

### 8.2 IndexedDB

**原理：**

IndexedDB 是浏览器提供的**事务型数据库**，类似于浏览器端的 SQLite。支持**索引、游标、事务、批量操作**。

**与 localStorage 的对比：**

| 对比维度 | localStorage | IndexedDB |
|----------|-------------|-----------|
| API 形式 | 同步（阻塞主线程） | 异步（Promise/回调） |
| 数据类型 | 仅字符串 | 任意结构化数据（File、Blob、对象等） |
| 容量 | ~5MB | 无上限（取决于硬盘） |
| 查询能力 | 无（只能按 key 取） | 支持索引、范围查询、排序 |
| 事务支持 | 无 | 支持 ACID 事务 |

**为什么不用于本项目？**

虽然 IndexedDB 更强大，但它的 API 比 localStorage 复杂得多（需要打开数据库、创建对象仓库、处理版本号等）。本项目的存储需求：
- 数据量小（用户配置、状态标记、草稿）
- 存储结构简单（单层 key-value）
- 需要同步读写（在渲染流程中直接读取）

这些都更适合 localStorage。如果未来需要存储大量离线数据（比如完整的技能树图片资源），IndexedDB 会是更好的选择。

### 8.3 Cache API

**原理：**

Cache API 是 **Service Worker** 的一部分，专门用于缓存 HTTP 请求和响应。它是 **PWA（Progressive Web App）** 实现离线访问的核心技术。

**为什么不用于本项目？**

本项目不是 PWA（无 Service Worker），且前端文件通过 HTTP 服务器提供，离线访问的需求不高。Cache API 主要用于：
- 离线时仍能加载页面和静态资源（HTML/CSS/JS）
- 加速重复请求（配合 Service Worker 拦截请求）
- 预缓存关键资源

## 9. 常见坑点与应对

### 9.1 JSON.parse 失败

**问题：** localStorage 存取对象时，如果存入的数据被手动修改或损坏，`JSON.parse` 会抛出异常。

```js
// 坏的数据被存入了
localStorage.setItem('sg_user', '{bad json}');
JSON.parse(localStorage.getItem('sg_user'));  // ❌ SyntaxError
```

**应对（本项目做法）：**

所有读取操作都用 `try-catch` 包裹，失败时返回默认值：

```js
function getCurrentUser() {
    try {
        const raw = localStorage.getItem('sg_user');
        return raw ? JSON.parse(raw) : null;
    } catch (e) {
        return null;  // ✅ 数据损坏 → 返回 null，不会崩溃
    }
}
```

### 9.2 存储空间满（QuotaExceededError）

**问题：** localStorage 容量约 5MB，超出时 `setItem` 抛出 `QuotaExceededError`。

```js
// 连续存大字符串
for (let i = 0; i < 10000; i++) {
    localStorage.setItem('key' + i, 'x'.repeat(1024));  // ❌ 某次会失败
}
```

**应对：**

```js
function saveToStorage(key, value) {
    try {
        localStorage.setItem(key, JSON.stringify(value));
    } catch (e) {
        if (e.name === 'QuotaExceededError') {
            console.warn('localStorage 存储已满，无法保存', key);
            // 可选的清理策略：删除最旧的缓存数据
            // 或提示用户清理浏览器数据
        }
    }
}
```

### 9.3 混合环境不一致

**问题：** 不同浏览器、同浏览器的不同模式（普通/无痕）对 localStorage 的支持可能有差异。Node.js 服务端渲染（SSR）中 localStorage 完全不存在。

**应对：**

始终用 `try-catch` 包裹读写操作，永远不假设 localStorage 可用。

### 9.4 同域多用户数据污染

**问题：** localStorage 按域名隔离，不按用户隔离。多用户在同一浏览器使用系统时，如果不手动做用户隔离，数据会互相覆盖。

**应对：** 详见第 6 节——key 中拼接 userId。

### 9.5 sessionStorage 跨标签页丢失

**问题：** 用户右键 → 在新标签页中打开 → sessionStorage 丢。

**效果举例：** 用户在仪表盘按 Ctrl+点击链接，新标签页打开后看不到之前的页面位置，而是回到仪表盘。这是设计意图（详见第 4 节），但如果你需要在跨标签页时保留状态，就需要用 localStorage。

### 9.6 内存标记与 localStorage 不同步

**问题：** 代码中既有内存变量（如 `window._sleepRecordedToday`）又有 localStorage 标记。如果不同步，会出现判断不一致。

```js
// 可能出现的 bug 场景
window._sleepRecordedToday = true;  // 内存标记 true
localStorage.removeItem('sg_sleep_recorded_date');  // 持久标记已删

isSleepRecordedToday();  // → true（因为内存标记优先），但持久标记已经没了
// 刷新页面后 → false（因为持久标记没了，内存标记清空）
```

**应对：**

始终保持`内存标记 ← localStorage` 的单向同步规则：

```js
function isSleepRecordedToday() {
    if (window._sleepRecordedToday) return true;      // 优先内存（最快）
    // 内存没有 → 查 localStorage
    var saved = localStorage.getItem('sg_sleep_recorded_date');
    if (saved === todayStr) {
        window._sleepRecordedToday = true;  // 同步到内存
        return true;
    }
    return false;
}
```

### 9.7 JSON.stringify 循环引用

**问题：** 对象中包含循环引用时，`JSON.stringify` 抛出错误：

```js
const obj = { name: 'test' };
obj.self = obj;  // 循环引用
JSON.stringify(obj);  // ❌ TypeError: Converting circular structure to JSON
```

**应对：**

在技能树保存时，清理运行时状态再序列化：

```js
_saveCurrentTree() {
    const data = {
        nodes: this.app.nodes.map(n => {
            const { _selected, _linking, _learningState, ...rest } = n;  // 解构排除运行时字段
            return rest;
        }),
        connections: this.app.connections
    };
    saveToStorage(key, data);
}
```

### 9.8 隐私模式兼容性

**Safari 隐私模式**下 localStorage 存在但只读（`setItem` 静默失败或在某些版本抛出异常），所有写入操作必须 try-catch。

```js
// 安全写法：setItem 始终 try-catch
try {
    localStorage.setItem('key', 'value');
} catch(e) {
    // 隐私模式下静默失败，功能降级但不崩溃
}
```

### 数据访问优先级（由快到慢）

```
1. 内存变量（AppData / window._xxx）     —— 微秒级，刷新即失
2. sessionStorage                        —— 毫秒级，关闭标签页即失
3. localStorage                          —— 毫秒级，手动清除前永久
4. 后端 API → SQLite                     —— 网络延迟 + 磁盘 I/O，但跨设备持久
```

### 写策略

```
用户操作 → 更新内存变量（即时响应）
         → 写入 localStorage（防丢兜底）
         → 异步请求后端（最终持久化，异步，不阻塞 UI）
```

## 11. 前端基础概念

> 本节梳理与浏览器存储、前端工程紧密相关的基础概念，帮助理解"为什么前端代码要这样写"。

---

### 11.1 SPA（单页应用 / Single Page Application）

**原理：**

传统网站（MPA，多页应用）每切换一个页面，浏览器都会向服务器发起 HTTP 请求，服务器返回完整的 HTML 文档，浏览器重新加载整个页面。

SPA 则不同：
- **首次加载**：浏览器下载一个完整的 HTML 壳 + 全部 JS/CSS
- **页面切换**：JS 动态替换页面内容，不再向服务器请求 HTML
- **只有数据请求**：需要新数据时，通过 `fetch` 异步调用 API，拿到 JSON 回来局部更新

```
MPA 模式：
  点击链接 → 请求 /about.html → 服务器返回完整 HTML → 浏览器整个页面刷新

SPA 模式：
  点击导航 → JS 执行 navigateTo('about') → 隐藏当前 div，显示 #page-about div
             需要数据时 → fetch('/api/about') → 拿到 JSON → 局部更新
```

**本项目中的体现：**

本项目是典型的 SPA。`index.html` 包含所有页面的 `<div class="page">` 容器，`router.js` 的 `navigateTo()` 控制哪个页面显示/隐藏：

```js
// router.js — 极简 SPA 路由核心逻辑
function navigateTo(pageName, subPage) {
    // 1. 隐藏所有页面
    document.querySelectorAll('.page').forEach(p => p.classList.remove('page--active'));
    // 2. 显示目标页面
    const page = document.getElementById('page-' + pageName);
    if (page) page.classList.add('page--active');
    // 3. 调用对应渲染函数
    renderers[pageName]();
    // 4. 保存到 sessionStorage（刷新后恢复）
    sessionStorage.setItem('lastPage', pageName);
}
```

**效果举例：**

- 用户在仪表盘按 Ctrl+2，瞬间切入行动页面，没有白屏、没有加载进度条
- 关闭后端后前端依然能显示 UI（虽然数据是空的）
- 页面切换速度在 10ms 以内，远快于传统 MPA 的 200ms+

**与 localStorage 的关系：**

SPA 的所有 JS 都在同一个页面生命周期内运行，所以内存变量可以全局共享（通过 `AppData`）。但刷新页面会导致所有 JS 变量丢失，所以需要用 localStorage 做持久化——这正是 SPA 架构下 localStorage 重要的根本原因。

### 11.2 同源策略（Same-Origin Policy）

**原理：**

浏览器的一项**安全机制**，限制一个源的文档/脚本如何与另一个源的资源交互。

**同源的定义：** 协议（http/https）+ 域名（localhost/example.com）+ 端口（3000/3001）**三者完全一致**。

```
http://localhost:3000/page/      http://localhost:3000/api/       ✅ 同源（同域名同端口）
http://localhost:3000/           http://127.0.0.1:3000/          ❌ 不同源（域名不同）
http://localhost:3000/           http://localhost:3001/          ❌ 不同源（端口不同）
http://localhost:3000/           https://localhost:3000/         ❌ 不同源（协议不同）
```

**localStorage 严格受同源策略限制：**

```js
// 在 http://localhost:3000 设置
localStorage.setItem('key', 'value');

// 在 http://localhost:3001 读取 → null ❌ 不同端口，读不到
// 在 http://127.0.0.1:3000 读取 → null ❌ 不同域名，读不到
// 在 https://localhost:3000 读取 → null ❌ 不同协议，读不到
```

**项目中的体现：**

- 前端运行在 `localhost:3000`，后端运行在 `localhost:3001` → 不同源
- 所以前端的 `fetch('/api/users/profile')` 实际上必须写 `fetch('http://localhost:3001/api/users/profile')`
- 这又引出了跨域问题（见下节）

**效果举例：**

- 如果你的同事在前端代码里写 `localStorage.getItem('sg_user')`，打开控制台在 `localhost:3000` 可以读到
- 但如果你在浏览器地址栏输入 `http://127.0.0.1:3000` 打开同样的页面，`sg_user` 是空的——因为存储在不同域名下
- 这就是为什么切换 localhost 和 127.0.0.1 访问同一个网站，登录态会丢失

### 11.3 跨域问题（CORS）

**原理：**

当浏览器向**不同源**的地址发起 Ajax/fetch 请求时，浏览器会先发送一个 `OPTIONS` 预检请求（Preflight），检查服务器是否允许跨域。

服务器需要在响应头中明确声明：

```
Access-Control-Allow-Origin: http://localhost:3000    ← 允许哪个源访问
Access-Control-Allow-Methods: GET, POST, PUT, DELETE  ← 允许哪些方法
Access-Control-Allow-Headers: Content-Type            ← 允许哪些请求头
```

**本项目中的体现：**

后端 `main.py` 或依赖中配置了 CORS 中间件：

```python
# 后端 Cross-Origin 配置（示意）
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000", "http://127.0.0.1:3000"],
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**效果举例：**

- 没有 CORS 配置：前端 `fetch('http://localhost:3001/api/xxx')` → 浏览器拦截，控制台报红色 CORS 错误
- 有 CORS 配置：正常通信
- 开发微信小程序时如果配置了 `allow_origins=["*"]`，会允许任意网站调用你的 API——生产环境应该收紧范围

**与 localStorage 的关系：**

CORS 和 localStorage 无关（localStorage 只受同源策略限制，不涉及跨域），但**理解跨域能帮你定位为什么前端请求失败**——有时候 API 报错不是后端挂了，而是 CORS 没配好。

### 11.4 JSON 序列化与反序列化

**原理：**

JSON（JavaScript Object Notation）是一种轻量级的数据交换格式。两个核心操作：

| 操作 | 方法 | 方向 | 用途 |
|------|------|------|------|
| 序列化 | `JSON.stringify(obj)` | 对象 → 字符串 | 存到 localStorage / 发送到后端 |
| 反序列化 | `JSON.parse(str)` | 字符串 → 对象 | 从 localStorage 读取 / 接收后端响应 |

```js
const obj = { name: 'test', level: 188, tags: ['a', 'b'] };

// 序列化
const str = JSON.stringify(obj);
// → '{"name":"test","level":188,"tags":["a","b"]}'

// 反序列化
const restored = JSON.parse(str);
// → { name: 'test', level: 188, tags: ['a', 'b'] }
```

**JSON.stringify 会丢掉什么：**

```js
JSON.stringify(undefined)              // → undefined（被丢弃）
JSON.stringify(function(){})           // → undefined（被丢弃）
JSON.stringify(Symbol('foo'))          // → undefined（被丢弃）
JSON.stringify(/regex/)                // → "{}"
JSON.stringify(new Date())             // → '"2026-07-30T00:00:00.000Z"'（变成字符串）

const obj = { name: 'test' };
obj.self = obj;                        // 循环引用
JSON.stringify(obj);                   // ❌ TypeError

const m = new Map([['a', 1]]);
JSON.stringify(m);                     // → "{}"（Map 不自动序列化）
```

**本项目中的体现：**

几乎每个 localStorage 操作都涉及 JSON：

```js
// 存 — 对象 → JSON 字符串
localStorage.setItem('sg_user', JSON.stringify(user));

// 读 — JSON 字符串 → 对象
const raw = localStorage.getItem('sg_user');
const user = raw ? JSON.parse(raw) : null;

// 技能树保存时清理循环引用
const { _selected, _linking, ...rest } = node;  // 干掉运行时字段
saveToStorage(key, rest);
```

**效果举例：**

- `JSON.stringify` 日期 → 字符串，`JSON.parse` 后字符串不会自动变回 Date。所以 `new Date(localStorage.getItem('date'))` 才能得到真正的 Date 对象
- 技能树节点如果附带 `_selected` 这样的运行时状态，`JSON.stringify` 会把它也存进去，下次加载回来节点变成"选中"状态——所以要显式排除

### 11.5 异步编程（async/await / Promise / fetch）

**原理：**

JavaScript 是**单线程**语言，不能"一边等一边做别的事"。异步编程就是解决这个问题：在等待（网络请求、文件读取）时不阻塞主线程，等结果回来再继续执行。

**三种形态的演进：**

```js
// 1. 回调函数（Callback）— 最原始
fetchUser(id, function(user) {
    fetchTasks(user.id, function(tasks) {
        // 回调地狱...
    });
});

// 2. Promise — 链式调用
fetchUser(id)
    .then(user => fetchTasks(user.id))
    .then(tasks => renderTasks(tasks))
    .catch(err => console.error(err));

// 3. async/await — 同步写法（语法糖，底层仍是 Promise）
async function loadUserAndTasks(id) {
    try {
        const user = await fetchUser(id);          // 等
        const tasks = await fetchTasks(user.id);   // 等
        renderTasks(tasks);
    } catch (err) {
        console.error(err);
    }
}
```

**事件循环（Event Loop）简解：**

```
同步代码 → 直接执行，遇到 await → 挂起函数，继续执行后面的同步代码
        → 异步结果回来 → 放入微任务队列 → 同步代码执行完后再处理微任务

console.log('1');
setTimeout(() => console.log('2'), 0);  // 宏任务
Promise.resolve().then(() => console.log('3'));  // 微任务
console.log('4');

// 输出顺序：1 → 4 → 3 → 2
// 为什么 3 在 2 前面？因为微任务优先级高于宏任务
```

**本项目中的体现：**

```js
// app.js — 启动时并行加载 8 个后端 API
const [profile, habitsData, goalsData, ...] = await Promise.all([
    fetchUserProfile(user.id).catch(() => null),
    fetchHabits(user.id).catch(() => null),
    fetchGoals(user.id).catch(() => null),
    // ...
]);

// renderHistoryTasks 改为 async，从后端分页加载
async function renderHistoryTasks() {
    const result = await fetchTaskHistory(userId, { page, page_size, ... });
    // 渲染...
}

// 降级策略 — try-catch 包异步，失败走 localStorage
async function fetchSkillTreeIndexAsync() {
    try {
        const res = await fetch('/api/skill-trees?user_id=' + uid);
        const data = await res.json();
        localStorage.setItem('skill_tree_index', JSON.stringify(data.trees));
        return data.trees;
    } catch(e) {
        return loadSkillTreeIndexLocal();  // 降级
    }
}
```

**效果举例：**

- 用户打开系统时，8 个 API 是**并行**请求的（`Promise.all`），不是串行等待。总耗时≈最慢的那个请求，而不是 8 个请求时间相加
- 如果某个 API 挂了，`.catch(() => null)` 保证 Promise.all 整体不崩溃
- 异步函数 `renderHistoryTasks()` 中使用了 `await`，但**返回的是 Promise**，调用者需要 `await` 它才能拿到结果——忘了 `await` 是常见的 bug 来源

**与 localStorage 的关系：**

localStorage 是**同步** API，`setItem`/`getItem` 会阻塞主线程。这就是为什么大数据的存储不应该用 localStorage，而应该用异步的 IndexedDB。但优点是：在同步的渲染流程中可以直接读取，不需要 await。

### 11.6 try-catch 错误处理

**原理：**

JavaScript 的 `try-catch` 用于捕获运行时异常，不让程序崩溃。

```js
try {
    // 可能出错的代码
    const data = JSON.parse(raw);
    localStorage.setItem('key', data);
} catch (e) {
    // 出错时执行这里，程序继续运行
    console.warn('出错了:', e.message);
    // 返回默认值/降级处理
}
```

**哪些操作必须 try-catch：**

| 操作 | 可能抛出的异常 | catch 后做什么 |
|------|---------------|---------------|
| `JSON.parse` | `SyntaxError`（数据损坏） | 返回 null/默认值 |
| `localStorage.setItem` | `QuotaExceededError`（空间满） | 忽略写入或清理旧缓存 |
| `fetch()` | `TypeError`（断网） | 降级到 localStorage |
| `await res.json()` | `SyntaxError`（非 JSON 响应） | 返回空数据 |

**本项目中的体现：**

```js
// 每一处 localStorage 读取都 try-catch
function getCurrentUser() {
    try {
        const raw = localStorage.getItem('sg_user');
        return raw ? JSON.parse(raw) : null;
    } catch (e) {
        return null;  // 绝不崩溃
    }
}

// 每一处 fetch 都 try-catch 或 .catch()
async function fetchHabits(userId) {
    try {
        const res = await fetch(`/api/habits?user_id=${userId}`);
        if (!res.ok) return null;
        return await res.json();
    } catch (e) {
        return null;  // 网络异常 → 返回 null，调用方自行处理
    }
}
```

**效果举例：**

- 用户手动修改了 localStorage 中的数据（F12 → Application → 乱改），`JSON.parse` 失败。如果没 try-catch，整个页面白屏。有 try-catch，页面正常显示，只是看到空数据
- 后端突然返回 500 错误，`res.ok` 为 false，没 try-catch 的话会继续执行 `res.json()` 但内容不是 JSON，解析失败报错。有 try-catch 或 `.catch()` 的话静默处理

### 11.7 闭包（Closure）与作用域

**原理：**

闭包是指一个函数**能记住并访问其定义时的作用域**，即使它在外层函数返回后执行。

```js
function createCounter() {
    let count = 0;                         // 私有变量
    return function() {                    // 闭包
        count++;
        return count;
    };
}

const counter = createCounter();
console.log(counter());  // 1
console.log(counter());  // 2
// count 变量没有被回收！闭包保留了它的引用
```

**本项目中的体现：**

```js
// pages/tasks.js — 模块通过 IIFE 或 script 作用域隔离
// 这些变量对外部不可见，形成闭包
let taskHistoryPage = 1;
let taskHistoryFilterStatus = '';
let taskHistorySortBy = 'newest';
let taskDeleteMode = false;

function renderHistoryTasks() {
    // 可以访问外层的 taskHistoryPage、taskHistoryFilterStatus 等
    // 这就是闭包——函数与其定义时的作用域绑定
}
```

**效果举例：**

```
每个 page 脚本文件加载后，内部定义的 let/const/function 都在文件级作用域
  ├── 页 A 和页 B 都有 renderTasks() 函数 → 互不冲突
  ├── 但 window 全局变量（如 AppData）所有页面共享
  └── 这也是为什么用 var 或 window.xxx 要小心——会污染全局

闭包的实际案例：
  renderHistoryTasks 引用了 taskHistoryPage 变量
  即使这个函数被 setTimeout 延迟执行，它仍然能访问到最新的 taskHistoryPage 值
```

**与 localStorage 的关系：**

闭包让前端可以封装 localStorage 的操作，形成私有接口：

```js
const storage = (function() {
    const PREFIX = 'sg_';    // 私有常量，外部不可修改

    function get(key) {
        try {
            return JSON.parse(localStorage.getItem(PREFIX + key));
        } catch(e) { return null; }
    }

    function set(key, value) {
        try { localStorage.setItem(PREFIX + key, JSON.stringify(value)); } catch(e) {}
    }

    return { get, set };  // 只暴露 get/set，隐藏 PREFIX
})();

storage.get('user');    // ✅ 正确
storage.PREFIX;         // ❌ undefined，外部访问不到
```

### 11.8 严格模式（'use strict'）

**原理：**

`'use strict'` 是 ES5 引入的一种更严格的 JavaScript 执行模式。在严格模式下，一些"静默失败"的语法会直接报错，帮助开发者提前发现潜在问题。

**关键区别：**

| 行为 | 非严格模式 | 严格模式 |
|------|-----------|---------|
| 未声明变量赋值 | 创建全局变量 | ❌ `ReferenceError` |
| `this` 为 undefined 的函数 | `this` → 全局对象 | `this` → `undefined` |
| 删除不可删除属性 | 静默失败 | ❌ 报错 |
| 重名对象属性 | 后者覆盖前者 | ❌ 报错 |
| `with` 语句 | 可用 | ❌ 报错 |

```js
// 非严格模式
x = 10;         // 隐式创建全局变量 x（可能是 bug）

// 严格模式
'use strict';
x = 10;         // ❌ ReferenceError: x is not defined
let y = 10;     // ✅ 必须显式声明
```

**本项目中的体现：**

```js
// 大多数页面文件顶部有 'use strict'
// skill-tree/js/ 中的文件有明确的 'use strict'

// 而 pages/*.js 使用 let/const 声明变量，不需要 'use strict' 也能拦截全局污染
// 但使用 var 或忘记声明时，严格模式能救命
```

**效果举例：**

- 在非严格模式下，如果你写 `taskHistroyPage = 1`（拼写错误），JS 会静默创建一个全局变量 `taskHistroyPage`，然后页面翻页功能永远不生效（因为实际读取的是 `taskHistoryPage`）
- 在严格模式下，这种拼写错误直接报错，让你**在开发阶段就发现**而不是留到线上

### 11.9 DOM 操作（Document Object Model）

**原理：**

DOM 是浏览器将 HTML 文档解析为**树形结构**的对象模型。JS 通过操作这个树来改变页面内容。

```
HTML: <div id="app"><p>你好</p></div>

DOM 树：
  document
    └── html
        └── body
            └── div#app
                └── p
                    └── "你好"
```

**核心操作：**

```js
// 查找
document.getElementById('page-tasks');        // 按 ID
document.querySelector('.card');              // 按 CSS 选择器（返回第一个）
document.querySelectorAll('.task-item');      // 按 CSS 选择器（返回所有）

// 修改
el.textContent = '新文本';                     // 纯文本（安全）
el.innerHTML = '<span>HTML</span>';           // HTML（注意 XSS 风险）
el.style.color = 'red';
el.classList.add('active');                   // CSS 类
el.classList.remove('active');
el.classList.toggle('active');

// 创建与插入
const div = document.createElement('div');
div.className = 'card';
div.textContent = '内容';
parent.appendChild(div);                      // 末尾追加
parent.insertBefore(div, refNode);            // 插到某元素前

// 删除
el.remove();                                  // 直接删除（现代浏览器）
parent.removeChild(el);                       // 传统方式
```

**本项目中的体现：**

```js
// 几乎全部页面渲染通过 DOM 操作完成
function renderHistoryTasks() {
    var el = document.getElementById('page-tasks');
    el.innerHTML = '<div>加载中...</div>';  // 先设加载状态

    // 异步获取数据后重建内容
    const html = tasks.map(t => `
        <div class="task-item" data-id="${t.id}">
            <span>${t.name}</span>
            <span class="exp-badge">+${t.exp} EXP</span>
        </div>
    `).join('');
    el.innerHTML = html;
}

// 事件绑定
document.querySelector('.btn').addEventListener('click', function(e) {
    // 处理点击
});
```

**与存储的关系：**

DOM 操作通常与 localStorage 配合形成"读取 → 渲染"模式：

```js
// 从 localStorage 读数据 → 渲染到 DOM
function renderUserInfo() {
    const user = getCurrentUser();               // localStorage 读取
    document.getElementById('user-name').textContent = user.name;  // DOM 显示
}
```

### 11.10 事件委托（Event Delegation）

**原理：**

事件冒泡（Event Bubbling）机制：当元素上触发事件时，事件会沿着 DOM 树向上冒泡到父元素、祖父元素……直到 document。

事件委托就是利用这一点：不在每个子元素上单独绑定事件，而是在**父元素**上监听，通过 `event.target` 判断是哪个子元素触发的。

```html
<div id="task-list">
    <div class="task-item" data-id="1">任务1</div>
    <div class="task-item" data-id="2">任务2</div>
    <div class="task-item" data-id="3">任务3</div>
</div>
```

```js
// ❌ 不推荐：每个任务单独绑定（新增任务还要重新绑定）
document.querySelectorAll('.task-item').forEach(el => {
    el.addEventListener('click', () => { /* ... */ });
});

// ✅ 推荐：事件委托，父元素监听一次
document.getElementById('task-list').addEventListener('click', function(e) {
    const item = e.target.closest('.task-item');  // 找到被点击的 task-item
    if (!item) return;                            // 点到了空白区域，忽略
    const id = item.dataset.id;                   // → "1"
    console.log('点击了任务', id);
});
```

**本项目中的体现：**

```js
// 任务板块 — 委托处理各种按钮点击
// 所有 .task-action-btn 的绑定通过父容器委托
// 新增任务时不需要重新绑定事件
```

**为什么任务板中大量使用 `innerHTML` 重建而事件不丢失？**

正是因为事件绑定在父容器上，子元素通过 `innerHTML` 重建后，事件依然有效。如果事件绑在子元素上，重建后所有事件绑定都丢了（需要重新绑定）。

**效果举例：**

- 用户添加了 10 个任务，每个任务都有"完成"、"删除"按钮。如果用事件委托，只需要在父容器绑定一次事件
- 用户删除某个任务后重新渲染，即使 `innerHTML` 完全重建，父容器的事件仍在工作
- 性能优势：1000 个任务只需要 1 个事件监听，而不是 1000 个

### 11.11 事件循环（Event Loop）深入

**原理：**

JS 是单线程的，但通过事件循环机制实现了非阻塞 I/O。理解事件循环对定位"为什么 `localStorage.getItem` 会卡"、"为什么 `await` 后面的代码没有立即执行"等问题至关重要。

```
执行流程：

              ┌──────────────────────────┐
              │      Call Stack（调用栈）   │ ← 代码执行的地方
              │  （同步代码在这里跑）       │
              └────────────┬─────────────┘
                           │ 遇到异步操作 → 交给 Web API
                           ▼
              ┌──────────────────────────┐
              │      Web API 层           │ ← 浏览器原生 API
              │  setTimeout / fetch / DOM │ ← 异步操作在这里等待
              └────────────┬─────────────┘
                           │ 条件满足 → 回调进入 Task Queue
                           ▼
              ┌──────────────────────────┐
              │      Task Queue（任务队列） │ ← 等待执行的回调
              │  ┌─────┐ ┌─────┐        │
              │  │宏任务│ │微任务│        │
              │  └─────┘ └─────┘        │
              └────────────┬─────────────┘
                           │ 调用栈空了 → 取任务执行
                           ▼
                         回到 Call Stack
```

**宏任务（MacroTask）vs 微任务（MicroTask）：**

| 类型 | 代表 | 执行时机 |
|------|------|----------|
| 宏任务 | `setTimeout`, `setInterval`, DOM 事件回调 | 每次事件循环取一个执行 |
| 微任务 | `Promise.then`, `async/await`, `MutationObserver` | 每个宏任务完成后，清空所有微任务 |

**关键结论：**

```js
console.log('1');
setTimeout(() => console.log('2'), 0);     // 宏任务 → 最后执行
Promise.resolve().then(() => console.log('3'));  // 微任务 → 其次执行
console.log('4');

// 输出: 1 → 4 → 3 → 2
// 解释:
//   1. 同步代码：输出 1 和 4
//   2. 清空微任务：输出 3
//   3. 取一个宏任务：输出 2
```

**localStorage 为什么是同步 API？**

localStorage 的设计目标是简单轻量的键值存储，读取本地磁盘数据**通常很快**（微秒到毫秒级），同步 API 在代码书写上更简单。但如果存储大数据（几 MB），同步读取会阻塞主线程几百毫秒，造成页面卡顿——这就是 localStorage 不适合存大量数据的原因。

```js
// ❌ 同步阻塞：存大 JSON 导致冻结
const bigData = localStorage.getItem('huge_key');  // 阻塞 100ms
// 这 100ms 内，页面不能做任何响应，不能滚动、不能点击

// ✅ 异步：IndexedDB 读取不阻塞主线程
const bigData = await indexedDBGet('huge_key');  // 不阻塞，后续代码继续执行
```

### 11.12 前端路由

**原理：**

前端路由是指**不经过服务器**，在浏览器端通过 JS 控制页面切换的机制。SPA 的核心基础设施。

**两种实现方式：**

| 方式 | 原理 | 本项目使用 |
|------|------|-----------|
| **Hash 路由** | URL 中 `#/tasks`，改变 hash 不触发页面刷新，通过 `hashchange` 事件监听 | ❌ 否 |
| **History API** | 使用 `pushState`/`popState` 改变 URL 路径，不触发页面刷新 | ❌ 否 |
| **显示隐藏** | 页面预先渲染，通过 CSS class 控制显隐（`.page--active`） | ✅ 是 |

**本项目实现：**

```js
// router.js — 基于显示隐藏的 SPA 路由
const PAGE_JS_MAP = {
    dashboard: 'dashboard',
    action: 'action',
    history: 'history',
    attributes: 'attributes',
    goals: 'goals',
    tasks: 'tasks',
    habits: 'habits',
    rewards: 'rewards',
    skills: 'skills',
    agent: 'agent',
};

function navigateTo(pageName, subPage) {
    // 1. 隐藏所有页面
    document.querySelectorAll('.page').forEach(p => p.classList.remove('page--active'));
    // 2. 显示目标页面
    const target = document.getElementById('page-' + pageName);
    if (target) target.classList.add('page--active');
    // 3. 懒加载页面 JS（如果还没加载）
    if (!loadedPages[pageName]) {
        loadPageJS(pageName);
    }
    // 4. 调用渲染函数
    renderers[pageName](subPage);
    // 5. 保存到 sessionStorage
    sessionStorage.setItem('lastPage', pageName);
}
```

**对比 Hash 路由：**

```
Hash 路由：
  http://localhost:3000/#/tasks      → 可加收藏夹
  http://localhost:3000/#/tasks/week → 支持子页面
  缺点是 URL 带 # 号

本项目方案：
  SPA 内的页面切换不改变 URL 地址
  始终是 http://localhost:3000（除了登录页）
  刷新后通过 sessionStorage 恢复页面位置
```

**效果举例：**

- 用户在任务页面点击侧边栏"仪表盘"，`navigateTo('dashboard')` 立即执行，没有网络请求
- 按 Ctrl+1 到 Ctrl+8 快速切换页面，这实质是在调用 `navigateTo(pages[key])`
- 刷新页面后从 sessionStorage 恢复上次位置（第 4 节已讲）

### 11.13 模块化加载

**原理：**

将 JS 代码拆分成多个文件（模块），每个文件管理自己的一部分功能，通过依赖加载组合成完整应用。

**本项目的加载方案：**

本项目不使用 ES Module（`import`/`export`）或 CommonJS（`require`），而是采用**传统 `<script>` 标签按顺序加载 + 全局变量共享**的方式：

```html
<!-- index.html — 严格按依赖顺序加载 -->
<script src="js/data.js"></script>      <!-- AppData 全局数据模型 -->
<script src="js/router.js"></script>    <!-- 路由 + PAGE_JS_MAP -->
<script src="js/utils.js"></script>     <!-- 工具函数 60+ -->
<script src="js/components.js"></script><!-- 可复用组件 -->
<script src="js/pages/dashboard.js"></script>
<script src="js/pages/action.js"></script>
<!-- ... 其他页面 ... -->
<script src="js/app.js"></script>       <!-- 入口初始化（最后加载） -->
```

```
依赖关系：
  data.js      → 定义 AppData（所有页面依赖）
  router.js    → 引用 AppData、navigateTo（所有页面依赖）
  utils.js     → 定义 getCurrentUser、fetchXxx（所有页面依赖）
  components.js → 定义统计卡片等（页面依赖）
  页面文件      → 引用以上所有全局变量
  app.js       → 引用以上所有 + 启动逻辑
```

**为什么不用 ES Module（import/export）？**

```js
// ES Module 方式
import { AppData } from './data.js';
import { navigateTo } from './router.js';

// 问题：需要现代浏览器，且所有文件都要改写
// 本项目的 <script> 加载方式虽然古老，但在没有构建工具（webpack/vite）的情况下最可靠
```

**与 localStorage 的关系：**

模块化加载保证了代码的执行顺序，而 localStorage 的读写不依赖加载顺序——无论在哪个模块读写，访问的都是同一个存储空间。

**效果举例：**

- `data.js` 定义了 `AppData.user = {}`，所有页面文件都可以直接使用 `AppData.user.name`
- 如果在 `data.js` 加载之前访问 `AppData`，会报 `ReferenceError`
- 但 localStorage 在任何时机都可以读写，不会报未定义错误

### 11.14 变量的可变性与不可变性

**原理：**

JS 有三种变量声明方式，对理解"为什么数据改了但页面没刷新"重要：

```js
const a = 10;
a = 20;             // ❌ TypeError: Assignment to constant variable

const obj = { name: 'test' };
obj.name = 'new';   // ✅ 对象内容可以改，const 阻止的是"重新赋值"，不是"修改属性"

let b = 10;
b = 20;             // ✅ let 可重新赋值

var c = 10;
c = 20;             // ✅ var 可重新赋值，但有作用域问题（函数作用域而非块级）
```

**关键区别：**

```js
// const 引用类型——地址不可变，内容可变
const list = [1, 2, 3];
list.push(4);              // ✅ list → [1, 2, 3, 4]（修改内容）
list = [5, 6];             // ❌ 重新赋值

// 冻结对象——真正不可变
const frozen = Object.freeze({ name: 'test' });
frozen.name = 'new';        // ❌ 静默失败（严格模式会报错）
```

**本项目中的体现：**

```js
// AppData 使用 const 声明（不可重新赋值，但属性可修改）
const AppData = {
    user: {},
    habits: [],
    // ...
};
AppData.user = { name: 'test' };  // ✅ 可以

// 防止数据被意外修改
// 在同步到后端后，保持前端数据不可变需要小心处理
```

**与 localStorage 的关系：**

`JSON.parse(localStorage.getItem())` 返回的是**全新的对象**，与之前存进去的对象没有引用关系。这是好事——避免了意外的引用牵连：

```js
const obj = { name: 'test' };
localStorage.setItem('key', JSON.stringify(obj));

obj.name = 'changed';  // 修改原对象

const loaded = JSON.parse(localStorage.getItem('key'));
console.log(loaded.name);  // → 'test' ✅ localStorage 中的数据不受影响

// 因为 JSON.stringify 深拷贝了数据，不再是同一个引用
```

### 11.15 深拷贝与浅拷贝

**原理：**

| 拷贝方式 | 做法 | 嵌套对象行为 | 示例 |
|----------|------|-------------|------|
| 赋值引用 | `obj2 = obj1` | 指向同一对象，改一个全变 | ❌ 最危险 |
| 浅拷贝 | `{...obj}` | 第一层独立，嵌套对象仍共享引用 | ⚠️ 需注意 |
| 深拷贝 | `JSON.parse(JSON.stringify(obj))` | 完全独立 | ✅ 最安全但性能较差 |

```js
const original = { name: 'test', address: { city: '北京' } };

// 赋值引用
const ref = original;
ref.name = 'changed';
console.log(original.name);  // → 'changed' ❌

// 浅拷贝
const shallow = { ...original };
shallow.name = 'new';
console.log(original.name);  // → 'changed'（第一层独立）
shallow.address.city = '上海';
console.log(original.address.city);  // → '上海' ❌ 嵌套对象还是共享

// 深拷贝
const deep = JSON.parse(JSON.stringify(original));
deep.address.city = '深圳';
console.log(original.address.city);  // → '北京' ✅ 完全独立
```

**本项目中的体现：**

```js
// 技能树发布时深拷贝 learner 数据，防止引用污染
published.learner = JSON.parse(JSON.stringify(learner));

// 从 localStorage 加载数据时天然深拷贝（JSON.parse 创建新对象）
// 修改加载后的对象不会影响 localStorage 中的原始数据
```

**效果举例：**

- 用户打开技能树，从 localStorage 加载数据。修改节点名称后自动保存，但 localStorage 中存的是保存前的快照——这是合理的，因为 `saveToStorage` 每次写入都是全新的序列化
- 如果使用赋值引用而不是深拷贝，修改一个"已渲染"的技能树节点名称，可能会意外影响到另一个"从 localStorage 加载"的节点

### 11.16 函数声明提升与暂时性死区

**原理：**

```js
// 函数声明提升（Hoisting）——可以"先调用，后声明"
foo();  // ✅ 正常工作
function foo() { console.log('foo'); }

// var 变量提升——声明提升，赋值不提升
console.log(x);  // → undefined（不报错）
var x = 10;

// let/const 暂时性死区——声明前使用报错
console.log(y);  // ❌ ReferenceError: Cannot access 'y' before initialization
let y = 10;
```

**本项目中的体现：**

```js
// 页面文件使用 function 声明，所以函数间调用顺序无关
// 可以在文件顶部调用 renderHistoryTasks()，而函数定义在文件末尾
// 这大大减轻了"谁先定义谁后定义"的心智负担

function renderHistoryTasks() { /* ... */ }
function renderHistoryEmpty() { /* ... */ }
// 无论哪个函数在前面，互相调用都没问题
```

**与 localStorage 的关系：**

因为函数声明提升，所有 `function` 定义的函数在代码执行前就已经可用。这意味着无论在文件的哪一行调用 `getCurrentUser()` 或 `saveToStorage()`，它们都已经准备好。
