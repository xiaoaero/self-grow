## 一、现状：现在根本没有鉴权

先看清起点，再谈选型。

### 1.1 当前实现（代码事实）

```python
# backend/routers/deps.py
async def get_current_user(user_id: int = Query(..., description="用户 ID")):
    user = get_user(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
```

- 登录 = 在 `login.html` 点一张用户卡片 → 前端把 `user` 存进 `localStorage['sg_user']`
- 之后所有请求带 `?user_id=N`，后端只校验"这个 id 存在吗"
- `users` 表**没有 password 字段**（只有 id/name/role/level/exp/total_exp/streak/joined）
- CORS 配置 `allow_origins=["*"]`
- `login.html` 第 34 行原文写着：`💡 后续版本将支持用户名密码登录`

**结论：任何人改一下 URL 参数就能看到别人的全部数据。** 这是本项目最严重的缺陷，面经 Q7 已经准备"主动认错"——本文的目标就是把它从"缺陷"变成"我做过的加固"。

### 1.2 顺带发现的一个 Bug（改造时必须一起修）

| 位置 | 存的 key |
|---|---|
| `login.html:95` 写入 | `localStorage['sg_user']` |
| `frontend/js/utils.js:316` 读取 | `localStorage['sg_user']` ✅ |
| `frontend/skill-tree/js/utils.js:90` 读取 | `localStorage['currentUser']` ❌ **读不到** |

**技能树编辑器永远拿不到 user_id**，目前靠 `getCurrentUserId() || 1` 兜底成用户 1。做鉴权改造时必须统一为一个 key，否则技能树 AI 的会话归属会一直是错的。

### 1.3 比"无鉴权"更严重：角色可以随便提（垂直越权）

按需求，**技能树编辑器只有管理员能进入**（普通用户连入口都不该有，只能查看已发布内容并学习）。但当前实现是：

```javascript
// frontend/skill-tree/index.html:46
var SKILL_TREE_ROLE = new URLSearchParams(location.search).get('role') || 'admin';
```

三个致命点叠加：

| 问题 | 说明 |
|---|---|
| **默认值就是 admin** | 不带任何参数打开 `skill-tree/index.html` → 直接是管理员，可保存 / 上线 / 删除整棵技能树 |
| **role 来自 URL 参数** | 普通用户把地址栏的 `?role=user` 改成 `?role=admin`（或直接删掉参数）就能提权 |
| **后端完全不校验 role** | 全仓库 `routers/` 里 `role` 只出现在返回用户信息的两行（`routers/users.py:26/56`），技能树相关端点**没有任何角色检查** |

前端 `frontend/js/pages/skills.js:424` 只对 admin 显示「✏️ 编辑技能」按钮——但这只是**把按钮藏起来**，属于典型的"靠 UI 做权限"。

**结论：普通用户目前可以直接打开编辑器页面获得完整管理员能力，后端也不拦。** 这比"看得到别人数据"更严重——是能改、能删、能覆盖别人已发布的技能树。

> 因此本次改造必须**同时**解决身份认证（你是谁）和角色授权（你能做什么）。只做前者，等于装了锁但把钥匙挂在门上。

## 二、先定标尺：本项目的约束是什么

脱离约束谈方案都是耍流氓。给 Self-Grow 画个像：

| 维度 | 现状 | 对鉴权的影响 |
|---|---|---|
| 部署形态 | Docker 单容器，FastAPI 同源提供前端静态资源 | **前后端同源**，Cookie 方案可行 |
| 访问场景 | 本机 + 手机/平板局域网访问 | 需支持跨域或同域多端 |
| 用户规模 | 1~5 人（自己 + 家人/室友） | 不需要企业级 IAM |
| 前端形态 | 原生 JS SPA + 独立的 skill-tree SPA（**两个入口**） | 需要**统一的取凭证方式** |
| 角色划分 | **只有 admin 能进入技能树编辑器（普通用户连入口都没有）；user 只能查看已发布内容并学习** | 必须做**后端强制的角色授权**；入口隐藏只是 UX，不是安全边界 |
| MCP 插件 | stdio（本地）+ streamable-http（远程） | **非浏览器客户端，拿不到 Cookie** |
| 数据敏感度 | 个人成长数据（习惯、财务、目标） | 中等，不需要金融级 |
| 面试诉求 | 需要"能讲的设计 + 能现场演示" | 方案要**有可讲的取舍**，不是越复杂越好 |
| 运维能力 | 单进程 SQLite，无人值守 | 不能引入 Redis、不能依赖外部 IdP |

**一句话约束**：单进程、同源、小规模、要有 API Key 能力、要能讲清楚。

## 三、常见登录方式全景（9 种，逐个评）

评价维度用 ★（5 星满）表示"对本项目的适配度"。

### A. URL 参数 user_id（**当前方案**）

**原理**：请求带 `?user_id=1`，后端查库确认存在。

| | |
|---|---|
| 优点 | 零成本；本地开发调试方便；Swagger 里直接填参数就能测 |
| 缺点 | **等于没有鉴权**；参数可枚举、可篡改；URL 会留在浏览器历史和日志里 |
| 适配度 | ★☆☆☆☆ |

> 唯一价值：作为**开发态降级开关**保留（用环境变量控制），生产必须关掉。

---

### B. Session-Cookie（有状态）

**原理**：登录成功后服务端生成 `session_id` 存内存/表，通过 `Set-Cookie` 下发（httpOnly + SameSite），后续请求自动携带。

| | |
|---|---|
| 优点 | **最省心**：浏览器自动带凭证，前端几乎零改造；httpOnly 天然防 XSS 窃取；服务端可随时踢人（删 session 即刻失效）；实现简单，不需要 JWT 库 |
| 缺点 | 服务端要存状态（本项目单进程内存即可，但重启丢失，需落表）；跨域/跨端要处理 `SameSite=None + Secure + HTTPS`；**非浏览器客户端（MCP、脚本）用起来别扭**；水平扩展要共享 session 存储 |
| 适配度 | ★★★★☆ |

> 单看"浏览器 + 同源 + 单机"，Session 的确又简单又安全。它在本项目被否决，不是因为它不好，而是因为**本项目有三类客户端根本不是浏览器**。下面专门论证。

---

### 3.1 为什么 Session-Cookie 在本项目不成立（重点）

Session 的全部能力建立在一条假设上：**客户端是浏览器，会自动维护 Cookie 罐**。
这个假设在 Self-Grow 里被三处打破——MCP 插件、技能树编辑器、以及"能演示"这件事本身。

### 理由一：MCP 插件没有 Cookie 上下文（决定性理由）

MCP 插件（`backend/mcp_server.py`）的运行方式是：

```
Claude Desktop / Cursor ──spawn──▶ python mcp_server.py ──HTTP──▶ /api/*
                    （stdio 管道，没有浏览器）
                    或
远程客户端 ──HTTP──▶ /api/*          （streamable-http 模式）
```

| Session 在这里的问题 | 具体表现 |
|---|---|
| **没有登录入口** | MCP 客户端是 LLM 驱动的，它无法"填写登录表单"。Session 必须由 `Set-Cookie` 下发，而 MCP 客户端不会跳登录页、不会保存 Cookie、更不会处理 302 |
| **没有 Cookie 存储** | stdio 模式是本地子进程，压根没有浏览器上下文；HTTP 模式下每个客户端实现千差万别，MCP 协议本身**没有定义凭证协商机制** |
| **非交互是刚需** | 用户配置一次就希望长期可用。Session 有过期时间（默认几分钟到几小时），过期后要重新登录——而 MCP 侧没有"人"来重新登录 |
| **无法用环境变量预置** | 现在 stdio 模式靠 `SELF_GROW_USER_ID` 环境变量指定用户（本地进程可信，合理）。Session 只能靠"先登录再拿 Cookie"，这个环境变量无法表达 |
| **多实例/重启丢会话** | Session 存内存则 MCP 服务重启后要重新登录；存表则每次请求多一次查询 |

**Bearer Token / API Key 天然解决以上全部**：配置一次字符串 → 每个请求带上 → 不需要任何交互、不需要 Cookie 存储、重启无影响、可撤销可轮换。

> 一句话：**Session 是"浏览器会话"的产物，而 MCP 的世界里没有浏览器。**

### 理由二：技能树编辑器是独立 SPA，跨入口且要带角色

技能树编辑器（`frontend/skill-tree/index.html`）和主应用不是同一个页面，它有三种打开方式：

```javascript
// 1. 主应用 skills.js:424 —— 新窗口打开编辑器（仅 admin 有按钮）
window.open('skill-tree/index.html', '_blank')

// 2. skills.js:470 / 526 —— iframe 内嵌查看器（普通用户）
'skill-tree/index.html?role=user&preview=true&treeId=...&userId=...'
```

Session 在这里会遇到一连串麻烦：

| 问题 | 说明 |
|---|---|
| **iframe 里的第三方 Cookie** | 虽然本项目同源（不触发第三方 Cookie 限制），但只要将来前后端分离或 CDN 部署，iframe 中的 Cookie 就会被浏览器拦截（`SameSite=None; Secure` + HTTPS 才能救，而局域网是 HTTP） |
| **新窗口 / 新标签页要重新登录** | Session 依赖当前浏览上下文；从主应用 `window.open` 出的新窗口虽然共享 Cookie，但**手机浏览器、隐私模式、不同浏览器**之间不共享，用户会反复被踢回登录页 |
| **角色信息无法自证** | 这是**最关键的**。按新需求，编辑器只有 admin 能进。Session 方案下，前端要知道"我是不是 admin"必须再调一次 `/api/auth/me`；而 Bearer Token 的**载荷里直接带 `role`**，前端解析即得，后端验签即信——**角色随凭证走，不随会话走** |
| **后端无法无状态地校验角色** | 技能树的写端点（保存/上线/删除/AI 编辑）每次都要确认"这个人是 admin"。Session 方案要查库拿 session → 拿 user → 拿 role（3 次 IO 或一次联表）；JWT 方案验签后直接从 payload 取（0 次 IO） |
| **AI 编辑接口的长耗时** | 技能树 AI 一次调用可能几十秒（`REQUEST_TIMEOUT` 甚至设到 300s）。Session 若在请求期间过期，长任务会在中途 401；JWT 的 exp 在**请求入口**校验一次即可，后续流程不再依赖 |

### 理由三：无法现场演示（面试场景的硬需求）

这是很实际但容易被忽略的一条：

- **Swagger（`/docs`）**：FastAPI 的 `OAuth2PasswordBearer` 会在文档右上角生成「Authorize」按钮，粘贴 token 后所有接口都能直接调试。**Session 方案下 Swagger 无法承载登录态**（除非手动抓 Cookie 塞进去），等于放弃了一个免费的演示舞台
- **curl / Postman 演示**：`curl -H "Authorization: Bearer xxx" ...` 一行就能演示受保护接口；Session 要先登录、存 Cookie、再带 Cookie，演示时容易翻车
- **两个入口的登录态不同步**：主应用登录了，技能树编辑器还要再登录一次（不同浏览器上下文时），演示时非常尴尬

### 理由四：单进程环境下，无状态反而更省事

| | Session | JWT |
|---|---|---|
| 服务重启 | 内存 session 全丢（用户被踢）；改存表则每次请求多一次查询 | 无影响（Access 2h 内照常可用） |
| 部署形态变化 | 将来若拆成前后端分离 / 多实例，要引入共享 session 存储（Redis） | 天然支持，无需改动 |
| 存储开销 | 每个活跃用户一条记录，还要定时清理过期 | 只需维护 refresh_tokens（可撤销部分） |

### 结论

> **Session 不是"不行"，是"不适合有三种客户端形态的本项目"。**
> 它的适用边界很清晰：纯浏览器、纯同源、无机器客户端——本项目三条都不满足。
> 如果哪天 Self-Grow 砍掉 MCP 插件和独立编辑器，只留一个同源 SPA，那我会毫不犹豫换回 Session（更简单也更安全）。**方案永远服务于形态，形态变了结论就该变。**

### C. JWT（Access + Refresh，无状态）⭐ **推荐**

**原理**：登录验证密码 → 签发短期 Access Token（2 小时）+ 长期 Refresh Token（30 天）；Access 放请求头 `Authorization: Bearer`，过期后拿 Refresh 换新的。

| | |
|---|---|
| 优点 | 服务端无状态（不存 session，重启不丢）；**天然支持多端**：浏览器、MCP、移动端、curl、Swagger 一视同仁；FastAPI 自带 `OAuth2PasswordBearer`，Swagger 右上角直接出现「Authorize」按钮，**面试可现场演示**；载荷可带 role/version，便于后续做权限 |
| 缺点 | 无法主动失效（需黑名单或短有效期兜底）；token 存 localStorage 有 XSS 风险（存 httpOnly Cookie 又有 CSRF 考量）；实现比 Session 略复杂（要写刷新逻辑、401 重试） |
| 适配度 | ★★★★★ |

**为什么它比 Session 更适合本项目**：
1. MCP 插件（HTTP 模式）和未来的移动端都是"非浏览器客户端"，Bearer 是它们的通用语言
2. Swagger 的 Authorize 按钮 = 面试现场演示的利器（Session 做不到）
3. 单进程 SQLite 环境里，"无状态"恰好避开了"session 存哪"的问题

---

### D. OAuth2 / 第三方登录（GitHub、微信、Google）

**原理**：接入授权服务器，用户跳转授权 → 回调拿 code → 换 token → 拿用户信息。

| | |
|---|---|
| 优点 | 不用自己存密码（最安全的一环）；用户体验好（一键登录）；面试官认这个名词 |
| 缺点 | **强依赖外部服务**（墙、额度、应用审核）；微信登录要企业资质；个人项目还要维护 client_secret；回调地址 + HTTPS 是硬门槛；**局域网/离线部署直接废掉** |
| 适配度 | ★★☆☆☆ |

> 典型的"为了显得高级而引入复杂度"。**个人自用系统 + 局域网部署，第三方登录是净负担。** 真想加，GitHub OAuth 是唯一现实选项（免费、无资质要求），可以作为"二期可选"。

---

### E. SSO / OIDC / CAS

**原理**：企业级单点登录，独立身份提供商（Keycloak、Authing 等）。

| | |
|---|---|
| 优点 | 多系统统一身份；企业级功能（MFA、审计、组织架构）齐全 |
| 缺点 | **完全过度设计**。要给 1~5 人的个人项目部署 Keycloak？运维成本和收益严重倒挂 |
| 适配度 | ★☆☆☆☆ |

> 面试时可以说"我知道它的位置，但这个项目不配用 SSO"——这句话本身是加分的。

---

### F. 邮箱 / 短信验证码（无密码）

**原理**：输入邮箱 → 收验证码 → 校验通过即登录。

| | |
|---|---|
| 优点 | 用户不用记密码；没有密码泄露风险；体验现代 |
| 缺点 | 依赖邮件/短信服务（要钱、要配置、可能失败）；个人项目自己一个人用，收发验证码比输密码还烦；短信要实名备案 |
| 适配度 | ★★☆☆☆ |

---

### G. Passkey / WebAuthn（无密码，生物识别）

**原理**：基于公私钥对，用指纹/面容/硬件密钥登录，私钥不出设备。

| | |
|---|---|
| 优点 | 目前最安全的方案；抗钓鱼；体验极佳（指纹一按） |
| 缺点 | 实现复杂度高（挑战-响应、凭证存储、跨设备同步）；浏览器兼容要处理；**多端（手机访问局域网服务）配置繁琐** |
| 适配度 | ★★☆☆☆（技术前瞻性 ★★★★★） |

> 适合作为"未来展望"在面试里提一句，体现技术视野，但别现在做。

---

### H. API Key / 静态令牌（面向机器）

**原理**：为每个客户端签发一个长期随机字符串，放在请求头。

| | |
|---|---|
| 优点 | 非交互客户端的**唯一现实选择**（MCP、定时任务、脚本、CI）；实现最简单（查表比对） |
| 缺点 | 泄露即失守（需支持轮换、撤销、作用域）；不适合作为人类的主登录方式 |
| 适配度 | ★★★★☆（**作为 JWT 的补充，而非替代**） |

> MCP 插件目前用 `SELF_GROW_USER_ID` 环境变量（默认 1）。改造后 HTTP 模式应改用 API Key，stdio 模式保留环境变量（本地进程本来就是可信的）。

---

### I. HTTP Basic

**原理**：`Authorization: Basic base64(user:pass)`，每次请求都带密码。

| | |
|---|---|
| 优点 | 极简；curl 友好 |
| 缺点 | 每次都传密码（base64 不是加密）；浏览器会弹原生弹窗（丑且无法登出）；无过期机制 |
| 适配度 | ★★☆☆☆ |

> 只适合内网小工具的临时方案，不适合有前端的系统。

---

### 补充形态 J. 本地免密模式（Trusted Mode）

**原理**：环境变量 `SELF_GROW_TRUSTED_MODE=1` 时，跳过鉴权，固定为指定用户。

| | |
|---|---|
| 优点 | 本地开发/演示零摩擦；Docker 一键体验时不用先注册；**面试演示时不会因为忘密码翻车** |
| 缺点 | 开了就是裸奔，必须显式开启且日志告警 |
| 适配度 | ★★★★☆（**作为开关存在，不作为方案**） |

## 五、选型结论

# ✅ 推荐：用户名密码 + JWT（Access + Refresh） + 本地免密开关 + MCP 独立 API Key

```
┌─────────────────────────────────────────────────┐
│  浏览器用户  → 用户名+密码 → JWT (Access+Refresh) │
│  MCP/脚本    → API Key（HTTP 模式）              │
│              或 SELF_GROW_USER_ID（stdio 本地）  │
│  本地开发/演示 → TRUSTED_MODE 开关跳过鉴权        │
└─────────────────────────────────────────────────┘
```

**四层各有分工，不互相替代。**

### 为什么选 JWT 而不是 Session（这是最容易被追问的一题）

**完整论证见 [3.1 节](#31-为什么-session-cookie-在本项目不成立重点)**，这里只记口播版四条：

1. **MCP 插件没有 Cookie 上下文。** 它是 LLM 驱动的非交互客户端，不会跳登录页、不存 Cookie、过期了也没人重新登录——Session 在这里**根本无法工作**，不是"别扭"而是"不可用"
2. **技能树编辑器是独立 SPA 且要带角色。** 三种打开方式（新窗口 / iframe / 直接输地址），Session 跨上下文体验差；更重要的是**角色信息要随凭证走**——JWT 载荷带 `role`，后端验签即得，Session 要查库
3. **Swagger 的 Authorize 按钮。** FastAPI 的 `OAuth2PasswordBearer` 会在 `/docs` 生成登录入口，面试可以现场演示；Session 方案下 Swagger 无法承载登录态
4. **单进程环境里无状态更省事。** Session 要么存内存（重启丢）、要么建表；JWT 两者都不用

如果追问"那 JWT 无法主动失效怎么办"，答：Access 只给 2 小时，Refresh 落表可撤销，改密码时递增 `token_version` 让旧 token 全部失效。**这就把缺点补上了。**

> 一句话总结：**Session 的适用边界是"纯浏览器 + 纯同源 + 无机器客户端"，本项目三条都不满足。**

### 为什么角色必须跟凭证绑定（呼应 1.3 的越权问题）

技能树编辑器只对 admin 开放，这个判断必须在**后端每个写端点**执行。JWT 载荷里带 `role` 带来的直接好处：

- 后端校验角色时 **0 次数据库查询**（验签后直接读 payload）
- 前端拿到 token 即可知道自己是不是 admin，**不需要额外请求**，也不需要信任 URL 参数
- 角色变更（管理员降级）通过 `token_version` 或重新签发立即生效

### 为什么不上 OAuth / SSO / Passkey

- **OAuth**：依赖外网与第三方审核，局域网离线部署直接废掉；个人项目维护 client_secret 是净负担
- **SSO**：给 1~5 人的项目上 Keycloak 是典型的过度设计
- **Passkey**：技术最好但实现复杂、多端配置繁琐，本期不做，作为二期展望

> 面试话术：**"我评估过 OAuth 和 SSO，最后没用。不是不会，是它们解决的是多系统和企业级身份治理的问题，我这个场景是单容器五人以内，引入它们是负收益。知道自己不该用什么，和知道该用什么同样重要。"**

### 6.1 数据层改动

```sql
-- users 表新增（幂等 ALTER）
ALTER TABLE users ADD COLUMN password_hash TEXT;      -- bcrypt 哈希（自带盐）
ALTER TABLE users ADD COLUMN token_version INTEGER NOT NULL DEFAULT 1;  -- 改密码/踢下线时 +1
ALTER TABLE users ADD COLUMN last_login TEXT;

-- 刷新令牌（可撤销，支持多端登出）
CREATE TABLE IF NOT EXISTS refresh_tokens (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    token_hash TEXT NOT NULL,          -- 存哈希，不存明文
    user_agent TEXT DEFAULT '',
    expires_at TEXT NOT NULL,
    revoked INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- MCP / 脚本用的 API Key
CREATE TABLE IF NOT EXISTS api_keys (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    name TEXT NOT NULL,                -- 如 "Claude Desktop"
    key_hash TEXT NOT NULL,            -- 存哈希
    last_used_at TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    revoked INTEGER NOT NULL DEFAULT 0
);
```

### 6.2 依赖

```
passlib[bcrypt]      # 密码哈希（纯Python后端，无需系统库）
PyJWT                # 或 python-jose[cryptography]
```

`pixi.toml` 加依赖 → `pixi update` → `pixi run export-reqs`（**遵守项目依赖管理约定：pixi 是唯一事实源**）

### 6.3 核心流程

| 流程 | 端点 | 说明 |
|---|---|---|
| 登录 | `POST /api/auth/login` | 用户名+密码 → bcrypt 校验 → 返回 `access_token`(2h) + 下发 `refresh_token`(30d, httpOnly) |
| 注册/初始化 | `POST /api/auth/register` | 首次部署时创建账号；可由 `SELF_GROW_ALLOW_REGISTER` 控制是否开放 |
| 刷新 | `POST /api/auth/refresh` | 读 httpOnly cookie 里的 refresh → 换新 access；Refresh Rotation（用掉即换新的） |
| 登出 | `POST /api/auth/logout` | 撤销当前 refresh（单端登出）；`/logout-all` 撤销全部（改密码时自动调用） |
| 改密码 | `POST /api/auth/password` | 校验旧密码 → 写新哈希 → `token_version += 1` → 撤销全部 refresh |
| 当前用户 | `GET /api/auth/me` | 替代现在前端从 localStorage 读用户信息的做法 |

### 6.4 依赖项改造（关键一行）

```python
# routers/deps.py
async def get_current_user(
    request: Request,
    credentials: HTTPAuthorizationCredentials = Security(oauth2_scheme),  # Bearer
```

**Token 存哪里**（面试会问）：
- Access Token → 内存变量 + localStorage 副本（刷新页面不丢）
- Refresh Token → **httpOnly + SameSite=Lax Cookie**（JS 拿不到 = XSS 偷不走）
- 同源部署下这个组合兼顾了体验与安全；如果未来前后端分离跨域，Refresh 也要走 Bearer 并接受 XSS 风险

### 6.7 安全细节清单

- [ ] bcrypt cost factor ≥ 12
- [ ] JWT 密钥从环境变量读，缺失时启动失败（不硬编码、不默认）
- [ ] 登录失败返回统一文案（"用户名或密码错误"），不泄露用户是否存在
- [ ] 同一 IP / 用户名失败 5 次锁定 10 分钟（内存计数器即可）
- [ ] Access 2h / Refresh 30d / Refresh Rotation / 复用检测
- [ ] 密码最小长度 8 位
- [ ] CORS 从 `*` 收紧为显式来源列表
- [ ] 关键操作（改密码、删除数据）要求重新输入密码
- [ ] 日志不打印 token、不打印完整 Authorization 头

### 6.9 角色权限设计（RBAC）— 编辑器仅管理员，普通用户无入口

> **✅ 已实施（2026-09-11）**：三道防线中的 ②③ 已落地（后端 `require_admin` + 编辑器页面启动自检），
> ① 入口按钮原本就只对 admin 渲染，本次改为以服务端 `AppData.user.role` 为准。
> 剩余未做：JWT 真实登录（`get_current_user` 目前仍是 URL 参数），见第一节现状。

> **需求（已确认）**：
> - **管理员（admin）**：可以进入技能树编辑器界面，进行创建/编辑/上线/删除/AI 编辑
> - **普通用户（user）**：**根本没有进入编辑器的入口**——不显示任何入口按钮；即使手动输入编辑器地址也会被拦截，只能查看已发布的技能树并学习
>
> 现状（见 1.3）：role 来自 URL 参数且默认 admin，后端零校验。本节给出落地方案。

#### 权限矩阵

| 能力 | user（普通） | admin（管理员） | 说明 |
|---|---|---|---|
| 查看已发布技能树（viewer / iframe） | ✅ | ✅ | `GET /api/skill-trees/{id}/published` |
| 学习进度打卡（开始学习 / 标记完成） | ✅ | ✅ | `PUT /api/skill-trees/{id}/learner` |
| 查看自己的技能树列表 / 技能库 | ✅ | ✅ | `GET /api/skill-trees` |
| **看到"编辑技能"入口按钮** | ❌ **不渲染** | ✅ | 技能页按钮、侧边栏入口一律不生成 |
| **进入编辑器页面 `skill-tree/index.html`** | ❌ **入口不存在；直接输地址也被拦截** | ✅ | 三道防线，见下 |
| **创建技能树** | ❌ | ✅ | `POST /api/skill-trees` |
| **保存草稿（增删改节点）** | ❌ | ✅ | `PUT /api/skill-trees/{id}` |
| **上线 / 更新上线版本** | ❌ | ✅ | `PUT /api/skill-trees/{id}/publish` |
| **删除技能树** | ❌ | ✅ | `DELETE /api/skill-trees/{id}` |
| **技能树 AI 编辑（chat / resume）** | ❌ | ✅ | `POST /api/skill-trees/{id}/chat` |

> 读（查看与学习）对所有人开放——技能库的意义就是给别人学；**"进入编辑器"这个动作本身是 admin 专属**，不只是写接口。

#### 关键认知：「不显示入口」≠「进不去」

静态文件服务的天然特性决定了：**只要文件在 `frontend/` 目录下被 serve，任何人敲对 URL 就能打开它**。

```
http://localhost:3001/frontend/skill-tree/index.html   ← 普通用户手敲这个地址
```

所以"隐藏入口"只是第一道防线，必须配齐三道：

| 防线 | 位置 | 作用 | 能否被绕过 |
|---|---|---|---|
| ① 入口不渲染 | `frontend/js/pages/skills.js` | 普通用户看不到"编辑技能"按钮，也不知道有这个页面 | ✅ 能（手敲 URL） |
| ② 页面启动自检 | `frontend/skill-tree/index.html` | 打开编辑器时先查身份与角色，非 admin 立即跳转/提示 | ⚠️ 能（禁用 JS、或直接调 API） |
| ③ **后端强制校验** | `routers/deps.py` 的 `require_admin` | 所有写接口非 admin 一律 403 | ❌ **不能，这是真正的边界** |

> 面试话术：**"入口隐藏是 UX，页面自检是兜底，后端校验才是安全边界。三层都要有，但只有第三层是真的锁。"**

#### 后端实现（关键：新增一个依赖函数）

```python
# routers/deps.py
async def require_admin(user=Depends(get_current_user)) -> dict:
    """管理员校验：所有技能树写操作都必须挂这个依赖"""
    if (user.get("role") or "user") != "admin":
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return user
```

逐一端点挂载，不改业务逻辑：

| 路由 | 改动 |
|---|---|
| `routers/skill_tree.py` | create / update / delete / publish 四个端点加 `Depends(require_admin)` |
| `routers/skill_tree_ai.py` | chat / chat/resume 加 `Depends(require_admin)`（**AI 能改树，必须当写操作管**） |
| `routers/users.py` | 保留 `GET /api/users` 给登录页列用户（登录前必须可调），但只返回 id/name/role |

**为什么是 403 而不是 401**：已登录但没权限 = 403（Forbidden）；没登录 = 401（Unauthorized）。两者混用会让前端无法区分"去登录"和"提示无权限"。

#### 前端实现（四处都要改，缺一不可）

| 位置 | 改动 |
|---|---|
| `frontend/js/pages/skills.js:424` | **入口只给 admin 渲染**：`isAdmin()` 为假时，不生成"✏️ 编辑技能"按钮，也不保留任何跳转到编辑器的链接/菜单项。普通用户**在界面上完全不知道编辑器存在** |
| `frontend/skill-tree/index.html:46` | **删掉 URL 取 role 的逻辑**（`|| 'admin'` 这个默认值必须消失）。改为启动时调 `/api/auth/me` 拿真实 role |
| `frontend/js/utils.js` | 新增 `isAdmin()`：从 token payload 解析 role（**只用于 UI 显示**，不做安全判断） |
| 主应用侧边栏 / 技能库弹窗 | 检查是否还有别的编辑器入口（如右键菜单、快捷键），一并加 `isAdmin()` 判断 |

改造后的编辑器启动流程（页面自检）：

```
打开 skill-tree/index.html
  → 读 localStorage token；无 → 跳 login.html
  → 调 /api/auth/me
      → 401          → 跳登录页
      → role != admin → 不留任何编辑 UI：
                          · 隐藏 #toolbar / #sidebar / #ai-panel（编辑器的全部操作区）
                          · 显示"⚠️ 仅管理员可进入编辑器"提示
                          · 提供「返回技能库」按钮（跳回主应用）
                          · 不初始化 App（不加载任何树数据）
      → role == admin → 正常初始化（SKILL_TREE_ROLE = 'admin'）
```

> 注意"**不初始化 App**"这一条：不能只是隐藏按钮就完事。因为 `App` 类一旦构造，就会去拉草稿数据、绑定事件——普通用户虽然看不见，但页面里已经加载了本不该让他们看到的草稿内容（未发布的树结构）。**要拦就拦在初始化之前。**

#### 会话归属：thread_id 必须编入 user_id

技能树 AI 的会话目前是 `stc_{uuid16}`，与用户无关。改造后必须带上用户与角色：

```python
thread_id = thread_id or f"stc_{user_id}_{uuid.uuid4().hex[:12]}"
```

并在 `run_skill_tree_chat` 入口校验 `thread_id` 前缀与当前 user_id 一致，不匹配直接 403——**否则 A 用户拿到 B 的 thread_id 就能续接对方会话**。

- [ ] 用 user 的 token 调 `PUT /api/skill-trees/{id}` → 期望 **403**（现在是 200）
- [ ] 用 user 的 token 调 `POST /api/skill-trees/{id}/chat` → 期望 **403**

- [ ] 以 user 身份打开编辑器时抓包 → 期望**没有请求草稿数据**（`GET /api/skill-trees/{id}` 未被调用）

### S4 的三个关键决策

1. **fetch 包装而非改 52 处调用**（`frontend/js/auth.js`）
   在 `window.fetch` 上包一层：自动给本站 API 请求加 `Authorization`，401 时用 refresh 换一对新 token 并重放原请求，失败才跳登录。**52 处 `fetch(...?user_id=)` 一行未改**，且将来迁移 Vue 可原样保留。
   注意：不拦截 `/api/auth/login` 与 `/api/auth/refresh`（否则递归）；并发 401 只发一次 refresh（Promise 去重）。

2. **refresh 双通道**（Cookie + 响应体）
   `SameSite=Lax` 的 httpOnly Cookie 在**跨域开发态**（前端 5173 / 后端 3001）不会随 XHR 发送。因此登录响应**同时**在 body 返回 `refresh_token`，`/api/auth/refresh` 取值顺序为「Cookie → body」。同源生产部署下 Cookie 生效（防 XSS 窃取），跨域开发时 body 通道兜底。

3. **CORS 从 `*` 收紧**
   原来 `allow_origins=["*"]` 会让浏览器拒绝一切携带凭证的响应。改为显式来源（环境变量 `SELF_GROW_CORS_ORIGINS` 可覆盖，填 `*` 则自动关闭 credentials）+ `allow_credentials=True`。

## 八、面试怎么讲这个设计

### 四个必答点

1. **"为什么这么做"**：原实现只校验 user_id 存在，等同于无鉴权；我做了密码哈希 + JWT 双令牌 + 可撤销 Refresh + API Key 四层，覆盖浏览器/机器/本地三种客户端
2. **"为什么不用 Session"**（口播 20 秒版）：
   > "Session 的全部能力建立在'客户端是浏览器'这个假设上，我这个项目有三处不满足：第一，MCP 插件是 LLM 驱动的非交互客户端，没有 Cookie 上下文，也不会跳登录页，Session 在它身上不是别扭而是根本用不了；第二，技能树编辑器是独立 SPA，有新窗口、iframe、直接输地址三种打开方式，而且我要在凭证里带角色信息——JWT 载荷带 role，后端验签即得，Session 得查库；第三，Swagger 的 Authorize 按钮能让我现场演示受保护接口，Session 方案下 Swagger 承载不了登录态。"
3. **"JWT 无法主动失效怎么办"**：短 Access（2h）+ Refresh 落表可撤销 + `token_version` 全局失效三重兜底
4. **"你怎么防止普通用户进编辑器改技能树"**：三道防线——普通用户在界面上**根本看不到入口**（按钮不渲染）；就算手敲编辑器地址，页面启动先查 `/api/auth/me`，非 admin 直接显示无权限且**不初始化 App**（连草稿数据都不请求）；退一万步绕过前端调接口，后端 `require_admin` 一律 403。**入口隐藏是 UX，页面自检是兜底，后端校验才是真的锁。**

### 三个加分点

- **"改造只动了一个依赖函数"**：当初把 `get_current_user` 抽到 `deps.py`，这次全局鉴权升级只改这一个文件，所有端点自动生效——**这是提前做抽象得到的回报**
- **"我修了一个垂直越权"**：原来编辑器 role 从 URL 读、默认 admin、后端零校验，普通用户改个参数就能获得管理员能力。**能主动讲出"越权"这个词，说明你知道安全不只是登录**
- **"我保留了 TRUSTED_MODE 开关"**：知道什么时候该放松安全（本地开发、演示），并显式告警，而不是一刀切

### 一个主动认的不足

> "Refresh Token 的复用检测我是在单进程内存里做的，如果将来多实例部署会失效；另外角色目前只有 admin/user 两级，没有做更细粒度的资源级授权（比如 A 用户只能改自己创建的技能树，现在是所有 admin 能改所有树）。这两个是我的下一步。"

## 九、常见坑清单

| 坑 | 说明 |
|---|---|
| bcrypt 72 字节截断 | bcrypt 只取密码前 72 字节，超长密码要前置 SHA-256 |
| JWT 库算法混淆 | 必须显式指定 `algorithms=["HS256"]`，否则存在 `alg: none` 漏洞 |
| localStorage 与 httpOnly 混用混乱 | 明确：Access 给 JS 用，Refresh 只给浏览器自动带，别都塞 localStorage |
| 401 与 403 混用 | 未认证用 401，已认证但无权限用 403（前端靠这个区分"去登录"和"提示无权限"） |
| **role 仍从 URL 读** | 必须删掉 `skill-tree/index.html:46` 的 URL 取 role 逻辑，改为 `/api/auth/me` 拿真实 role；否则前面所有后端校验都被前端这个默认值绕过 |
| **把权限做在前端** | 隐藏"编辑技能"按钮只是 UX（用户还能手敲 URL）。安全边界必须在后端（`require_admin`），前端判断只能用于显示 |
| **只隐藏 UI 却仍初始化 App** | 编辑器页面若不拦住 `new App()`，普通用户虽然看不见按钮，但草稿数据已经被请求并暴露在页面里。要在初始化之前拦截 |
| **入口藏了但页面还在** | `frontend/skill-tree/index.html` 是静态文件，只要被 serve 就能直接访问。入口隐藏 ≠ 进不去，必须配页面自检 + 后端校验 |
| **技能树 AI 会话串号** | thread_id 必须编成 `stc_{user_id}_{uuid}`，且 resume 时校验前缀与当前用户一致，否则拿到别人的 thread_id 就能续接会话 |
| **AI 编辑接口漏挂权限** | `/api/skill-trees/{id}/chat` 能改树，必须和写操作一样挂 `require_admin`，容易漏 |
| 忘记同步 thread_id（协调 Agent） | 主/子图 `thread_id` 也要编入 `user_id`，否则多用户会话串号 |
| 技能树编辑器的 key 不一致 | `currentUser` vs `sg_user`，改造时统一 |
| 改密码后旧 token 仍有效 | 靠 `token_version` 解决，别忘了撤销 refresh_tokens |
| MCP stdio 模式强行上 Key | 本地 spawn 的进程本来就可信，加 Key 只会让配置变麻烦 |
| 登录页用户列表接口被锁死 | `GET /api/users` 必须在未登录时可访问（登录页要用），别一刀切把所有端点都挂上鉴权 |
