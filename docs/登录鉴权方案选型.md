# 登录鉴权方案选型

> 编写日期：2026-09-09
> 目标：为 Self-Grow 设计一套"够安全、能讲清楚、能演示"的登录鉴权方案
> 现状代码依据：`routers/deps.py`、`routers/users.py`、`login.html`、`db/init.py`

---

## 一、现状：现在根本没有鉴权

先看清起点，再谈选型。

### 1.1 当前实现（代码事实）

```python
# backend/routers/deps.py
async def get_current_user(user_id: int = Query(..., description="用户 ID")):
    user = get_user(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
```

- 登录 = 在 `login.html` 点一张用户卡片 → 前端把 `user` 存进 `localStorage['sg_user']`
- 之后所有请求带 `?user_id=N`，后端只校验"这个 id 存在吗"
- `users` 表**没有 password 字段**（只有 id/name/role/level/exp/total_exp/streak/joined）
- CORS 配置 `allow_origins=["*"]`
- `login.html` 第 34 行原文写着：`💡 后续版本将支持用户名密码登录`

**结论：任何人改一下 URL 参数就能看到别人的全部数据。** 这是本项目最严重的缺陷，面经 Q7 已经准备"主动认错"——本文的目标就是把它从"缺陷"变成"我做过的加固"。

### 1.2 顺带发现的一个 Bug（改造时必须一起修）

| 位置 | 存的 key |
|---|---|
| `login.html:95` 写入 | `localStorage['sg_user']` |
| `frontend/js/utils.js:316` 读取 | `localStorage['sg_user']` ✅ |
| `frontend/skill-tree/js/utils.js:90` 读取 | `localStorage['currentUser']` ❌ **读不到** |

**技能树编辑器永远拿不到 user_id**，目前靠 `getCurrentUserId() || 1` 兜底成用户 1。做鉴权改造时必须统一为一个 key，否则技能树 AI 的会话归属会一直是错的。

## 二、先定标尺：本项目的约束是什么

脱离约束谈方案都是耍流氓。给 Self-Grow 画个像：

| 维度 | 现状 | 对鉴权的影响 |
|---|---|---|
| 部署形态 | Docker 单容器，FastAPI 同源提供前端静态资源 | **前后端同源**，Cookie 方案可行 |
| 访问场景 | 本机 + 手机/平板局域网访问 | 需支持跨域或同域多端 |
| 用户规模 | 1~5 人（自己 + 家人/室友） | 不需要企业级 IAM |
| 前端形态 | 原生 JS SPA + 独立的 skill-tree SPA（两个入口） | 需要**统一的取 token 方式** |
| MCP 插件 | stdio（本地）+ streamable-http（远程） | **非交互场景需要 API Key** |
| 数据敏感度 | 个人成长数据（习惯、财务、目标） | 中等，不需要金融级 |
| 面试诉求 | 需要"能讲的设计 + 能现场演示" | 方案要**有可讲的取舍**，不是越复杂越好 |
| 运维能力 | 单实例 MySQL，无人值守 | 不能引入 Redis、不能依赖外部 IdP |

**一句话约束**：单进程、同源、小规模、要有 API Key 能力、要能讲清楚。

## 三、常见登录方式全景（9 种，逐个评）

评价维度用 ★（5 星满）表示"对本项目的适配度"。

### A. URL 参数 user_id（**当前方案**）

**原理**：请求带 `?user_id=1`，后端查库确认存在。

| | |
|---|---|
| 优点 | 零成本；本地开发调试方便；Swagger 里直接填参数就能测 |
| 缺点 | **等于没有鉴权**；参数可枚举、可篡改；URL 会留在浏览器历史和日志里 |
| 适配度 | ★☆☆☆☆ |

> 唯一价值：作为**开发态降级开关**保留（用环境变量控制），生产必须关掉。

---

### B. Session-Cookie（有状态）

**原理**：登录成功后服务端生成 `session_id` 存内存/表，通过 `Set-Cookie` 下发（httpOnly + SameSite），后续请求自动携带。

| | |
|---|---|
| 优点 | **最省心**：浏览器自动带凭证，前端几乎零改造；httpOnly 天然防 XSS 窃取；服务端可随时踢人（删 session 即刻失效）；实现简单，不需要 JWT 库 |
| 缺点 | 服务端要存状态（本项目单进程内存即可，但重启丢失，需落表）；跨域/跨端要处理 `SameSite=None + Secure + HTTPS`；**非浏览器客户端（MCP、脚本）用起来别扭**；水平扩展要共享 session 存储 |
| 适配度 | ★★★★☆ |

> 如果 Self-Grow 永远是"浏览器 + 同源 + 单机"，Session 其实是最优解，简单且安全。真正卡住它的是 **MCP 插件和独立 skill-tree SPA** 这两类非典型客户端。

---

### C. JWT（Access + Refresh，无状态）⭐ **推荐**

**原理**：登录验证密码 → 签发短期 Access Token（2 小时）+ 长期 Refresh Token（30 天）；Access 放请求头 `Authorization: Bearer`，过期后拿 Refresh 换新的。

|     |                                                                                                                                                                       |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 优点  | 服务端无状态（不存 session，重启不丢）；**天然支持多端**：浏览器、MCP、移动端、curl、Swagger 一视同仁；FastAPI 自带 `OAuth2PasswordBearer`，Swagger 右上角直接出现「Authorize」按钮，**面试可现场演示**；载荷可带 role/version，便于后续做权限 |
| 缺点  | 无法主动失效（需黑名单或短有效期兜底）；token 存 localStorage 有 XSS 风险（存 httpOnly Cookie 又有 CSRF 考量）；实现比 Session 略复杂（要写刷新逻辑、401 重试）                                                        |
| 适配度 | ★★★★★                                                                                                                                                                 |

**为什么它比 Session 更适合本项目**：
1. MCP 插件（HTTP 模式）和未来的移动端都是"非浏览器客户端"，Bearer 是它们的通用语言
2. Swagger 的 Authorize 按钮 = 面试现场演示的利器（Session 做不到）
3. 单实例 MySQL 环境里，"无状态"恰好避开了"session 存哪"的问题

---

### D. OAuth2 / 第三方登录（GitHub、微信、Google）

**原理**：接入授权服务器，用户跳转授权 → 回调拿 code → 换 token → 拿用户信息。

| | |
|---|---|
| 优点 | 不用自己存密码（最安全的一环）；用户体验好（一键登录）；面试官认这个名词 |
| 缺点 | **强依赖外部服务**（墙、额度、应用审核）；微信登录要企业资质；个人项目还要维护 client_secret；回调地址 + HTTPS 是硬门槛；**局域网/离线部署直接废掉** |
| 适配度 | ★★☆☆☆ |

> 典型的"为了显得高级而引入复杂度"。**个人自用系统 + 局域网部署，第三方登录是净负担。** 真想加，GitHub OAuth 是唯一现实选项（免费、无资质要求），可以作为"二期可选"。

---

### E. SSO / OIDC / CAS

**原理**：企业级单点登录，独立身份提供商（Keycloak、Authing 等）。

| | |
|---|---|
| 优点 | 多系统统一身份；企业级功能（MFA、审计、组织架构）齐全 |
| 缺点 | **完全过度设计**。要给 1~5 人的个人项目部署 Keycloak？运维成本和收益严重倒挂 |
| 适配度 | ★☆☆☆☆ |

> 面试时可以说"我知道它的位置，但这个项目不配用 SSO"——这句话本身是加分的。

---

### F. 邮箱 / 短信验证码（无密码）

**原理**：输入邮箱 → 收验证码 → 校验通过即登录。

| | |
|---|---|
| 优点 | 用户不用记密码；没有密码泄露风险；体验现代 |
| 缺点 | 依赖邮件/短信服务（要钱、要配置、可能失败）；个人项目自己一个人用，收发验证码比输密码还烦；短信要实名备案 |
| 适配度 | ★★☆☆☆ |

---

### G. Passkey / WebAuthn（无密码，生物识别）

**原理**：基于公私钥对，用指纹/面容/硬件密钥登录，私钥不出设备。

| | |
|---|---|
| 优点 | 目前最安全的方案；抗钓鱼；体验极佳（指纹一按） |
| 缺点 | 实现复杂度高（挑战-响应、凭证存储、跨设备同步）；浏览器兼容要处理；**多端（手机访问局域网服务）配置繁琐** |
| 适配度 | ★★☆☆☆（技术前瞻性 ★★★★★） |

> 适合作为"未来展望"在面试里提一句，体现技术视野，但别现在做。

---

### H. API Key / 静态令牌（面向机器）

**原理**：为每个客户端签发一个长期随机字符串，放在请求头。

| | |
|---|---|
| 优点 | 非交互客户端的**唯一现实选择**（MCP、定时任务、脚本、CI）；实现最简单（查表比对） |
| 缺点 | 泄露即失守（需支持轮换、撤销、作用域）；不适合作为人类的主登录方式 |
| 适配度 | ★★★★☆（**作为 JWT 的补充，而非替代**） |

> MCP 插件目前用 `SELF_GROW_USER_ID` 环境变量（默认 1）。改造后 HTTP 模式应改用 API Key，stdio 模式保留环境变量（本地进程本来就是可信的）。

---

### I. HTTP Basic

**原理**：`Authorization: Basic base64(user:pass)`，每次请求都带密码。

| | |
|---|---|
| 优点 | 极简；curl 友好 |
| 缺点 | 每次都传密码（base64 不是加密）；浏览器会弹原生弹窗（丑且无法登出）；无过期机制 |
| 适配度 | ★★☆☆☆ |

> 只适合内网小工具的临时方案，不适合有前端的系统。

---

### 补充形态 J. 本地免密模式（Trusted Mode）

**原理**：环境变量 `SELF_GROW_TRUSTED_MODE=1` 时，跳过鉴权，固定为指定用户。

| | |
|---|---|
| 优点 | 本地开发/演示零摩擦；Docker 一键体验时不用先注册；**面试演示时不会因为忘密码翻车** |
| 缺点 | 开了就是裸奔，必须显式开启且日志告警 |
| 适配度 | ★★★★☆（**作为开关存在，不作为方案**） |

## 五、选型结论

# ✅ 推荐：用户名密码 + JWT（Access + Refresh） + 本地免密开关 + MCP 独立 API Key

```
┌─────────────────────────────────────────────────┐
│  浏览器用户  → 用户名+密码 → JWT (Access+Refresh) │
│  MCP/脚本    → API Key（HTTP 模式）              │
│              或 SELF_GROW_USER_ID（stdio 本地）  │
│  本地开发/演示 → TRUSTED_MODE 开关跳过鉴权        │
└─────────────────────────────────────────────────┘
```

**四层各有分工，不互相替代。**

### 为什么选 JWT 而不是 Session（这是最容易被追问的一题）

Session 在本项目里其实够用，选 JWT 的决定性理由只有三条，都要能讲出来：

1. **客户端形态不只有浏览器。** MCP 插件（HTTP 模式）、未来的移动端、curl 调试都是 Bearer 友好、Cookie 别扭的场景
2. **Swagger 的 Authorize 按钮。** FastAPI 的 `OAuth2PasswordBearer` 会自动在 `/docs` 生成登录入口，面试可以现场演示"登录后才能调接口"——**这是可展示性上的额外收益**
3. **单进程环境里无状态更省事。** Session 要么存内存（重启丢）、要么建表；JWT 两者都不用

如果追问"那 JWT 无法主动失效怎么办"，答：Access 只给 2 小时，Refresh 落表可撤销，改密码时递增 `token_version` 让旧 token 全部失效。**这就把缺点补上了。**

### 为什么不上 OAuth / SSO / Passkey

- **OAuth**：依赖外网与第三方审核，局域网离线部署直接废掉；个人项目维护 client_secret 是净负担
- **SSO**：给 1~5 人的项目上 Keycloak 是典型的过度设计
- **Passkey**：技术最好但实现复杂、多端配置繁琐，本期不做，作为二期展望

> 面试话术：**"我评估过 OAuth 和 SSO，最后没用。不是不会，是它们解决的是多系统和企业级身份治理的问题，我这个场景是单容器五人以内，引入它们是负收益。知道自己不该用什么，和知道该用什么同样重要。"**

## 六、落地设计

### 6.1 数据层改动

```sql
-- users 表新增（幂等 ALTER）
ALTER TABLE users ADD COLUMN password_hash TEXT;      -- bcrypt 哈希（自带盐）
ALTER TABLE users ADD COLUMN token_version INTEGER NOT NULL DEFAULT 1;  -- 改密码/踢下线时 +1
ALTER TABLE users ADD COLUMN last_login TEXT;

-- 刷新令牌（可撤销，支持多端登出）
CREATE TABLE IF NOT EXISTS refresh_tokens (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    token_hash TEXT NOT NULL,          -- 存哈希，不存明文
    user_agent TEXT DEFAULT '',
    expires_at TEXT NOT NULL,
    revoked INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- MCP / 脚本用的 API Key
CREATE TABLE IF NOT EXISTS api_keys (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    name TEXT NOT NULL,                -- 如 "Claude Desktop"
    key_hash TEXT NOT NULL,            -- 存哈希
    last_used_at TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    revoked INTEGER NOT NULL DEFAULT 0
);
```

### 6.2 依赖

```
passlib[bcrypt]      # 密码哈希（纯Python后端，无需系统库）
PyJWT                # 或 python-jose[cryptography]
```

`pixi.toml` 加依赖 → `pixi update` → `pixi run export-reqs`（**遵守项目依赖管理约定：pixi 是唯一事实源**）

### 6.3 核心流程

| 流程 | 端点 | 说明 |
|---|---|---|
| 登录 | `POST /api/auth/login` | 用户名+密码 → bcrypt 校验 → 返回 `access_token`(2h) + 下发 `refresh_token`(30d, httpOnly) |
| 注册/初始化 | `POST /api/auth/register` | 首次部署时创建账号；可由 `SELF_GROW_ALLOW_REGISTER` 控制是否开放 |
| 刷新 | `POST /api/auth/refresh` | 读 httpOnly cookie 里的 refresh → 换新 access；Refresh Rotation（用掉即换新的） |
| 登出 | `POST /api/auth/logout` | 撤销当前 refresh（单端登出）；`/logout-all` 撤销全部（改密码时自动调用） |
| 改密码 | `POST /api/auth/password` | 校验旧密码 → 写新哈希 → `token_version += 1` → 撤销全部 refresh |
| 当前用户 | `GET /api/auth/me` | 替代现在前端从 localStorage 读用户信息的做法 |

### 6.4 依赖项改造（关键一行）

```python
# routers/deps.py
async def get_current_user(
    request: Request,
    credentials: HTTPAuthorizationCredentials = Security(oauth2_scheme),  # Bearer
) -> dict:
    # 1. TRUSTED_MODE → 直接返回默认用户（开发/演示）
    # 2. Bearer token → 验签 + 检查 token_version + exp
    # 3. X-API-Key 头 → 查 api_keys 表（MCP / 脚本）
    # 4. 都失败 → 401（而不是现在的 404）
    ...
```

**所有现有端点无需改动**——它们本来就 `Depends(get_current_user)`，改这一个依赖函数即可全局生效。这是当初抽 `deps.py` 的回报，改造时可以专门讲这一点。

### 6.5 前端改造

| 文件 | 改动 |
|---|---|
| `login.html` | 用户卡片 → 用户名+密码表单（保留卡片做快速切换**仅在 TRUSTED_MODE**） |
| `frontend/js/utils.js` | 统一 `apiFetch()`：自动带 `Authorization`；遇 401 自动用 refresh 重试一次，仍失败跳登录页 |
| `frontend/js/app.js` | 启动时用 `/api/auth/me` 拿用户信息，不再信 localStorage 里的完整用户对象 |
| `frontend/skill-tree/js/utils.js` | **修复 key 不一致**（`currentUser` → `sg_user`），并从 token 解析 user_id |
| `frontend/js/chat.js` | `AppData?.user?.id \|\| 1` 这种兜底全部去掉，401 直接跳登录 |

**Token 存哪里**（面试会问）：
- Access Token → 内存变量 + localStorage 副本（刷新页面不丢）
- Refresh Token → **httpOnly + SameSite=Lax Cookie**（JS 拿不到 = XSS 偷不走）
- 同源部署下这个组合兼顾了体验与安全；如果未来前后端分离跨域，Refresh 也要走 Bearer 并接受 XSS 风险

### 6.6 MCP 插件

| 模式 | 方案 |
|---|---|
| stdio（本地，Claude Desktop spawn） | 保留 `SELF_GROW_USER_ID`——本地进程本身可信，无需网络凭证 |
| streamable-http（远程） | 请求头 `X-API-Key`，查 `api_keys` 表；支持在用户中心生成/撤销/查看最后使用时间 |

### 6.7 安全细节清单

- [ ] bcrypt cost factor ≥ 12
- [ ] JWT 密钥从环境变量读，缺失时启动失败（不硬编码、不默认）
- [ ] 登录失败返回统一文案（"用户名或密码错误"），不泄露用户是否存在
- [ ] 同一 IP / 用户名失败 5 次锁定 10 分钟（内存计数器即可）
- [ ] Access 2h / Refresh 30d / Refresh Rotation / 复用检测
- [ ] 密码最小长度 8 位
- [ ] CORS 从 `*` 收紧为显式来源列表
- [ ] 关键操作（改密码、删除数据）要求重新输入密码
- [ ] 日志不打印 token、不打印完整 Authorization 头

### 6.8 兼容与迁移

## 八、面试怎么讲这个设计

### 三个必答点

1. **"为什么这么做"**：原实现只校验 user_id 存在，等同于无鉴权；我做了密码哈希 + JWT 双令牌 + 可撤销 Refresh + API Key 四层，覆盖浏览器/机器/本地三种客户端
2. **"为什么不用 Session"**：客户端不只有浏览器（MCP 插件），且 JWT 在单进程环境下不需要解决 session 存储问题；FastAPI 的 OAuth2PasswordBearer 还顺带给了 Swagger 演示能力
3. **"JWT 无法主动失效怎么办"**：短 Access（2h）+ Refresh 落表可撤销 + `token_version` 全局失效三重兜底

### 两个加分点

- **"改造只动了一个依赖函数"**：当初把 `get_current_user` 抽到 `deps.py`，这次全局鉴权升级只改这一个文件，所有端点自动生效——**这是提前做抽象得到的回报**
- **"我保留了 TRUSTED_MODE 开关"**：知道什么时候该放松安全（本地开发、演示），并显式告警，而不是一刀切

### 一个主动认的不足

> "Refresh Token 的复用检测我是在单进程内存里做的，如果将来多实例部署会失效；另外我还没做 MFA。这两个是我的下一步。"

## 九、常见坑清单

| 坑 | 说明 |
|---|---|
| bcrypt 72 字节截断 | bcrypt 只取密码前 72 字节，超长密码要前置 SHA-256 |
| JWT 库算法混淆 | 必须显式指定 `algorithms=["HS256"]`，否则存在 `alg: none` 漏洞 |
| localStorage 与 httpOnly 混用混乱 | 明确：Access 给 JS 用，Refresh 只给浏览器自动带，别都塞 localStorage |
| 401 与 403 混用 | 未认证用 401，已认证但无权限用 403 |
| 忘记同步 thread_id | 协调 Agent 的会话 `thread_id` 必须编入 `user_id`，否则多用户会话串号 |
| 技能树编辑器的 key 不一致 | `currentUser` vs `sg_user`，改造时统一 |
| 改密码后旧 token 仍有效 | 靠 `token_version` 解决，别忘了撤销 refresh_tokens |
| MCP stdio 模式强行上 Key | 本地 spawn 的进程本来就可信，加 Key 只会让配置变麻烦 |
