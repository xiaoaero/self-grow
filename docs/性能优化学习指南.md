# 第一部分：性能优化基础

## 1.1 为什么要优化？

### 大白话

性能优化就是**让程序更快、更省资源**。具体到 Web 应用，就是：

- 用户点了按钮，**响应快**（不要转圈 3 秒）
- 很多用户同时用，**扛得住**（不会卡死）
- 服务器**省钱**（不用买更高配的机器）

### 什么时候该优化？

有一个经典原则：**先让功能正确，再谈性能**（Premature optimization is the root of all evil —— 过早优化是万恶之源）。

原因很简单：代码写得太"巧妙"往往更难懂、更难改。为了一个可能永远用不上的优化，把代码搞得绕来绕去，得不偿失。

**正确姿势**：

1. 先把功能写对、写清楚
2. **测量**哪里慢（用工具，不是靠猜）
3. 只优化真正慢的、影响体验的地方

**项目结合**：Self Grow 是个人应用（1 个用户、操作间隔 > 1 秒），SQLite 完全够用。文档里讲的很多优化手段，对当前场景是"杀鸡用牛刀"——但它们是你将来做多用户 SaaS 时的必修课。

---

## 1.2 核心指标

| 指标 | 含义 | 通俗解释 |
|------|------|---------|
| **响应时间（Latency）** | 一个请求从发出到收到响应的时间 | 从下单到拿到外卖 |
| **QPS / RPS** | 每秒处理多少请求 | 收银台每秒结多少单 |
| **并发数** | 同时在处理的请求数 | 同时有多少人在排队 |
| **P50 / P95 / P99** | 50% / 95% / 99% 的请求在多少毫秒内完成 | P95=500ms 表示 95% 的人 500ms 内搞定 |
| **吞吐量** | 单位时间处理的数据量 | 跟 QPS 类似 |
| **错误率** | 多少请求失败了 | 100 单里几单出问题 |

**重点看 P95 和错误率，不要只看平均值。** 平均值会骗人——一半请求 10ms、另一半 5 秒，平均 2.5 秒看起来还行，但一半用户已经疯了。

> 更多指标解释和本项目压测方法，见 `docs/压测说明.md`（注意：那里的数字是**估算**，项目没实测过）。

---

## 1.3 优化的分层思路

性能问题可以发生在整条链路的任何一个环节。优化前先搞清楚"瓶颈在哪一层"：

```
浏览器 ──► 网络 ──► Web 服务器 ──► 业务代码 ──► 数据库 ──► (外部 API / AI)
 │            │          │             │            │
 │            │          │             │            └── SQLite / MySQL / Redis
 │            │          │             └── FastAPI / 你的函数
 │            │          └── nginx / uvicorn
 │            └── CDN / HTTP 缓存 / 压缩
 └── 渲染 / JS / 图片
```

**经验法则**：绝大多数项目的瓶颈在**数据库层**（连接池不够、锁冲突、慢查询），其次是**外部 API 调用**（尤其 AI 接口，几百毫秒到几十秒）。你代码本身写得再快，数据库和外部 API 扛不住就全完蛋。

所以优化优先级通常是：**数据库 > 外部调用 > 网络 > 后端逻辑 > 前端**。

这一部分是"先看自己家里有什么"——Self Grow 已经用了一些不错的优化，理解它们能帮你建立"优化是什么样"的直觉。

## 2.1 数据库：WAL 模式 + 锁等待 + 同步级别

**代码位置**：`backend/db/connection.py`

```python
def get_conn():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL")       # 写不阻塞读
    conn.execute("PRAGMA busy_timeout=5000")      # 写锁最多等 5 秒
    conn.execute("PRAGMA synchronous=NORMAL")     # 降低同步开销
    return conn
```

这三行是 SQLite 最经典的性能三件套：

### ① journal_mode=WAL（写不阻塞读）

SQLite 默认模式下，一个连接在**写**的时候，会锁住整个数据库文件，**读**也得等着（读和写互相阻塞）。

WAL（Write-Ahead Log，预写日志）模式改变了这个机制：

- 写操作不再直接改主数据库文件，而是先写到一个独立的 `-wal` 日志文件
- 读操作照常读主文件，**不会被写操作阻塞**
- 后台再找机会把日志合并回主文件

**效果**：读和写可以**并发**进行。对"读多写少"的应用（比如个人成长数据，读报表远多于写记录）提升巨大。

**大白话**：原来像"单人卫生间"——一个人进去（写），其他人（读）都得等。WAL 像"加了排队号"——写的人去侧门排队，读的人照常进主门。

### ② busy_timeout=5000（锁冲突时等待而非报错）

多个写操作同时发生时，SQLite 默认会**立即**抛 `database is locked` 错误。设置了 `busy_timeout` 后，遇到锁会**等待最多 5 秒**，锁释放了就能继续，而不是直接失败。

**效果**：高频写入时，大幅减少"database is locked"报错。

### ③ synchronous=NORMAL（降低同步开销）

SQLite 默认 `synchronous=FULL`：每次写操作都**确保数据已经写进磁盘物理介质**才返回，最安全但最慢。

`NORMAL` 模式：在 WAL 模式下，允许某些情况不强制立即落盘（因为 WAL 日志本身已提供一定的崩溃恢复能力）。性能约提升 2 倍。

> 三者的关系：WAL 是"读写分离"、busy_timeout 是"排队而非砸门"、synchronous 是"少做点保险动作"。详见 `docs/压测说明.md` §2.7。

## 2.2 数据库：索引 + 分页

### 索引

**代码位置**：`backend/db/init.py`，有 5 个索引：

```sql
CREATE INDEX IF NOT EXISTS idx_action_logs_user_date ON action_logs(user_id, date);
CREATE INDEX IF NOT EXISTS idx_tasks_user_status   ON tasks(user_id, status);
CREATE INDEX IF NOT EXISTS idx_tasks_user_source   ON tasks(user_id, source_type);
CREATE INDEX IF NOT EXISTS idx_task_history_user   ON task_history(user_id);
CREATE INDEX IF NOT EXISTS idx_exp_answers_user    ON exp_answers(user_id);
```

索引是什么？见 §3.1.1 的详细解释。这里先记住：**给经常拿来 `WHERE` 查询的字段建索引，查询能快几个数量级**。本项目给 `action_logs.user_id + date`、`tasks.user_id + status` 这些高频查询字段都建了索引。

### 分页

**代码位置**：`db/actions.py` 和 `db/tasks.py` 都用了 `LIMIT / OFFSET / page_size`：

```python
# 只查一页，而不是把全部记录拉出来
SELECT * FROM action_logs WHERE user_id = ? ORDER BY start_time DESC LIMIT ? OFFSET ?
```

分页的意义：如果用户有 1 万条行动记录，一次性全查出来 → 慢 + 内存大。分页只查当前页（比如 50 条），又快又省。**"只取需要的数据"是最简单也最有效的优化**。

## 2.3 前端：页面 JS 懒加载 + 缓存

**代码位置**：`frontend/js/router.js`

```javascript
const loadedPages = new Set();   // 记录哪些页面 JS 已加载

function loadPageJS(pageName) {
    if (loadedPages.has(pageName)) return Promise.resolve();  // 已加载，直接返回
    const src = PAGE_JS_MAP[pageName];
    return new Promise((resolve) => {
        const script = document.createElement('script');
        script.src = src;
        script.onload = () => { loadedPages.add(pageName); resolve(); };
        document.body.appendChild(script);
    });
}
```

### 这是什么优化？

**懒加载（lazy loading）+ 缓存**：

- **懒加载**：首屏只加载核心脚本和当前页面的 JS，其他页面的 JS（action.js、tasks.js 等）**等用户真的切到那个页面才加载**。
- **缓存（loadedPages）**：加载过的页面记到 `Set` 里，下次再切过去直接复用，不重复加载。

### 为什么快？

如果没有懒加载，用户一打开首页，就要下载**所有**页面的 JS（本项目前端有 11 个页面 JS，共 2.8 万行）。首屏加载时间会很长。懒加载把"下载所有代码"变成"按需下载"。

**大白话**：懒加载像"自助餐厅"——你想吃什么才去拿什么，而不是一进门就把整个餐厅的菜全端到桌上。

## 2.4 前端：8 个接口并行请求 + 逐个降级

**代码位置**：`frontend/js/app.js`

```javascript
const [profile, habitsData, lastWeekData, profileStats,
       recentActivities, rewardsData, goalsData, scheduledTasksData]
    = await Promise.all([
        fetchUserProfile(user.id).catch(() => null),
        fetchHabits(user.id).catch(() => null),
        fetchLastWeekHabits(user.id).catch(() => null),
        // ... 共 8 个请求
    ]);
```

### 两个优化点

**① Promise.all 并行**：8 个接口**同时**发出，而不是一个一个串行等。串行是"发一个 → 等回来 → 再发下一个"，8 个请求可能要 8 倍时间；并行是"8 个同时发"，总时间 ≈ 最慢的那个。

**② 逐个 `.catch(() => null)` 降级**：每个请求独立容错，某个接口挂了返回 `null`，**不影响其他 7 个**。前端拿到 `null` 就用本地默认数据渲染，页面照样能打开。

**大白话**：并行像"同时派 8 个快递员去取 8 个包裹"，而不是一个快递员跑 8 趟；降级像"某个包裹取不到，其他 7 个照常送，不整单退货"。

## 2.5 前端：防抖（debounce）

**代码位置**：`frontend/js/router.js`

```javascript
let _lastSubnavToggle = 0;
function _debounceSubnavToggle() {
    const now = Date.now();
    if (now - _lastSubnavToggle < 100) return false;  // 100ms 内的重复点击忽略
    _lastSubnavToggle = now;
    return true;
}
```

### 这是什么？

**防抖（debounce）**：短时间内连续触发的事件，只处理第一次或最后一次。这里的意思是：用户 100ms 内连点两次"行动"菜单，只响应一次，避免重复切换导航造成的闪烁和重复渲染。

**典型场景**：搜索框输入（用户每敲一个字就触发一次搜索请求，防抖后等停止输入 300ms 再搜）、窗口 resize、按钮连点。

> 防抖和节流的区别见 §3.3.3。

## 2.6 AI：LLM 实例缓存 + 多模型热切换

**代码位置**：`backend/services/coordinator/llm.py`

```python
_llm_cache: dict[tuple, ChatOpenAI] = {}

def get_llm(temperature: float = 0.3, user_id: int = None) -> ChatOpenAI:
    cfg = get_active_config(user_id or 1, "llm")
    model = (cfg or {}).get("model") or AI_MODEL
    api_key = (cfg or {}).get("api_key") or AI_API_KEY
    base_url = (cfg or {}).get("base_url") or AI_BASE_URL

    cache_key = (temperature, model, base_url, api_key)
    if cache_key not in _llm_cache:
        _llm_cache[cache_key] = ChatOpenAI(...)   # 只在配置变化时重建
    return _llm_cache[cache_key]
```

### 为什么这是优化？

`ChatOpenAI` 实例的创建涉及连接初始化等开销。如果每次调用 AI 都 `new` 一个实例，又慢又浪费连接。

这里的做法是**缓存实例**：用 `(temperature, model, base_url, api_key)` 四元组做 key，配置没变就复用同一个实例，配置变了 key 就变，自动重建。

**效果**：正常使用下实例只创建一次，后续全部命中缓存；切换模型时又自动感知、无缝重建，无需重启服务。

**大白话**：像"提前泡好一壶茶"——来人就倒，不用每次现烧水；换茶叶（换模型）时才重新泡一壶。

### 补充：另一个 LLM 缓存的细节（ai_client.py）

**代码位置**：`backend/services/ai_client.py`

除了 `llm.py` 的四元组缓存，项目还有第二个 AI 客户端（供纯文本生成用），它用的是**模块级单例**：

```python
_llm_instance: ChatOpenAI | None = None      # 模块级单例
_llm_cache_key: tuple | None = None

def _get_llm(temperature, max_tokens, user_id):
    global _llm_instance, _llm_cache_key
    cache_key = (temperature, max_tokens, model, base_url, api_key)
    if _llm_instance is None or _llm_cache_key != cache_key:
        _llm_instance = ChatOpenAI(...)      # 只在配置变化时重建
        _llm_cache_key = cache_key
    return _llm_instance
```

代码注释里写明了优化意图：

> **LLM 实例模块级缓存：复用连接池，省去每次调用的 DNS/TLS 握手**

这揭示了缓存的两个真实收益：

1. **省 DNS 解析**：每次 `new ChatOpenAI` 底层都要重新解析域名
2. **省 TLS 握手**：HTTPS 的加密握手是几百毫秒的开销，复用连接就省掉了

### 补充：超时与重试的权衡（也是优化）

**代码位置**：`backend/services/ai_client.py`

```python
REQUEST_TIMEOUT = 300     # 显式 300 秒超时（不是默认的 5 秒）
MAX_RETRIES = 0           # 不重试
DEFAULT_MAX_TOKENS = 4096 # 给足输出空间
```

这里有两个反直觉但正确的决策：

**① 为什么超时设 300 秒而不是默认 5 秒？**

httpx 默认超时是 5 秒。但 AI 推理模型长文本生成可能要几分钟，5 秒就超时会导致**静默重试**，反而放大延迟。显式设 300 秒，避免"假超时"。

**② 为什么不重试（MAX_RETRIES=0）？**

AI 生成类任务重试收益很低——重试意味着重新生成一遍，又花一遍钱和时间，还放大延迟。所以干脆不重试，失败了直接报错让上层处理。

> **优化启示**：不是所有"超时短、重试多"都是好的。要根据业务特性权衡——AI 生成是"重试收益低"的典型。

### 补充：流式生成（体验优化）

**代码位置**：`backend/services/ai_client.py`

```python
async def call_ai_text_stream(...):
    async for chunk in llm.astream(messages):   # 边生成边产出
        if text:
            yield text
```

流式输出让长文本生成"打字机式"呈现，**总时间没变，但用户不用干等**。这是"感知性能"优化——详见 §3.5.1。

# 第三部分：常见优化方式详解

> 这一部分是重点。每个优化点按「是什么 → 为什么快 → 怎么做 → 本项目能不能用」四段讲解。

## 3.1 数据库层

### 3.1.1 索引（Index）

**是什么**：索引就像书的目录。没有目录，你要找"第 5 章的某个知识点"得从头翻到尾；有目录，翻到目录页一看就知道在第几页。

数据库同理。没有索引，`SELECT * FROM action_logs WHERE user_id = 1` 要**逐行扫描**整个表（全表扫描，O(n)）；有 `user_id` 的索引，数据库直接用树结构（B-tree）定位，复杂度降到 O(log n)。

**为什么快**：全表扫描 100 万行要遍历 100 万次；有索引只要约 20 次比较（log₂(100万) ≈ 20）。

**怎么做**：

```sql
CREATE INDEX idx_action_logs_user_date ON action_logs(user_id, date);
```

**注意事项**（新手常踩的坑）：

1. **给高频查询字段建索引**：`WHERE` 后面的字段。本项目给 `user_id`、`date`、`status` 都建了。
2. **联合索引有顺序**：`(user_id, date)` 的索引，查 `WHERE user_id = 1` 用得上，查 `WHERE date = '2026-09-06'` 用不上（因为 user_id 排前面）。最左前缀原则。
3. **索引不是越多越好**：每个索引都要占空间、每次**写**操作都要维护索引。写多读少的表，索引多了反而拖慢写入。
4. **索引对 `LIKE '%xxx'` 无效**：以 `%` 开头的模糊查询无法用索引。

### 索引的原理：B-tree

索引底层是一棵 **B-tree**（平衡多叉树）。以 `user_id` 索引为例：

```
                [ 50 ]
               /      \
          [ 20, 35 ]  [ 65, 80 ]
          /    |   \   /   |   \
        ...   ... ... ... ... ...    ← 叶子节点存实际数据位置
```

- 查找 `user_id = 35`：从根节点开始，判断 35 在哪个区间，一路往下，**最多比较几次就定位**
- 全表扫描：从第一行读到最后一行，100 万行读 100 万次

**为什么快**：B-tree 的高度很低（100 万数据也只要 3~4 层），每次比较能排除一半数据。

**项目结合**：`action_logs` 表会随打卡记录不断增长。查"某用户某天的行动"时，`idx_action_logs_user_date` 索引让查询从"全表扫描"变成"树查找"，数据越多差距越大。

### 索引失效的常见场景

建了索引但没用上，等于白建。常见失效场景：

```sql
-- ① 对索引字段做了运算
WHERE YEAR(date) = 2026            -- 失效
WHERE date >= '2026-01-01'         -- 有效

-- ② 模糊查询以 % 开头
WHERE name LIKE '%跑步%'           -- 失效
WHERE name LIKE '跑步%'            -- 有效

-- ③ 类型不匹配
WHERE user_id = '1'                -- 如果 user_id 是整数，这里字符串可能导致失效

-- ④ OR 条件里有一个字段没索引
WHERE a = 1 OR b = 2               -- 如果 b 没索引，整体可能不走索引
```

**本项目能不能用**：已经在用了（5 个索引）。如果发现某个查询慢，先 `EXPLAIN QUERY PLAN` 看有没有走索引。

### 3.1.2 连接池（Connection Pool）

**是什么**：数据库连接的创建/销毁是有开销的（握手、分配资源）。连接池就是**提前建好一批连接放着，用完归还，不销毁**，下次复用。

**为什么快**：省去了每次"新建连接 → 用完销毁"的开销。高并发下，反复建连接是很大的浪费。

**本项目现状**：`get_conn()` 是**每次新建连接、用完即关**（`conn.close()`），**没有连接池**。

**怎么做**（如果要用）：

```python
# 以 SQLite 为例，其实 SQLite 更适合用"单连接复用"，而不是池
# 更通用的做法（MySQL/PostgreSQL）用 SQLAlchemy 的连接池：
from sqlalchemy import create_engine
engine = create_engine("postgresql://...", pool_size=10)
```

**注意**：SQLite 比较特殊，它是文件数据库，通常建议**单写连接 + WAL**，而不是传统意义的连接池。本项目"每次新建连接"在低并发下没问题，高并发下才是瓶颈。

### 3.1.3 N+1 查询问题

**是什么**：先查出一个列表（1 次查询），然后对列表里**每一条**又单独查一次（N 次查询），总共 N+1 次。

**例子**：

```python
# 反例：N+1
habits = get_habits(user_id)          # 1 次查询，拿到 20 个习惯
for h in habits:
    checkins = get_checkins(h["id"])   # 每个习惯查一次，共 20 次 → 21 次查询
```

**为什么慢**：20 个习惯要发 21 次请求；如果有 100 个习惯就是 101 次。网络往返和查询开销成倍增加。

**怎么做**：用**一次查询**拿到所有数据（JOIN 或 IN 批量查询）：

```python
# 正例：一次 JOIN 搞定
SELECT habits.*, checkins.* FROM habits
LEFT JOIN checkins ON checkins.habit_id = habits.id
WHERE habits.user_id = ?
```

**本项目能不能用**：如果发现某段代码"循环里查库"，就要警惕是不是 N+1。

### 3.1.4 批量操作

**是什么**：把多条 INSERT/UPDATE 合并成一条，减少数据库往返次数。

**为什么快**：每次数据库操作都有"网络/进程间通信 + 事务"开销。100 条 INSERT 单独发是 100 次开销，合并成一条是 1 次。

**怎么做**：

```python
# 反例：100 次提交
for action in actions:
    conn.execute("INSERT INTO action_logs ...")   # 100 次
    conn.commit()                                  # 100 次提交

# 正例：批量 + 一次提交
conn.executemany("INSERT INTO action_logs ...", data)  # 1 次
conn.commit()                                          # 1 次提交
```

**本项目能不能用**：`create_nodes_batch`（技能树）已经是批量创建节点的思想；`db/batch.py` 里的归档/结算也是批量处理。可以继续把"循环单条 INSERT"改成 `executemany`。

### 3.1.5 慢查询优化（EXPLAIN + 避免 SELECT *）

**是什么**：定位慢 SQL，优化它。

**怎么做**：

1. **用 EXPLAIN 看执行计划**：`EXPLAIN QUERY PLAN SELECT ...`，看有没有走索引、有没有全表扫描。
2. **避免 `SELECT *`**：只查需要的字段，减少数据传输量。`SELECT id, name` 比 `SELECT *`（几十个字段）省得多。
3. **避免在 WHERE 里对字段做运算**：`WHERE YEAR(date) = 2026` 用不上索引，应改成 `WHERE date >= '2026-01-01' AND date < '2027-01-01'`。

### 3.1.6 读写分离 / 分库分表（进阶）

**是什么**：数据量大到单库扛不住时的方案。

- **读写分离**：主库写、从库读，读流量分摊到多个从库。
- **分库分表**：按 user_id 哈希把数据分散到多个库/表。

**为什么快**：把压力从"一个库扛"变成"多个库分摊"。

**本项目能不能用**：**暂时完全不需要**。单用户 SQLite 场景，这些是"万吨油轮"级别的方案，现在是"小渔船"阶段。

## 3.2 后端层

### 3.2.1 缓存（Cache）

**是什么**：把"算过一次、短时间不会变"的结果存起来，下次直接返回，不重复算/查。

**为什么快**：查数据库（几毫秒~几十毫秒）远慢于读内存（微秒级）。缓存把"查库"变成"读内存"。

**缓存层级**（从近到远、从快到慢）：

| 层级 | 例子 | 速度 | 本项目现状 |
|------|------|------|-----------|
| 进程内缓存 | Python 字典 | 微秒级 | ✅ 用了（LLM 实例缓存、loadedPages） |
| 分布式缓存 | Redis / Memcached | 毫秒级 | ❌ 未用 |
| 浏览器缓存 | localStorage / Cache-Control | 客户端本地 | 部分用 |

**怎么做**：

```python
# 进程内缓存（简单版）
_cache = {}
def get_user_stats(user_id, date):
    key = (user_id, date)
    if key in _cache:
        return _cache[key]
    result = db.query(...)          # 查库
    _cache[key] = result
    return result
```

**注意事项**：缓存最大的坑是**失效**（数据变了但缓存没更新，读到旧数据）。所以只缓存"变化不频繁"的数据，并设计好失效策略（TTL、主动清除）。

### 缓存的三大经典问题

引入缓存后，会带来三个新问题（面试常考）：

**① 缓存穿透**：查一个**根本不存在**的数据，缓存里没有，每次都要查数据库。

```
恶意查询 user_id = 99999（不存在）
  → 缓存没命中（因为从不缓存"不存在"）
  → 每次都打数据库
```

**解法**：缓存"空结果"（把"不存在"也缓存，设短 TTL），或用布隆过滤器拦截。

**② 缓存击穿**：某个**热点数据**刚好过期，瞬间大量请求同时打数据库。

```
"今日统计"缓存过期的那一刻
  → 100 个用户同时请求
  → 100 个请求同时查数据库
```

**解法**：加互斥锁（只让一个请求去查库、重建缓存，其他等），或"永不过期 + 后台异步刷新"。

**③ 缓存雪崩**：**大量缓存同时过期**，数据库瞬间被压垮。

```
某天 0 点，所有"今日统计"缓存同时过期
  → 所有请求全部打到数据库
```

**解法**：给过期时间加随机值（错峰过期），或缓存预热。

> 这三个问题在当前单用户场景**都不会发生**（没有高并发），但理解它们是做多用户系统缓存的基本功。

### 缓存的更新策略

| 策略 | 做法 | 特点 |
|------|------|------|
| **Cache Aside**（旁路缓存） | 读：先查缓存，没有就查库并写缓存；写：先写库再删缓存 | 最常用，实现简单 |
| **Read Through** | 读：缓存层自己查库回填 | 业务代码无感 |
| **Write Through** | 写：同时写缓存和库 | 数据一致性好 |
| **Write Behind** | 写：先写缓存，异步刷库 | 写快，但可能丢数据 |

**项目结合**：本项目目前只有"进程内 LLM 实例缓存"（无过期问题）。如果将来给"今日统计"加缓存，用 **Cache Aside** 最简单——读统计时查缓存，没有就查库并写缓存；打卡后删缓存。

**本项目能不能用**：可以把"今日统计"这类一天不变的数据缓存起来，避免每次进首页都查一堆。

### 3.2.2 异步化（别让同步阻塞事件循环）

**是什么**：FastAPI 支持 `async`，但**如果 async 函数里执行了同步的阻塞操作，整个事件循环会被卡住**。

**本项目曾有的坑（已于 2026-09-08 修复）**：`backend/services/coordinator/agents/base.py` 里，子 Agent 执行工具原本是**同步**调用：

```python
tool_result = tool_fn.invoke(args)   # ❌ 同步！会阻塞事件循环
```

在 `async` 的 agent_node 里执行同步的数据库操作，相当于"服务员在等菜时把身体横在门口"，其他所有请求都被卡住。后果是：多域"并行"派发（`asyncio.gather`）实际因为工具同步而串行。

**现在的做法**：把同步操作丢到线程池（`asyncio.to_thread`），一行解决：

```python
import asyncio

# ✅ 同步工具丢线程池，事件循环不被卡住
tool_result = await asyncio.to_thread(tool_fn.invoke, args)
```

> 注意：工具函数本身仍是同步的（24 个工具全是 `def`，内部是同步 sqlite3），改的是**调用方式**。这是"同步操作与异步框架共存"的标准解法，也是 `main.py` 里 `ThreadPoolExecutor(1)` 跑定时任务的同一思路。

**为什么不用"工具改 async"**：那需要换异步数据库驱动（`aiosqlite`）并改 24 个工具函数，单用户 SQLite 场景下收益不匹配成本。

### 3.2.3 响应压缩（gzip）

**是什么**：后端把响应内容压缩后发给前端，前端解压。

**为什么快**：JSON 文本压缩率很高（常能压到 1/3 ~ 1/5），网络传输时间大幅缩短。尤其对大响应（长列表、大 JSON）效果明显。

**怎么做**（FastAPI）：

```python
from fastapi.middleware.gzip import GZipMiddleware
app.add_middleware(GZipMiddleware, minimum_size=1000)  # 大于 1KB 的响应才压缩
```

**本项目能不能用**：响应体普遍不大，收益有限，但加一行无坏处。

### 3.2.4 限流（Rate Limiting）

**是什么**：限制单个用户/IP 在单位时间内的请求次数。

**为什么重要**：防"单用户打爆服务"——一个脚本疯狂刷接口，把服务器资源耗尽。限流不是"提速"，而是**保护服务不被拖垮**。

**怎么做**（FastAPI）：

```python
# 用 slowapi 库
from slowapi import Limiter
limiter = Limiter(key_func=lambda: "global")
@limiter.limit("100/minute")
@router.get("/api/actions")
```

**本项目能不能用**：本项目**无限流**（压测文档 §2.1 已指出），公网部署前建议加。

### 3.2.5 HTTP 连接复用

**是什么**：调用外部 API（如 AI 接口）时，复用 HTTP 连接，而不是每次新建。

**为什么快**：每次新建 HTTP 连接要 TCP 三次握手 + TLS 握手，几百毫秒开销。复用连接省掉握手。

**怎么做**：用带连接池的 HTTP 客户端（httpx 的 `AsyncClient`、requests 的 `Session`），而不是每次 `httpx.get()` 新建。

**本项目现状**：`ChatOpenAI` 底层用的 httpx 客户端，但没有显式的连接池配置；`max_retries=0`（不重试）。

## 3.3 前端层

### 3.3.1 代码分割与懒加载

**是什么**：把代码按需拆成小块，用到才加载。本项目已经用了（见 §2.3），这里是补充说明。

**更进阶的做法**：用构建工具（Vite/Webpack）做**代码分割**，自动把每个路由的代码打成独立的 chunk，配合 `import()` 动态导入。

**本项目现状**：手动实现了 `loadPageJS`（动态 `<script>` 标签），原理和代码分割一致，只是没有用构建工具（项目是零框架零构建的）。

### 3.3.2 图片优化

**是什么**：图片往往是网页里最"重"的资源。优化图片能显著加速加载。

**怎么做**：

1. **懒加载**：图片滚到可视区才加载（`<img loading="lazy">`）
2. **用对的格式**：照片用 WebP/JPEG，图标用 SVG，不要用 PNG 存照片
3. **压缩尺寸**：不要上传 4000px 的原图，缩到实际显示尺寸的 2 倍即可
4. **CDN 加速**：图片走 CDN，就近分发

**本项目能不能用**：有图片上传（奖励图片），可以加上传时压缩、按需缩放。

### 3.3.3 防抖 vs 节流（重要区分）

两者都用于"高频触发的事件"，但行为不同：

| | 防抖（debounce） | 节流（throttle） |
|---|---|---|
| 行为 | 停止触发 N 秒后才执行一次 | 每 N 秒最多执行一次 |
| 比喻 | 电梯：等人进完才关门 | 游戏帧率：固定间隔刷新 |
| 适用 | 搜索输入、表单校验、窗口 resize | 滚动加载、按钮防连点、实时刷新 |

```javascript
// 防抖：停止 300ms 后才执行
function debounce(fn, delay = 300) {
    let timer;
    return (...args) => {
        clearTimeout(timer);
        timer = setTimeout(() => fn(...args), delay);
    };
}

// 节流：每 300ms 最多执行一次
function throttle(fn, interval = 300) {
    let last = 0;
    return (...args) => {
        const now = Date.now();
        if (now - last >= interval) { last = now; fn(...args); }
    };
}
```

**本项目现状**：router.js 里的 `_debounceSubnavToggle` 其实是"100ms 内忽略重复点击"，更像节流的简化版。

### 3.3.4 虚拟列表

**是什么**：列表有 1 万条数据时，只渲染**当前可视区**的那几十条，滚动时动态替换。

**为什么快**：DOM 节点是浏览器渲染最贵的部分。1 万条数据如果全渲染成 DOM，页面会卡死；虚拟列表永远只渲染可视区的几十条，滚动流畅。

**本项目能不能用**：行动历史（action history）如果数据多了，可以用虚拟列表代替"全量渲染 + 分页"。

### 3.3.5 CDN

**是什么**：内容分发网络，把静态资源（JS/CSS/图片）复制到全球各地的服务器，用户就近下载。

**为什么快**：物理距离近 → 网络延迟低。同时减轻源服务器压力。

**本项目能不能用**：前端是本地部署，暂时不需要；部署到公网后，可以把前端静态文件放到 CDN。

## 3.4 网络层

### 3.4.1 HTTP 缓存（Cache-Control / ETag）

**是什么**：告诉浏览器"这个资源可以缓存多久"，下次访问直接用本地缓存，不发请求。

**怎么做**：

```
Cache-Control: max-age=86400     # 缓存 1 天
Cache-Control: no-cache          # 每次都验证
ETag: "abc123"                    # 资源指纹，内容变了 ETag 变
```

**为什么快**：静态资源（JS/CSS/图片）基本不变，缓存后用户第二次访问**零请求**，秒开。

**本项目能不能用**：前端 JS/CSS 可以加 `Cache-Control`；但开发阶段要注意"改了代码但浏览器用旧缓存"的问题（用版本号 query 如 `app.js?v=2` 解决）。

### 3.4.2 keep-alive（连接保持）

**是什么**：HTTP 默认每次请求都新建 TCP 连接，keep-alive 让多个请求复用同一个 TCP 连接。

**为什么快**：省掉反复三次握手。浏览器和现代服务器默认都开了 keep-alive，一般无需手动处理。

### 3.4.3 HTTP/2

**是什么**：HTTP 协议的升级版，支持**多路复用**——一个连接上可以同时传输多个请求/响应。

**为什么快**：HTTP/1.1 下浏览器对同一域名的并发连接有上限（约 6 个），超过就要排队；HTTP/2 一个连接搞定所有请求，还能做头部压缩。

**怎么做**：通常由反向代理（nginx）或托管平台（Cloudflare）开启，应用层无感。

### 3.4.4 压缩（gzip / brotli）

见 §3.2.3，网络层的压缩和响应压缩是同一件事的两面：后端压、浏览器解。

## 3.5 AI 应用特有的优化

> 这是 AI 应用（本项目核心场景）最值得关注的部分。

### 3.5.1 流式输出（SSE）

**是什么**：AI 生成一句话可能要 10 秒。一次性等 10 秒再返回，用户体验很差。流式输出让 AI **边生成边推送**，用户立刻能看到字一个个蹦出来。

**为什么重要**：不是"更快"，而是**感知更快**。总时间没变，但用户不用干等。

**本项目现状**：`/api/coordinator/stream/{thread_id}` 是 SSE **占位实现**，前端也还没接，走的是普通 POST 等完整响应。**这是本项目最值得补的一个优化**。

### 3.5.2 模型降级与超时

**是什么**：

- **超时**：给 AI 调用设置超时时间，别让一个慢请求拖垮整个服务
- **降级**：主模型挂了/超时，自动切到备用模型，或用缓存结果兜底

**本项目现状**：`REQUEST_TIMEOUT = 120`（120 秒超时），`MAX_RETRIES = 0`（不重试）。但**没有降级**——AI 挂了就直接失败。

**怎么做**：

```python
try:
    result = await call_model(primary_model, timeout=30)
except TimeoutError:
    result = await call_model(fallback_model, timeout=30)  # 降级
```

### 3.5.3 减少 token 消耗

**是什么**：AI 调用按 token 计费、token 越多越慢。减少 token 直接降本提速。

**怎么做**：

1. **精简系统提示词**：别写一大段废话
2. **上下文截断**：只传相关的历史，不传全部对话（本项目已用 `MAX_HISTORY=10`，见 `agents/base.py`）
3. **摘要代替原文**：长历史先让 AI 总结成摘要再传（本项目主 Agent 用"近 5 条记录摘要"，见 `graph.py`）
4. **结构化输出**：让 AI 只返回 JSON，别返回大段自然语言

**本项目现状**：已经用了上下文截断 + 摘要，做得不错。技能树 AI 的"树状态截断"还没做（大树上 token 爆炸，见 `docs/技能树AI-LangGraph改造方案.md` P5）。

### 3.5.4 并发调用

**是什么**：有多个独立的 AI 调用时，并行发，别串行等。

**本项目现状**：协调 Agent 用 `asyncio.gather` 并行派发多个子 Agent（但因子 Agent 内部工具同步，实际没真正并行——见 §3.2.2）。

### 3.5.5 结果缓存

**是什么**：相同的问题/操作，缓存 AI 的结果，下次直接返回，不再调 AI。

**适用场景**：重复性查询（如"今天总结"）、确定性任务。不适用于需要实时生成的内容。

**注意**：AI 结果缓存要小心——AI 有随机性，缓存可能返回"过时的答案"。

### 3.5.6 提示词缓存（Prompt Caching）

**是什么**：很多模型服务商（Anthropic、OpenAI、DeepSeek 等）支持**提示词缓存**——如果两次请求的系统提示词（或前缀）相同，第二次的这部分 token 会命中缓存，**便宜且更快**。

**为什么快**：系统提示词（往往几百到几千 token）如果每次都要重新处理，又慢又贵。缓存后，模型直接复用之前计算好的结果，只处理变化的部分。

**怎么做**：

- 把**稳定不变的部分**（系统提示词、工具描述、few-shot 示例）放在前面
- 把**变化的部分**（用户消息）放在最后
- 保持系统提示词稳定，不要每次拼接不同的内容

**项目结合**：`agents/base.py` 里，系统提示词（`SystemMessage`）是固定的，用户指令是变化的——这本身就符合"前缀缓存"的最佳实践。如果提示词能进一步精简并保持稳定，能同时降本提速。

### 3.5.7 模型分工：大模型 vs 小模型

**是什么**：不是所有任务都需要最强（最贵、最慢）的模型。简单的任务用小模型，复杂的用大模型，成本和时间都能大幅下降。

**怎么分工**：

| 任务 | 用什么模型 | 理由 |
|------|-----------|------|
| 意图路由（判断"这是要记行动还是查统计"） | 小模型 | 简单分类，小模型够用 |
| 参数提取（"跑步30分钟"→ 结构化参数） | 小模型 | 结构化提取，稳定 |
| 长文本生成、深度分析 | 大模型 | 需要强的生成和推理能力 |

**为什么快**：小模型通常比大模型快 5~10 倍、便宜 10 倍以上。把 80% 的简单任务交给小模型，只把 20% 的难任务交给大模型，整体速度大幅提升。

**项目结合**：协调 Agent 的路由（`router_node`）和子 Agent 的意图判断，都是相对简单的分类/提取任务，理论上可以用更小更快的模型。目前项目统一用配置的模型，如果按"路由用小模型、总结用大模型"分工，能进一步提速。

## 3.6 测量与定位（怎么知道慢在哪）

优化最忌讳"凭感觉瞎改"。先测量，再优化。

### 方法一：计时打点

```python
import time
start = time.time()
result = db.query(...)
print(f"查询耗时 {time.time() - start:.3f}s")
```

### 方法二：Python profiling

```bash
# cProfile 找出最耗时的函数
python -m cProfile -s cumulative main.py
```

### 方法三：SQL 执行计划（EXPLAIN）

SQLite 用 `EXPLAIN QUERY PLAN` 看查询有没有走索引：

```sql
-- 有索引：走索引（快）
EXPLAIN QUERY PLAN SELECT * FROM action_logs WHERE user_id = 1;
-- 输出：SEARCH action_logs USING INDEX idx_action_logs_user_date (user_id=?)

-- 没索引：全表扫描（慢）
EXPLAIN QUERY PLAN SELECT * FROM action_logs WHERE note LIKE '%跑步%';
-- 输出：SCAN action_logs
```

**关键看输出里的两个词**：

- `SEARCH ... USING INDEX` → 走了索引，快 ✅
- `SCAN ...` → 全表扫描，慢 ❌

### 方法四：Python profiling（cProfile）

找出"哪个函数最耗时"：

```bash
# 生成性能报告
python -m cProfile -s cumulative main.py

# 输出示例（按累计耗时排序）
#    ncalls  tottime  cumtime  filename:lineno(function)
#      100    0.001    3.500   db/actions.py:42(get_action_logs)   ← 最耗时
#     1000    0.020    2.100   services/exp_service.py:17(award_exp)
#   ...
```

**看 `cumtime`（累计耗时）列**：它包含了"这个函数调用的子函数的总耗时"，最能反映"时间到底花在哪条调用链上"。

### 方法五：压测（Locust）

模拟大量用户，找到性能拐点。详见 `docs/压测说明.md`。

### 方法六：浏览器 DevTools

F12 打开开发者工具：

- **Network 面板**：每个请求的耗时、大小、状态码。看哪个接口慢、哪个文件大
- **Performance 面板**：录制一段操作，看前端渲染瓶颈（JS 执行、布局、绘制）
- **Lighthouse**：一键生成性能评分报告，给出优化建议

### 优化的闭环（重要）

性能优化不是"改一次就完"，而是循环：

```
测量 → 定位瓶颈 → 优化 → 再测量 → 对比 → (有效就保留，无效就回退)
```

**没有对比的优化等于没优化**——你改了代码，怎么知道真的变快了？量出"优化前 vs 优化后"的数字，才叫优化。

**项目结合**：如果将来要优化 `action_logs` 查询，正确流程是：先 `EXPLAIN` 看有没有走索引 → 没走就加索引 → 用计时打点对比加索引前后的耗时。

# 附录：性能优化 checklist

排查性能问题时，按这个顺序过一遍：

```
□ 1. 先测量：哪里慢？（profiling / EXPLAIN / DevTools / 压测）
□ 2. 数据库：有没有索引？有没有 N+1？能不能批量？能不能分页？
□ 3. 外部调用：AI/HTTP 调用有没有超时？能不能并行？能不能缓存？
□ 4. 后端：有没有同步阻塞事件循环？响应能不能压缩？要不要限流？
□ 5. 前端：JS 能不能懒加载？图片能不能优化？列表能不能虚拟化？能不能防抖节流？
□ 6. 网络：静态资源能不能缓存？能不能走 CDN？能不能开 HTTP/2？
□ 7. AI 特化：能不能流式输出？token 能不能省？能不能降级？
□ 8. 最后再问：这个优化真的有必要吗？（避免过早优化）
```
