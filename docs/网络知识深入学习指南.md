# 第一部分：网络基础概念

## 1.1 为什么需要网络？

想象一下没有网络的世界：你的数据只能存在一台电脑上，想在手机上看电脑的文件？只能用 U 盘拷贝。想和朋友分享照片？只能当面传。

**网络的本质**：让多台设备（手机、电脑、服务器）能够互相通信，共享数据。

在你的 Self Grow 项目中：
- **浏览器**（客户端）运行在你的电脑上，显示前端界面
- **FastAPI 后端**（服务器）也运行在你的电脑上，处理数据和 AI 调用
- 两者通过"网络协议"通信，即使它们在同一台机器上

```
┌─────────────┐     HTTP 请求      ┌─────────────┐
│   浏览器     │ ──────────────────→ │  FastAPI     │
│   (客户端)   │ ←────────────────── │  (服务器)    │
│  localhost:3000│    HTTP 响应      │  localhost:3001│
└─────────────┘                     └─────────────┘
```

## 1.2 网络分层模型

网络通信非常复杂，所以工程师把它分成**多个层次**，每层各司其职。

### OSI 七层模型（理论模型）

| 层 | 名称 | 功能 | 现实中的例子 |
|----|------|------|-------------|
| 7 | 应用层 | 用户直接使用的协议 | HTTP、HTTPS、DNS、SMTP |
| 6 | 表示层 | 数据格式转换、加密 | SSL/TLS、JPEG、JSON |
| 5 | 会话层 | 建立/管理/终止会话 | Socket、RPC |
| 4 | 传输层 | 端到端可靠传输 | TCP、UDP |
| 3 | 网络层 | 路由寻址 | IP、ICMP、路由器 |
| 2 | 数据链路层 | 帧传输、差错检测 | Ethernet、WiFi |
| 1 | 物理层 | 比特流传输 | 网线、光纤、无线电波 |

### TCP/IP 四层模型（实际使用）

实际互联网使用的是简化的四层模型：

```
┌─────────────────────────────────────────────────────────┐
│  应用层 (HTTP, DNS, SMTP, FTP...)                       │  ← 你的项目在这里
├─────────────────────────────────────────────────────────┤
│  传输层 (TCP, UDP)                                       │  ← 保证数据可靠传输
├─────────────────────────────────────────────────────────┤
│  网络层 (IP, ICMP)                                       │  ← 负责寻址和路由
├─────────────────────────────────────────────────────────┤
│  网络接口层 (Ethernet, WiFi)                             │  ← 物理传输
└─────────────────────────────────────────────────────────┘
```

**项目结合**：你的 FastAPI 后端监听 `localhost:3001`，浏览器访问 `http://localhost:3000`，整个通信链路是：

1. **应用层**：浏览器构造 HTTP 请求（GET /api/users/profile）
2. **传输层**：TCP 协议确保数据可靠传输
3. **网络层**：IP 协议寻址到 `127.0.0.1`（本机）
4. **网络接口层**：通过回环接口在本机内传输

## 1.3 IP 地址：设备的"门牌号"

### 什么是 IP 地址？

每台联网设备都有一个唯一的数字标识，就像每栋房子都有一个门牌号。

```
IPv4 格式：4 组数字，每组 0-255，用点分隔
例如：192.168.1.100
      127.0.0.1（本机回环地址）
```

### 常见 IP 地址分类

| 类型 | 范围 | 用途 |
|------|------|------|
| `127.0.0.1` | 固定 | 本机回环地址（localhost） |
| `192.168.x.x` | 私有 | 局域网内设备（如家庭WiFi） |
| `10.x.x.x` | 私有 | 大型企业内网 |
| `8.8.8.8` | 公网 | Google DNS 服务器 |

### 项目中的体现

```javascript
// frontend/js/utils.js
const API_BASE = window.__SELF_GROW_API_BASE__ || 'http://localhost:3001';
```

- `localhost` 是域名，DNS 会把它解析为 `127.0.0.1`
- `127.0.0.1` 是特殊地址，永远指向本机
- 所以浏览器访问 `http://localhost:3001` = 访问本机上运行的 FastAPI 服务

### 为什么用 `127.0.0.1` 而不是 `192.168.x.x`？

```
127.0.0.1（localhost）→ 本机通信，不经过网卡，速度极快
192.168.x.x → 需要经过路由器，适用于多设备间通信
```

你的项目开发时，前后端都在同一台电脑上，所以用 `localhost` 最合适。

## 1.4 端口：设备内的"房间号"

### 为什么需要端口？

一台电脑可能同时运行多个网络服务（Web 服务器、数据库、邮件服务器），IP 地址只能定位到电脑，**端口**定位到具体的服务。

```
一台电脑 (IP: 127.0.0.1)
├── 端口 3000 → Python HTTP Server（前端）
├── 端口 3001 → FastAPI 后端
├── 端口 5432 → PostgreSQL 数据库
├── 端口 6379 → Redis 缓存
└── 端口 3306 → MySQL 数据库
```

### 端口号范围

```
0-1023：系统保留端口（HTTP=80, HTTPS=443, SSH=22）
1024-49151：注册端口（常用服务）
49152-65535：动态端口（临时使用）
```

### 项目中的端口配置

```python
# backend/config.py
try:
    PORT = int(os.getenv("PORT", "3001"))
except (ValueError, TypeError):
    log.warning("⚠️ PORT 环境变量格式错误，使用默认端口 3001")
    PORT = 3001
```

你的项目使用：
- **3000 端口**：`python -m http.server` 提供前端静态文件
- **3001 端口**：FastAPI 后端 API 服务

### 为什么要用不同端口？

```
浏览器访问 http://localhost:3000 → 前端页面
浏览器访问 http://localhost:3001/api/users → 后端 API
```

**分离的好处**：
1. 前后端独立开发、独立部署
2. 生产环境可以只部署后端，前端用 CDN
3. 开发时可以独立重启某个服务

## 1.5 DNS：域名到 IP 的翻译官

### 什么是 DNS？

DNS（Domain Name System）就像电话簿，把人类易记的域名翻译成机器能理解的 IP 地址。

```
你在浏览器输入：www.google.com
DNS 查询过程：
1. 浏览器缓存 → 没有
2. 操作系统缓存 → 没有
3. 路由器缓存 → 没有
4. ISP DNS 服务器 → 找到！返回 142.250.80.46
5. 浏览器连接 142.250.80.46
```

### 项目中的 DNS 使用

```javascript
// 当你访问 http://localhost:3001/api/users/profile 时
// "localhost" 会被 DNS 解析为 127.0.0.1

// 但在后端配置中，有时直接用 IP：
# backend/main.py
content = f"window.__SELF_GROW_API_BASE__ = 'http://127.0.0.1:{PORT}';"
```

这里直接用 `127.0.0.1` 而不是 `localhost`，避免了 DNS 查询的开销。

### 本地 hosts 文件

```bash
# Windows: C:\Windows\System32\drivers\etc\hosts
# Linux/Mac: /etc/hosts

# 你可以自定义域名解析：
127.0.0.1    myapp.local
127.0.0.1    api.myapp.local
```

## 1.6 协议：通信的"语言规则"

### 什么是协议？

协议就是通信双方必须遵守的规则，就像两个人约定好"我说中文，你也必须回中文"。

### 常见网络协议

| 协议 | 用途 | 默认端口 |
|------|------|---------|
| HTTP | 网页传输 | 80 |
| HTTPS | 加密网页传输 | 443 |
| TCP | 可靠数据传输 | - |
| UDP | 快速数据传输 | - |
| WebSocket | 实时双向通信 | 80/443 |
| FTP | 文件传输 | 21 |
| SSH | 安全远程登录 | 22 |

### 项目涉及的协议

```
你的项目主要使用 HTTP 协议：

浏览器 ──── HTTP/1.1 ────→ FastAPI 后端
         GET /api/users/profile HTTP/1.1
         Host: localhost:3001
         Accept: application/json

FastAPI ──── HTTP/1.1 ────→ 浏览器
         HTTP/1.1 200 OK
         Content-Type: application/json
         {"user": {"name": "冒险者", "level": 188}}
```

## 1.7 客户端-服务器模型 (C/S)

### 基本概念

```
┌──────────────┐                    ┌──────────────┐
│    客户端     │  ── 请求 ──→       │    服务器     │
│  (Client)    │  ←─ 响应 ──        │  (Server)    │
└──────────────┘                    └──────────────┘
```

- **服务器 (Server)**：等待并响应请求的一方（FastAPI、Nginx）

```python
    # 服务器处理请求，返回响应
```

```javascript
// frontend/js/utils.js - 客户端
async function fetchUserProfile(userId) {

        const resp = await fetch(`${API_BASE}/api/users/profile?user_id=${userId}`);
```

# 第二部分：TCP 与 UDP 协议

## 2.1 传输层的作用

第一部分讲了 IP 地址可以定位到具体的电脑，但一台电脑上可能运行着多个服务。**传输层**的任务就是：**确保数据从一台电脑的某个端口，准确传送到另一台电脑的某个端口**。

```
你的电脑 (127.0.0.1)                    FastAPI 服务器 (127.0.0.1:3001)
┌──────────────┐                        ┌──────────────┐
│ 浏览器       │  TCP 段                │ FastAPI 进程  │
│ 端口 52847   │ ───────────────────→   │ 端口 3001    │
│              │  src:52847 dst:3001    │              │
│              │  data: GET /api/users  │              │
└──────────────┘                        └──────────────┘
```

传输层有两个核心协议：**TCP** 和 **UDP**。

---

## 2.2 TCP：可靠的"快递员"

### TCP 是什么？

TCP（Transmission Control Protocol，传输控制协议）是一种**面向连接的、可靠的**传输协议。它保证数据**不丢失、不重复、按顺序到达**。

### 三次握手（建立连接）

TCP 在传输数据前，需要先建立连接。这个过程叫**三次握手**：

```
客户端 (浏览器)                         服务器 (FastAPI)
      │                                      │
      │  ① SYN                              │
      │  "我要建立连接，我的初始序列号是 1000" │
      │  ─────────────────────────────────→  │
      │                                      │
      │  ② SYN + ACK                        │
      │  "收到，同意连接，我的序列号是 5000，  │
      │   期待收到你的第 1001 号数据"          │
      │  ←─────────────────────────────────  │
      │                                      │
      │  ③ ACK                              │
      │  "收到，确认你的序列号，开始传数据"    │
      │  ─────────────────────────────────→  │
      │                                      │
      │  ===== 连接建立，开始传输数据 =====   │
```

**为什么是三次而不是两次？**

想象打电话的场景：
1. 你说"喂，能听到吗？"（SYN）—— 确认你的声音能传到对方
2. 对方说"能听到，你能听到我吗？"（SYN+ACK）—— 确认对方的声音也能传到你
3. 你说"能听到"（ACK）—— 确认双向通信正常

三次握手确保**双方都确认了彼此的收发能力**。

### 四次挥手（关闭连接）

数据传输完成后，需要关闭连接。这个过程叫**四次挥手**：

```
客户端                                服务器
   │                                    │
   │  ① FIN                            │
   │  "我的数据发完了，准备关闭"          │
   │  ──────────────────────────────→   │
   │                                    │
   │  ② ACK                            │
   │  "收到你的关闭请求，但我还有数据"    │
   │  ←──────────────────────────────   │
   │                                    │
   │  （服务器继续发送剩余数据...）       │
   │                                    │
   │  ③ FIN                            │
   │  "我的数据也发完了，可以关闭了"      │
   │  ←──────────────────────────────   │
   │                                    │
   │  ④ ACK                            │
   │  "确认关闭，再见"                   │
   │  ──────────────────────────────→   │
   │                                    │
   │  ===== 连接完全关闭 =====          │
```

**为什么是四次而不是三次？**

因为 TCP 是**全双工**的（双方可以同时发送数据），所以关闭连接需要双方分别确认：
1. 客户端说"我发完了"（FIN）
2. 服务器说"收到，但我还有数据"（ACK）
3. 服务器发完剩余数据后说"我也发完了"（FIN）
4. 客户端说"确认关闭"（ACK）

### TCP 的可靠性机制

#### 1. 序列号和确认应答

```
发送方                              接收方
   │                                    │
   │  数据包 seq=1, len=100             │
   │  ──────────────────────────────→   │
   │                                    │
   │  ←──────────────────────────────   │
   │  ACK=101 (期望下一个字节的序号)     │
   │                                    │
   │  数据包 seq=101, len=200           │
   │  ──────────────────────────────→   │
   │                                    │
   │  ←──────────────────────────────   │
   │  ACK=301                           │
```

每个字节都有编号，接收方通过 ACK 告诉发送方"我收到了哪些数据"。

#### 2. 超时重传

```
发送方                              接收方
   │                                    │
   │  数据包 seq=1                      │
   │  ────────────────╳  (丢失了!)      │
   │                                    │
   │  （等待一段时间，没收到 ACK）        │
   │                                    │
   │  重新发送数据包 seq=1               │
   │  ──────────────────────────────→   │
   │                                    │
   │  ←──────────────────────────────   │
   │  ACK=101                           │
```

如果发送方在一定时间内没有收到 ACK，就认为数据丢失了，自动重传。

#### 3. 流量控制

接收方通过**滑动窗口**告诉发送方"我还能接收多少数据"：

```
接收方窗口大小 = 1000 字节

发送方：
  已发送未确认: [seq 1-500]
  可以继续发送: [seq 501-1000]  ← 窗口内
  不可发送:    [seq 1001+]     ← 超出窗口
```

防止发送方发得太快，接收方来不及处理。

#### 4. 拥塞控制

当网络拥塞时（太多数据同时传输），TCP 会自动降低发送速度：

```
慢启动阶段：窗口大小指数增长
  1 → 2 → 4 → 8 → 16 → ...

遇到拥塞：窗口大小减半
  16 → 8 → ...

然后线性增长：
  8 → 9 → 10 → ...
```

## 2.3 UDP：快速的"信使"

### UDP 是什么？

UDP（User Datagram Protocol，用户数据报协议）是一种**无连接的、不可靠的**传输协议。它**不保证数据到达、不保证顺序、不保证不重复**。

### UDP 的工作方式

```
发送方                              接收方
   │                                    │
   │  数据报 src:52847 dst:5000         │
   │  ──────────────────────────────→   │
   │                                    │
   │  数据报 src:52847 dst:5000         │
   │  ────────────╳  (丢失了!)          │
   │                                    │
   │  （没有重传机制，丢了就丢了）        │
```

UDP 没有连接建立的过程，直接发送数据。没有 ACK、没有重传、没有流量控制。

### TCP vs UDP 对比

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接方式 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认+重传） | 不可靠 |
| 顺序性 | 保证顺序 | 不保证 |
| 速度 | 较慢（建立连接+确认） | 快（无额外开销） |
| 流量控制 | 有 | 无 |
| 拥塞控制 | 有 | 无 |
| 传输方式 | 字节流 | 数据报 |
| 典型应用 | HTTP、FTP、SSH | DNS、视频、游戏 |

### 为什么 HTTP 选择 TCP？

```
HTTP 需要：
✅ 数据完整（不能丢字节）     → TCP 的确认重传
✅ 顺序正确（HTML 不能乱序）  → TCP 的序列号
✅ 连接可靠（不能中断）       → TCP 的三次握手
❌ 不需要极低延迟            → 可以接受 TCP 的开销
```

网页内容（HTML、CSS、JS）每一个字节都很重要，丢失或乱序会导致页面渲染错误，所以 HTTP 选择 TCP。

### 4. HTTP Keep-Alive（TCP 连接复用）

```
不用 Keep-Alive：
  请求1 → TCP三次握手 → 传输 → TCP四次挥手
  请求2 → TCP三次握手 → 传输 → TCP四次挥手
  请求3 → TCP三次握手 → 传输 → TCP四次挥手

用 Keep-Alive：
  TCP三次握手 → 请求1 → 响应1 → 请求2 → 响应2 → 请求3 → 响应3 → TCP四次挥手
```

你的项目中，前端启动时 `Promise.all` 并行发送 8 个请求。现代浏览器和 FastAPI 默认都支持 HTTP Keep-Alive，这 8 个请求可能复用同一个 TCP 连接：

| 概念 | 通俗解释 | 项目体现 |
|------|---------|---------|
| **三次握手** | 建立连接前的"握手确认" | 浏览器访问后端时自动发生 |
| **四次挥手** | 关闭连接前的"双向告别" | 请求完成后自动发生 |
| **序列号** | 数据包的"快递单号" | TCP 保证数据不丢不乱 |
| **超时重传** | "没收到回复就再发一次" | 网络抖动时自动恢复 |
| **流量控制** | "别发太快，我处理不过来" | 防止服务器被压垮 |
| **UDP** | 快但不可靠的传输 | DNS 查询、视频通话常用 |
| **Keep-Alive** | 复用 TCP 连接 | 前端 8 个并行请求可能共享连接 |

# 第三部分：HTTP 协议详解

## 3.1 HTTP 是什么？

HTTP（HyperText Transfer Protocol，超文本传输协议）是应用层协议，定义了客户端和服务器之间**如何交换信息**。

```
客户端发送请求 → 服务器处理请求 → 服务器返回响应
```

HTTP 的特点：
- **无状态**：每次请求独立，服务器不记得上一次请求
- **请求-响应模型**：客户端先发请求，服务器再返回响应
- **基于 TCP**：HTTP 请求通过 TCP 连接传输

---

## 3.2 HTTP 请求的结构

一个完整的 HTTP 请求由三部分组成：**请求行**、**请求头**、**请求体**。

### 实际请求示例

当你在浏览器访问 `http://localhost:3001/api/users/profile?user_id=1` 时，浏览器发出的请求是：

```http
GET /api/users/profile?user_id=1 HTTP/1.1          ← 请求行
Host: localhost:3001                               ← 请求头
Accept: application/json                           ← 请求头
User-Agent: Mozilla/5.0 (Windows NT 10.0)         ← 请求头
Accept-Language: zh-CN,zh;q=0.9                    ← 请求头
Connection: keep-alive                             ← 请求头
                                                 ← 空行（请求头结束）
                                                 ← 请求体（GET 没有请求体）
```

### 请求行详解

```
GET /api/users/profile?user_id=1 HTTP/1.1
│    │                              │    │
│    │                              │    └─ HTTP 版本
│    │                              └────── 请求路径 + 查询参数
│    └────────────────────────────────────── HTTP 方法
```

#### HTTP 方法

| 方法 | 用途 | 有请求体？ | 项目示例 |
|------|------|-----------|---------|
| GET | 获取资源 | ❌ | `GET /api/tasks` 获取今日任务 |
| POST | 创建资源 | ✅ | `POST /api/tasks` 创建新任务 |
| PUT | 更新资源（全量） | ✅ | `PUT /api/tasks/5` 更新任务 |
| PATCH | 更新资源（部分） | ✅ | `PATCH /api/tasks/5/status` 修改状态 |
| DELETE | 删除资源 | ❌ | `DELETE /api/tasks/5` 删除任务 |

### 请求头详解

请求头携带额外信息，以 `Key: Value` 格式出现：

```http
Host: localhost:3001
# 目标主机。HTTP/1.1 必须有 Host 头。

Accept: application/json
# 告诉服务器"我期望接收 JSON 格式的响应"。

Content-Type: application/json
# 告诉服务器"我发送的请求体是 JSON 格式的"（POST/PUT 时使用）。

Authorization: Bearer <token>
# 认证信息，携带 token 让服务器识别身份。

User-Agent: Mozilla/5.0 ...
# 浏览器类型和版本，服务器可以据此返回不同内容。

Connection: keep-alive
# 保持 TCP 连接不断开，下一个请求可以复用。

Cache-Control: no-cache
# 告诉浏览器不要使用缓存，必须从服务器获取最新数据。
```

### 请求体详解

请求体携带客户端发送给服务器的数据。GET 请求没有请求体，POST/PUT/PATCH 有。

```json
// POST /api/tasks 的请求体
{
    "title": "学习网络知识",
    "category": "study",
    "priority": "high",
    "exp": 100,
    "intro": "深入理解 TCP/IP"
}
```

## 3.3 HTTP 响应的结构

服务器收到请求后，返回一个 HTTP 响应。

### 实际响应示例

```http
HTTP/1.1 200 OK                                    ← 状态行
Content-Type: application/json; charset=utf-8      ← 响应头
Content-Length: 256                                 ← 响应头
```

### 状态码详解

状态码告诉客户端请求的结果。三位数字，分为五类：

#### 2xx 成功

| 状态码 | 含义 | 项目示例 |

| 200 OK | 请求成功 | 所有正常 API 调用 |
| 201 Created | 资源创建成功 | 创建任务、创建习惯 |

| 状态码 | 含义 | 说明 |
|--------|------|------|

## 4.2 项目中的 API 封装

你的项目有两套 API 封装，一套在 `utils.js`，一套在 `agent.js`。

### utils.js 的封装

```javascript
// frontend/js/utils.js
const API_BASE = window.__SELF_GROW_API_BASE__ || 'http://localhost:3001';

// GET 请求
async function fetchGoals(userId) {
    try {
        const resp = await fetch(`${API_BASE}/api/goals?user_id=${userId}`);
        if (!resp.ok) return null;  // 失败返回 null
        return await resp.json();
    } catch (e) {
        console.warn('获取目标失败:', e);
        return null;  // 网络错误也返回 null
    }
}

// POST 请求
async function createGoalOnBackend(userId, data) {
    try {
        const resp = await fetch(`${API_BASE}/api/goals`, {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ user_id: userId, ...data })
        });
        if (!resp.ok) return null;
        return await resp.json();
    } catch (e) {
        console.warn('创建目标失败:', e);
        return null;
    }
}
```

### agent.js 的封装

```javascript
// frontend/js/pages/agent.js
function getApiBase() {
    return window.__SELF_GROW_API_BASE__ || 'http://127.0.0.1:3001';
}

// GET 请求（更严格，失败抛异常）
async function apiGet(path) {
    const url = `${getApiBase()}${path}`;
    const resp = await fetch(url);
    if (!resp.ok) {
        const err = await resp.text().catch(() => '请求失败');
        throw new Error(`API 错误 ${resp.status}: ${err}`);
        // 不是返回 null，而是抛出错误
    }
    return resp.json();
}

// POST 请求
async function apiPost(path, data) {
    const url = `${getApiBase()}${path}`;
    const options = {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
    };
    if (data !== undefined) {
        options.body = JSON.stringify(data);
    }
    const resp = await fetch(url, options);
    if (!resp.ok) {
        const err = await resp.text().catch(() => '请求失败');
        throw new Error(`API 错误 ${resp.status}: ${err}`);
    }
    return resp.json();
}
```

### 两种封装的对比

| 特性 | utils.js 的封装 | agent.js 的封装 |
|------|----------------|----------------|
| 失败处理 | 返回 `null` | 抛出 `Error` |
| 调用方式 | `const data = await fetchGoals(id); if (data) { ... }` | `try { const data = await apiGet(path); } catch (e) { ... }` |
| 适用场景 | 非关键数据（可以降级到模拟数据） | 关键操作（必须处理错误） |

## 4.3 异步编程：Promise 和 async/await

### 为什么需要异步？

JavaScript 是**单线程**的，同一时间只能做一件事。如果同步等待网络请求，页面就会卡住：

```javascript
// ❌ 同步方式（不存在，但假设存在）
const data1 = fetchSync(url1);  // 页面卡住 2 秒
const data2 = fetchSync(url2);  // 页面再卡住 2 秒
// 总共卡住 4 秒
```

```javascript
// ✅ 异步方式
const [data1, data2] = await Promise.all([
    fetch(url1),  // 同时发起两个请求
    fetch(url2),
]);
// 总共只卡住 2 秒（两个请求并行）
```

### Promise

Promise 代表一个"未来会有结果"的操作：

```javascript
const promise = fetch('/api/tasks');
// promise 有三种状态：
// pending   - 进行中
// fulfilled - 成功（有结果）
// rejected  - 失败（有错误）

// 使用 then 处理结果
promise
    .then(response => response.json())
    .then(data => console.log(data))
    .catch(error => console.error(error));
```

### async/await

async/await 是 Promise 的语法糖，让异步代码看起来像同步代码：

```javascript
// 用 async/await 重写
async function loadTasks() {
    try {
        const resp = await fetch('/api/tasks');  // 等待请求完成
        const data = await resp.json();          // 等待解析完成
        console.log(data);
    } catch (error) {
        console.error(error);
    }
}
```

### Promise.all：并行请求

```javascript
// frontend/js/app.js — 并行加载 8 个 API
const [profile, habitsData, lastWeekData, profileStats, recentActivities, rewardsData, goalsData, scheduledTasksData] = await Promise.all([
    fetchUserProfile(user.id).catch(() => null),   // 请求1
    fetchHabits(user.id).catch(() => null),         // 请求2
    fetchLastWeekHabits(user.id).catch(() => null), // 请求3
    fetchProfileStats(user.id).catch(() => null),   // 请求4
    fetchRecentActivities(user.id).catch(() => null), // 请求5
    fetchRewards(user.id).catch(() => null),         // 请求6
    fetchGoals(user.id).catch(() => null),           // 请求7
    fetchScheduledTasks(user.id).catch(() => null),  // 请求8
]);
```

**关键点**：
- `.catch(() => null)` 确保单个请求失败不会阻塞其他请求
- 8 个请求**同时发出**，不等前一个完成
- Promise.all 等待**所有**请求完成后，一次性返回结果

## 4.4 CORS 跨域

### 什么是跨域？

浏览器的安全策略规定：**只能向同源（协议+域名+端口都相同）的服务器发送请求**。

```
同源示例：
  http://localhost:3000 → http://localhost:3000  ✅ 同源
  http://localhost:3000 → http://localhost:3001  ❌ 不同端口 = 跨域
  http://localhost:3000 → https://localhost:3000 ❌ 不同协议 = 跨域
  http://localhost:3000 → http://example.com     ❌ 不同域名 = 跨域
```

### 为什么你的项目会有跨域问题？

```
前端：http://localhost:3000  (端口 3000)
后端：http://localhost:3001  (端口 3001)

端口不同 → 跨域！
```

### CORS 的工作原理

CORS（Cross-Origin Resource Sharing，跨域资源共享）通过 HTTP Headers 告诉浏览器"允许跨域请求"。

```
浏览器                                    服务器 (localhost:3001)
   │                                        │
   │  预检请求 OPTIONS                       │
   │  Origin: http://localhost:3000          │
   │  Access-Control-Request-Method: POST    │
   │  ──────────────────────────────────→    │
   │                                        │
   │  预检响应                                │
   │  Access-Control-Allow-Origin: *         │
   │  Access-Control-Allow-Methods: *        │
   │  ←──────────────────────────────────    │
   │                                        │
   │  实际请求 POST                          │
   │  Content-Type: application/json         │
   │  ──────────────────────────────────→    │
   │                                        │
   │  响应                                   │
   │  Access-Control-Allow-Origin: *         │
   │  ←──────────────────────────────────    │
```

### 项目中的 CORS 配置

```python
# backend/main.py
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],      # 允许所有来源（生产环境应该限制）
    allow_methods=["*"],      # 允许所有 HTTP 方法
    allow_headers=["*"],      # 允许所有请求头
)
```

`allow_origins=["*"]` 表示允许任何来源的跨域请求。这在开发阶段很方便，但在生产环境中应该限制为具体域名：

```python
# 生产环境应该这样配置
app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "http://localhost:3000",
        "https://yourdomain.com",
    ],
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["*"],
)
```

### 项目中的错误处理模式

```javascript

async function fetchGoals(userId) {

    const url = `${getApiBase()}${path}`;
    const resp = await fetch(url);
    if (!resp.ok) {
        const err = await resp.text().catch(() => '请求失败');
        throw new Error(`API 错误 ${resp.status}: ${err}`);

// 调用方处理异常
```

# 第五部分：服务器架构与并发

## 5.1 进程、线程、协程

### 进程（Process）

进程是操作系统分配资源的最小单位。每个进程有独立的内存空间。

```
你的电脑上同时运行的进程：
├── Chrome 浏览器进程（多个标签页共享）
├── Python http.server 进程（前端静态文件服务）
├── FastAPI/Uvicorn 进程（后端 API 服务）
├── 操作系统进程
└── 其他应用进程
```

### 线程（Thread）

线程是进程内执行任务的最小单位。同一个进程内的线程共享内存。

```
FastAPI 进程内部：
├── 主线程（监听端口、路由分发）
├── 工作线程 1（处理请求 1）
├── 工作线程 2（处理请求 2）
└── 工作线程 3（处理请求 3）
```

### 协程（Coroutine）

协程是更轻量级的"线程"，由程序自己调度（不是操作系统）。

```
FastAPI 协程模型：
├── 主协程
├── 协程 1（处理 GET /api/tasks）  ← 没有等待数据库时，让出执行权
├── 协程 2（处理 GET /api/habits） ← 没有等待时，继续执行
└── 协程 3（处理 GET /api/goals）  ← 几千个协程可以同时运行
```

### 对比

| 特性 | 进程 | 线程 | 协程 |
|------|------|------|------|
| 内存 | 独立 | 共享 | 共享 |
| 创建开销 | 大 | 中 | 极小 |
| 切换开销 | 大（内核态） | 中 | 极小（用户态） |
| 并发数 | 几十~几百 | 几百~几千 | 几万~几十万 |
| 适用场景 | 不同服务 | CPU 密集型 | I/O 密集型 |

## 5.2 阻塞 I/O vs 非阻塞 I/O

### 阻塞 I/O（同步）

```python
# 同步方式（阻塞）
def handle_request():
    data = database.query("SELECT * FROM users")  # 阻塞！等待数据库
    result = process(data)                          # 继续处理
    return result
# 在等待数据库返回时，整个线程被阻塞，不能处理其他请求
```

### 非阻塞 I/O（异步）

```python
# 异步方式（非阻塞）
async def handle_request():
    data = await database.query("SELECT * FROM users")
    # 等待数据库时，让出执行权，其他协程可以运行
    # 数据库返回后，继续执行
    result = process(data)
    return result
# 等待期间可以处理其他请求
```

### 直观比喻

```
阻塞（同步）：你去餐厅点餐
  你点菜 → 站在厨房门口等 → 菜好了 → 你端走
  （整个餐厅只有你一个顾客能被服务）

非阻塞（异步）：你去餐厅点餐
  你点菜 → 回座位玩手机 → 菜好了叫号 → 你去取
  （餐厅可以同时服务很多顾客）
```

## 5.3 WSGI vs ASGI

### WSGI（Web Server Gateway Interface）

WSGI 是 Python Web 应用的标准接口，**同步**模型。

```
请求 → WSGI 服务器（Gunicorn）→ WSGI 应用（Flask/Django）→ 响应
                                      ↑
                              同步处理，一个请求一个线程
```

### ASGI（Asynchronous Server Gateway Interface）

ASGI 是 WSGI 的异步升级版，支持**异步**和**WebSocket**。

```
请求 → ASGI 服务器（Uvicorn）→ ASGI 应用（FastAPI）→ 响应
                                      ↑
                              异步处理，一个协程可以处理多个请求
```

### 你的项目为什么用 FastAPI + ASGI？

```python
# backend/main.py
# 启动时使用 Uvicorn（ASGI 服务器）
if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=PORT)
```

原因：
1. **异步数据库查询**：FastAPI 的 `async` 路由可以并发处理多个请求
2. **WebSocket 支持**：ASR 语音识别需要 WebSocket
3. **AI 调用不阻塞**：调用外部 AI API 时，协程让出执行权

## 5.4 Python http.server vs FastAPI

你的项目同时使用了两种服务器：

### `python -m http.server`（前端）

```bash
python -m http.server 3000
```

特点：
- **单线程**：一次只能处理一个请求
- **只提供静态文件**：不能执行代码
- **同步阻塞**：请求来了就处理，处理完才接下一个
- **不适合生产环境**

### FastAPI + Uvicorn（后端）

```python
uvicorn.run(app, host="0.0.0.0", port=3001)
```

特点：
- **异步多协程**：可以同时处理大量请求
- **API 处理**：查询数据库、调用 AI、计算经验
- **非阻塞**：等待 I/O 时处理其他请求
- **生产就绪**：配合 Gunicorn 可以用在生产环境

## 5.5 FastAPI 的异步架构详解

### 路由函数的 async/await

```python
# backend/routers/users.py
@router.get("/api/users/profile")
async def user_profile(user=Depends(get_current_user)):
    """获取用户完整资料"""
    user_id = user["id"]
    
    # 这些都是异步操作
    total_exp = get_total_exp_from_dimensions(user_id)  # 数据库查询
    exp_to_next = exp_for_level(level)                   # CPU 计算
    
    # 返回时不会阻塞其他请求
    return {
        "user": {...},
        "todayStats": {...},
        "yesterdayStats": {...},
    }
```

### 事件循环（Event Loop）

```
Uvicorn 事件循环：

1. 监听 3001 端口
2. 收到请求 1（GET /api/tasks）→ 创建协程 1
3. 收到请求 2（GET /api/habits）→ 创建协程 2
4. 协程 1 查询数据库（等待 I/O）→ 让出执行权
5. 协程 2 查询数据库（等待 I/O）→ 让出执行权
6. 数据库返回结果 1 → 协程 1 继续执行
7. 协程 1 返回响应
8. 数据库返回结果 2 → 协程 2 继续执行
9. 协程 2 返回响应
```

### 并行请求的处理

```javascript
// 前端并行发送 8 个请求
await Promise.all([
    fetchUserProfile(user.id),    // 请求 1
    fetchHabits(user.id),         // 请求 2
    fetchLastWeekHabits(user.id), // 请求 3
    fetchProfileStats(user.id),   // 请求 4
    fetchRecentActivities(user.id), // 请求 5
    fetchRewards(user.id),        // 请求 6
    fetchGoals(user.id),          // 请求 7
    fetchScheduledTasks(user.id), // 请求 8
]);
```

在 FastAPI 端的处理：

```
时间 0ms：8 个请求几乎同时到达
时间 0ms：创建 8 个协程，开始执行
时间 1ms：协程 1-8 都在查询数据库（等待 I/O）
时间 5ms：协程 1 数据库返回，计算 EXP
时间 6ms：协程 2 数据库返回
时间 7ms：协程 3-8 陆续返回
时间 10ms：所有响应返回浏览器
```

如果用同步方式（Flask）：

```
时间 0ms：请求 1 进入线程 1，开始查询数据库
时间 0ms：请求 2 等待线程...
时间 0ms：请求 3 等待线程...
...
时间 5ms：请求 1 完成，请求 2 进入线程 2
...
时间 40ms：所有请求完成（串行，慢 8 倍）
```

# 第六部分：Web 安全与进阶

## 6.1 HTTPS 与 TLS

### HTTP 的问题

HTTP 数据是**明文传输**的：

```
浏览器 → 明文密码 "admin123" → 服务器
              ↑
         可以被中间人截获！
```

### HTTPS 的解决方案

HTTPS = HTTP + TLS（Transport Layer Security）

```
浏览器                                    服务器
   │                                        │
   │  ① ClientHello（支持的加密算法）        │
   │  ──────────────────────────────────→    │
   │                                        │
   │  ② ServerHello + 证书                   │
   │  ←──────────────────────────────────    │
   │                                        │
   │  ③ 验证证书，生成密钥                    │
   │  ──────────────────────────────────→    │
   │                                        │
   │  ④ 加密通信开始                         │
   │  ≡≡≡≡≡≡≡≡≡≡ 加密数据 ≡≡≡≡≡≡≡≡≡≡≡≡≡    │
```

### 项目中的 HTTPS

你的项目开发环境使用 HTTP（`http://localhost:3001`），但在生产环境中应该使用 HTTPS：

```
开发环境：http://localhost:3000  → http://localhost:3001（同一台机器，安全）
生产环境：https://yourdomain.com → https://api.yourdomain.com（需要 HTTPS）
```

## 6.2 WebSocket 实时通信

### HTTP 的局限性

HTTP 是**单向的**：客户端发请求，服务器返回响应。服务器不能主动推送数据给客户端。

```
传统轮询（效率低）：
  浏览器：有新数据吗？→ 服务器：没有
  浏览器（1秒后）：有新数据吗？→ 服务器：没有
  浏览器（1秒后）：有新数据吗？→ 服务器：有！给你
  （浪费大量请求在"没有"上）
```

### WebSocket 的优势

WebSocket 是**全双工**的：建立连接后，双方都可以随时发送数据。

```
WebSocket：
  浏览器：建立连接
  服务器：收到新数据 → 主动推送
  服务器：又有新数据 → 又推送
  （实时、高效、无浪费）
```

### 项目中的 WebSocket 实现

你的项目用 WebSocket 实现了**实时语音识别**：

```python
# backend/routers/expression.py

async def websocket_asr(websocket: WebSocket):

    asr = ASRConnection(model="paraformer-realtime-v2", sample_rate=16000)
    asr.start()  # 启动 DashScope ASR 服务
    
    async def receive_audio():
        """接收浏览器发送的音频数据"""
        while True:
            data = await websocket.receive_bytes()  # 接收二进制音频
            asr.send_audio(data)  # 转发到 DashScope
    
    async def send_results():
        """将识别结果推送给浏览器"""
        while True:
            result = asr.get_result()  # 获取识别结果
            if result:
                await websocket.send_json({
                    "type": "transcript",
                    "text": result.get("text", ""),
                    "is_end": result.get("is_end", False),
                })
            await asyncio.sleep(0.05)  # 50ms 轮询
```

## 6.3 RESTful API 设计

### REST 是什么？

REST（Representational State Transfer）是一种 API 设计风格，核心思想是**用 URL 表示资源，用 HTTP 方法表示操作**。

### 你的项目中的 RESTful 设计

```
用户资源：
  GET    /api/users          → 获取用户列表
  GET    /api/users/profile  → 获取用户详情
  POST   /api/users/login    → 用户登录

任务资源：
  GET    /api/tasks          → 获取今日任务
  GET    /api/tasks/all      → 获取所有任务（分页）
  POST   /api/tasks          → 创建任务
  PUT    /api/tasks/{id}     → 更新任务
  PATCH  /api/tasks/{id}/status → 修改任务状态
  DELETE /api/tasks/{id}     → 删除任务

习惯资源：
  GET    /api/habits         → 获取习惯列表
  POST   /api/habits         → 创建习惯
  PUT    /api/habits/{id}/toggle → 切换打卡状态

奖励资源：
  GET    /api/rewards        → 获取奖励列表
  POST   /api/rewards        → 创建奖励
  GET    /api/rewards/{id}/image → 获取奖励图片
```

### URL 设计原则

```python
# 好的设计
GET  /api/tasks          → 获取任务列表
POST /api/tasks          → 创建任务
GET  /api/tasks/5        → 获取 ID=5 的任务
PUT  /api/tasks/5        → 更新 ID=5 的任务
DELETE /api/tasks/5      → 删除 ID=5 的任务

# 不好的设计
GET  /api/getTasks       → ❌ 动词不应在 URL 中
POST /api/createTask     → ❌ 用 POST 方法表示"创建"
GET  /api/deleteTask?id=5 → ❌ 用 DELETE 方法表示"删除"
```

```
    │
    ▼
用户点击"停止录音"
    │
    ▼
关闭 WebSocket 连接
    │ ws.close()
    │ → TCP 四次挥手
    │ → 断开与 DashScope 的连接
```

### 链路 3：AI 调用外部服务

```
用户点击"AI 分析习惯"
    │
    ▼
前端发起请求
    │ POST /api/habits/ai-insights
    │ → FastAPI 接收请求
    │
    ▼
FastAPI 调用外部 AI API
    │ langchain_openai.ChatOpenAI
    │ → HTTP POST https://api.sfkey.cn/v1/chat/completions
    │ → TCP 连接到外部服务器
    │ → TLS 加密（HTTPS）
    │ → 发送 JSON 请求
    │ → 等待 AI 处理（可能几秒）
    │ ← 接收 JSON 响应
    │
    ▼
FastAPI 返回结果给前端
    │ HTTP 200 OK + AI 分析结果
    │
    ▼
前端显示分析结果
```

## 6.5 安全性注意事项

### 1. HTTPS 在生产环境必须启用

```python
# 生产环境应该这样启动
uvicorn main:app --host 0.0.0.0 --port 443 --ssl-keyfile=key.pem --ssl-certfile=cert.pem
```

### 2. CORS 不应该用 `allow_origins=["*"]`

```python
# ❌ 开发环境（方便但不安全）
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
)

# ✅ 生产环境
app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "https://yourdomain.com",
        "https://www.yourdomain.com",
    ],
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Content-Type", "Authorization"],
)
```

### 3. API Key 不能暴露在前端

```python
# ✅ 后端调用 AI（安全）
# backend/services/ai_client.py
llm = ChatOpenAI(
    model=AI_MODEL,
    api_key=AI_API_KEY,  # 从 .env 读取，不暴露给前端
    base_url=AI_BASE_URL,
)
```

```javascript
// ❌ 如果前端直接调用 AI API（不安全）
// API Key 会暴露在浏览器中
const resp = await fetch('https://api.openai.com/v1/chat', {
    headers: { 'Authorization': 'Bearer sk-...' }  // 可被查看
});
```

### 4. 输入验证

```python
# backend/schemas/api.py
class CreateTaskRequest(BaseModel):
    title: str
    category: str
    priority: str = "medium"
    exp: int = 0
    intro: str = ""
    # Pydantic 自动验证输入类型和格式
```

## 6.6 知识总结

| 概念 | 通俗解释 | 项目体现 |
|------|---------|---------|
| **TCP 三次握手** | 建立连接前的确认 | HTTP/HTTPS 的基础 |
| **TCP 四次挥手** | 关闭连接时的告别 | 请求完成后自动发生 |
| **UDP** | 快但不可靠 | DNS 查询 |
| **HTTP 请求结构** | 请求行+请求头+请求体 | 每个 API 调用 |
| **HTTP 方法** | GET/POST/PUT/DELETE | 任务 CRUD |
| **状态码** | 200/404/500 等 | 错误处理 |
| **Content-Type** | 数据格式声明 | JSON 通信 |
| **CORS** | 跨域安全策略 | 前后端分离必须 |
| **异步编程** | 不阻塞其他操作 | Promise.all 并行请求 |
| **ASGI** | 异步 Web 服务器接口 | FastAPI + Uvicorn |
| **WebSocket** | 全双工实时通信 | 语音识别 ASR |
| **HTTPS/TLS** | 加密传输 | 生产环境必须 |
| **RESTful** | API 设计规范 | 所有路由设计 |
